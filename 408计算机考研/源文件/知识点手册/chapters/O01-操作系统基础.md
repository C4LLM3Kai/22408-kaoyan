## 操作系统的基本概念

### 操作系统的定义与双重角色

**操作系统（Operating System，OS）**是控制和管理整个计算机系统的硬件与软件资源、合理调度任务与分配资源、并为用户和其他软件提供统一接口与运行环境的最基本的**系统软件**。

从使用层次看，计算机系统自下而上分四层：**硬件 → 操作系统 → 应用程序 → 用户**。硬件提供基本计算资源，操作系统把资源管起来并向上提供运行环境、充当桥梁，应用程序利用这些资源解决用户问题。这是「人机交互视角」的分层，与计算机组成原理中 CPU 内部结构的分层不是一回事。

操作系统的角色可概括为两重身份、外加一个效果：

1. **作为计算机系统资源的管理者**。把用户看作「雇主」、计算机看作「机器」，操作系统就是那位「工人」：协调并控制各个部件工作。
2. **作为用户与计算机硬件系统之间的接口**。工人接收雇主命令并执行任务——这对应操作系统提供的用户接口与程序接口；用户使用硬件必须经过操作系统这一必经媒介。
3. **实现对计算机资源的抽象与扩充**。只有硬件、没有任何软件支撑的计算机称为**裸机**；操作系统在裸机之上把底层硬件抽象成更好的逻辑资源，于是呈现给用户的是一台功能更强、更易用的**扩充机器**（有些教材也叫「虚拟机」，这里指的是操作系统提供的逻辑计算机环境，不是 VMware 那种虚拟化软件造出来的虚拟机）。

### 操作系统的四大功能

作为资源管理者，操作系统的功能按管理对象分为四类，这四类恰好对应本手册后面四章的内容。

**处理机管理**：多道程序环境下，处理机的分配和运行都以进程（或线程）为基本单位，所以处理机管理**本质上就是对进程的管理**——提到「进程管理」时指的也是这块。主要内容包括进程控制、进程同步、进程通信、死锁处理以及处理机调度。

**存储器管理**：为多道程序提供良好的内存运行环境，提高内存利用率。主要内容包括内存分配与回收、地址映射、内存保护与共享、内存扩充（虚拟存储）。

**文件管理**：用户可见的持久化信息通常以文件形式组织，负责这部分的部分称为**文件系统**，功能包括文件存储空间的管理、目录管理、文件读 / 写操作及访问保护。注意操作系统管理的是文件的**物理结构、逻辑结构、目录组织**，而不是文件的内容——所以「操作系统管理源程序的内容」是错的。

**设备管理**：处理用户的 I/O 请求，屏蔽设备差异，方便用户使用各类外设并提高设备利用率。主要包括缓冲管理、设备分配、设备驱动处理和虚拟设备。

### 用户接口与程序接口

操作系统向上提供的接口分两大类，这一组概念经常被拿来设陷阱。

**用户接口**面向普通终端用户，供其直接向操作系统发出请求：

- **命令接口**：用户通过输入命令组织和控制作业的执行。
  - **联机命令接口（交互式命令接口）**：适用于分时系统或实时系统，特点是「说一句，做一句」——用户输入一条命令，系统立即解释并执行。
  - **脱机命令接口（批处理命令接口 / 作业控制语言）**：适用于批处理系统，特点是「列好清单，再逐项完成」——用户预先提交一组作业控制命令，系统调度到该作业时自动解释执行，无须实时干预。
- **图形用户接口（GUI）**：通过窗口、图标、菜单、按钮等图形元素操作计算机，底层仍通过系统调用与内核交互。GUI 程序本身不算操作系统的一部分，但它完成的功能都是通过系统调用实现的。

**程序接口**面向应用程序，本质上就是一组**系统调用**。它是应用程序在运行时请求操作系统服务、访问系统资源的**唯一合法途径**。

:::warn 用户接口与程序接口不能互换
「操作系统提供给应用程序的接口」是**系统调用**（程序接口），不是库函数、不是中断、不是原语。库函数由编程语言的函数库提供，属于用户程序的一部分，位于系统调用的上层；中断是硬件与操作系统之间的通信手段，对应用程序透明；原语是操作系统内部不可中断的底层程序，不直接暴露给应用层。
:::

### 操作系统的四大特征

操作系统之所以区别于其他系统软件，在于它具备四个基本特征：**并发、共享、虚拟、异步**。

**并发（Concurrency）**：两个或多个事件在**同一时间间隔内**发生。多道程序环境下，内存中同时驻留若干道程序，操作系统通过调度让它们交替执行，宏观上都在运行、微观上轮流占用 CPU。

必须区分**并行（Parallel）**：两个或多个事件在**同一时刻**真正同时发生。并行需要硬件支持（多流水线或多处理机 / 多核）。单处理机系统中任一时刻只有一个程序占用处理机，多道程序之间只能**并发**而不能并行；但处理机与设备、处理机与通道、设备与设备之间相互独立，是可以并行的。多核计算机上，多道程序之间既并发也并行。

**共享（Sharing）**：系统中的资源可供内存中多个并发执行的进程共同使用，有两种方式：

- **互斥共享方式**：某些资源虽可供多个进程使用，但**一个时间段内只允许一个进程访问**。典型例子是打印机、磁带机等物理设备，以及软件中的栈、变量、表格等**临界资源**。
- **同时共享（同时访问）方式**：某些资源允许**一个时间段内由多个进程「同时」访问**，这里的「同时」往往是宏观上的，微观上各进程交替访问（即分时共享）。典型例子是磁盘设备、用可重入代码编写的文件。

判断方法：若若干进程交替使用某设备对结果没有影响，就允许同时访问（磁盘）；若会产生影响，就必须互斥访问（打印机）。

**虚拟（Virtual）**：把一个物理实体变为若干个逻辑上的对应物。物理实体实际存在，逻辑对应物是用户感受到的。三种典型实现：**虚拟处理器**（多道程序分时使用一个处理器，**时分复用**）、**虚拟存储器**（利用覆盖、交换、请求分页 / 分段 / 段页等技术逻辑扩充容量，**空分复用**）、**虚拟设备**（SPOOLing 把一台物理 I/O 设备虚拟为多台逻辑设备）。

**异步（Asynchronism）**：多道程序并发执行、争抢有限的系统资源，因此进程的执行不是一贯到底的，而是**走走停停、以不可预知的速度向前推进**。可以通过同步机制约束执行顺序、限制最终结果。

:::key 并发与共享互为存在条件
这是本章第一条必背结论：
1. **资源共享以程序并发为条件**——若系统不允许程序并发执行，同一时间段内只有一个程序在跑，自然不存在资源共享问题；
2. **若系统不能对资源共享实施有效管理，则必将影响程序的并发执行，甚至根本无法并发执行**。

另外两条从属关系也要记住：**没有并发性就谈不上虚拟性**（一个时间段内只运行一道程序，虚拟就没有意义）；**只有系统拥有并发性，才有可能导致异步性**。所以四个特征中，**并发和共享是最基本的两个**。
:::

:::exam 真题考法：并发与并行、多道程序系统
- **2009-23**：单处理机系统中可并行的是（处理机与设备、处理机与通道、设备与设备），进程与进程不能并行。
- **2018-23**：多任务操作系统「具有并发和并行的特点」「需要实现对共享资源的保护」正确；「需要运行在多 CPU 平台上」错误——多任务与硬件是否多核无关。
- **2022-23**：多道程序系统「不必支持虚拟存储管理」正确（早期多道批处理直接把所有进程的数据全部装入内存），「进程数越多 CPU 利用率越高」错误——进程过多会因争抢 CPU 而降低利用率。
:::

## 操作系统发展历程

### 手工操作阶段

早期用户把程序和数据穿孔在纸带或卡片上，装入输入设备后手动控制读入内存并启动运行；程序的装入、执行、结果输出全过程都依赖人工。这一阶段**没有操作系统**。两个突出缺点：① **用户独占全机**，无资源竞争但资源利用率极低；② **CPU 长时间空闲**，等待人工完成 I/O，计算能力没有发挥出来。

### 批处理阶段

为解决人机矛盾以及 CPU 与 I/O 设备速度不匹配的矛盾，出现了**脱机输入 / 输出技术**：引入一台外围机，在 CPU 不参与的情况下预先完成 I/O 准备——输入时把纸带 / 卡片上的数据读入磁带供 CPU 后续调入，输出时 CPU 先把结果写入磁带再由外围机输出。由于 I/O 完全脱离主机控制，故称脱机 I/O；由主机直接管理 I/O 的方式则称联机 I/O。脱机 I/O 显著减少了 CPU 空闲时间。

在脱机 I/O 的基础上，为实现作业的自动连续处理，出现了配备**监督程序（Monitor）**的批处理系统，这是操作系统开始出现的标志。

**单道批处理系统**：作业成批提交，但**内存中始终保持只有一道作业**。三个特征：

- **自动性**：磁带上的作业可自动连续执行，无须人工干预，缓解了一定程度的人机速度矛盾。
- **顺序性**：作业按磁带顺序依次装入内存，先装入者先完成。
- **单道性**：内存中仅允许一道用户程序运行，待其完成或异常终止后才调入下一道。

缺点是：当正在运行的作业发起 I/O 请求时，高速 CPU 不得不空闲等待低速 I/O 结束，**资源利用率依然很低**。

**多道批处理系统**：每次往内存中读入多道程序，作业成批运行。作业先存放在外存的**后备队列**中，作业调度程序按一定算法选取若干作业调入内存，使其并发执行、共享系统资源。**当某道程序因 I/O 请求而暂停运行时，借助中断技术 CPU 立即转去运行另一道程序**。

多道程序设计技术的三个特点（必背）：

1. **多道**：计算机内存中同时存放多道相互独立的程序。
2. **宏观上并行**：同时进入系统的多道程序都处于运行过程中——它们先后开始运行，但都还没有运行完毕。
3. **微观上串行**：内存中的多道程序轮流占有 CPU，交替执行。

主要优点：多道程序并发执行、共享资源，资源利用率大幅提升，CPU 和其他资源更能保持「忙碌」状态，系统吞吐量增大。主要缺点：**用户响应时间长**，**没有人机交互功能**——提交作业后只能等待处理完成，中间不能控制自己的作业（无法调试程序、无法在运行过程中输入参数）。

多道程序设计需要解决：① 处理器的分配策略；② 多道程序的内存分配与保护；③ I/O 设备的分配与调度；④ 大量程序与数据的组织、存储方式及其安全性与一致性。此外，引入多道技术后系统**失去了封闭性和顺序性**（这是异步性的来源），并且由于需要频繁中断，**系统开销比单道批处理更大**。

:::warn 多道 ≠ 并行，也不依赖虚拟存储
- 多道批处理系统的「并行」是**宏观并行、微观串行**。单 CPU 上多道程序之间没有真正的并行，真正的并行要求多处理机 / 多核。
- 多道程序设计技术与硬件是否多核**无关**，单核也可以是多道批处理系统。
- **多道程序系统不必支持虚拟存储管理**。早期多道批处理把需要执行的所有进程的数据一次性全部引入内存。所以「多道 → 必须有虚拟内存」是错的。
- 多道程序设计**并不提高单个作业的处理速度**，它提高的是资源利用率和系统吞吐量，代价是**牺牲了交互性**。
:::

### 分时操作系统

分时技术把处理器时间划分为很短的时间片，轮流分配给各用户程序使用；若某程序在其时间片内未完成计算，则暂停运行、释放处理器给其他程序，待下一轮再继续。由于计算机运行极快、程序轮转迅速，每个用户都获得「独占计算机」的体验。

分时操作系统允许多个用户通过终端同时连接一台主机并与系统交互，彼此互不干扰。它基于多道程序设计，但与多道批处理系统有本质区别：**批处理追求高吞吐量和资源利用率，无须人工干预；分时以人机交互为核心目标**。四个主要特征：

1. **同时性（多路性）**：允许多个终端用户同时使用同一台计算机。
2. **交互性**：用户可通过终端以人机对话方式直接控制程序运行并与之交互。
3. **独立性**：各用户的操作相互隔离，任一用户都感觉系统为其独占。
4. **及时性**：用户请求能在较短时间内获得响应。

主要缺点：**不能优先处理一些紧急任务**——系统对各个用户 / 作业完全公平，循环服务一个时间片，不区分任务紧急性。

### 实时操作系统

实时操作系统是为在**严格的时间限制内**完成关键任务而设计的系统，它摒弃分时的时间片轮转机制，改用基于任务紧迫性或截止时间的调度策略，确保高优先级任务及时获得处理器；主要特点是**及时性和可靠性**（确定性、高可靠性、强时效性）。

- **硬实时系统**：必须保证某个特定动作在规定时间内完成，否则可能引发灾难性后果（飞机的控制系统、导弹制导系统）。
- **软实时系统**：允许偶尔违反时间规定，只要不引起永久性损害即可（飞机订票系统、银行管理系统）。

### 网络操作系统、分布式系统与微机操作系统

**网络操作系统**在单机操作系统基础上扩展网络功能，支持计算机之间的通信、数据传输与资源共享（如文件、打印机共享）。各计算机保持独立运行，用户需**显式指定远程资源的位置**才能访问，系统不提供统一的全局视图。

**分布式系统**由多台计算机组成，节点地位对等、无固定主从关系，资源可被所有用户透明共享，可扩展性与容错能力强，能把一个任务分解为多个子任务分布到不同节点并行执行、协同完成。管理这类系统的操作系统称**分布式操作系统**，核心特点是**分布性、并行性和透明性**，其中透明性最关键。

二者区别：网络操作系统**仅实现资源共享与通信**，用户需主动干预远程操作；分布式操作系统通过协同机制共同完成同一任务，向用户提供**单一系统映像**。

**微机操作系统**按用户数与任务并发能力分三类：**单用户单任务**（早期的 MS-DOS）、**单用户多任务**（Windows XP 及后续版本、macOS、现代 Linux 桌面版）、**多用户多任务**（UNIX、Linux 服务器版、Windows Server 系列）。

### 各类操作系统对比

| 阶段 | 核心思想 | 主要优点 | 主要缺点 | 是否支持交互 |
|---|---|---|---|---|
| 手工操作 | 人工装入、人工控制 | 无资源竞争 | 用户独占全机，CPU 利用率极低 | 有人工干预，无系统交互 |
| 单道批处理 | 脱机 I/O + 监督程序自动逐个运行作业 | 自动性、顺序性，缓解人机速度矛盾 | 单道性，I/O 时 CPU 空闲，利用率低 | 无 |
| 多道批处理 | 内存驻留多道程序，I/O 时切换 | 资源利用率高，吞吐量大 | 响应时间长，无交互能力，开销大 | 无 |
| 分时系统 | 时间片轮转，多用户共享一台主机 | 及时响应，解决人机交互，各用户独立 | 对紧急任务不能优先处理 | 有（核心目标） |
| 实时系统 | 按紧迫性 / 截止时间调度，抢占式 | 及时性、可靠性强，可优先响应紧急任务 | 交互流畅性不如分时，开销大 | 有，但面向特定任务 |
| 网络操作系统 | 互连各机，实现通信与资源共享 | 扩大资源共享范围 | 需显式指定远程资源，无全局视图 | 有 |
| 分布式系统 | 节点对等，协同完成同一任务 | 分布性、并行性、透明性、可扩展 | 实现复杂，一致性维护难 | 有 |

:::warn 各操作系统对比的四条排序
**资源利用率**：多道批处理 > 分时 > 实时；**交互性**：分时 > 实时 > 批处理；**及时性**：实时 > 分时 > 批处理；**可靠性**：实时系统最强。
:::

:::exam 真题考法：多道批处理系统的特点
- **2016-23**：「批处理系统允许多个用户与计算机直接交互」错误（批处理没有交互能力）；「批处理系统分为单道和多道」「中断技术使多道批处理系统的 I/O 设备可与 CPU 并行工作」正确。
- **2017-28**：多道程序系统的优点是 CPU 利用率高、系统吞吐量大、I/O 设备利用率高；**系统开销小是错的**——组织作业和切换作业都要额外开销。
- **2022-23**：见前文「并发与共享」处的考法说明。
:::

## 程序运行环境

### CPU 运行模式：内核模式与用户模式

#### 内核与内核态

为确保操作系统正确运行，必须严格区分操作系统代码与用户程序的执行环境。绝大多数计算机系统通过硬件支持实现这一区分：为处理机设置至少两种独立的运行模式——**用户态（目态）** 和**内核态（管态、系统态、核心态）**。

硬件通过**程序状态字寄存器（PSW）**中的一个**模式位**标识当前运行模式。不同教材约定可能相反，统考按「**0 表示内核态，1 表示用户态**」理解（也有资料写 1 表示内核态，题目若给出约定以题目为准）。**系统引导时硬件从内核态开始工作**，完成操作系统加载后才切换到用户态执行用户程序。

与两种模式对应，内存空间也分两块：**内核空间**是操作系统程序和数据占用的内存空间，**只有内核态下才可以访问**；**用户空间**是用户代码占用的内存空间，用户态下可以访问。CPU 访问内存时会进行特权级检查，只有当前特权级高于被访问数据的特权级时才能访问。

**操作系统内核**是紧靠硬件、常驻内存的核心软件，把与硬件紧密相关的模块（中断处理程序、设备驱动程序）、运行频率较高的模块（时钟管理、进程调度）以及各模块共用的基础操作集中放置，以保护核心模块免受应用程序破坏并提升运行效率。内核功能分两类：

1. **支撑功能**：**时钟管理**（提供系统时间、产生定时中断，用于时间片轮转、实时任务的截止时间控制、批处理作业进度衡量）、**中断机制**（保存与恢复现场、转移控制权到处理程序）、**原语**（由若干条指令组成、完成特定功能、具有原子性即不可被中断的操作，如进程切换、进程同步、资源分配，常通过关中断保证原子性）。
2. **系统资源管理功能**：进程管理、存储器管理、设备管理，以及支持它们的内核数据结构（PCB、设备控制块、内存分配表、缓冲区、各类链表和消息队列等）及基本操作。

#### 特权指令与非特权指令

双重模式机制通过**指令分类**提供保护：

- **特权指令**：仅能在内核态执行，可访问全部地址空间（包括用户空间和内核空间），执行关键操作。包括：I/O 指令（输入 / 输出指令）、开 / 关中断指令、置时钟指令、设置中断屏蔽字、修改 PSW（模式位）、存取用于内存保护的寄存器（如页表基址寄存器）、修改中断向量表、停机 / 重启指令，以及**由内核态转为用户态**的操作本身。
- **非特权指令**：可在任意模式下执行，主要用于一般计算和数据处理，其内存访问被限制在用户地址空间，无法直接操作硬件或系统核心资源。例如：算术逻辑运算指令（加法、取非）、数据传送指令、跳转 / 分支指令、压栈指令、设置断点指令、**陷入指令（trap）**。

上述限制由**硬件强制实施**：若用户程序试图执行特权指令，硬件将产生**非法指令异常**，操作系统捕获该异常后终止该程序并重新调度。

:::warn 关于模式的四条高频错误说法
1. 「CPU 处于内核态时**只能**执行特权指令」——**错**。内核态既能执行特权指令，也能执行非特权指令。
2. 「CPU 处于用户态时只能执行非特权指令」——**对**（2022-27 的答案）。
3. 「从用户态转到内核态是靠一条指令修改 PSW 的模式位完成的」——**错**。修改 PSW 的指令本身是特权指令，用户态根本执行不了。用户态到内核态是**在响应中断或异常时由硬件自动完成**的。
4. 「中断处理程序负责把 CPU 从用户态转为内核态」——**错**。模式切换发生在中断响应阶段（硬件完成），中断处理程序开始执行时 CPU **已经**处于内核态了。
:::

#### 状态切换的时机与方式

**用户态 → 内核态**（由硬件在中断 / 异常响应阶段自动完成，共四条途径）：

1. 用户程序请求操作系统服务，执行**系统调用**（主动）。
2. 发生**外中断**（如 I/O 完成、时钟信号到来）。
3. 用户程序执行过程中产生**异常**（如除零、缺页）。
4. 用户程序试图执行**特权指令**，触发非法指令异常。

**内核态 → 用户态**：由内核通过特定的返回指令（如 x86 的 `IRET`）完成，**该操作在内核态执行**。

:::key 两条「发生」与「执行」的区分
- 2012-23：问「不可能在**用户态发生**的事件」，答案是**进程切换**。系统调用在用户态发生（用户程序发起）、外部中断和缺页也都可能在 CPU 执行用户程序时发生；只有进程切换必须由内核完成，用户态不可能发生。
- 2024-23：问「中断或异常**发生时** CPU 处于内核态」，这是**错的**——事件发生的那一瞬间 CPU 可能还在用户态，只有响应中断的过程中硬件才切换到内核态。
- 因此做题时务必分清「事件发生时的模式」与「处理程序执行时的模式」，以及「在用户态发生 / 执行」两种不同问法。
:::

**内核栈与用户栈**：每个进程都有用户栈和内核栈。用户栈运行在用户态，存放用户程序的函数局部变量、参数、返回地址，仅在用户态下被访问。内核栈运行在内核态，当进程**通过系统调用、中断或异常进入内核态时，硬件自动切换到内核栈**，它存放内核函数的调用链、临时变量及内核执行上下文。

每个进程都需要**独立的内核栈**：所有进程运行时都可能通过系统调用陷入内核态，若第一个进程陷入内核后主动让出 CPU，第二个进程再陷入内核时若共享内核栈，就会破坏第一个进程的栈数据。

**普通函数调用不需要保存 PSW**，因为全程发生在用户态、不涉及特权级切换；而**允许多重中断时 PSW 必须保存**，因为中断可能在用户态也可能在内核态响应，需要记录被中断时的模式以便正确返回。

:::exam 真题考法：用户态 / 内核态
- **2011-24**：在用户态执行的是**命令解释程序**（shell）；进程调度程序、缺页处理程序、时钟中断处理程序都在内核态。
- **2013-28**：会导致用户态切到内核态的是**整数除以零**（异常）和 **read 系统调用**；`sin()` 函数调用不会（纯计算库函数全程用户态）。
- **2014-25**：不能在用户态执行的是**关中断指令**；trap 指令、跳转指令、压栈指令都可以在用户态执行。
- **2015-24**：不可能导致用户态转内核态的是 **`NOT R0`**（寄存器取非，不访存、不触发调用）；`DIV`（可能除零）、`INT n`（软中断）、`MOV`（访存可能缺页或越界）都可能。
- **2021-23**：只能在内核态执行的是 **I/O 指令**；trap、数据传送、设置断点指令都可在用户态。
- **2022-27**：CPU 处于用户态时只能执行非特权指令。
- **2023-26**：会导致 CPU 从内核态转为用户态的是**执行系统调用**（服务例程执行完毕返回时）；阻塞进程、执行 CPU 调度、唤醒进程完成时仍在内核态。
:::

### 中断和异常的处理

引入内核态与用户态后，操作系统必须解决两者之间的安全切换问题：系统在内核中设立若干称为「门」的受控入口，而**用户程序进入内核态的唯一合法途径就是中断或异常**。当 CPU 运行用户程序时一旦发生中断或异常，硬件会自动把处理器切换到内核态并跳转到对应处理程序，这一机制由硬件强制保障。

中断机制对现代操作系统至关重要：当某程序因等待 I/O 等事件暂时无法继续执行时，系统需及时将其挂起、转而调度其他就绪程序。在抢占式多任务系统中，这一调度主要依赖中断（尤其是**时钟中断**）触发。**中断机制是多道程序设计得以实现的前提。**

#### 中断与异常的定义

- **中断（Interrupt）**，也称**外中断**：来自 CPU 执行指令**外部**的事件，通常用于信息输入 / 输出。例如设备发出的 I/O 结束中断（表示 I/O 操作已完成）、时钟中断（表示一个固定时间片已到，用于计时、进程调度或启动定时任务）。外中断与**当前执行指令无关**，只发生在指令执行结束后。
- **异常（Exception）**，也称**内中断**：来自 CPU 执行指令**内部**的事件，如程序的非法操作码、地址越界、运算溢出、虚存系统的缺页，以及**专门的陷入指令**（系统调用）等引起的事件。异常与当前执行指令**相关**，一旦发生就必须立即处理。

#### 中断与异常的分类

**外中断（硬件中断）**分为两类：

- **可屏蔽中断**：通过 **INTR 线**发出的中断请求，通过改变屏蔽字可以实现多重中断，使中断处理更灵活（如时钟中断、I/O 中断）。
- **不可屏蔽中断**：通过 **NMI 线**发出的中断请求，通常是紧急的硬件故障，如电源掉电。

**异常（内中断）**分为三类：

- **故障（Fault）**：由指令执行引起的异常，如非法操作码、缺页故障、除数为 0、运算溢出、存储保护错。**故障处理后返回第 i 条指令重新执行**（例如缺页处理完成后重访原内存地址）。
- **自陷（Trap，也称陷入）**：一种事先安排的「异常」事件，用于在用户态下调用操作系统内核程序，如条件陷阱指令、系统调用指令。它**返回下一条指令**（第 i+1 条）。
- **终止（Abort）**：出现了使 CPU 无法继续执行的硬件故障，如控制器出错、存储器校验错。这类错误一般无法修复，处理程序只能强制退出程序。

从软硬件归属看：**故障和自陷属于软件中断（程序性异常），终止和外中断属于硬件中断**。

:::warn 几个容易混淆的归类
- **时钟中断属于外中断**（来自 CPU 外部的事件），不是内中断。
- **缺页属于内中断中的故障（Fault）**，不是外中断；缺页处理（调页、页面置换）只在核心态完成。
- **系统调用（访管指令 / trap 指令引发）属于内中断中的自陷**，也叫**访管中断**。所以「系统调用属于内中断」是正确的说法。
- **异常不能被屏蔽**——包括故障、自陷、终止，以及外中断里的不可屏蔽中断。
- 中断判优时，**异常和不可屏蔽中断不受中断屏蔽字影响**。
:::

#### 中断处理流程

以 CPU 正在执行用户程序的第 $i$ 条指令为例，大致过程如下：

1. **检测与判优**：CPU 在指令执行过程中发现异常，或在指令执行结束后检测到中断请求信号，并对同时到达的多个请求做优先级裁决。
2. **检查是否可响应**：检查 EFLAGS 寄存器的 IF 标志，判断能否响应可屏蔽中断。
3. **查中断向量表**：硬件根据中断类型号找到对应的**中断向量**，其中保存该处理程序的入口地址。
4. **特权级校验与切栈**：若当前是用户态，硬件自动改模式位、转入内核态，并把栈指针从用户栈切到**内核栈**。
5. **保护现场**：**硬件**在中断隐指令阶段自动保存**断点（PC）**和**程序状态字（PSW）**压入内核栈；**操作系统软件**保存**通用寄存器与通用地址寄存器的内容**以及**中断屏蔽字**（每位对应一种中断类型，用于屏蔽同级或低级中断、防止同类型中断嵌套，是**按类型屏蔽而非全局关中断**）。
6. **执行中断处理程序**。
7. **恢复现场并返回**：从内核栈弹出软件保存的寄存器与用户栈指针，执行 `IRET` 指令，由硬件自动弹出 EIP（PC）、CS、EFLAGS，恢复用户态执行流。

关于**断点**：异常在第 $i$ 条指令执行过程中被发现，处理后**返回第 $i$ 条指令重新执行**（如缺页处理后重访原地址）；中断在指令执行结束后被发现，处理后**返回第 $i+1$ 条指令继续执行**。若判定为不可恢复的致命错误，则终止该用户程序。

**中断向量表**：本质是一个**数组**，索引是中断类型号（连续整数编号），表项是中断服务程序的入口地址，**由操作系统初始化**。地址关系为：中断向量基址寄存器 + 中断信号偏移量 = 中断向量的地址。用数组实现是因为它需要**随机访问**且编号连续，能按索引在 $O(1)$ 时间内定位。

:::exam 真题考法：中断处理
- **2009-22**：能引起外部中断的事件是**键盘输入**；除数为 0、浮点运算下溢、访存缺页都属于内部异常。
- **2012-24**：中断处理一定会保存而子程序调用不需要保存的是**程序状态字寄存器**。
- **2015-23**：处理外部中断时应该由**操作系统**保存的是**通用寄存器的内容**；PC 和 PSW 由硬件自动保存，TLB 和 Cache 由硬件透明管理。
- **2018-29**：时钟中断服务程序要更新「内核中时钟变量的值」「当前进程占用 CPU 的时间」「当前进程在时间片内的剩余执行时间」三项。
- **2020-27**：由操作系统完成的是「提供中断服务」「初始化中断向量表」「保存中断屏蔽字」；「保存被中断程序的断点」由硬件完成。
- **2022-31**：由操作系统完成的是「保存通用寄存器的内容」和「执行系统调用服务程序」；「保存断点和 PSW」「将 CPU 模式改为内核态」由硬件完成。
- **2023-24**：中断向量表适合采用的数据结构是**数组**。
:::

#### 中断处理与子程序调用的区别

| 比较项 | 中断处理 | 子程序调用 |
|---|---|---|
| 程序间关系 | 中断处理程序与被中断程序相互独立，无固定关联 | 子程序与主程序属于同一程序，是主从关系 |
| 触发方式 | 通常随机发生 | 由 `CALL` 指令显式触发，程序员事先安排 |
| 实现基础 | 需要硬件电路支持才能完成 | 完全由软件实现 |
| 入口地址来源 | 由中断向量表提供 | 由 `CALL` 指令的地址码指定 |
| 现场保护 | 中断隐指令（硬件）自动保存 PC、PSW；OS 保存通用寄存器 | `CALL` 指令把当前 PC 压栈；不保存 PSW |
| 优先级裁决 | 需对同时到达的多个请求判优 | 无此操作 |
| 执行时的特权级 | 被调用过程（系统调用）一定在内核态 | 可能用户态也可能内核态 |

### 系统调用

#### 系统调用的定义与功能

**系统调用（System Call）**是操作系统提供给应用程序（程序员）使用的接口，可视为一种特殊的公共子程序调用，是应用程序**主动**向操作系统发出的服务请求。

系统中各种共享资源均由操作系统内核统一管理，因此**凡是与共享资源有关的操作（存储分配、I/O 传输、文件管理等）都必须通过系统调用向内核提出服务请求，由内核代为完成**，再把结果返回应用程序——目的是保证系统的稳定性和安全性，防止用户程序进行非法操作。

一个操作系统提供的系统调用有几十条乃至上百条，**每个系统调用都有唯一的系统调用号**。按功能大致分为六类：

| 功能类别 | 具体内容 |
|---|---|
| 设备管理 | 设备的请求或释放、设备启动等 |
| 文件管理 | 文件的读、写、创建及删除等 |
| 进程控制 | 进程的创建、撤销、阻塞及唤醒等 |
| 进程通信 | 进程之间的消息传递或信号传递等 |
| 内存管理 | 内存的分配、回收，获取作业占用内存区的大小和起始地址等 |
| 系统控制 | 时钟设置、系统状态查询等 |

判断某个操作是否「通过系统调用完成」的诀窍是**站在程序员的角度想：这件事是不是我（应用程序）主动请求的？**

:::warn 哪些操作必须通过系统调用，哪些不必
判断诀窍是**站在程序员角度想：这件事是不是我（应用程序）主动请求的？**
- **需要**：创建新进程（`fork`）、打开 / 读写文件（`open`、`read`、`write`）、申请动态内存（`malloc` 空间不够时可能调用 `brk` / `mmap`）、`sleep` 睡眠、设备启动。
- **不需要**：**页置换**（由缺页异常触发，是操作系统内部机制）、**进程调度**（由时钟中断或阻塞 / 唤醒事件触发）、**生成随机整数**（一般由用户态库函数 `rand()` 算得）、纯计算类库函数（`strlen`、`sqrt`、`sin`）。
- **陷阱**：`printf` 最终会通过 `write` 输出数据，`malloc` 在小块分配时可能完全在用户态完成，所以「库函数一定不含系统调用」也是错的。
:::

#### 系统调用与库函数的区别

| 比较项 | 系统调用 | 库函数 |
|---|---|---|
| 提供者 | 操作系统内核 | 编程语言的函数库 |
| 运行特权级 | 内核态（调用者发起时在用户态） | 用户态 |
| 是否切换特权级 | 必须切换（用户态 → 内核态 → 用户态） | 一般不切换 |
| 与共享资源的关系 | 凡涉及共享资源的操作必须使用 | 有些封装了系统调用，有些完全不含系统调用 |
| 是否可移植 | 不同操作系统接口不同（Windows 的 Win32 API 与 UNIX/Linux 的 POSIX 标准不同） | 依赖于具体语言的运行库 |

因此：「**不同的操作系统为应用程序提供了统一的系统调用接口**」是**错的**——不同操作系统的内核架构不同，系统调用编号、语义和参数形式都可能不同，较统一的只是上层 API 标准。操作系统真正提供给应用程序的接口本质上仍是**系统调用**，库函数只是一层封装。

系统调用与普通过程调用的四点差异：

1. **运行状态不同**：普通过程调用的调用者与被调用者运行在同一特权级；系统调用的调用者在用户态、被调用者在内核态。
2. **状态转换不同**：普通过程调用无须特权级切换、可直接跳转；系统调用必须通过**陷入指令（Trap）**触发，先切至内核态再由内核分派。
3. **返回机制不同**：系统调用执行完毕后，内核可能根据调度策略决定是否切换进程；普通过程调用总是直接返回原调用点。
4. **嵌套调用限制不同**：系统调用的嵌套深度受**内核栈**空间限制；普通过程调用仅受**用户栈**大小约束。

#### 系统调用的执行过程

:::key 系统调用的四个阶段（必背）
**① 传递系统调用参数 → ② 执行陷入指令（trap）并切换至内核态 → ③ 定位并执行相应的服务程序 → ④ 恢复现场并返回用户态**

对应 2017-24 的答案是 ③→②→④→①。

1. **传递参数**：用户程序把系统调用号及参数压入堆栈或放入指定的通用寄存器。
2. **执行陷入指令**：该指令**在用户态执行**，执行后立即引发一个**内中断（访管中断）**，硬件把 CPU 从用户态切到内核态；硬件把 PC、PSW 压入内核栈，内核（软件）保存通用寄存器内容。
3. **定位并执行服务程序**：内核按系统调用号查询**系统调用表**（数组，表项为各服务例程的入口地址），执行服务逻辑。
4. **恢复现场并返回**：内核恢复被中断进程的 CPU 现场，把模式切回用户态，控制权交还用户程序，从断点继续执行。

几个必须记住的细节：
- **陷入指令 = trap 指令 = 访管指令 = 自陷指令 = 陷阱指令**，它是**非特权指令**，**在用户态执行**。
- **发出系统调用请求在用户态，对系统调用的响应处理在核心态**。
- **系统调用号**标识系统调用的类型；**中断类型号（中断向量号）**标识中断或异常的类型，两者不能混。
- 自陷指令触发异常时保存的断点是**下一条指令的地址**（若保存的还是该指令的地址，就会陷入死循环）。
- 由硬件完成：**保存断点和 PSW、把 CPU 模式改为内核态**；由操作系统完成：**保存通用寄存器内容、执行系统调用服务程序**。
:::

```c
/* 用户态发起系统调用的直观过程（x86 Linux 早期实现示意） */
/* 1. 传递参数：系统调用号放 eax，参数依次放 ebx、ecx、edx */
/* 2. 执行陷入指令（用户态执行），引发访管中断，CPU 转内核态 */
/* 3. 内核查系统调用表，执行对应的服务例程 */
/* 4. 返回用户态，从断点继续执行，返回值在 eax 中 */

int fd = open("data.txt", 0); /* 库函数封装，内部最终是一条 int 0x80 / syscall */
```

:::exam 真题考法：系统调用
- **2010-23**：操作系统提供给应用程序的接口是**系统调用**。
- **2017-24**：执行系统调用过程的正确顺序是**传递参数 → 陷入指令 → 执行服务程序 → 返回用户态**。
- **2019-25**：「执行系统调用服务程序时 CPU 处于内核态」「操作系统通过提供系统调用避免用户程序直接访问外设」「系统调用是内核为应用程序提供服务的接口」正确；「不同操作系统提供统一的系统调用接口」错误。
- **2021-32**：通过系统调用完成的操作是**创建新进程**；页置换、进程调度不是应用程序发起的，生成随机整数一般无需系统调用。
- **2022-31**：见前文（由硬件完成的 vs 由操作系统完成的）。
- **2024-23**：每个系统调用都有对应的内核服务例程，系统添加新类型设备时需注册相应的中断服务例程，均正确。
:::

### 程序的链接与装入

#### 从源程序到可执行程序的三步

把一个用户源程序变成可在内存中执行的程序，通常要经过三步：

1. **编译**：由**编译程序**把用户源代码翻译成若干**目标模块**。
2. **链接**：由**链接程序**把这些目标模块及其所需的**库函数**合并，形成一个完整的**装入模块**（可执行文件）。
3. **装入（加载）**：由**装入程序**把装入模块载入内存，并启动其执行。

#### 逻辑地址与物理地址

编译后的每个目标模块通常从 0 号单元开始编址，这种地址称为该模块的**相对地址（逻辑地址）**。链接程序把多个目标模块合并为完整的可执行程序时，依次把各模块的相对地址拼接成一个统一的、从 0 开始编址的**逻辑地址空间（虚拟地址空间）**。以 32 位系统为例，该逻辑地址空间的范围为 $0 \sim 2^{32}-1$。

进程运行时使用的地址**都是逻辑地址**：用户程序和程序员只需关注逻辑地址，底层的内存管理机制对其完全透明。**不同进程可以拥有相同的逻辑地址**，因为它们各自拥有独立的逻辑地址空间，这些地址会被映射到主存的不同位置。

**物理地址空间**是主存中所有物理存储单元的集合，是地址转换的最终目标——无论执行指令还是访问数据，最终都必须通过物理地址从主存读写。早期系统在程序装入内存时把逻辑地址转换为物理地址，这一过程称**地址重定位**；现代支持虚拟内存的系统则由**内存管理单元（MMU）** 在硬件层面于运行时自动完成：操作系统为每个进程维护一张**页表**记录逻辑页到物理页框的映射，MMU 依页表动态换算，对用户程序完全透明。

#### 三种链接方式

**静态链接**：在程序运行之前，把各目标模块及其所需的库函数链接成一个完整的装入模块，此后不再拆分。链接过程中需完成两项关键操作：

- **地址调整**：各目标模块编译后均以 0 为起始地址，链接时需根据其在装入模块中的实际位置统一加上偏移量。例如模块 A 长度为 $L$、模块 B 紧邻其后存放，则原本从 0 编址的模块 B 在装入模块中从地址 $L$ 处开始，其内部所有地址都要加上 $L$。
- **外部符号解析**：把模块间引用的外部符号（如函数名）替换为确定的地址。若模块 A 中含语句 `CALL B`（B 是模块 B 入口的外部符号），链接程序会把它解析为模块 B 在装入模块中的起始地址 $L$。

**装入时动态链接**：编译后生成的一组目标模块在装入内存时采用**边装入边链接**的方式。装入某个模块时若遇到对外部模块的调用，装入程序立即查找并装入相应的外部目标模块，并替换其中的外部符号。优点是便于修改和更新（只需替换被修改的模块，无须重建整个程序）、便于实现对目标模块的共享。

**运行时动态链接**：对装入时动态链接的改进。**在程序执行过程中，仅当需要调用某个尚未装入内存的目标模块时，操作系统才动态加载并链接该模块**；运行中未使用的模块既不会被装入内存，也不会进行链接。优点是既能加快程序装入过程，又能节省内存空间。

| 链接方式 | 链接时机 | 优点 | 缺点 |
|---|---|---|---|
| 静态链接 | 程序运行之前 | 装入后运行无额外开销 | 模块修改需重新生成整个装入模块；无法共享目标模块 |
| 装入时动态链接 | 装入内存时边装入边链接 | 便于修改更新；便于共享目标模块 | 仍要把用到的模块全部装入，未用到的模块也占空间 |
| 运行时动态链接 | 执行过程中调用到时才链接 | 加快装入；节省内存，未用模块不装入 | 实现复杂，运行时才有链接开销 |

#### 三种装入方式

**绝对装入**：**仅适用于单道程序环境**。内存中始终只有一个程序，其驻留位置在编译前即可确定，编译程序直接生成使用绝对地址的目标代码，装入程序按这些地址把程序和数据载入内存；此时逻辑地址与物理地址完全一致，无须任何修改。程序中的符号地址由编译器或汇编器在编译 / 汇编阶段转换为绝对地址；绝对地址也可由程序员直接指定，但缺乏灵活性。

**可重定位装入（静态重定位）**：多道程序环境下编译程序无法预知模块在内存中的位置，因此装入模块通常从地址 0 开始编址，程序中的地址都是相对于模块起始位置的逻辑地址。装入时系统根据内存空闲情况为它分配**一块连续的内存区域**，把整个模块载入，**随后一次性把所有逻辑地址改为对应的物理地址**。转换在装入时完成且运行期间不再改变，故称**静态重定位**。缺点是：进程必须在装入前**一次性获得所需的全部内存空间**，内存不足则无法装入；一旦装入，进程运行期间**既不能移动位置，也不能动态申请额外内存**。

**动态运行时装入（动态重定位）**：装入程序把模块载入内存后**并不立即转换地址**，而是把转换推迟到指令实际执行时进行：系统用**重定位寄存器**存放该模块在内存中的起始物理地址，程序中保留逻辑地址，物理地址由硬件在运行时计算（逻辑地址 + 重定位寄存器内容）。优点是**支持程序在内存中移动**，便于操作系统进行紧凑（合并分散的空闲块）、有效减少外部碎片，并允许在运行期间动态调整进程的内存布局。

| 装入方式 | 地址转换时机 | 适用环境 | 能否在内存中移动 | 典型配合 |
|---|---|---|---|---|
| 绝对装入 | 编译（汇编）时 | 单道程序环境 | 否 | 无 |
| 可重定位装入（静态重定位） | 装入时一次性完成 | 多道程序环境 | 否 | 固定分区、单一连续分配 |
| 动态运行时装入（动态重定位） | 指令执行时由硬件完成 | 多道程序环境 | 是 | 页式、段式等需移动进程的方案 |

:::warn 重定位三问
1. **动态重定位依赖硬件支持**：必须有重定位寄存器（基址寄存器）和地址变换机构，所以「动态重定位依赖目标程序本身」是错的。
2. **静态重定位不能移动进程**：它把地址一次性改死，进程一旦装入就固定，所以「页式存储管理可以采用静态重定位」是错的（页式需要移动和换出换入）。
3. **固定分区可以采用静态重定位**：作业装入后位置不变且占连续空间，正适合静态重定位。
:::

### 程序运行时的内存映像与地址空间

程序被加载运行时，操作系统为它建立一个虚拟地址空间，该空间的逻辑布局称为**进程的内存映像**，反映运行时代码、数据、堆、栈等部分的组织方式。与磁盘上的静态可执行文件不同，**内存映像是动态的**：虚拟内存机制下进程的整个地址空间无须全部驻留物理内存，只有在实际访问某一部分时才通过缺页中断把它从磁盘调入。

典型的进程虚拟地址空间从**低地址到高地址**依次为：

1. **只读代码段**：含 `.init`（启动时自动调用的初始化代码）、`.text`（主程序及自定义函数编译后的机器指令）、`.rodata`（只读数据，如字符串常量）。代码段**只读**，防止运行时意外修改指令，同时允许多个进程共享同一份代码以节省内存。
2. **读 / 写数据段**：存放全局变量和静态变量。`.data` 存放**已初始化**的（如 `int x = 5;`）；`.bss` 存放**未初始化**的（如 `int y;`）。
3. **堆**：运行时**动态申请**内存的区域，用 `malloc()` 申请、`free()` 释放。**堆从低地址向高地址增长**，大小不固定。
4. **共享库的存储映射区**：提供进程依赖的公共函数代码（如 `printf()`），**运行时动态映射**到进程地址空间，只读且可被多个进程共享。
5. **用户栈**：支持函数调用，存放局部变量、函数参数、返回地址等临时信息，由系统自动管理，遵循**后进先出（LIFO）**。**栈从高地址向低地址扩展**。

32 位 Linux 的典型布局中，`0xFFFFFFFF` 附近是**操作系统内核区**（对用户进程不可见），往下依次是用户栈、共享库映射区、堆、读 / 写数据段、只读代码段，最低处是未使用区。注意**代码段和数据段的大小在程序加载时就已确定，而堆和栈可以在运行过程中动态扩展和收缩**。

:::key 内存映像的三条必背结论
1. **增长方向**：**堆从低地址向高地址增长，栈从高地址向低地址增长**，两者相向而生，中间是共享库映射区。
2. **`.bss` 段存放未初始化的全局 / 静态变量**，它在可执行文件中不占实际磁盘空间（只需记录大小），但在内存映像中占位。
3. **PCB 不属于进程的虚拟地址空间**：虽然 PCB 是管理进程的核心数据结构，但它由操作系统内核维护、存放在系统内核区中，**对用户进程不可见**。
:::

```c
/* 各区域存放内容对照示例 */
int g_init = 5;      /* .data ：已初始化的全局变量 */
int g_uninit;        /* .bss  ：未初始化的全局变量 */
const char *s = "hi";/* .rodata：字符串常量（只读数据段） */

int main(void) {
    static int s_init = 1;  /* .data：已初始化的静态变量 */
    int local = 3;          /* 栈   ：局部变量 */
    int *p = malloc(4);     /* 堆   ：动态申请，返回的地址交给指针 p */
    free(p);
    return 0;
}
```

:::exam 真题考法
- 进程虚拟地址空间中各区域的存放内容（含 `.text`、`.data`、`.bss`、堆、栈的归属判断）是近年新出现且反复出现的角度，要求看到一段 C 代码能立刻指出每个变量落在哪个区。
- 「代码段和数据段大小在加载时确定、堆栈可动态伸缩」也是常见判断点。
:::

## 操作系统结构

随着操作系统功能不断扩展、代码规模持续增长，合理的结构设计对降低系统复杂度、提升安全性和可靠性至关重要。考纲要求掌握五种：分层、模块化、宏内核、微内核、外核。

### 分层结构

**分层法**把操作系统划分为若干层，**最底层（层 0）为硬件，最高层（层 N）为用户接口**，每层只能调用紧邻它的**下层**所提供的功能和服务（**单向依赖**）。

优点：① **便于调试与验证**，系统可自底向上逐层开发与测试——第 1 层完成且验证无误后再开发第 2 层，因为它只依赖已验证的下层；若某层出错，可把错误定位在该层内部，因为它的所有下层都已通过验证。② **易于扩充与维护**，在保持层间接口不变的前提下，可以独立修改、替换或新增某一层的实现而不影响其他层。

问题：① **层次划分困难**，合理界定各层的功能边界较复杂，且一旦依赖关系固化，系统架构可能缺乏灵活性。② **运行效率较低**，执行一个高层功能通常需自上而下穿越多个中间层，每层之间的参数传递与控制转移都会引入额外开销。

:::warn 分层的两条秒杀结论
看到「分层式架构」就要立刻想到：**单向依赖（各层只能调用紧邻下层）** 与 **便于调试与验证 / 结构清晰**。反过来，「具有非常灵活的依赖关系」必定是错误选项——分层法恰恰是牺牲灵活性换取清晰性。
:::

### 模块化结构

**模块化**把操作系统按功能划分为若干具有一定独立性的模块，每个模块实现特定的管理功能，并明确定义与其他模块之间的接口，通过接口通信；还可以进一步把模块细分为子模块，同样规定子模块之间的接口。这种方法称**模块-接口法**。

模块划分的粒度需要权衡：模块**过小**虽然降低了单个模块的复杂性，但会导致模块间交互频繁、增加系统整体复杂度；模块**过大**则模块内部结构复杂、难以维护。

模块的**独立性**至关重要——模块独立性越高、相互依赖越少，系统结构越清晰。衡量模块独立性的两个标准：

- **内聚性**：模块内部各组成部分之间联系的紧密程度。**内聚性越高，模块独立性越好**。
- **耦合度**：模块之间相互依赖和影响的程度。**耦合度越低，模块独立性越好**。

优点：① 提高了操作系统设计的正确性、可理解性和可维护性；② 增强了系统的可适应性，便于功能扩展；③ 支持并行开发，加速操作系统研制进程。

缺点：① 模块间的接口规定很难满足对接口的实际需求；② 各模块设计者齐头并进，每个决定无法建立在上一已验证的正确决定的基础上，因此无法找到一个可靠的决定顺序（即**更难调试和验证**）。

### 宏内核

**宏内核**（也称**单内核、大内核**）把系统的主要功能模块集成在一个紧密耦合的整体中，统一**运行于内核态**，从而为用户程序提供高性能的系统服务。目前主流操作系统如 Linux、Windows、Android、macOS、iOS 都是宏内核或混合内核架构。

优点：**性能高**。各模块共享地址空间，可直接调用彼此的函数，减少了上下文切换和消息传递的开销，信息共享和相互调用都很方便。

缺点：随着体系结构和应用需求发展，需要操作系统提供的服务日益复杂、代码规模急剧膨胀，导致**内核庞大、功能复杂、结构混乱、难以维护**；更严重的是，**大内核中某个功能模块出错就可能导致整个系统崩溃**（例如文件系统运行在内核态，它一出问题系统就直接崩溃），可靠性下降，面临典型的「软件危机」。

需要说明的是，现在的宏内核**早已不是当年纯粹的形式**，而是广泛吸取微内核架构的优点后揉合而成的**混合内核**。例如 macOS 和 iOS 采用的 XNU 内核即融合了 Mach 微内核与 BSD 宏内核的特性；谷歌的 Fuchsia 和华为的 HarmonyOS NEXT 则采用了微内核架构。这正说明宏内核与微内核并非对立，而是相互借鉴、融合发展。

### 微内核

**微内核架构**把操作系统中最基本的功能保留在内核，其他非核心功能**移到用户态执行**，以降低内核的设计复杂性。移出的功能组织为若干独立的**服务程序（服务器）**，彼此之间以及与客户进程之间的交互都通过微内核提供的**消息传递机制**完成。所以微内核结构把操作系统划分为两大部分：**微内核 + 多个服务器**。

微内核是精心设计的小型内核，仅实现最核心的机制，通常包含：① 与硬件紧密相关的部分；② 基本的资源管理机制；③ 客户与服务器之间的通信支持。它遵循「**机制与策略分离**」原则——与硬件紧密相关的**机制**放入微内核，**策略**交由用户态服务器实现：

| 微内核中的机制部分 | 用户态服务器中的策略部分 |
|---|---|
| 进程 / 线程的创建、切换、调度队列管理、多处理机同步 | 进程如何分类、优先级如何确认 |
| 低级存储器管理：页表管理、逻辑地址到物理地址的映射等地址变换机制 | 采用何种页面置换算法、如何进行内存分配与回收 |
| 中断和陷入的捕获与分发（识别事件类型后转交服务器） | 各类中断 / 异常事件的具体处理逻辑 |

于是进程管理、存储器管理和 I/O 管理都被一分为二：属于机制的很小一部分在内核，绝大部分在微内核外的各种服务器中实现。**大多数服务器都要比微内核大**，因此微内核能保持极小规模。

优点（2023 统考真题的四个正确项）：

1. **扩展性和灵活性**：新增或修改功能只需调整相应服务器，无须改动内核代码。
2. **可靠性和安全性**：只有微内核运行在内核态，其余模块都运行在用户态，**一个模块中的错误只会使这个模块崩溃，而不会使整个系统崩溃**（文件服务出问题只需强行停止再重启，系统不会崩）；同时内核代码量和特权代码量少，攻击面更小。
3. **可移植性**：与 CPU 和 I/O 硬件有关的代码均放在内核中，其他各种服务器与硬件平台无关，因而移植到另一平台所需修改较小。
4. **分布式计算**：客户和服务器之间、服务器和服务器之间采用消息传递机制，使微内核系统能很好地支持分布式系统和网络系统。

缺点（主要是**性能差**）：每次服务请求都需要**频繁地在核心态和用户态之间进行切换**，操作系统的执行开销偏大；用户态下的各功能模块不能直接相互调用，只能通过内核中的「消息传递」间接通信，性能因此降低。为改善效率，可以把频繁使用的系统服务移回内核，但这又会使微内核的容量明显增大。

尽管宏内核在桌面操作系统中取得了绝对胜利，微内核因其高可靠性和可验证性，在**实时、工业控制、航空航天及军事**等关键任务领域特别流行。

### 外核

**外核（exokernel）** 的设计思想截然不同：**尽可能减少抽象层次，把物理资源直接暴露给用户级系统，自身仅负责资源的安全分配与隔离**。

外核是运行于内核态的极小程序，核心职责是把底层硬件资源（磁盘块、内存页、网络包缓冲区等）划分为**互不重叠的子集**分配给不同的用户级系统（例如一个系统分到磁盘 0～1023 块、另一个分到 1024～2047 块），并检查各系统只能访问被授权的资源。应用请求资源时外核只检查是否空闲，空闲就直接交给应用，怎么访问由应用自己决定。**外核分离了对硬件的使用与保护**，使应用能直接使用未经内核抽象的硬件。其上可在用户空间构建**库操作系统（library OS）** 自行实现文件系统、进程调度、虚拟内存管理等传统功能，由于直接操作物理资源、无须经过强制抽象层，避免了不必要的数据拷贝、地址转换与上下文切换开销。

优点：

1. **减少抽象开销（减少了映像层）**：传统操作系统强制引入虚拟内存、虚拟文件系统等映射层，每个虚拟机都以为自己的磁盘块号从 0 到最大编号，虚拟机监控程序因而必须维护重映像表；有了外核，**这个重映像处理就不需要了，外核只需记录已分配给各虚拟机的资源**。
2. **提升灵活性与性能**：用户级系统可按应用特性优化资源管理策略（例如数据库直接管理磁盘块），充分发挥硬件潜力。
3. **清晰分离保护与实现**：外核仅负责资源保护，功能实现完全置于用户空间，结构简洁且易于验证；它把多道程序（在外核内）与用户操作系统代码（在用户空间内）加以分离，负载不重，因为**外核所做的只是保持多个虚拟机彼此不发生冲突**。

### 五种结构对比

| 结构 | 核心思想 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|
| 分层 | 分若干层，层 0 是硬件、层 N 是用户接口，各层只能调用紧邻下层（单向依赖） | 便于调试验证、结构清晰；易扩充维护 | 层次划分困难、依赖关系固定不灵活；穿越多层效率低 | 早期的 THE、Multics |
| 模块化 | 按功能划分模块，规定接口通信，可再分子模块（模块-接口法） | 正确性 / 可理解性 / 可维护性提高；可适应性强；支持并行开发 | 接口难以设计；各模块决定无先后依赖，难以找到可靠的决定顺序，更难调试验证 | 多数现代系统采用模块化思想 |
| 宏内核 | 主要功能模块紧密耦合，全部运行在内核态 | 性能高，模块间可直接调用、信息共享方便 | 内核庞大复杂、难维护；一个模块出错可能导致整个系统崩溃 | Linux、Windows、Android |
| 微内核 | 只保留最基本功能在内核，其余作为用户态服务器，靠消息传递通信 | 扩展灵活、可靠安全、可移植、支持分布式 | 频繁特权级切换与消息传递导致性能差 | Minix、Fuchsia、HarmonyOS NEXT |
| 外核 | 内核只负责资源分配与保护，把物理资源直接交给用户级系统，由库操作系统实现功能 | 减少抽象与重映像开销、灵活高效、保护与实现分离 | 用户级系统实现负担重，缺乏统一抽象，应用兼容性差 | Exokernel 实验系统 |

## 操作系统引导

操作系统（如 Windows、Linux 等）以程序形式存储在硬盘等**外部存储设备**中。**操作系统引导**是指计算机通过执行一系列引导程序，依次定位启动设备、确定可引导分区、加载其中的操作系统内核，最终完成系统启动的**链式过程**。

### 引导的完整流程

1. **CPU 激活与 BIOS 初始化**。通电后 CPU 的 `RESET` 引脚产生逻辑值复位 CPU；CPU 唤醒后在 `0xFFFFFFF0` 处执行一条**长跳转指令**，跳到固化在 ROM 中的启动代码处（即 **BIOS**，基本输入 / 输出系统），把它加载到 RAM 执行。BIOS 中主要存放**自诊断程序**、**CMOS 设置程序**、**系统自动装载程序**与主要 I/O 驱动和中断服务；它还在**内存最开始处建立临时的中断向量表**供引导过程使用。BIOS 针对具体主板设计，与所安装的操作系统无关。

2. **硬件自检（POST，Power-On Self-Test）与启动设备选择**。BIOS 检查硬件能否满足运行的基本条件；有问题则蜂鸣报警、启动中止，无问题则显示 CPU、内存、硬盘等信息。随后 BIOS 依据 **CMOS 设置**（主板上由电池供电、保存启动顺序与系统时间等参数的配置存储器）或 **UEFI 固件**确定**启动顺序（Boot Sequence）**——排在前面的设备优先获得控制权。

3. **加载主引导记录 MBR**。BIOS 按启动顺序**把控制权转交给排在第一位的存储设备**，即读取该设备的**第一个扇区（最前面的 512 字节）**并放入内存指定位置（BIOS 的最后一个任务）。若这 512 字节的最后两个字节是 `0x55` 和 `0xAA`（**主引导记录签名**，标识该磁盘是否为引导盘），该设备就可用于启动；否则控制权转交给启动顺序中的下一个设备。这 512 字节就是**主引导记录（MBR）**，作用是告诉计算机到硬盘的哪个位置去找操作系统，由三部分组成：

   | 字节范围 | 内容 |
   |---|---|
   | 第 1～446 字节 | 调用操作系统的机器码（引导代码） |
   | 第 447～510 字节 | 分区表（Partition Table），共 64 字节，分 4 项、每项 16 字节 |
   | 第 511～512 字节 | 主引导记录签名 `0x55` 和 `0xAA` |

   每个主分区的 16 个字节中，**第 1 个字节若为 `0x80` 就表示该主分区是激活分区（活动分区），控制权要转交给它；四个主分区里面只能有一个是激活的**。其余字节记录分区的起止物理位置、分区类型、第一个扇区的逻辑地址和扇区总数。扇区总数只有 4 字节、最多表示 $2^{32}$ 个扇区，若每扇区 512 字节则**单个分区最大不超过 2TB**；要使用更大硬盘只能提高每扇区字节数或增加扇区总数（GPT 方案解决的正是这个问题）。

4. **定位活动分区并加载分区引导记录 PBR**。MBR 中的引导代码**扫描分区表**找到标记为「活动」的条目，读取其第一个扇区——**分区引导记录（PBR）**，有的资料称**卷引导记录 VBR**——加载到内存。PBR 包含该分区特定的引导代码：识别并加载该分区的**文件系统驱动**（如 FAT32 / NTFS 驱动）、文件系统元数据（簇大小、根目录位置等），以及指向启动管理器文件的指针。

5. **加载启动管理器**。按分区引导记录找到并加载活动分区内的**启动管理器**（`boot loader`），如 Linux 的 **GRUB**、Windows 的 **Bootmgr**，它提供多操作系统或内核版本的选择界面。

6. **加载操作系统内核**。启动管理器把用户选定的**内核映象加载到内存**并跳转执行。内核完全接管系统控制权，**重建自己的中断处理机制**（替换 BIOS 的实模式中断向量，建立页故障、系统调用、外设中断等机制），**不再依赖 BIOS 提供的服务**，同时启用分页机制、建立内核页表。

7. **内核初始化与用户环境启动**。内核初始化内存管理（内核页表、进程地址空间框架）、进程调度（PCB 链表、就绪队列与阻塞队列）和设备驱动子系统，然后启动**第一个用户态进程**（如 Linux 的 `init`，PID 为 1），由它加载系统各模块直至出现登录界面，启动过程完成。

:::key 引导链一句话记忆
**CPU 复位 → ROM 中的 BIOS/UEFI → 硬件自检 POST → 按 CMOS 启动顺序 → MBR（446 引导码 + 64 分区表 + 0x55AA 签名）→ 活动分区 → PBR → 启动管理器（GRUB/Bootmgr）→ 加载内核到内存 → 内核接管、重建中断机制、初始化 → 启动 init（PID=1）**
:::

:::warn 引导过程的易错点
1. **MBR 只有 512 字节，位于磁盘第 1 个扇区（0 号磁头 0 道 1 扇区）**，签名 `0x55` 和 `0xAA` 在最后两个字节。
2. **分区表只有 64 字节，只能存 4 个主分区项**；四个主分区里**有且只有一个**可以标记为激活。
3. **「计算机开机后操作系统所处的位置」答案是「以上都不对」**——先执行 ROM 中的引导程序，把 MBR 中的程序放入内存执行，再由它把操作系统装入内存并移交 CPU 控制权；操作系统本身既不在 ROM 也不在 MBR。
4. **操作系统最终被加载到 RAM**（不是 BIOS、ROM、EPROM），因为内核需要被 CPU 频繁读写并建立运行时数据结构。
5. **中断向量表的两次建立**：BIOS 阶段在内存最低端建立**临时**中断向量表供引导使用，操作系统初始化阶段**重建**属于自己的中断向量表，所以「中断向量表需要在操作系统初始化过程中创建」正确；而**硬盘分区表**在磁盘分区时创建、**文件系统根目录和索引节点表**在格式化文件系统时创建（2022-24 的干扰项）。
6. **实地址模式**：开机后系统首先工作在实地址模式下（Intel 为 80286 及其后处理器提供的 8086 兼容模式，20 位地址空间即 1MB，**不支持分页存储管理**）；一旦进入保护模式就不再使用 BIOS。BIOS 通过 `INT` 指令调用中断服务程序把内核从磁盘装入内存，例如 `int 0x19` 把启动盘 0 号磁头对应盘面 0 磁道 1 扇区中的引导程序装入内存。
:::

:::exam 真题考法：操作系统引导
- **2013-29**：计算机开机后操作系统最终被加载到 **RAM**。
- **2022-24**：需要在操作系统初始化过程中创建的是**中断向量表**。
- **2021、2022 统考**均考查过引导的阶段性任务划分（谁把什么加载到哪、哪一步依赖中断机制），要求能把上面的链条按顺序说清。
:::

## 虚拟机

### 虚拟机与虚拟机管理程序

**虚拟机（Virtual Machine，VM）** 是指通过**虚拟化技术**，把一台物理计算机抽象为多台逻辑上独立的计算环境，每台虚拟机都表现为**完整硬件系统的精确复制品**。虚拟化技术的核心在于隐藏底层物理硬件的细节，向上层提供统一且隔离的执行平台，每台虚拟机都可独立运行一个操作系统。

提供虚拟化功能的程序称**虚拟机管理程序**，同义术语还有**虚拟机监控程序**、**Virtual Machine Monitor（VMM）**、**Hypervisor**。注意**提供虚拟机管理程序并不属于操作系统的任务**——第二类虚拟机管理程序本身就是应用程序。两个必须区分的主体：运行在底层硬件上的操作系统称**宿主操作系统（Host OS）**，运行在虚拟机中的操作系统称**客户操作系统（Guest OS）**。

### 第一类虚拟机管理程序（裸金属架构）

第一类虚拟机管理程序**直接运行在物理硬件之上**，从技术上讲它就像一个操作系统，因为它是系统中**唯一处于最高特权级的软件**。它具备多道程序功能，向上层提供若干台虚拟机；每台虚拟机都是裸机的精确复制品，因此可以在不同虚拟机上运行任何不同的操作系统。

虚拟机作为**用户态的一个进程**运行，不允许执行敏感指令；然而虚拟机上的操作系统**认为自己运行在内核态（实际上不是）**，这种状态称为**虚拟内核态**。当客户操作系统执行一条仅允许在真实内核态下执行的**敏感（特权）指令**时，会触发异常并**陷入虚拟机管理程序**：在支持硬件虚拟化的 CPU（Intel VT-x、AMD-V）上，管理程序能判断指令来自客户操作系统还是用户程序，前者代为完成、后者模拟真实硬件的异常响应；在早期不支持硬件虚拟化的 CPU 上，所有敏感指令被透明重定向到管理程序，由它用软件模拟。

### 第二类虚拟机管理程序（寄居架构）

第二类虚拟机管理程序以**应用程序的形式运行在宿主操作系统**（如 Windows 或 Linux）之上，依赖宿主系统进行资源分配与调度，本质上是一个用户态进程；尽管如此，它仍向客户操作系统伪装成完整的硬件平台。**VMware Workstation 是 x86 平台上首个广泛使用的第二类虚拟机管理程序。**

首次启动时，第二类虚拟机管理程序模拟一台新计算机的行为，期望找到的驱动器可以是虚拟设备；用户把客户操作系统安装到**虚拟磁盘**上（实际上只是宿主操作系统中的一个文件），安装完成后即可正常启动和运行。

虚拟化技术在 Web 主机领域应用广泛：若无虚拟化，服务商只能提供**共享托管**（用户无法控制软件环境）或**独占托管**（成本高昂）；借助虚拟化，单台物理服务器可同时运行多个虚拟机，每台虚拟机对用户而言都是一台完整的服务器，支持自定义操作系统与软件，且成本显著降低——这正是当前主流云服务器服务的基础。

### 两类虚拟机管理程序对比

| 比较项 | 第一类（裸金属架构） | 第二类（寄居架构） |
|---|---|---|
| 运行位置 | 直接运行在硬件之上，唯一处于最高特权级 | 运行在宿主操作系统之上，本质是用户态进程 |
| 资源分配方式 | 直接控制和分配硬件资源，分配方式类似外核 | 依赖宿主操作系统分配和调度资源 |
| 性能 | 更好 | 较差，需要宿主操作系统中介 |
| 可支持的虚拟机数量 | 更多 | 较少，宿主操作系统自身也消耗资源 |
| 运行模式 | 运行在最高特权级，可执行最高特权指令 | 部分运行在用户态、部分在内核态，部分特权指令会被 VMM 截获 |
| 可迁移性 | 较差 | 导出镜像文件即可迁移 |
| 典型代表 | VMware ESXi、Xen、KVM | VMware Workstation、VirtualBox |

:::exam 真题考法：虚拟机
近年统考考查过虚拟化技术的原理与特点（如两类 VMM 的位置判断、「客户操作系统认为自己处于内核态」这一虚拟内核态的说法是否正确）。答题要点是抓住：**第一类 VMM 独占最高特权级、第二类 VMM 寄居在宿主 OS 之上**，以及**客户操作系统的「内核态」是虚拟的**。
:::

## 本章小结表

| 考纲条目 | 核心内容 | 必须记住的结论 |
|---|---|---|
| 操作系统的概念 | 控制和管理软硬件资源、合理调度任务与分配资源、为上层提供统一接口与运行环境的最基本系统软件 | 四层结构：硬件 → 操作系统 → 应用程序 → 用户；裸机 + OS = 扩充机器 |
| 双重角色 | 系统资源的管理者；用户与硬件之间的接口；实现对资源的抽象与扩充 | 用户接口（命令接口 + GUI）与程序接口（系统调用）不能混淆 |
| 四大功能 | 处理机管理、存储器管理、文件管理、设备管理 | 处理机管理本质上是进程管理；OS 管文件的组织方式而非内容 |
| 四大特征 | 并发、共享、虚拟、异步 | 并发与共享互为存在条件；没有并发就谈不上虚拟；并发才能导致异步 |
| 并发与并行 | 并发是同一时间间隔内、宏观同时微观交替；并行是同一时刻真正同时 | 并行需要多处理机 / 多流水线等硬件支持；单处理机上进程只能并发 |
| 手工操作阶段 | 用户独占全机，人工控制全过程 | 此阶段没有操作系统；CPU 利用率极低 |
| 单道批处理 | 内存中始终保持一道作业，脱机 I/O + 监督程序 | 特征为自动性、顺序性、单道性；I/O 时 CPU 空闲 |
| 多道批处理 | 内存驻留多道程序，I/O 时借助中断切换 | 多道、宏观并行、微观串行；优点利用率高吞吐大，缺点无交互响应长 |
| 分时系统 | 时间片轮转，多用户共用一台主机 | 同时性、交互性、独立性、及时性；首次实现人机交互 |
| 实时系统 | 按紧迫性 / 截止时间调度，抢占式 | 及时性、可靠性；分硬实时与软实时 |
| 各类系统排序 | —— | 资源利用率：批处理 > 分时 > 实时；交互性：分时 > 实时 > 批处理；及时性：实时 > 分时 > 批处理 |
| CPU 运行模式 | 内核态（管态）与用户态（目态），由 PSW 的模式位标识 | 内核态可执行全部指令；用户态只能执行非特权指令 |
| 特权指令 | I/O、开关中断、置时钟、修改 PSW 与内存保护寄存器、改中断向量表、内核态转用户态 | 用户程序执行特权指令会触发非法指令异常，由硬件强制实施 |
| 状态切换的途径 | 系统调用、外中断、异常、试图执行特权指令 | 用户态 → 内核态由硬件在中断响应时自动完成；内核态 → 用户态由 `IRET` 完成 |
| 中断与异常 | 中断是外中断（外设、时钟）；异常是内中断（故障、自陷、终止） | 外中断分可屏蔽（INTR）与不可屏蔽（NMI）；异常不可屏蔽 |
| 中断处理流程 | 判优 → 查中断向量表 → 特权级校验与切栈 → 保护现场 → 执行处理程序 → 恢复现场 | 硬件保存 PC 和 PSW；操作系统保存通用寄存器和中断屏蔽字 |
| 中断向量表 | 索引为中断类型号，表项为处理程序入口地址 | 本质是**数组**，由操作系统初始化，支持随机访问 |
| 系统调用 | 应用程序主动请求内核服务的唯一合法接口 | 与库函数不同：内核提供、必须切换特权级；不同 OS 接口不统一 |
| 系统调用过程 | 传参 → 陷入指令（用户态）→ 内核态执行服务程序 → 返回用户态 | 陷入指令 = trap = 访管指令，在用户态执行；硬件保存断点与 PSW |
| 链接方式 | 静态链接、装入时动态链接、运行时动态链接 | 越晚链接越省空间、越灵活，但运行时开销与实现复杂度更高 |
| 装入方式 | 绝对装入、可重定位装入（静态重定位）、动态运行时装入（动态重定位） | 静态重定位装入后不能移动；动态重定位需要重定位寄存器等硬件支持 |
| 内存映像 | 由低到高：代码段、数据段、堆、共享库映射区、栈 | 堆向高地址增长、栈向低地址增长；PCB 不在进程虚拟地址空间内 |
| 分层结构 | 层 0 是硬件、层 N 是用户接口，单向依赖 | 便于调试验证、易扩充维护；划分困难、效率较低 |
| 模块化结构 | 按功能划模块、定接口，模块-接口法 | 内聚性越高、耦合度越低，模块独立性越好 |
| 宏内核 | 主要功能模块紧密耦合，全部运行在内核态 | 性能高；内核臃肿难维护，一个模块出错可能全系统崩溃 |
| 微内核 | 只保留最基本机制在内核，其余为用户态服务器，靠消息传递 | 扩展灵活、可靠安全、可移植、支持分布式；性能差 |
| 外核 | 内核只管资源分配与保护，资源直接交给用户级系统 | 减少映像层与抽象开销；用库操作系统实现传统功能 |
| 操作系统引导 | BIOS/UEFI → POST → MBR → PBR → 启动管理器 → 内核 → init | MBR 共 512 字节（446 + 64 + 2），签名 `0x55AA`，只能有 4 个主分区项 |
| 虚拟机 | 把一台物理机虚拟为多台逻辑独立、硬件完整的虚拟机 | 第一类为裸金属架构（VMM 在最高特权级）；第二类为寄居架构（VMM 是应用） |

## 易错清单

1. **「内核态只能执行特权指令」错**（内核态能执行所有指令）；**「用户态只能执行非特权指令」对**——2022-27 的直接考点。
2. **修改 PSW 模式位的指令本身是特权指令**，所以用户态 → 内核态不可能靠执行指令完成，一定是**中断 / 异常响应时由硬件自动切换**。
3. **「中断处理程序负责切换模式」错**：中断处理程序开始执行时 CPU 已经在内核态了；**「中断或异常发生时 CPU 处于内核态」也错**：事件发生那一瞬间 CPU 可能仍在用户态。要分清「发生」与「处理」，2012-23 与 2024-23 都考这个区分。
4. **进程切换不可能在用户态发生**（2012-23），但系统调用、外部中断、缺页都可能在 CPU 执行用户程序时发生。
5. **trap、跳转、压栈、数据传送、设置断点指令都是非特权指令**，可在用户态执行；只有 **I/O 指令、开 / 关中断指令** 这类才必须在内核态（2014-25、2021-23）。
6. **`NOT R0` 不会引起模式切换**（不访存、不触发调用）；而 `DIV`（可能除零）、`INT n`（软中断）、`MOV`（访存可能缺页或越界）都可能（2015-24）。
7. **中断与异常的归属容易搞反**：时钟中断是**外中断**；缺页、除零、非法操作码、系统调用都是**内中断（异常）**，其中缺页属**故障**、系统调用属**自陷**。
8. **异常不能被屏蔽**，不可屏蔽中断也不能被屏蔽；中断屏蔽字是**按类型**屏蔽而非全局关中断。
9. **硬件保存断点（PC）和 PSW，操作系统保存通用寄存器和中断屏蔽字**（2015-23、2020-27、2022-31 反复正反问）。
10. **普通函数调用不保存 PSW**（全程同特权级）；允许多重中断时才必须保存，因为可能在用户态也可能在内核态响应中断。
11. **中断向量表用数组实现**，因为需要按下标随机访问（2023-24）；不要选队列或链表。
12. **「不同的操作系统为应用程序提供统一的系统调用接口」是错的**；「操作系统提供给应用程序的接口」指的是**系统调用**，不是库函数、中断或原语（2010-23、2019-25）。
13. **库函数不等于系统调用**：`sin()`、`strlen()`、`rand()` 完全在用户态；`printf` 底层会调用 `write`，`malloc` 在大块分配时可能调用 `brk` / `mmap`。
14. **创建新进程需要系统调用，页置换和进程调度不需要**（前者由缺页异常自动触发，后者由时钟中断等隐式触发）——2021-32 的考点。
15. **系统调用顺序必须是「先传参、再陷入、后执行服务程序、最后返回用户态」**，不要把返回用户态排到中间（2017-24）。
16. **多道批处理系统不必支持虚拟存储管理**（2022-23）；**多道程序系统的系统开销并不更小**（2017-28 的干扰项）；它也**不提高单个作业的运行速度**，提升的是资源利用率与吞吐量。
17. **进程数越多 CPU 利用率不一定越高**，进程过多会因争抢 CPU 反而降低利用率。
18. **静态重定位的进程装入后不能移动、也不能动态申请内存**；需要移动进程（页式、紧凑操作）的场景必须用动态重定位。
19. **`.bss` 存放未初始化的全局 / 静态变量**，已初始化的放 `.data`；代码段只读；**堆向高地址增长、栈向低地址增长**，方向相反不能记反。
20. **PCB 不属于进程的虚拟地址空间**，它由内核维护、对用户进程不可见。
21. **MBR 只能描述 4 个主分区，四个里只有一个可以是激活分区**；签名 `0x55AA` 位于第 511～512 字节；**开机时操作系统既不在 ROM 也不在 MBR 中**，最终落在 RAM。
22. **中断向量表会被建立两次**：BIOS 阶段建立临时表供引导使用，操作系统初始化时重建属于自己的中断向量表；分区表、文件系统根目录、索引节点表都不是操作系统初始化阶段创建的（2022-24）。
23. **宏内核性能高但可靠性差，微内核可靠性高但性能差**；「微内核具有较好的性能」是错误选项（2023-23 中 Ⅰ 项为错）。
24. **第二类虚拟机管理程序本身是应用程序**，「提供虚拟机管理程序属于操作系统的任务」是错的；**客户操作系统的「内核态」是虚拟内核态**。
