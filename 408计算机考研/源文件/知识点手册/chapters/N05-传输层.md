传输层是「面向通信部分的最高层，用户功能中的最低层」。它在 408 里的地位非常特殊：**选择题年年出，大题几乎每隔一两年就出一次**，而且大题往往不是单纯考定义，而是把「序号/确认号推算 + 窗口计算 + 拥塞窗口逐轮演算 + 时间估算」揉在一道题里。也就是说，这一章真正要练的不是背概念，而是**四类手算能力**：

1. **序号与确认号的推算**（连接建立、数据传送、连接释放三个阶段都要会）；
2. **窗口的推算**（发送窗口 = min(rwnd, cwnd)，还要能判断窗口内哪些字节能发）；
3. **拥塞窗口的逐轮演算**（慢开始、拥塞避免、快重传、快恢复的分支处理）；
4. **时间估算**（RTT、MSL、RTO 的加减）。

本章按考纲条目顺序展开，所有计算公式都配上可以自己验算一遍的数字例子。三次握手、四次挥手、窗口滑动、拥塞控制这四块，一律给完整的算例表格。

### 传输层提供的服务

#### 传输层的功能

##### 进程到进程的逻辑通信

**传输层（transport layer）** 的核心任务是：**为运行在不同主机上的应用进程之间提供逻辑通信**。注意这里的「逻辑通信」四个字。

从应用层看过去，只要把报文交给下面的传输层，传输层就好像能沿水平方向把它直接送到对方的传输层，哪怕两台主机相隔几千公里。但事实上，两个传输层之间**并不存在一条水平方向的物理连接**——数据仍然要一层层向下走，经过网络层、数据链路层、物理层，到达对端后再一层层向上递交。「逻辑通信」的含义就是「好像是这样通信，但事实上并非真的这样通信」。

传输层向上提供的是**应用进程之间**的通信，所以叫 **端到端（end-to-end）通信**；网络层提供的是**主机到主机**的通信。这两个层次的「端」含义完全不同：

| 对比项 | 网络层 | 传输层 |
|---|---|---|
| 通信主体 | 主机到主机（host-to-host） | 进程到进程（process-to-process，端到端） |
| 标识方式 | IP 地址 | IP 地址 + 端口号（套接字） |
| 典型协议 | IP、ICMP、ARP | TCP、UDP |
| 是否区分进程 | 不区分，只找到主机 | 必须区分，交付给具体进程 |

:::key 一句话区分
网络层解决「**送到哪台主机**」，传输层解决「**送到哪台主机的哪个进程**」。IP 地址定位主机，端口号定位进程，两者合起来（套接字）才能唯一确定一次进程间通信的端点。
:::

##### 复用与分用

**复用（multiplexing）**：发送方的多个应用进程可以共用同一个传输层协议（TCP 或 UDP）发送数据，传输层给数据加上适当的首部后交给网络层。

**分用（demultiplexing）**：接收方的传输层在剥去报文首部后，依据首部中的**端口号**把数据正确交付给目的应用进程。

要注意网络层也有复用与分用，但**复用的含义不同**：

- 网络层的复用：不同**协议**的数据（TCP 报文段、UDP 用户数据报、ICMP 报文等）都可以封装成 IP 数据报发送出去；
- 网络层的分用：接收方剥去 IP 首部后，依据首部中的**协议字段**把数据交付给相应的上层协议。

也就是说，**网络层按「协议」分用，传输层按「端口」分用**。这是统考选择题里反复出现的辨析点。

:::warn 复用还是分用？
「多个进程共用一个传输层协议」是**复用**；「依据端口号把数据交给正确的进程」是**分用**。题目问「UDP 实现分用时依据哪个字段」——答案是**目的端口号**，不是源端口号。源端口号的作用是让对方知道该把回复送到哪里。
:::

##### 其他功能

传输层还需要承担下面这些功能，其中哪些真正实现，取决于用的是 TCP 还是 UDP：

- **差错检测**：TCP 和 UDP 都用「首部 + 数据 + 伪首部」的校验和检测误码。但**校验和只能检测误码，不能纠错，更不能保证可靠交付**。
- **流量控制**：TCP 有，通过接收窗口 rwnd 抑制发送速率；UDP 没有。
- **拥塞控制**：TCP 有，通过拥塞窗口 cwnd 防止过多数据注入网络；UDP 没有。
- **可靠传输**：TCP 有（确认、重传、排序、去重）；UDP 没有。
- **连接建立与释放**：TCP 有；UDP 无连接。

:::exam 出题角度
2014 年第 39 题考的就是「传输层功能的辨析」：「UDP 提供无连接服务」「UDP 提供复用/分用服务」「UDP 通过差错校验保障可靠数据传输」三个说法中哪个正确——前两个对，第三个错。**「有校验和」不等于「可靠传输」**，这是本节最经典的陷阱。
:::

不同的操作系统，进程标识符（PID）的命名规则、格式、长度都不一样；更关键的是**进程的创建与撤销是动态的**，同一个进程在不同时刻的 PID 会发生变化，通信的另一方根本无法预先知道。

:::key 为什么用端口号而不用进程号
需要一个**独立于操作系统、相对稳定**的进程标识——这就是端口号。

端口号引入后，接收方只需「监听某个众所周知的端口」，就可以稳定地接收来自任意主机的请求，而完全不关心对方是哪个操作系统、进程号是多少。
:::

:::exam 补充
按 OSI 的说法，传输层的服务访问点叫 **TSAP（Transport layer Service Access Point）**，其具体形式就是传输层端口。各层的 SAP 依次是：物理层 PSAP（物理接口）、数据链路层 DLSAP（MAC 地址）、网络层 NSAP（IP 地址）、传输层 TSAP（端口）、会话层 SLSAP、表示层 PLSAP。这一条属于「层与 SAP 对应关系」的送分点。
:::

#### 传输层寻址与端口

##### 端口号

**端口（port）** 是传输层使用的、用来标识应用进程的软件标识符，也叫**端口号（port number）**。

- 端口号占 **16 比特**，取值范围 **0 ~ 65535**（共 $2^{16}=65536$ 个）。
- 端口号是**软件层面的概念**，与硬件无关。它存在于传输层首部中，标识的是「本机协议栈应用层中的某个应用进程」。
- **端口号只具有本地意义**：端口号只用来标识本机应用层的进程。因特网中不同计算机上的**相同端口号之间没有任何关系**，相互独立。
- **TCP 与 UDP 的端口号也是相互独立的**。同一个端口号 53 在 UDP 里给 DNS 用，在 TCP 里也可以给 DNS 用，二者互不冲突。

:::key 必背
端口号 16 位、取值范围 0~65535、只有本地意义、TCP 与 UDP 端口号相互独立。这四句话几乎每年都有题在考。
:::

##### 三类端口号

| 类别 | 范围 | 说明 | 举例 |
|---|---|---|---|
| **熟知端口号**（well-known port） | **0 ~ 1023** | 由 IANA 统一指派给最重要的应用层协议，固定不变 | FTP 21、HTTP 80、DNS 53 |
| **登记端口号**（registered port） | **1024 ~ 49151** | 给没有熟知端口号的应用程序使用，必须在 IANA 登记以防重复 | 微软远程桌面 3389 |
| **短暂端口号**（ephemeral port，也叫客户端端口号/临时端口号） | **49152 ~ 65535** | 客户端进程在通信时由操作系统**临时动态分配**，通信结束后被回收并放入空闲端口池 | 客户端发起连接时使用的端口 |

三类端口号的边界必须记牢：**1023 / 49151** 是两个分界点。有的教材把第二类写成「1024~49151」、第三类写成「49152~65535」，分界点完全一致。

:::warn 三类端口号的分界
题目经常这样设陷阱：给一个端口号 65535，问它属于哪一类——属于**短暂端口号**（客户端），不是登记端口号。再比如问「服务器端使用的端口一定是熟知端口吗」——不一定，服务器进程同样可以使用登记端口号（如 3389）。
:::

##### 套接字

仅仅用「IP 地址 + 端口号」还不能完整描述一次通信，因为一次 TCP 连接是**双向**的，需要两端各一个端点。

**套接字（socket）**：

$$ \text{socket} = (\text{IP 地址} : \text{端口号}) $$

**TCP 连接**由通信两端的两个套接字唯一确定（四元组）：

$$ \text{TCP 连接} ::= \{\text{socket}_1,\ \text{socket}_2\} = \{(\text{IP}_1:\text{port}_1),\ (\text{IP}_2:\text{port}_2)\} $$

这一条解释了两个重要现象：

- 同一台主机上的同一个服务器端口（比如 80）可以同时接受**很多**客户端连接，因为每个连接的「四元组」不同；
- 反过来，两台主机之间如果四元组完全相同，那就是**同一条**连接（这也解释了为什么端口号复用一般不会冲突）。

:::exam 出题角度
常考形式：给出若干条 TCP 连接的四元组，问「哪两条是同一个连接」「这条连接的两端套接字分别是什么」。判断标准就是**四元组是否完全一致**。
:::

##### 常见协议的熟知端口号表（必背）

| 应用层协议 | 端口号 | 使用的传输层协议 | 用途要点 |
|---|---|---|---|
| FTP | **21**（控制）/ **20**（数据） | TCP | 21 传命令，20 传数据（主动模式） |
| SSH | **22** | TCP | 安全远程登录 |
| Telnet | **23** | TCP | 远程登录（明文） |
| SMTP | **25** | TCP | 发送邮件（客户 → 服务器） |
| DNS | **53** | UDP（域名解析）/ TCP（区域传送） | 域名解析 |
| DHCP | **67**（服务器）/ **68**（客户端） | UDP | 服务器监听 67，客户端用 68 接收 |
| TFTP | **69** | UDP | 简单文件传输 |
| HTTP | **80** | TCP | 网页明文传输 |
| POP3 | **110** | TCP | 接收邮件（下载到本地） |
| IMAP | **143** | TCP | 接收邮件（服务器上管理） |
| HTTPS | **443** | TCP | 网页加密传输 |
| SNMP | **161** | UDP | 网络管理 |
| RIP | **520** | UDP | 路由信息协议 |

记忆技巧：

- **FTP 一对**：21 发命令、20 传数据；
- **邮件三兄弟**：SMTP 25（发）、POP3 110（收）、IMAP 143（收）；
- **DNS 53**：「我要解析（53）域名」；
- **DHCP 67/68**：服务器 67、客户端 68，相邻一对；
- **HTTP 80 明文、HTTPS 443 加密**；
- **TFTP 69 / SNMP 161 / RIP 520** 都是 UDP，这三个最容易和 TCP 混淆。

:::warn 高频陷阱
1. **RIP 用 UDP 520 端口**，不是 TCP；BGP 才用 TCP 179。（2017 年、2021 年都出现过这类辨析。）
2. **DNS 主要用 UDP 53**，但区域传送（zone transfer）用 TCP 53。题目若说「DNS 只使用 UDP」，那是错的。
3. **DHCP 两个端口都要记**：服务器 67、客户端 68，不要颠倒。
4. **SNMP 用 UDP 161**，SNMP Trap 用 UDP 162。
:::

#### 无连接服务与面向连接服务

传输层向应用层提供两类服务，对应两个协议：

- **面向连接的服务**：TCP（Transmission Control Protocol，传输控制协议）。通信前必须先建立连接，通信结束后释放连接，提供可靠的、按序的、面向字节流的服务。
- **无连接的服务**：UDP（User Datagram Protocol，用户数据报协议）。通信前不建立连接，提供尽最大努力交付的、不可靠的、面向报文的服务。

##### TCP 与 UDP 的全面对比

| 对比项 | UDP | TCP |
|---|---|---|
| 连接方式 | 无连接 | 面向连接（三报文握手建立、四报文挥手释放） |
| 可靠性 | 不可靠，尽最大努力交付 | 可靠（确认、重传、排序、去重） |
| 数据组织方式 | **面向报文**，应用层给多长就发多长，一次发一个报文，既不合并也不拆分 | **面向字节流**，把数据看成无结构的字节序列，可自行划分成报文段 |
| 首部开销 | **8 字节**，固定 | **20 字节**固定 + 最多 40 字节选项 = 最长 60 字节 |
| 流量控制 | 无 | 有（接收窗口 rwnd） |
| 拥塞控制 | 无 | 有（拥塞窗口 cwnd，四种算法） |
| 差错检测 | 有校验和（IPv4 中可选用，全 0 表示不校验） | 有校验和（**必选**，出错则丢弃并等待重传） |
| 是否保证按序到达 | 不保证 | 保证 |
| 通信模式 | 一对一、一对多、多对一、多对多（支持广播与组播） | 只能是**一对一**（单播） |
| 连接状态 | 无状态 | 需要维护发送/接收缓存、序号、确认号、拥塞控制参数等大量状态 |
| 适用场景 | 实时性要求高、能容忍少量丢失：DNS、DHCP、TFTP、SNMP、RIP、实时音视频 | 要求可靠：HTTP、FTP、SMTP、POP3、IMAP、SSH、Telnet |

:::warn 三个最容易错的对比点
1. **「面向报文」与「面向字节流」**：UDP 保留应用层报文的边界，一次发一个；TCP 不保留边界，可能把两个小报文合并成一个段发出，也可能把一个大报文拆成多个段。所以 2010 年前后的选择题里「TCP 和 UDP 都可以对报文进行合并拆分」是错的——**只有 TCP 可以**。
2. **校验和覆盖范围**：UDP 与 TCP 的校验和都覆盖「伪首部 + 首部 + 数据」，而 **IP 数据报首部校验和只校验首部**，不含数据。
3. **广播/组播**：只有 UDP 支持广播和组播，TCP 只支持单播。
:::

### UDP 协议

#### UDP 数据报

##### UDP 的特点

- **无连接**：发送数据前不需要建立连接，每个 UDP 用户数据报独立处理，互不影响。因此 UDP 不需要像 TCP 那样维护连接状态。
- **尽最大努力交付**：不保证可靠，不保证按序，不保证不重复。
- **面向报文**：应用层交下来多长的报文，UDP 就原样封装成一个 UDP 用户数据报发送，既不合并也不拆分。因此应用层必须自己选择合适大小的报文——报文太长，交给 IP 层后可能被分片，降低效率；报文太短，首部开销占比过大。
- **支持多种通信模式**：一对一、一对多、多对一、多对多，即支持单播、广播、组播。
- **首部开销小**：只有 8 字节。
- **无流量控制、无拥塞控制**：即使网络已经拥塞，UDP 也不会降低发送速率。这一点在网络拥塞时可能造成大量丢包，但也正是实时业务（语音、视频）需要 UDP 的原因——宁可丢几个包，也不要因为等待重传而引入大延迟。

:::key 记忆口诀
UDP 的六条特点：**无连接、不可靠、面向报文、支持广播组播、首部小、无流量/拥塞控制**。
:::

##### UDP 用户数据报的格式

UDP 用户数据报 = **8 字节首部 + 数据部分**。首部只有四个字段，每个字段 **2 字节**：

| 字段 | 长度 | 含义 |
|---|---|---|
| **源端口** | 2 B | 发送方进程的端口号。不需要对方回复时可全置 0 |
| **目的端口** | 2 B | 接收方进程的端口号，**分用就靠这个字段** |
| **长度** | 2 B | UDP 用户数据报的**总长度 = 首部 8 B + 数据部分长度**，单位字节 |
| **校验和** | 2 B | 检测整个用户数据报在传输中是否出现误码。全 0 表示**不进行校验** |

:::key 长度字段
因为长度字段只有 16 位，所以 UDP 用户数据报的最大总长度是 $2^{16}-1=65535$ 字节，其中数据部分最多 $65535-8=65527$ 字节。**「长度」字段的最小值是 8**（此时数据部分为空）。
:::

:::warn 「长度」字段的两种问法
题目给「长度字段 = 1500」，则**数据部分长度 = 1500 − 8 = 1492 字节**；题目给「UDP 数据部分 1500 字节」，则**长度字段 = 1500 + 8 = 1508**。这两个方向都要会，也是选择题的经典送分/送命点。
:::

##### UDP 不保证可靠交付

因为 UDP 没有确认与重传机制，所以：

- 数据报丢失后不会重传；
- 数据报到达顺序可能与发送顺序不同；
- 数据报可能重复到达。

**校验和只能检测误码。** 接收方发现校验出错时，**通常直接丢弃该数据报**，不产生任何差错报告（注意：UDP 本身不会因此发送 ICMP 差错报文，但若目的端口不可达，接收方的 IP 层可能回送 ICMP 端口不可达——这是 IP 层的职责，不要混为一谈）。

#### UDP 校验

##### 校验和的计算范围

UDP 的校验和覆盖三个部分：

$$ \text{校验范围} = \text{12 字节伪首部} + \text{8 字节 UDP 首部} + \text{UDP 数据部分} $$

若这三部分的总长度不是偶数个字节，还要在末尾**补 1 个全 0 字节**凑成偶数（因为要按 2 字节为单位分组相加）。**补充的全 0 字节只用于计算校验和，不发送。**

##### 伪首部（pseudo-header）

**伪首部**共 **12 字节**，结构如下：

| 字段 | 长度 | 取值 |
|---|---|---|
| 源 IP 地址 | 4 B | 取自 IP 数据报首部，不是「本机 IP」的抽象概念，而是实际发送用的那个源地址 |
| 目的 IP 地址 | 4 B | 取自 IP 数据报首部 |
| 全 0 字段 | 1 B | 保留，置 0（有教材称「保留字节」） |
| 协议号 | 1 B | **UDP 为 17** |
| UDP 长度 | 2 B | UDP 用户数据报的总长度（首部 + 数据），**与首部中「长度」字段的值相同** |
| 合计 | **12 B** | |

:::key 伪首部的作用（必背）
伪首部的作用是**让传输层能够检查数据是否被错误地交付到了本主机、本协议**。它把源 IP、目的 IP、协议号一起纳入校验范围，于是：

1. 如果 IP 数据报被错误地投递到**错误的地址**（目的 IP 不符），校验和会失败；
2. 如果 IP 数据报被错误地交给了**错误的协议**（协议号不符），校验和也会失败。

**伪首部既不在网络中传送（发送方算完就丢弃），也不向上层递交**，它只在两端计算校验和时临时构造。这一点是选择题的高频正确选项。
:::

##### 校验和的计算过程

**发送方计算步骤**：

1. 把 UDP 首部中的**校验和字段置为 0**；
2. 在 UDP 用户数据报前面临时加上 12 字节伪首部；
3. 把「伪首部 + 首部 + 数据」按 **2 字节（16 位）为一组**划分成若干个「字」。若总长度是奇数个字节，在末尾补 1 个全 0 字节；
4. 对所有 16 位字进行**二进制反码求和**：逐字相加，每次相加若最高位产生进位，就把进位**回卷**加回到最低位（cyclic carry）；
5. 把求和结果**逐位取反**，写入 UDP 首部的校验和字段。

**接收方校验步骤**：

1. 给收到的 UDP 用户数据报前面加上 12 字节伪首部；
2. 同样按 2 字节分组，做二进制反码求和；
3. 把结果取反。若结果为 **0**，说明传输无误码；否则说明出现误码，**丢弃该数据报**。

:::key 全 0 的含义
**发送方把校验和字段置为全 0，表示「不进行校验」**（这是 IPv4 下 UDP 允许的，IPv6 下 UDP 校验和是必选的）。接收方收到校验和字段为全 0 的数据报，就不做校验，直接交付。

另外还有一个容易忽略的细节：**如果校验和的计算结果恰好是全 0，那么应当写入全 1（即 0xFFFF），而不是全 0**。因为全 0 已经被「不校验」这个特殊含义占用了。这就是所谓「**全 0 表示不校验，全 1（即零的反码）表示校验和为 0**」。
:::

##### 完整算例（可以自己验算一遍）

设某 UDP 用户数据报的各字段（用十六进制表示）：

- 源 IP 地址 = `C0A8 0101`（即 192.168.1.1）
- 目的 IP 地址 = `0A00 0005`（即 10.0.0.5）
- 协议号 = `0011`（即十进制的 17）
- UDP 长度 = `000C`（即 12 字节：8 字节首部 + 4 字节数据）
- 源端口 = `1F90`，目的端口 = `0053`
- 数据部分 = `0102 0304`（4 字节）

第一步：构造需要参与运算的全部 16 位字。

| 序号 | 内容 | 16 位十六进制 |
|---|---|---|
| ① | 源 IP 高位 | `C0A8` |
| ② | 源 IP 低位 | `0101` |
| ③ | 目的 IP 高位 | `0A00` |
| ④ | 目的 IP 低位 | `0005` |
| ⑤ | 全 0 字节 + 协议号 | `0011` |
| ⑥ | UDP 长度 | `000C` |
| ⑦ | 源端口 | `1F90` |
| ⑧ | 目的端口 | `0053` |
| ⑨ | 长度字段 | `000C` |
| ⑩ | 校验和（置 0） | `0000` |
| ⑪ | 数据第 1 个 16 位 | `0102` |
| ⑫ | 数据第 2 个 16 位 | `0304` |

（第①~⑥项合起来正是 12 字节伪首部，第⑦~⑩项是 UDP 的 8 字节首部，第⑪⑫项是数据部分。）

:::warn 注意两个「长度」
⑥ 是伪首部里的 UDP 长度，⑨ 是 UDP 首部里的长度字段，**两处必须是同一个值**（本题都是 `000C`），但它们**是两个不同的字段**，做加法时两个都要算进去，不要漏掉其中一个，也不要误以为重复而只算一次。
:::

第二步：二进制反码求和（用十六进制加法）。

```plain
  C0A8
+ 0101
= C1A9
+ 0A00
= CBA9
+ 0005
= CBAE
+ 0011
= CBBF
+ 000C
= CBCB
+ 1F90
= EB5B
+ 0053
= EBAE
+ 000C
= EBBA
+ 0000
= EBBA
+ 0102
= ECBC
+ 0304
= EFC0
```

求和结果为 `EFC0`，过程中没有产生 16 位溢出，因此无需回卷。

第三步：取反。

$$ \overline{\texttt{EFC0}} = \texttt{103F} $$

所以**校验和字段应写入 `103F`**。

第四步：接收方验证。把全部字（含 `103F`）再加一遍：

```plain
  EFC0          （前面全部字之和）
+ 103F          （校验和字段）
= FFFF
```

结果为全 1，取反后为全 0，说明传输无误码。✔

**回卷进位算例（考得比上面这个还多）**

上面的算例比较「小」，恰好没有出现 16 位溢出。但真实题目里几乎一定会溢出，所以「回卷」这一步必须练熟。设求和的**中间结果**为 `B9B6`（已包含前面所有字，尚未取反），此时还剩最后一个 16 位字 `65C5` 需要加入：

```plain
   1011 1001 1011 0110   (0xB9B6)
 + 0110 0101 1100 0101   (0x65C5)
 -------------------------
 1 0001 1111 0111 1011   (0x11F7B)   ← 产生了 1 位溢出进位
```

**回卷**：把溢出的最高位进位 1 加回最低位：

```plain
   0001 1111 0111 1011   (0x1F7B)
 +                     1
 -------------------------
   0001 1111 0111 1100   (0x1F7C)   ← 反码和
```

**取反**得到校验和：

```plain
   0001 1111 0111 1100   (0x1F7C)
 → 1110 0000 1000 0011   (0xE083)   ← 校验和
```

验证：把 `0x1F7C` 与 `0xE083` 相加，$1F7C + E083 = FFFF$，取反为 0，正确。✔

:::key 回卷的两种等价写法
1. **文字写法**：先把全部字相加，若结果超过 16 位，把高位进位加到低 16 位上——这就是「回卷（cyclic carry）」；
2. **工程写法**：每加一个字就检查一次进位并立刻回卷（本例就是这样做的）。两种写法结果完全一致。

**做题时的顺序一定要记住**：先全部反码求和（含回卷）→ 再取反 → 写入校验和字段。**取反必须放在最后**，先把中间结果取反再相加就错了。
:::

:::warn 校验和计算题的三个坑
1. **做加法时忘了把伪首部算进去**。伪首部一定要算，而且 UDP 的协议号是 **17**（TCP 是 6）。
2. **忘了回卷进位**。只要 16 位相加产生进位，就必须把进位加回到最低位。2024 年第 39 题就专门考了这个「中间结果 + 最后一个字」的回卷与取反。
3. **最后一步忘了取反**，或者取反后忘了「全 0 要写成全 1」。
:::

##### TCP 校验与 UDP 校验的差别

TCP 的校验和计算过程与 UDP **完全相同**（反码求和 + 回卷 + 取反），只有两处不同：

- 伪首部中的**协议号是 6**（而不是 17）；
- 伪首部中的长度字段是 **TCP 报文段的长度**（而不是 UDP 长度）。

**TCP 的校验和是必选的**（不能用「全 0」表示不校验），而出错时同样只是丢弃，由超时重传机制来弥补。

:::exam 出题角度
UDP 校验是选择题的常客，典型问法有三类：①「伪首部的作用是什么」②「校验和的覆盖范围包括什么」③「给出若干 16 位字，求校验和」。第③类只需老老实实做反码加法。另外还会考「全 0 校验和表示什么」——**表示不校验**，不是「校验通过」。
:::

### TCP 协议

#### TCP 段

##### TCP 的主要特点

- **面向连接**：通信前必须先建立连接，通信结束后必须释放连接。
- **只能一对一**：每条 TCP 连接只能有两个端点（两个套接字），因此不支持广播和组播。
- **可靠交付**：无差错、不丢失、不重复、按序到达。
- **全双工通信**：TCP 连接的两端都设有发送缓存和接收缓存，数据可以双向同时传输。
- **面向字节流**：TCP 把应用层交下来的数据看成**一连串无结构的字节流**。TCP 不保留应用层报文的边界，发送方可以根据情况把字节流划分成若干个大小合适的报文段，接收方再把它们还原成字节流。

:::key 面向字节流的三个推论
1. **序号以字节为单位编号**，不是以报文段为单位。一个报文段的序号 = 该报文段数据部分第一个字节的序号。
2. 应用层的一次「写」操作，可能对应多个 TCP 报文段；多次「写」操作，也可能被合并进一个 TCP 报文段。
3. TCP 连接的两端只是「字节流的两端」，TCP 自己并不知道这次传输在应用层是一条消息还是半条消息。
:::

##### TCP 报文段的首部格式

TCP 报文段 = **首部 + 数据载荷**。首部由**固定首部 20 字节**和**选项 + 填充（最多 40 字节）**组成，因此 TCP 首部最长 **60 字节**。

| 字段 | 长度 | 含义 |
|---|---|---|
| **源端口** | 2 B | 发送方进程端口号 |
| **目的端口** | 2 B | 接收方进程端口号 |
| **序号 seq** | 4 B | 本报文段数据载荷的**第一个字节**的序号，取值 0 ~ $2^{32}-1$，到最大值后回到 0 |
| **确认号 ack** | 4 B | 期望收到对方**下一个**报文段的第一个字节的序号；仅在 ACK=1 时有效 |
| **数据偏移** | 4 bit | 指出 TCP 报文段**数据载荷的起始位置**距报文段起始位置有多远，即**首部长度**，以 **4 字节**为单位 |
| **保留** | 6 bit | 保留今后使用，目前置 0（新版标准中部分位已被 ECE、CWR 占用，用于拥塞控制通知） |
| **URG** | 1 bit | 紧急标志位。URG=1 时紧急指针字段有效 |
| **ACK** | 1 bit | 确认标志位。ACK=1 时确认号字段才有效；**连接建立后所有报文段都必须把 ACK 置 1** |
| **PSH** | 1 bit | 推送标志位。置 1 表示接收方应尽快交付应用进程，不必等接收缓存填满 |
| **RST** | 1 bit | 复位标志位。置 1 表示连接出现严重差错，必须释放连接后重新建立；也用来拒绝非法报文段或拒绝打开连接 |
| **SYN** | 1 bit | 同步标志位。用于建立连接。SYN=1 且 ACK=0 是连接请求；SYN=1 且 ACK=1 是连接接受 |
| **FIN** | 1 bit | 终止标志位。置 1 表示发送方数据已全部发完，要求释放连接 |
| **窗口** | 2 B | 指**本报文段发送方自己的接收窗口**大小（接收缓存可用空间），以**字节**为单位，用于流量控制。最大 65535 字节 |
| **校验和** | 2 B | 覆盖伪首部 + TCP 首部 + 数据载荷；计算方法与 UDP 相同，但协议号为 6 |
| **紧急指针** | 2 B | URG=1 时有效，以字节为单位指出本报文段中紧急数据的长度 |
| **选项** | 可变 | 最长 40 B。常用：MSS 选项、窗口扩大选项、时间戳选项、选择确认 SACK 选项 |
| **填充** | 可变 | 使首部长度能被 4 字节整除 |

##### 序号与确认号：本节第一重点

这是 TCP 全部计算题的根基，必须彻底分清。

**序号 seq（sequence number）**：本报文段**数据载荷的第一个字节**的序号。如果本报文段不携带数据，则「不消耗序号」——但 SYN 和 FIN 是例外，见后文。

**确认号 ack（acknowledgement number）**：**期望收到对方下一个报文段的第一个数据字节的序号**，同时也是对「到 ack−1 为止的所有数据都已正确收到」的确认。

:::key 序号与确认号一句话区分
- **seq 说的是「我发的这段数据从第几号字节开始」**——回答「我在说什么」；
- **ack 说的是「我想听你从第几号字节往下讲」**——回答「我听到哪儿了」。

若确认号为 $N$，则表明：**序号到 $N-1$ 为止的所有数据都已正确接收**。
:::

**与 GBN 的区别（易错）**：在后退 N 帧协议中，ACK $n$ 表示「序号到 $n$ 为止的数据已正确接收，期望收到 $n+1$」；而 **TCP 中 ack $=N$ 表示「到 $N-1$ 为止已正确接收，期望收到 $N$」**。两者的下标含义差 1，千万不要混用。

**示例**：甲向乙发送一段 300 字节的数据，seq=201。这段数据占用序号 201~500。若乙正确收到，则乙回复的确认号 ack $=501$。

:::key 序号取值规则（必背，覆盖握手/挥手/数据三个阶段）
| 报文类型 | 是否消耗序号 |
|---|---|
| **SYN 报文段**（握手第 1、2 次） | **消耗 1 个序号** |
| **FIN 报文段**（挥手第 1、3 次） | **消耗 1 个序号** |
| 纯 ACK 报文段（不携带数据） | **不消耗序号** |
| 携带有数据的报文段 | 消耗的序号数 = 数据字节数 |
| 握手第 3 次的 ACK | 携带数据则消耗相应字节数；不携带数据则不消耗（下一报文段序号仍为 x+1） |
| 挥手第 4 次的 ACK | **规定不能携带数据，也不消耗序号** |
:::

##### 数据偏移

- 占 **4 比特**，以 **4 字节**为单位。
- 因为 4 比特最大能表示 15，所以 TCP 首部最长 $15\times4=60$ 字节。
- 固定首部 20 字节，对应数据偏移 $=20/4=5$，二进制 `0101`。
- 因为首部长度必须是 4 字节的整数倍，所以若「固定首部 + 选项」的长度不能被 4 整除，要用**填充**字段补足。

:::warn 数据偏移 vs IP 首部长度 vs IP 片偏移
三个「偏移」含义完全不同，题目最爱混着考：

- **TCP 数据偏移**：TCP 首部长度，单位 4 字节，最小值 5、最大值 15；
- **IP 首部长度**：IP 首部长度，单位 4 字节，最小值 5、最大值 15；
- **IP 片偏移**：该分片的数据在原始数据报中的相对位置，单位 **8 字节**。
:::

##### 六个标志位

| 标志位 | 名称 | 作用 |
|---|---|---|
| **URG** | 紧急 | 置 1 时紧急指针有效，紧急数据「插队」传到接收方并直接上交应用进程，不等接收缓存排队。即使窗口为 0 也可以发送紧急数据 |
| **ACK** | 确认 | 置 1 时确认号才有效。**连接建立后所有报文段都必须置 1** |
| **PSH** | 推送 | 置 1 时接收方尽快交付应用进程，不必等缓存填满。用于交互式通信（如 Telnet） |
| **RST** | 复位 | 置 1 表示连接出现严重差错，须释放并重建；也用于拒绝非法报文段或拒绝打开连接 |
| **SYN** | 同步 | 用于建立连接。**SYN=1 的报文段不能携带数据，但要消耗一个序号** |
| **FIN** | 终止 | 置 1 表示数据发完，要求释放连接。**FIN=1 的报文段即使不携带数据也要消耗一个序号** |

:::exam 出题角度
- 「主机 A 的应用进程突然崩溃，随后 A 向 B 发送了一个 TCP 报文段」——该报文段的 **RST=1**（B 收到后释放连接）。
- 「哪个标志位用于拒绝非法的 TCP 报文段」——**RST**。
- 「连接建立后哪个标志位始终为 1」——**ACK**。
:::

##### 窗口、紧急指针、选项与填充

**窗口字段**：占 2 字节，指出「发送本报文段的一方的**接收窗口**」大小，即本机接收缓存的可用空间，用来告诉对方「你最多还能给我发多少字节」。这是 TCP 流量控制的实现手段。

**紧急指针字段**：占 2 字节，以字节为单位指出本报文段数据载荷中紧急数据的长度。紧急数据位于数据载荷的最前面，其后是普通数据。

**选项字段**：最长 40 字节。常见选项有：

- **最大报文段长度 MSS 选项**：在连接建立时协商；
- **窗口扩大选项**：把窗口字段从 16 位扩展到更大（因为 65535 字节的窗口对高带宽时延积链路太小）；
- **时间戳选项**：用于更精确地计算 RTT；
- **选择确认 SACK 选项**：用于选择性重传。

**填充字段**：使首部长度能被 4 字节整除。

##### MSS 与 MTU 的关系

三个缩写必须分清：

| 缩写 | 全称 | 所在层 | 含义 |
|---|---|---|---|
| **MTU** | Maximum Transmission Unit，最大传送单元 | 数据链路层 | 一个帧的数据字段能装下的最大字节数 |
| **MSS** | Maximum Segment Size，最大报文段长度 | 传输层（TCP） | TCP 报文段**数据载荷部分**的最大长度，**不包括 TCP 首部** |
| **MSL** | Maximum Segment Lifetime，最长报文段寿命 | 传输层（TCP） | 一个 TCP 报文段在网络中最长的生存时间 |

$$ \text{MSS} = \text{MTU} - \text{IP 首部长度} - \text{TCP 首部长度} $$

以最常见的以太网为例：MTU = 1500 B，IP 首部 20 B，TCP 首部 20 B，则

$$ \text{MSS} = 1500 - 20 - 20 = 1460\ \text{B} $$

:::warn MSS 相关的四个坑
1. **MSS 只算数据载荷，不算首部**。题目说「MSS = 1000 B，发送 3000 B 的报文」，那就是 3 个报文段，数据分别为 1000、1000、1000。
2. **MSS 与窗口值无关**。窗口是「还能收多少字节」，MSS 是「一段最多装多少字节」。
3. **MSS 选项只在连接建立阶段协商**，不在每一个报文段里出现。
4. **MTU 是链路层的概念，MSS 是传输层的概念**，问「MSS 在哪一层确定」答传输层（TCP 选项），问「MTU 由谁决定」答数据链路层。
:::

##### TCP 发送报文段的时机

正常情况下，TCP 什么时候把数据封装成报文段发出去？规则有四条：

1. 发送缓存中存放的数据达到 **MSS 字节**时，就组装成一个 TCP 报文段发送出去；
2. 应用进程指明要求发送（即 TCP 支持的 **PUSH 推送操作**）；
3. 发送方的一个**计时器期限到了**，即使没达到 MSS 也把当前已有的数据发送出去；
4. 若接收窗口小于 MSS，则应等待接收窗口达到 MSS 的一半或者 MSS，两者任一时机成熟再发送。

**Nagle 算法**：对于一个 TCP 连接，第一个字节立即发送出去，然后继续缓存要发送的数据；只有收到上一个报文段的确认后，才发送已缓存的数据。这样每轮都要等上一个报文段的数据全部被确认，才发下一个报文段，可以有效地减少小报文段（避免「糊涂窗口综合征」）。

**Nagle 算法算例**：应用层连续产生 3 次「写」操作，每次 1 字节，准备发给对方（假设每次写之间的间隔很短）。

| 时刻 | 事件 | 发送方动作 |
|---|---|---|
| $t_0$ | 第 1 个字节到达发送缓存 | Nagle 算法规定第一个字节**立即发送**，不等待 |
| $t_1$ | 第 2 个字节到达发送缓存 | 第 1 个字节的确认**尚未到达**，于是**缓存**，不发送 |
| $t_2$ | 第 3 个字节到达发送缓存 | 仍然缓存，此时缓存里有 2 字节 |
| $t_3$ | 收到第 1 个字节的确认 | 把缓存中的 2 字节组装成一个报文段发送出去 |
| $t_4$ | 又收到确认 | 缓存为空，等待下一次数据 |

对比：若不用 Nagle 算法，则可能发出 3 个各含 1 字节数据的报文段，每个都要带 20 字节 TCP 首部 + 20 字节 IP 首部，**首部开销是数据的 40 倍**，效率极低。Nagle 算法把「小报文段问题」从发送侧抑制住了。

**两个边界情况**：

- 若应用层数据攒够了 MSS，则**立即发送**，不受 Nagle 算法限制；
- 若应用层设置了 TCP_NODELAY 选项（禁用 Nagle），或使用了 PSH 推送操作，也**立即发送**。

#### TCP 连接管理

TCP 连接管理 = **连接建立（三报文握手）** + **连接释放（四报文挥手）** + **状态转换**。这是全章最重要的一节，也是历年大题的主要素材。

##### 三报文握手建立连接

设客户（Client）A 主动打开，服务器（Server）B 被动打开（先处于 LISTEN 监听状态）。

**第 1 次握手（A → B）**：A 向 B 发送 **TCP 连接请求报文段**：

$$ \text{SYN}=1,\quad \text{ACK}=0,\quad \text{seq}=x $$

- 其中 $x$ 是 A 选择的**初始序号**；
- **SYN 报文段不能携带数据，但要消耗一个序号**；
- A 进入 **SYN-SENT（同步已发送）** 状态。

**第 2 次握手（B → A）**：B 若同意建立连接，则向 A 发送 **TCP 连接请求确认报文段**：

$$ \text{SYN}=1,\quad \text{ACK}=1,\quad \text{seq}=y,\quad \text{ack}=x+1 $$

- $y$ 是 B 独立选择的初始序号；
- `ack = x+1` 表示 B 已正确收到 A 的 SYN（它占了序号 $x$），期望 A 下一个报文段从 $x+1$ 开始；
- 同样，**这个报文段也不能携带数据，也要消耗一个序号**；
- B 进入 **SYN-RCVD（同步已接收）** 状态。

**第 3 次握手（A → B）**：A 收到 B 的确认后，还要再向 B 发送一个 **ACK 报文段**（普通确认，不带 SYN）：

$$ \text{ACK}=1,\quad \text{seq}=x+1,\quad \text{ack}=y+1 $$

- `ack = y+1` 表示 A 已正确收到 B 的 SYN（它占了序号 $y$）；
- A 进入 **ESTABLISHED（连接已建立）** 状态；
- B 收到这个 ACK 后也进入 **ESTABLISHED** 状态，连接正式建立。

:::key 三报文握手的三个报文段
| 次序 | 方向 | SYN | ACK | seq | ack |
|---|---|---|---|---|---|
| 1 | A→B | 1 | 0 | $x$ | 无意义 |
| 2 | B→A | 1 | 1 | $y$ | $x+1$ |
| 3 | A→B | 0 | 1 | $x+1$ | $y+1$ |

**第 1、2 次握手绝对不能携带数据；第 3 次握手可以携带数据**（若携带数据则按数据字节数消耗序号，且此时 seq 从 $x+1$ 开始；若不携带数据，则不消耗序号，下一个数据报文段的序号仍是 $x+1$）。
:::

##### 为什么是三次握手，而不是两次

这是必考的一道「原理题」，标准答案的核心是：**防止已失效的连接请求报文段突然又传到服务器，造成服务器资源浪费**。

设想只用两次握手的情形：

1. A 发出第 1 个连接请求，但在某个网络结点长时间滞留；
2. A 超时后重发连接请求，第 2 个请求顺利到达 B，两次握手完成，连接建立、传送数据、然后释放；
3. 之后，**那个滞留已久的第 1 个请求报文段**终于到达 B；
4. B 收到这个「已失效的连接请求」，误以为 A 又要建立连接，于是发出确认并直接进入连接状态，**为这个根本不存在的连接分配资源、等待数据**；
5. 而 A 并不知道这件事，不会给 B 发数据。B 的资源就被白白浪费（甚至长期占用）。

**三次握手可以杜绝这种情况**：B 在第 2 次握手时只是「同意」，并不立即认为连接建立；A 收到 $(\text{SYN}=1,\text{ACK}=1,\text{ack}=x+1)$ 后会发现——我并没有请求建立这个连接呀！于是 A **不发送第 3 次握手的确认**，B 收不到确认，就会超时释放这个半开的连接，资源不会被长期占用。

:::key 补充：三次握手的另一个作用
三次握手还使双方都能**确认对方的接收能力和发送能力都正常**，并**协商初始序号**（以及 MSS、窗口扩大因子等参数）。但从统考答题的角度看，**第一位的理由是「防止已失效的连接请求报文段造成资源浪费」**。
:::

##### 四报文挥手释放连接

TCP 连接是全双工的，因此**每个方向都必须单独释放**，这就是「四次挥手」的根本原因。设 A 主动关闭，B 被动关闭。

**第 1 次挥手（A → B）**：A 发送 **连接释放报文段**，并停止发送数据：

$$ \text{FIN}=1,\quad \text{seq}=u $$

- **FIN 报文段即使不携带数据，也要消耗一个序号**；
- A 进入 **FIN-WAIT-1（终止等待 1）** 状态。

**第 2 次挥手（B → A）**：B 收到后发出确认：

$$ \text{ACK}=1,\quad \text{seq}=v,\quad \text{ack}=u+1 $$

- B 进入 **CLOSE-WAIT（关闭等待）** 状态；
- A 收到此报文后进入 **FIN-WAIT-2（终止等待 2）** 状态。

**此时连接处于半关闭（half-close）状态**：A 已经没有数据要发送了，但 **B 仍然可以继续向 A 发送数据**，A 也必须继续接收。这个阶段可能持续很久（B 还有大量数据没发完）。

**第 3 次挥手（B → A）**：B 把剩余数据全部发送完毕后，发送 **连接释放报文段**：

$$ \text{FIN}=1,\quad \text{ACK}=1,\quad \text{seq}=w,\quad \text{ack}=u+1 $$

- 注意这里的 `ack` 仍然是 $u+1$（因为 A 的 FIN 之后没有新数据，B 不需要更新确认号；这就是所谓「对之前收到的连接释放报文段的**重复确认**」）；
- B 进入 **LAST-ACK（最后确认）** 状态。

**第 4 次挥手（A → B）**：A 收到 B 的 FIN 后发出确认：

$$ \text{ACK}=1,\quad \text{seq}=u+1,\quad \text{ack}=w+1 $$

- **这个报文段规定不能携带数据，也不消耗序号**；
- A 进入 **TIME-WAIT（时间等待）** 状态，必须等待 **2MSL** 后才能进入 **CLOSED** 状态；
- B 收到这个 ACK 后立即进入 **CLOSED** 状态。

:::key 四报文挥手汇总
| 次序 | 方向 | FIN | ACK | seq | ack | 发送方状态 |
|---|---|---|---|---|---|---|
| 1 | A→B | 1 | 1 | $u$ | $v$（无实际意义） | A 进 FIN-WAIT-1 |
| 2 | B→A | 0 | 1 | $v$ | $u+1$ | B 进 CLOSE-WAIT，A 进 FIN-WAIT-2 |
| 3 | B→A | 1 | 1 | $w$ | $u+1$ | B 进 LAST-ACK |
| 4 | A→B | 0 | 1 | $u+1$ | $w+1$ | A 进 TIME-WAIT，B 进 CLOSED |

**挥手第 1、3 次（FIN）固定消耗一个序号；挥手第 4 次的 ACK 不携带数据也不消耗序号。**
:::

##### 为什么是四次挥手

因为 TCP 连接是**全双工**的，两个方向的数据传输相互独立，因此「我发完了」与「你发完了」必须分别通知、分别确认：

- A 发 FIN 只表示「**A 没有数据要发给 B 了**」，不表示 B 也没有数据要发给 A；
- B 收到 FIN 后必须先回一个 ACK（第 2 次挥手），但 B 可能还有数据没发完，所以**不能立刻把自己的 FIN 也搭车发过去**；
- 必须等 B 的数据全部发完，B 才能发自己的 FIN（第 3 次挥手），A 再确认（第 4 次挥手）。

:::key 什么时候可以合并成三次？
如果 B 收到 A 的 FIN 时**恰好已经没有数据要发送了**，那么 B 可以把第 2 次和第 3 次挥手**合并**成一个报文段（FIN=1 且 ACK=1）发出。此时总共只有三个报文段，但**逻辑上仍然是四次挥手**。

这个「可以合并」的假设是许多时间计算题的前提。
:::

##### 为什么需要 TIME-WAIT 与 2MSL

**MSL（Maximum Segment Lifetime，最长报文段寿命）**：一个 TCP 报文段在网络中最长的生存时间。RFC 793 建议为 2 分钟，实际由操作系统决定，通常在几十秒到几分钟之间。

**TIME-WAIT 计时器设置为 2MSL**，原因有两个：

**原因一：确保 A 发送的最后一个 ACK（第 4 次挥手）能够到达 B。**

如果 A 发完最后一个 ACK 就立即关闭并进入 CLOSED，那么这个 ACK 万一丢失，B 就会一直停留在 LAST-ACK 状态并**超时重传 FIN+ACK**（第 3 次挥手）。此时 A 已经关闭，收不到也回不了这个报文，B 就永远无法正常释放连接。

正确做法是：A 进入 TIME-WAIT 并计时 2MSL。在这段时间内：

- 若 A 又收到了 B 重传的 FIN+ACK，就说明自己刚才发的 ACK 丢了，于是**重发 ACK 并重新开始 2MSL 计时**；
- 一个报文段从 A 到 B 最多用 1 MSL，B 重传的报文段从 B 回 A 也最多用 1 MSL，因此 2MSL 足以覆盖「ACK 丢失 + FIN 重传到达」的最坏情况。

**原因二：让本次连接中产生的所有报文段都从网络中消失。**

各 TCP 报文段到达主机的时间长短不一，A 在收到 B 的 FIN 后，可能还有本次连接中**较早发出的报文段**仍在网络中游荡。如果 A 立即关闭，然后又马上用相同的四元组建立新连接，这些旧报文段就可能被新连接误收，造成数据混乱。

经过 2MSL（一个报文段一来一回的最大时间），可以保证本次连接产生的**所有报文段都已从网络中消失**，这时再建立新连接就不会冲突。

:::warn TIME-WAIT 的三个易错点
1. **只有主动关闭方进入 TIME-WAIT**。被动关闭方（先收到 FIN 的一方）收到最后一个 ACK 后**立即**进入 CLOSED。
2. **TIME-WAIT 占用的是「端口」而非「连接」**：服务器重启时若报「Address already in use」，正是因为 TIME-WAIT 尚未结束。
3. **2MSL 中的 MSL 不是 RTT**。题目若给「RTT = 50 ms，MSL = 800 ms」，则 2MSL = 1600 ms，与 RTT 无关。
:::

##### 连接释放的最短时间（经典算例）

| 情形 | 主动关闭方从发出 FIN 到进入 CLOSED | 被动关闭方从收到 FIN 到进入 CLOSED |
|---|---|---|
| 最短（B 无数据要发，第 2、3 次挥手合并） | **1 RTT + 2 MSL** | **1.5 RTT** |
| 一般情形 | 大于 1 RTT + 2 MSL | 大于 1.5 RTT |

**为什么主动方是 1 RTT + 2MSL**：FIN 发出后经 0.5 RTT 到达 B，B 立即回 FIN+ACK，再经 0.5 RTT 到达 A，共 1 RTT；A 随后发最后一个 ACK 并进入 TIME-WAIT，等待 2 MSL。

**为什么被动方是 1.5 RTT**：B 收到 FIN 用 0.5 RTT，立刻发 FIN+ACK；这个确认 + FIN 经 0.5 RTT 到达 A，A 发最后一个 ACK；这个 ACK 再经 0.5 RTT 到达 B，B 才进入 CLOSED。合计 $0.5+0.5+0.5=1.5$ RTT。

:::exam 2022 年第 39 题（原文条件）
客户 C 和服务器 S 已建立 TCP 连接，RTT = 50 ms，MSL = 800 ms，C 主动请求断开连接。从 C 发出 FIN 的时刻算起，C 和 S 进入 CLOSED 状态所需的时间至少分别是多少？

**解**：单向传播时延 = RTT/2 = 25 ms。最短情形下 S 收到 C 的 FIN 后立即发出 ACK 和 FIN（合并为一次）。

- **C**：50 ms 时收到 S 的 FIN+ACK，发出最后一个 ACK 并进入 TIME-WAIT；等待 $2\text{MSL} = 1600$ ms 后关闭。总时间 $= 50 + 1600 = \mathbf{1650\ ms}$。
- **S**：25 ms 时收到 C 的 FIN 并发出 FIN+ACK；75 ms 时收到 C 的最后一个 ACK，随即进入 CLOSED。总时间 $= \mathbf{75\ ms}$。

答案：**1650 ms，75 ms**。
:::

##### TCP 的状态转换

TCP 连接在其生存期中会处于不同的**状态**。统考不要求背完整的 11 状态图，但下面这些状态必须能把「谁在哪个状态、接下来往哪走」对应上。

| 状态 | 含义 | 谁进入 |
|---|---|---|
| **CLOSED** | 关闭（虚拟的起始/终止状态） | 双方初始 |
| **LISTEN** | 监听，等待对方的连接请求 | 被动打开一方（服务器） |
| **SYN-SENT** | 已发送连接请求，等待对方确认 | 主动打开一方，发完第 1 次握手 |
| **SYN-RCVD** | 已收到连接请求并发出确认，等待对方确认 | 服务器，发完第 2 次握手 |
| **ESTABLISHED** | 连接已建立，可以传输数据 | 双方，握手完成 |
| **FIN-WAIT-1** | 已发送 FIN，等待对方确认 | 主动关闭方，发完第 1 次挥手 |
| **FIN-WAIT-2** | 已收到对方对自己 FIN 的确认，等待对方的 FIN | 主动关闭方，收到第 2 次挥手 |
| **CLOSE-WAIT** | 已收到对方的 FIN 并确认，等待本进程发完剩余数据 | 被动关闭方，发完第 2 次挥手 |
| **LAST-ACK** | 已发送自己的 FIN，等待对方确认 | 被动关闭方，发完第 3 次挥手 |
| **TIME-WAIT** | 已发送最后一个 ACK，等待 2MSL | 主动关闭方，发完第 4 次挥手 |
| **CLOSING** | 双方同时关闭时的罕见状态（不常考） | 罕用 |

**客户端（主动打开 + 主动关闭）的典型路径**：

```plain
CLOSED → SYN-SENT → ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED
```

**服务器（被动打开 + 被动关闭）的典型路径**：

```plain
CLOSED → LISTEN → SYN-RCVD → ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED
```

:::warn 状态题的两个陷阱
1. **LISTEN 是服务器在收请求之前的状态**，不是「握手第一步之后」的状态。收到 SYN 之后才进 SYN-RCVD。
2. **FIN-WAIT-2 是「我已经挥手了，等对方也挥手」**，此时连接处于半关闭；CLOSE-WAIT 才是「对方挥手了，我还没挥」。
:::

##### 连接建立与释放中的序号计算（完整例题）

**例题 1（握手序号，2019 年第 39 题原型）**

主机甲主动发起与主机乙的 TCP 连接，甲、乙选择的初始序号分别为 2018 和 2046。问第三次握手 TCP 段的确认序列号是多少？

- 第 1 次握手：甲 → 乙，`SYN=1, seq=2018`。SYN 消耗一个序号，所以甲的数据将从 2019 开始。
- 第 2 次握手：乙 → 甲，`SYN=1, ACK=1, seq=2046, ack=2018+1=2019`。
- 第 3 次握手：甲 → 乙，`ACK=1, seq=2019, ack=2046+1=2047`。

**答案：2047。**

**例题 2（握手序号，2011 年第 39 题原型）**

主机甲向主机乙发送一个 `(SYN=1, seq=11220)` 的 TCP 段请求建立连接。若乙接受，则乙回送的 TCP 段可能是什么？

- 第 2 次握手必须同时置 `SYN=1` 和 `ACK=1`；
- 乙必须确认甲的 SYN：`ack = 11220 + 1 = 11221`；
- 乙自己的初始序号可以独立选择，题目没有限制，取 11221 是可能的。

**答案：`(SYN=1, ACK=1, seq=11221, ack=11221)`。**

**例题 3（含数据传送与挥手，2020 年第 39 题原型）**

甲、乙建立 TCP 连接时，甲发送的 SYN 段序号为 1000；断开连接时，甲发送给乙的 FIN 段序号为 5001。求在无任何重传的情况下，甲向乙已发送的应用层数据字节数。

- SYN 占用序号 1000，因此**第一个应用数据字节的序号是 1001**；
- FIN 的序号 5001 表示「写完这些数据之后的下一个序号是 5001」，即数据占用到 5000；
- 数据字节数 $= 5001 - 1001 = \mathbf{4000}$ 字节。（FIN 本身虽消耗一个序号，但位于应用数据之后，不计入数据量。）

**答案：4000 B。**

**例题 4（含数据传送的序号，2013 年第 39 题原型）**

甲收到乙发来的一个 TCP 段，其 `seq=1913`、`ack=2046`、有效载荷 100 字节。求甲立即回送给乙的 TCP 段的序号与确认号。

- 乙的 `ack=2046` 表示乙期望甲下一次从序号 2046 开始发送，因此**甲回发段的 seq = 2046**；
- 乙本段数据从 1913 开始、长达 100 字节，占用序号 1913~2012，故甲下一步期望收到 2013，**甲的 ack = 2013**。

**答案：seq = 2046，ack = 2013。**

**例题 5（累积确认，2011 年第 40 题原型）**

甲向乙发送 3 个连续的 TCP 段，有效载荷分别为 300、400、500 字节，**第 3 个段的序号为 900**。若乙仅正确接收到第 1 和第 3 个段，乙发送给甲的确认序号是多少？

先倒推各段的起始序号：

| 段 | 载荷 | 起始序号 | 序号范围 |
|---|---|---|---|
| 第 1 段 | 300 B | $900-400-300=200$ | 200 ~ 499 |
| 第 2 段 | 400 B | $900-400=500$ | 500 ~ 899 |
| 第 3 段 | 500 B | 900 | 900 ~ 1399 |

乙正确收到第 1 段（200~499）和第 3 段（900~1399），但缺少第 2 段（500~899）。TCP 使用**累积确认**，只能确认到「连续正确收到的最高序号」，因此乙回送 `ack = 500`。

**答案：500。**

**例题 6（连续段与累积确认，2009 年第 38 题原型）**

甲向乙发送两个连续的 TCP 段，有效载荷分别为 300 字节和 500 字节，第一个段的序号为 200。乙正确接收两个段后，发送给甲的确认序列号是多少？

- 第 1 段：seq=200，占 200~499；
- 第 2 段：seq=500，占 500~999；
- 乙已连续正确收到 200~999，故 `ack = 1000`。

**答案：1000。**

:::key 序号计算题的通用步骤
1. **先判断报文段类型**：是 SYN、FIN，还是普通数据段？
2. **折算成序号区间**：SYN 和 FIN 各占 1 个序号，普通数据段占「字节数」个序号。
3. **先确定起始点，再推终点**：若题目给的是「第 $k$ 段的序号」，要先把前面几段的长度加起来倒推出各段起点。
4. **确认号一律取「连续正确收到的最高序号 + 1」**（累积确认）。
5. **检查是否跨过 $2^{32}-1$ 回绕**（大数值题要注意，普通题目不会涉及）。
:::

#### TCP 可靠传输

TCP 的可靠传输建立在**滑动窗口 + 确认重传**之上。它的机制可以看成是**后退 N 帧（GBN）与选择重传（SR）的结合**：正常情况下用累积确认（像 GBN），配合 SACK 选项时可以只重传丢失的部分（像 SR）。

##### 序号与确认机制

- TCP 是**面向字节流**的，所以序号以**字节**为单位连续编号，而不是以报文段为单位。
- 接收方收到按序到达的数据后，返回确认号 ack = 期望收到的下一个字节序号。
- 接收方可以**捎带确认**（piggybacking）：把确认信息搭载在自己要发送的数据报文段的 ack 字段中。若不发送数据，也可以立即单独发送确认。
- **累计确认（cumulative acknowledgment）**：ack $=N$ 表示「序号到 $N-1$ 为止的所有数据都已按序正确收到」。即使收到了 $N$ 之后的不连续数据，也不会把 ack 推到 $N$ 之后。

:::key 累积确认的后果
正是因为累积确认，「收到 3 个段但缺中间那个」时确认号仍停在缺失段的起点。这也解释了**快速重传**为什么能工作：接收方每收到一个失序段，就重复发一次相同的 ACK，发送方收到 3 个重复 ACK 就知道对应报文段丢了。
:::

##### 超时重传

**基本思想**：每发送一个报文段就为该报文段设置一个**超时计时器（重传计时器）**。若在计时器到期之前收到了确认，就撤销该计时器；否则认为该报文段丢失，重传它。

注意几个细节：

- 发送方发出报文段后**必须暂时保留其副本**（以备重传），收到确认后才能清除；
- 报文段和确认都要**编号**，才能知道收到的是对哪一段的确认；
- 若收到两个重复的报文段，说明对方一定发生了超时重传，此时应**丢弃较晚收到的那个重复报文段，并再回送一次确认**。

##### 超时重传时间 RTO 的选择

RTO 的选择是 TCP 中最复杂的问题之一。

**加权平均往返时间 $RTT_S$**：

$$ \text{新的 } RTT_S = (1-\alpha)\times \text{旧的 } RTT_S + \alpha \times \text{新的 RTT 样本},\qquad 0\le\alpha<1 $$

第一次测量到 RTT 样本时，直接取 $RTT_{S1}=RTT_1$。RFC 6298 推荐的 $\alpha = 1/8 = 0.125$。$\alpha$ 越接近 0，新样本影响越小；越接近 1，新样本影响越大。

**RTT 偏差的加权平均 $RTT_D$**：

$$ \text{新的 } RTT_D = (1-\beta)\times \text{旧的 } RTT_D + \beta\times\left|RTT_S - \text{新的 RTT 样本}\right|,\qquad 0\le\beta<1 $$

第一次测量时 $RTT_{D1} = RTT_1 \div 2$。RFC 6298 推荐的 $\beta = 1/4 = 0.25$。

**超时重传时间**：

$$ \boxed{\ RTO = RTT_S + 4\times RTT_D\ } $$

:::key 计算顺序（RFC 6298 规定）
得到一个新的 RTT 样本时，**先用「旧的 $RTT_S$」计算新的 $RTT_D$，再计算新的 $RTT_S$**。顺序写反结果会不同。
:::

**算例**：设第 1 次测得 RTT 样本 $=2$ 个单位。

- $RTT_{S1} = 2$；
- $RTT_{D1} = 2 \div 2 = 1$；
- $RTO_1 = RTT_{S1} + 4\times RTT_{D1} = 2 + 4 = 6$。

若第 2 次测得 RTT 样本 $=4$：

- 先用旧的 $RTT_{S1}=2$ 算 $RTT_D$：$RTT_{D2} = (1-\tfrac14)\times 1 + \tfrac14\times|2-4| = 0.75 + 0.5 = 1.25$；
- 再算 $RTT_{S2} = (1-\tfrac18)\times 2 + \tfrac18\times 4 = 1.75 + 0.5 = 2.25$；
- $RTO_2 = 2.25 + 4\times 1.25 = 2.25 + 5 = 7.25$。

**完整演算题（含一次超时样本，必须跳过）**

设从第 1 次开始依次测得 RTT 样本为 $RTT_1=2$、$RTT_2=4$、$RTT_3=1.75$，第 4 次测量时**发生了超时重传**，第 5 次测得 $RTT_5=3$。取 $\alpha=1/8$、$\beta=1/4$。求每次测量后算出的 RTO。

| 测量次序 | RTT 样本 | 是否采用 | 计算 $RTT_D$ | 计算 $RTT_S$ | RTO |
|---|---|---|---|---|---|
| 第 1 次 | 2 | ✔ | $RTT_{D1} = 2/2 = 1$ | $RTT_{S1}=2$ | $2+4\times1=\mathbf{6}$ |
| 第 2 次 | 4 | ✔ | $0.75\times1+0.25\times\lvert 2-4\rvert = 1.25$ | $0.875\times2+0.125\times4=2.25$ | $2.25+4\times1.25=\mathbf{7.25}$ |
| 第 3 次 | 1.75 | ✔ | $0.75\times1.25+0.25\times\lvert 2.25-1.75\rvert = 1.0625$ | $0.875\times2.25+0.125\times1.75=2.1875$ | $2.1875+4.25=\mathbf{6.4375}$ |
| 第 4 次 | — | ✘（超时重传） | 不计算 | 不计算 | **加倍**为 $6.4375\times2=\mathbf{12.875}$ |
| 第 5 次 | 3 | ✔ | 沿用旧的 $RTT_S=2.1875$：$0.75\times1.0625+0.25\times\lvert 2.1875-3\rvert=1.0$ | $0.875\times2.1875+0.125\times3=2.2890625$ | $2.2890625+4\times1.0=\mathbf{6.2890625}$ |

:::key 这类题的三条执行纪律
1. **先判断样本是否可用**：只要该次报文段发生了重传，这个 RTT 样本就作废，**既不算 $RTT_D$ 也不算 $RTT_S$**（Karn 算法）。
2. **算 $RTT_D$ 时用「旧的 $RTT_S$」**，算完 $RTT_D$ 再更新 $RTT_S$（RFC 6298 规定的顺序）。
3. **超时那一次不是「什么也不做」**，而是把 RTO **加倍**（指数退避），否则后续会反复超时。
:::

:::warn 「Karn 算法」在两种语境下的含义要分清（统考经常混着考）
- **严格意义的 Karn 算法**（RFC 6298 之前的经典表述）：**只要报文段被重传了，就不采用其 RTT 样本**去更新 $RTT_S$。
- **加上指数退避的修正版**（RFC 6298 实际采用）：发生超时重传时，**先把 RTO 加倍**（$RTO \leftarrow 2\times RTO$），后续若仍超时则继续加倍，直到收到确认。

因此做题时看到「发生超时重传」这句话，要同时做两件事：**① 该次的 RTT 样本作废；② 当前的 RTO 值加倍**。看到「根据 Karn 算法不考虑重传报文段的 RTT 样本」这句话，则只需做第 ① 件。
:::

##### Karn 算法

**RTT 测量本身有歧义**：当报文段发生重传时，发送方收到一个确认，无法判断这个确认是**对原报文段**的还是**对重传报文段**的。

- 若误判为对**原报文段**的确认，算出的 $RTT_S$ 和 RTO 会**偏大**，降低传输效率；
- 若误判为对**重传报文段**的确认，算出的 $RTT_S$ 和 RTO 会**偏小**，导致后续不必要的大量重传，加重网络负担。

**Karn 算法的基本思想**：

$$ \text{凡是报文段被重传了，就不采用其 RTT 样本去计算 } RTT_S \text{ 和 } RTO $$

**Karn 算法的缺陷与修正**：若报文段的时延突然大幅增大并长期保持，按 Karn 算法不使用重传段的样本，RTO 就无法更新，会导致报文段被反复重传。

**修正方法**：报文段每发生一次重传，就把 **RTO 加倍**（即取新 RTO 为旧 RTO 的 2 倍，指数退避）。典型说法是「每重传一次，RTO 增大为原来的 2 倍」。

:::exam 出题角度
Karn 算法在选择题中通常考「基本思想」：**重传的报文段不用于计算 RTT 样本**；以及「重传时 RTO 加倍」。这两个结论记住即可，不需要推导。
:::

##### 快速重传

**前提：接收方要立即发送确认，不要等自己有数据要发时才捎带确认。**

**规则**：发送方一旦收到 **3 个连续的重复确认（冗余 ACK）**，就立即重传对应的报文段，**不等重传计时器超时**。

为什么是 3 个？收到 3 个重复确认意味着有 3 个报文段已经离开了网络并停留在接收方缓存中，说明**只是个别报文段丢失，网络并没有严重拥塞**，因此可以大胆重传。

**算例**：发送方发送 $M_1,M_2,M_3,M_4,M_5$，其中 $M_2$ 丢失。

| 事件 | 发送方动作 | 接收方动作 |
|---|---|---|
| 发送 $M_1$~$M_5$ | 正常发送 | — |
| $M_1$ 到达 | — | 按序，回 `ack=M2 起点` |
| $M_3$ 到达 | — | 失序，回 `ack=M2 起点`（**第 1 个重复确认**） |
| $M_4$ 到达 | — | 失序，回 `ack=M2 起点`（**第 2 个重复确认**） |
| $M_5$ 到达 | — | 失序，回 `ack=M2 起点`（**第 3 个重复确认**） |
| 收到第 3 个重复确认 | **立即重传 $M_2$** | — |
| $M_2$ 到达 | — | 此时 $M_1$~$M_5$ 全部按序到达，回 `ack=M6 起点` |

:::key 重复确认的个数
「收到 3 个重复确认」= 加上**原本的那一个**确认，发送方共收到 **4 个对同一报文段的确认**。题目若说「一连收到 3 个对同一个报文段的重复确认」，指的是**冗余的那 3 个**。这个 3 的计数是高频陷阱。
:::

**快速重传的收益**：对于个别丢失的报文段，发送方不会出现超时重传，也就不会误认为网络拥塞而把 cwnd 减到 1。实践证明，使用快速重传可以使整个网络的吞吐量提高约 20%。

##### 选择确认 SACK

**问题**：TCP 接收方只能对**按序收到的数据中的最高序号**给出确认。当发送方超时重传时，接收方之前已经收到、只是未按序到达的数据**也会被重传**，浪费带宽。

**解决**：TCP 可以使用**选择确认（Selective Acknowledgment，SACK）**，RFC 2018 建议标准。

接收方把「已收到但与前面字节流不连续的字节块」的边界信息通过 SACK 选项告诉发送方，发送方就只重传真正缺失的部分，不再重传已经正确到达的数据。

SACK 选项的格式约束：

- 「允许 SACK」选项占 1 字节，SACK 选项长度占 1 字节；
- 指明一个字节块的边界需要 4 字节（因为序号是 4 字节），一个字节块需要两个边界，即 8 字节；
- 因此一个 SACK 选项**最多能指明 4 个字节块**。

:::warn SACK 的两个限定
1. **SACK 只是「通知」，不是「协议规定发送方必须怎么做」**。SACK 相关文档并没有规定发送方应如何响应，因此**大多数 TCP 实现仍然重传所有未被确认的数据块**。
2. SACK 仍然保留了原有的确认号字段，即**累积确认仍然有效**，SACK 只是补充信息。
:::

##### 发送窗口与可连续发送的字节范围

TCP 发送方在没有收到确认的情况下，可以**把序号落在发送窗口内的数据依次全部发送出去**。

- 发送窗口的**左沿**：收到新的确认后才向右移动；没收到确认则不动。
- 发送窗口的**右沿**：通常因为收到新的确认而不断右移；也可能因为对方接收窗口变小而**不动**。
- **TCP 标准不赞成把窗口右沿向左收缩**（即不允许把已经承诺可以发送的序号重新收回），因为窗口里的数据可能已经发出去了，收缩会引发错误。

**发送窗口内的序号集是发送缓存序号集的子集**；**接收窗口的序号集是接收缓存序号集的子集**。

##### 重传次数的计算

**规则**：TCP 每重传一次，RTO **加倍**（指数退避）。所以从第 1 次超时开始，第 $n$ 次重传后的累计等待时间为

$$ T_n = RTO\times(1 + 2 + 4 + \cdots + 2^{n-1}) = RTO\times(2^n - 1) $$

**算例**：设初始 RTO = 1 s，问「从第一次超时算起，经过多少时间发送方将进行第 4 次重传」。

| 次序 | 等待时间 | 累计等待时间 |
|---|---|---|
| 第 1 次重传 | 1 s | 1 s |
| 第 2 次重传 | 2 s | 3 s |
| 第 3 次重传 | 4 s | 7 s |
| 第 4 次重传 | 8 s | **15 s** |

即 $1\times(2^4-1)=15$ s。

:::warn 重传次数题的两个坑
1. **RTO 是每次加倍，不是每次加固定值**。若题目只说「RTO=1s，超时后进行第 3 次重传」，答案是 $1+2+4=7$ s。
2. **要分清「报文段数」和「字节数」**。例如「发送窗口 5000 B，MSS = 1000 B，其中第 2 段丢失」，则窗口内最多能装 5 个报文段，快速重传后发送方需重传 1 个（在无 SACK 且假定后续段都已到达的情况下），总发送报文段数 = 原发的 5 个 + 重传的 1 个。计算时要**先列出每段占用的序号区间**，再逐段判断是否重传。
:::

#### TCP 流量控制

##### 流量控制的含义

**流量控制（flow control）** 的目的：让发送方发送数据的速率不要太快，使接收方来得及接收。

- 它是**点对点、端到端**的问题（接收端控制发送端），与**拥塞控制**（全局性问题，涉及所有主机和路由器）不同；
- TCP 不是靠「速率」，而是靠**滑动窗口**来实现：接收方在返回的确认报文段中，用**窗口字段**告诉发送方「我还能收多少字节」。

:::key 流量控制与拥塞控制的区别（必背）
- **流量控制**：抑制发送端速率，使**接收端**来得及接收。**点对点、端到端**问题，由接收窗口 rwnd 实现。
- **拥塞控制**：防止过多数据注入网络，使**网络中的路由器和链路**不过载。**全局性**问题，涉及所有主机、所有路由器，由拥塞窗口 cwnd 实现。
:::

##### 发送窗口的确定

$$ \boxed{\ \text{发送窗口 } swnd = \min(rwnd,\ cwnd)\ } $$

- $rwnd$（receiver window）：接收方通过 TCP 首部窗口字段通告的接收窗口大小，取决于接收缓存的可用空间；
- $cwnd$（congestion window）：发送方维护的拥塞窗口，取决于网络的拥塞程度。

**若题目不考虑拥塞控制**（如 2010 年第 39 题「题目未给出拥塞窗口」），则取 $swnd = rwnd$。

##### 发送缓存与接收缓存

**发送缓存**里存放：

1. 发送方应用程序交给 TCP 准备发送的数据；
2. TCP 已发送出去但尚未收到确认的数据。

**接收缓存**里存放：

1. 按序到达但尚未被应用进程取走的数据；
2. 未按序到达的数据。

注意：**发送窗口 ⊆ 发送缓存**，**接收窗口 ⊆ 接收缓存**。当接收方通告 `rwnd = 0` 时，发送方必须停止发送普通数据。

##### 窗口滑动与序号计算的完整算例

设 A、B 已建立 TCP 连接。B 通告接收窗口 `rwnd = 400` 字节，A 的发送窗口也设为 400 字节。A 已有从序号 1 开始的大批数据要发送。

**初始状态**：

| 项目 | 值 |
|---|---|
| 发送窗口 | seq 1 ~ 400 |
| 已发送未确认 | （空） |
| 可发送未发送 | 1 ~ 400 |

**步骤 1**：A 连续发送 4 个 100 字节的报文段（把窗口用完）。

| 报文段 | 序号 | 状态 |
|---|---|---|
| ① | 1 ~ 100 | 已发送，未确认 |
| ② | 101 ~ 200 | 已发送，未确认 |
| ③ | 201 ~ 300 | **在传输中丢失** |
| ④ | 301 ~ 400 | 已发送，失序到达 |

此时发送窗口仍为 1~400，但**窗口内已无可发送的字节**。

**步骤 2**：B 收到①②，接着收到失序的④（301~400）。B 先按序确认 `ack = 201`；再对失序的④**立即回送一个重复确认**，仍然是 `ack = 201`，并通告 `rwnd = 300`。

- `ack = 201` 表示 A 可以把发送窗口左沿推进到 201；
- `rwnd = 300` 表示 B 还能收 300 字节，所以窗口右沿为 $201 + 300 - 1 = 500$；
- 新发送窗口为 **seq 201 ~ 500**。

| 项目 | 值 |
|---|---|
| 发送窗口 | 201 ~ 500 |
| 已发送未确认 | 201 ~ 400（③丢失，④失序到达） |
| 可发送未发送 | 401 ~ 500（共 100 字节） |

**步骤 3**：A 在新窗口内发送序号 401~500 的报文段（100 字节）。

**步骤 4**：B 收到 401~500。因为 201~300 这一段仍然缺失，401~500 仍是**失序到达**，B **立即再回送一次重复确认** `ack = 201`。

此时 A 累计收到了对 201 的确认：

| 收到的确认 | 性质 | 累计重复确认数 |
|---|---|---|
| `ack = 201` | ①②按序到达后的**正常确认** | 0 |
| `ack = 201` | 对失序段④（301~400）的重复确认 | **1** |
| `ack = 201` | 对失序段（401~500）的重复确认 | **2** |

**重复确认只有 2 个，尚未达到快速重传的触发条件（需要 3 个）**，所以 A 只能等超时。

**步骤 5**：A 的③号报文段重传定时器超时，重传 201~300。B 收到后凑齐了 201~500，返回 `ack = 501`。

- A 收到 `ack = 501` 后，窗口左沿推进到 501；
- 若此时 B 通告 `rwnd = 0`，则窗口右沿变为 500，**即窗口收缩为零**。

**步骤 6（零窗口）**：A 不能再发送普通数据，但必须启动**持续计时器**。计时器超时后，A 发送一个**零窗口探测报文段**（仅携带 1 字节数据），B 收到后回送确认并通告现在的接收窗口值：

- 若仍为 0，A 重新启动持续计时器，重复探测；
- 若变为 300，则 A 的发送窗口变为 501 ~ 800，可以继续发送，死锁局面被打破。

**变体**：若 A 把发送窗口做得更大（例如序号 1~800），则在③丢失后，失序到达的每一段都会让 B 再回送一个重复确认，**凑满 3 个重复确认就会触发快速重传**，A 立刻重传 201~300，**不必等超时**。这也说明：**重复确认是靠失序报文段一个攒出来的，窗口越大越容易触发快速重传。**

:::key 窗口计算的三步法
1. **窗口左沿** = 收到的最新确认号 ack；
2. **窗口大小** = 通告的 rwnd（若不考虑拥塞控制）；若考虑拥塞控制则取 $\min(rwnd,cwnd)$；
3. **窗口右沿** = 左沿 + 窗口大小 − 1；
4. **还能发送的字节数** = 窗口右沿 − 已发送未确认数据的最大序号。

**要点：已发送但未收到确认的数据仍然占用发送窗口。**
:::

:::exam 这个算例告诉你两件事
1. **窗口是随每个通告值动态调整的**：同一个发送方，窗口先是 1~400，然后是 201~500，最后是 501~800。每次调整都要用「新 ack 作左沿、新 rwnd 定大小」重新算，不能沿用旧窗口。
2. **「已发送未确认」的数据始终占着窗口**：步骤 2 中虽然窗口左沿推到了 201、窗口大小变成 300，但 201~400 这一段仍然被占用，所以新窗口里能发的只有 401~500 这 100 字节。这一步算错，整题的答案就全错。
:::

##### 零窗口与持续计时器

**死锁问题**：接收方 B 的接收缓存满了，于是通告 `rwnd=0`。A 收到后停止发送，等待 B 的**非零窗口通知**。但如果：

- B 的缓存腾出空间后发出的**非零窗口通知丢失**；
- 则 A 一直等 B 的通知，B 一直等 A 发数据——**双方永远互相等待，形成死锁**，吞吐量降到 0。

**解决办法：持续计时器（persistence timer）**。

- 只要 TCP 连接的一方**收到对方的零窗口通知，就启动持续计时器**；
- 持续计时器超时后，发送一个**零窗口探测报文段**（只携带 1 字节数据）；
- 对方在确认这个探测报文段时，给出自己**当前的接收窗口值**；
- 若接收窗口仍为 0，收到确认的一方**重新启动持续计时器**；
- 若接收窗口不为 0，死锁局面就被打破。

**两个容易困惑的问题**：

1. **接收窗口为 0 时，B 还能接收报文段吗？** 能。TCP 规定：**即使接收窗口值为 0，也必须接受零窗口探测报文段、确认报文段以及携带有紧急数据的报文段。**
2. **零窗口探测报文段丢了怎么办？** 它也有重传计时器，超时后会被重传，所以死锁仍能被打破。

:::exam 出题角度
「零窗口探测报文段携带多少数据」——**1 字节**；「由谁发起」——**收到零窗口通知的一方**；「持续计时器的作用」——**打破零窗口造成的互相等待死锁**。
:::

##### 流量控制与拥塞控制的结合算例

**2010 年第 39 题原型**：甲、乙已建立 TCP 连接，MSS = 1000 B。甲当前拥塞窗口为 4000 B，甲向乙连续发送两个最大段后，收到乙发送的第一个段的确认段，确认段中通告的接收窗口大小为 2000 B。问此时甲还可以向乙发送的最大字节数是多少？

**解**：

- 发送窗口 $= \min(cwnd,\ rwnd) = \min(4000,\ 2000) = 2000$ B；
- 甲已发送 2 个段（共 2000 B），其中只有第 1 个段被确认，**第 2 个段（1000 B）仍未被确认，仍占用发送窗口**；
- 因此还能发送的最大字节数 $= 2000 - 1000 = \mathbf{1000}$ B。

**答案：1000 B。**

**2016 年第 41 题原型（窗口与拥塞控制结合）**：H3 与 S 建立 TCP 连接，S 分配 20 KB 接收缓存，MSS = 1 KB，RTT = 200 ms，H3 初始序号 100，拥塞窗口初始阈值 32 KB，S 端接收缓存**只存不取**。问：

**(1) 第二次握手段的 SYN、ACK 值与确认序号？**

`SYN = 1，ACK = 1，ack = 100 + 1 = 101`。

**(2) H3 收到的第 8 个确认段通告的接收窗口是多少？此时拥塞窗口和发送窗口各是多少？**

| 项目 | 计算 |
|---|---|
| S 已收到数据 | $8\times1\ \text{KB} = 8$ KB |
| 剩余接收缓存（rwnd） | $20 - 8 = \mathbf{12}$ KB |
| cwnd（慢开始，每确认 1 段 +1 MSS） | $1 + 8 = \mathbf{9}$ KB |
| 发送窗口 | $\min(12,\ 9) = \mathbf{9}$ KB |

**(3) 发送窗口等于 0 时，下一个待发送的数据段序号是多少？**

H3 的第一个数据字节序号为 $100 + 1 = 101$。接收缓存装满 20 KB，即 $20\times1024 = 20480$ 字节。数据占用序号 101 ~ $101+20480-1 = 20580$。因此**下一个待发送数据段的序号为 20581**。

**(4) 从 t 时刻 H3 请求断开连接起，S 释放该连接的最短时间是多少？**

S 是被动关闭方，最短为 **1.5 RTT** $= 1.5\times200 = \mathbf{300}$ ms。

:::warn 这类题的通用陷阱
1. **不要忘记「已发送未确认」的数据仍占窗口**。这是 2010 年题的关键。
2. **接收缓存「只存不取」时，rwnd 单调减少**，要用「总缓存 − 已收数据」计算，不能直接用初始值。
3. **cwnd 每次增加的是「1 MSS」而不是「1 KB」**，在 MSS 不等于 1 KB 时要换算。
4. **时间问的是「谁」释放连接**：主动方看 $1\text{RTT} + 2\text{MSL}$，被动方看 $1.5\text{RTT}$。
:::

#### TCP 拥塞控制

##### 拥塞控制的基本概念

**拥塞（congestion）**：网络中注入的分组过多，超出了网络资源（链路带宽、路由器处理能力、缓存）所能处理的能力，导致路由器队列堆积、分组丢失、吞吐量反而下降。

**拥塞控制**：防止过多的数据注入网络，使网络中的路由器和链路不致过载。这是一个**全局性**的过程，涉及所有主机、所有路由器和与降低网络传输性能有关的所有因素。

**讨论前提**（这三条是教材约定的简化条件，题目通常默认成立）：

1. 数据**单方向传送**，另一个方向只传送确认；
2. 接收方**总是有足够大的接收缓存**，因此发送窗口仅由网络拥塞程度决定，不考虑流量控制；
3. 以 **MSS 的个数**作为讨论单位（而不是字节）。

**拥塞窗口 cwnd**：由发送方维护，其值取决于网络的拥塞程度，**动态变化**。四种拥塞控制算法本质上都是在控制 cwnd 的增长与下降。

**判断网络出现拥塞的依据**：没有按时收到应当到达的 TCP 确认报文段，而产生了**超时重传**。

$$ swnd = \min(cwnd,\ rwnd) $$

- 不考虑拥塞控制时：$swnd = rwnd$；
- 不考虑流量控制时：$swnd = cwnd$。

**慢开始门限 ssthresh** 的使用规则：

- 当 $cwnd < ssthresh$ 时，使用**慢开始**算法；
- 当 $cwnd > ssthresh$ 时，停止慢开始，改用**拥塞避免**算法；
- 当 $cwnd = ssthresh$ 时，**既可使用慢开始，也可使用拥塞避免**（统考通常按「可以使用慢开始」处理，即在 $cwnd=ssthresh$ 时仍翻倍到 $2\times ssthresh$，或按题目约定）。

:::warn $cwnd = ssthresh$ 时的分歧
不同教材/实现对这个边界处理不同：

- **RFC 5681 推荐**：$cwnd < ssthresh$ 用慢开始，$cwnd \ge ssthresh$ 用拥塞避免（即等于门限时用拥塞避免，每 RTT 只 +1 MSS）；
- 有的教材写「$cwnd = ssthresh$ 时两种算法都可以」。

**统考真题通常取「翻倍到 2×ssthresh 之后再转拥塞避免」这一种**（例如 2009 年题 39，$ssthresh=8$，$cwnd$ 经 1→2→4→8→**9**，即第 4 个 RTT 只 +1）。做题时**优先看题目是否给了阶段提示**；若没有，按以下稳妥流程：只要 $cwnd$ 已经达到 $ssthresh$，**下一轮就 +1**。本章所有演算均按此约定。
:::

##### 慢开始与拥塞避免

**慢开始（slow start）算法**：

- 初始时 $cwnd = 1$ MSS；
- **每收到一个对新报文段的确认，就把 cwnd 增加 1 MSS**；
- 于是每经过一个传输轮次（即 1 个 RTT），cwnd 就**翻倍**（指数增长）。

「慢开始」的「慢」并不是指 cwnd 增长速率慢，而是指**刚开始时 cwnd 设为 1**，比一上来就向网络注入大量报文段「慢」得多。

**拥塞避免（congestion avoidance）算法**：

- **每收到一个对新报文段的确认，就把 cwnd 增加 1/cwnd 个 MSS**；
- 于是每经过一个传输轮次（1 个 RTT），cwnd **增加 1 个 MSS**（线性增长，称为「加法增大」）。

:::key 两种阶段的对比（必背）
| 阶段 | 每收到 1 个新确认，cwnd 增加 | 每经过 1 个 RTT，cwnd 增加 |
|---|---|---|
| 慢开始 | 1 MSS | 翻倍（$\times 2$） |
| 拥塞避免 | $1/cwnd$ 个 MSS | $+1$ MSS |
:::

##### 快重传与快恢复

**快重传（fast retransmit）**：

- 前提：接收方**不要等自己发送数据时才捎带确认，而要立即发送确认**，即使收到失序报文段也要立即发出对已收到报文段的**重复确认**；
- 规则：发送方一旦收到 **3 个连续的重复确认**，就**立即重传**对应的报文段，不等重传计时器超时。

**快恢复（fast recovery）**：

- 发送方一旦收到 3 个重复确认，就知道只是丢失了**个别**报文段，而**不是网络拥塞**，于是**不启动慢开始**，而是执行快恢复；
- 规则：把 $ssthresh$ 和 $cwnd$ **都调整为当前 cwnd 值的一半**，然后**直接开始执行拥塞避免算法**。

**另一种实现**：把 $cwnd$ 再增大一些，即 $cwnd = \text{新 }ssthresh + 3$。理由：既然收到了 3 个重复确认，就说明有 3 个数据报文段已经离开了网络、停留在接收方缓存中，网络中少了 3 个报文段，可以适当把 cwnd 增大一些。（本章演算统一采用第一种：$cwnd = ssthresh = \text{原 }cwnd/2$。）

:::key 两种拥塞事件的不同处理（核心对比表，必背）
| 情况 | 触发条件 | ssthresh 更新 | cwnd 更新 | 后续阶段 |
|---|---|---|---|---|
| **超时重传** | 重传计时器超时，未收到确认 | $ssthresh = \text{当前 }cwnd \div 2$ | $cwnd = 1$ MSS | **先慢开始，到达门限后转拥塞避免** |
| **三个重复确认（快重传）** | 收到 3 个重复 ACK | $ssthresh = \text{当前 }cwnd \div 2$ | $cwnd = \text{新 }ssthresh$ | **直接进入拥塞避免，不经过慢开始** |
:::

:::warn 超时与三重确认的最大区别
- **超时**：$cwnd$ 直接**降到 1**（回到慢开始，重新指数增长）；
- **三重确认**：$cwnd$ **只降到一半**（直接进拥塞避免，线性增长）。

两者的 $ssthresh$ 更新规则相同，都是「当前 cwnd 的一半」。**判断分支用哪一个，就看去重传的原因**。
:::

##### cwnd 逐轮次演算表（含两种情况）

**场景设定**（为了表格干净，约定初始 $cwnd=1$ MSS，初始 $ssthresh = 16$ MSS，MSS = 1 KB）：

- RTT1~RTT6：正常，无丢失；
- **RTT7 结束时刻发生超时重传**（对应 cwnd 为 32 时超时，$ssthresh$ 更新为 16）；
- RTT8~RTT15：恢复正常；
- **RTT16 结束时刻收到 3 个重复确认**（快重传 + 快恢复）。

**逐轮次演算表**：

| 轮次 | 轮次开始时的 cwnd（MSS） | 阶段 | 本事件 | ssthresh（MSS） | 轮次结束时的 cwnd（MSS） |
|---|---|---|---|---|---|
| RTT1 | 1 | 慢开始 | — | 16 | 2 |
| RTT2 | 2 | 慢开始 | — | 16 | 4 |
| RTT3 | 4 | 慢开始 | — | 16 | 8 |
| RTT4 | 8 | 慢开始 | — | 16 | 16 |
| RTT5 | 16 | 拥塞避免 | — | 16 | 17 |
| RTT6 | 17 | 拥塞避免 | — | 16 | 18 |
| RTT7 | 18 | 拥塞避免 | （按设定此处超时，cwnd = 18） | $18/2 = 9$ | **1** |
| RTT8 | 1 | 慢开始 | 超时后重启 | 9 | 2 |
| RTT9 | 2 | 慢开始 | — | 9 | 4 |
| RTT10 | 4 | 慢开始 | — | 9 | 8 |
| RTT11 | 8 | 慢开始 | — | 9 | **16** |
| RTT12 | 16 | 拥塞避免 | — | 9 | 17 |
| RTT13 | 17 | 拥塞避免 | — | 9 | 18 |
| RTT14 | 18 | 拥塞避免 | — | 9 | 19 |
| RTT15 | 19 | 拥塞避免 | — | 9 | 20 |
| RTT16 | 20 | 拥塞避免 | **收到 3 个重复确认** | $20/2 = 10$ | **10** |
| RTT17 | 10 | 拥塞避免 | 快恢复后直接进拥塞避免 | 10 | 11 |
| RTT18 | 11 | 拥塞避免 | — | 10 | 12 |
| RTT19 | 12 | 拥塞避免 | — | 10 | 13 |
| RTT20 | 13 | 拥塞避免 | — | 10 | 14 |

表格的几个关键点：

1. **RTT4 结束时 cwnd = 16 = ssthresh**，进入「等于门限」的边界；
2. **RTT5 开始时 cwnd = 16，按「已达门限就 +1」的约定只增加到 17**（若按翻倍约定则为 32）——做题时务必先看题目的阶段提示；
3. **RTT7 超时**：$ssthresh = 18/2 = 9$，$cwnd$ 立即降为 1，是**瞬时完成的状态变更**，不占一个 RTT；
4. **RTT8~RTT10 慢开始**使 cwnd 依次为 2、4、8；RTT11 开始时 cwnd = 8 < ssthresh = 9，仍属慢开始，结束时翻倍到 16；
5. RTT12 开始 cwnd = 16 > ssthresh = 9，转入拥塞避免，每轮 +1；
6. **RTT16 收到 3 个重复确认**：$ssthresh = 20/2 = 10$，$cwnd = 10$，**直接进拥塞避免**（RTT17 只 +1 到 11，而不是降到 1）。

:::key 从表里读出三条规律
1. **慢开始阶段**：每一轮的 cwnd 是上一轮的 2 倍；
2. **拥塞避免阶段**：每一轮的 cwnd 是上一轮 +1；
3. **每遇到一次拥塞事件（超时或三重确认），ssthresh 就变成当时 cwnd 的一半**，然后：
   - 超时 → cwnd 从 1 重新开始；
   - 三重确认 → cwnd 从新 ssthresh 开始。
:::

##### cwnd 随传输轮次变化的曲线描述

把上面的表格画成「横轴为传输轮次、纵轴为 cwnd」的曲线，形状可以这样描述：

1. **第 1 段（RTT1~RTT4）**：从 $(1,1)$ 出发，**陡峭地指数上升**，依次经过 $(2,2)$、$(3,4)$、$(4,8)$、$(5,16)$。曲线呈上凸的指数形状；这一段叫**慢开始**。
2. **第 2 段（RTT5~RTT7）**：从 cwnd = 16 开始，**变成平缓的线性上升**，依次 $(5,16)$、$(6,17)$、$(7,18)$。斜率很小（每轮 +1）；这一段叫**拥塞避免**。
3. **超时点（RTT7 结束）**：曲线**垂直断崖式下跌**到 cwnd = 1。注意 $ssthresh$ 同时被更新为原 cwnd 的一半（9），画图时要把门限线也画下来。
4. **第 3 段（RTT8~RTT11）**：从 1 又开始**指数上升**（1→2→4→8→16）。注意因为 $ssthresh$ 已经变小（9），这段指数上升比第 1 段更早被门限截住。
5. **第 4 段（RTT12~RTT16）**：越过门限后**转为线性上升**（16→17→18→19→20）。
6. **三重确认点（RTT16 结束）**：曲线**只下降到新门限的一半位置**（从 20 降到 10），而不是掉到 1。这是与超时最直观的图形差别。
7. **第 5 段（RTT17 起）**：从 10 开始**线性上升**（10→11→12→13→14），**没有指数段**。

:::key 曲线三个视觉特征
- 慢开始段是**上凸的指数曲线**（翻倍）；
- 拥塞避免段是**斜率极小的直线**（+1）；
- **超时是「掉到 1」的深谷，三重确认是「掉到一半」的浅谷**。
:::

##### 经典计算题完整解析

**题目一（2009 年第 39 题原型）**：一个 TCP 连接总是以 1 KB 的最大段长发送 TCP 段，发送方有足够多的数据要发送。当拥塞窗口为 16 KB 时发生了超时，如果接下来的 4 个 RTT 时间内 TCP 段的传输都是成功的，那么当第 4 个 RTT 时间内发送的所有 TCP 段都得到肯定应答时，拥塞窗口大小是多少？

**解**：超时处理：$ssthresh = 16/2 = 8$ KB，$cwnd = 1$ KB。

| 轮次 | 轮次开始时 cwnd | 阶段 | 轮次结束时 cwnd |
|---|---|---|---|
| 第 1 个 RTT | 1 KB | 慢开始 | 2 KB |
| 第 2 个 RTT | 2 KB | 慢开始 | 4 KB |
| 第 3 个 RTT | 4 KB | 慢开始 | 8 KB |
| 第 4 个 RTT | 8 KB | 因 $cwnd=8=ssthresh$，转拥塞避免 | **9 KB** |

**答案：9 KB。**

**题目二（2014 年第 38 题原型）**：甲、乙已建立 TCP 连接，$MSS=1$ KB，甲一直有数据发送；乙每收到一个数据段都会发出一个接收窗口为 10 KB 的确认段。若甲在 t 时刻发生超时时拥塞窗口为 8 KB，求从 t 时刻起不再发生超时的情况下，经过 10 个 RTT 后甲的发送窗口。

**解**：超时处理：$ssthresh = 8/2 = 4$ KB，$cwnd = 1$ KB。

| 轮次 | 轮次开始 cwnd | 阶段 | 轮次结束 cwnd |
|---|---|---|---|
| 1 | 1 KB | 慢开始 | 2 KB |
| 2 | 2 KB | 慢开始 | 4 KB |
| 3 | 4 KB | 已达门限，转拥塞避免 | 5 KB |
| 4 | 5 KB | 拥塞避免 | 6 KB |
| … | … | 每轮 +1 | … |
| 10 | 11 KB | 拥塞避免 | 12 KB |

10 个 RTT 后 $cwnd = 12$ KB。但接收窗口始终为 10 KB，所以

$$ swnd = \min(12,\ 10) = \mathbf{10\ KB} $$

**答案：10 KB。**

**题目三（2022 年第 38 题原型）**：$MSS = 1$ KB，甲一直有数据向乙发送，当甲的拥塞窗口为 16 KB 时计时器超时，则甲的拥塞窗口再次增长到 16 KB 所需要的最少时间是多少（以 RTT 计）？

**解**：$ssthresh = 16/2 = 8$ KB，$cwnd = 1$ KB。

| 轮次 | 轮次开始时 cwnd | 阶段 | 轮次结束后 cwnd |
|---|---|---|---|
| 1 | 1 KB | 慢开始 | 2 KB |
| 2 | 2 KB | 慢开始 | 4 KB |
| 3 | 4 KB | 慢开始 | 8 KB |
| 4 | 8 KB | 转拥塞避免 | 9 KB |
| 5 | 9 KB | 拥塞避免 | 10 KB |
| 6 | 10 KB | 拥塞避免 | 11 KB |
| 7 | 11 KB | 拥塞避免 | 12 KB |
| 8 | 12 KB | 拥塞避免 | 13 KB |
| 9 | 13 KB | 拥塞避免 | 14 KB |
| 10 | 14 KB | 拥塞避免 | 15 KB |
| 11 | 15 KB | 拥塞避免 | **16 KB** |

从 1 KB 涨回 16 KB：慢开始走 3 轮到达 8 KB，之后拥塞避免每轮 +1 KB 需要 8 轮，共 $3 + 8 = \mathbf{11}$ RTT。

**答案：11 RTT。**

**题目四（2017 年第 39 题原型）**：甲向乙发起 TCP 连接，$MSS = 1$ KB，RTT = 5 ms，乙开辟的接收缓存为 64 KB。求甲从连接建立成功到发送窗口达到 32 KB 所需的最少时间。

**解**：接收窗口 64 KB 不构成限制（32 < 64）。慢开始阶段每 RTT 翻倍：

$$ 1 \to 2 \to 4 \to 8 \to 16 \to 32\ (\text{KB}) $$

从 1 KB 到 32 KB 需要 **5 个 RTT**，最少时间 $= 5\times5 = \mathbf{25}$ ms。

**题目五（2020 年第 38 题原型）**：$MSS = 1$ KB，RTT = 2 ms，在不出现拥塞的前提下，拥塞窗口从 8 KB 增长到 32 KB 所需的**最长**时间是多少？

**解**：求最长时间应按增长较慢的**拥塞避免**（每 RTT +1 KB）计算。

$$ 32 - 8 = 24\ \text{KB} \Rightarrow 24\ \text{个 RTT},\qquad 24\times2 = \mathbf{48}\ \text{ms} $$

**答案：48 ms。**

**题目六（2015 年第 39 题原型）**：甲、乙新建 TCP 连接，甲的拥塞控制初始阈值为 32 KB，甲以 $MSS = 1$ KB 的段发送数据，乙为该连接分配 16 KB 接收缓存，对每个数据段确认，忽略段传输延迟。若乙收到的数据全部存入缓存不被取走，则甲从连接建立成功起，在未超时的情况下经过 4 个 RTT 后，甲的发送窗口是多少？

**解**：初始 $cwnd = 1$ KB，$ssthresh = 32$ KB，全程处于慢开始。

| 轮次 | 发送的段数 | 累计写入接收缓存 |
|---|---|---|
| 第 1 个 RTT | 1 | 1 KB |
| 第 2 个 RTT | 2 | 3 KB |
| 第 3 个 RTT | 4 | 7 KB |
| 第 4 个 RTT | 8 | **15 KB** |

经过 4 个 RTT 后共写入 15 KB，接收缓存还剩 $16 - 15 = 1$ KB，即 $rwnd = 1$ KB。此时 $cwnd = 16$ KB。

$$ swnd = \min(16,\ 1) = \mathbf{1\ KB} $$

**答案：1 KB。**

**题目七（2023 年第 47 题原型）**：主机 H 从 FTP 服务器下载一个 18000 B 的文件 F，建立数据连接时初始序号为 100，$MSS = 1000$ B，拥塞控制初始阈值为 4 MSS，RTT = 10 ms，忽略 TCP 传输时延，全程无差错、无丢包乱序。

**(1) 文件第一个字节的序号是多少？**

初始序号 100 被 SYN 占用，所以第一个数据字节序号为 $100 + 1 = \mathbf{101}$。

**(2) 断开数据连接时，FTP 发送的第二次挥手的 ACK 序号是多少？**

18000 B 数据占用序号 101 ~ 18100，随后发送的 FIN 序号为 18101。服务器在第二次挥手中确认该 FIN，故 `ack = 18101 + 1 = 18102`。

**(3) 当 H 收到确认序号为 2101 的确认段时，cwnd 是多少？收到 7101 时呢？**

初始 $cwnd = 1$ MSS，$ssthresh = 4$ MSS。慢开始阶段每收到一个新确认 +1 MSS：

| 确认号 | 累计确认的数据段数 | cwnd |
|---|---|---|
| 1101 | 1 | 2 MSS |
| 2101 | 2 | **3 MSS** |
| 3101 | 3 | 4 MSS（$=ssthresh$，之后转拥塞避免） |
| 4101 | 4 | 5 MSS（拥塞避免，+1） |
| … | … | 每 1000 B 数据 +1 MSS |
| 7101 | 7 | **8 MSS** |

所以收到 `ack=2101` 时 $cwnd = \mathbf{3\ MSS}$；收到 `ack=7101` 时 $cwnd = \mathbf{8\ MSS}$（因为 7 个段被确认，其中前 3 个走慢开始到 4 MSS，之后 4 个走拥塞避免，$4+4=8$）。

:::warn 这一段要特别小心
从「cwnd = 4 MSS 时转拥塞避免」之后，**每收到 1 个新确认只 +1 MSS**（在 MSS = 1 段的讨论单位下，拥塞避免每收到一个确认增加 $1/cwnd$ 个 MSS，但按「每 RTT +1」的离散轮次来处理更稳妥）。做题时一定要先判断**当前收到第几个新确认**，再决定是「翻倍」还是「+1」。
:::

##### 拥塞控制与流量控制的区别（第四遍强调）

| 对比项 | 流量控制 | 拥塞控制 |
|---|---|---|
| 目的 | 使**接收方**来得及接收 | 使**网络**不过载 |
| 范围 | 点对点、端到端（接收端 → 发送端） | 全局性（涉及所有主机、所有路由器） |
| 实现手段 | 接收窗口 rwnd | 拥塞窗口 cwnd |
| 是否 TCP 独有 | UDP 完全没有 | UDP 完全没有 |
| 组合关系 | $swnd = \min(rwnd,\ cwnd)$ | 同左 |

##### 传输层滑动窗口与数据链路层滑动窗口的区别

这一对比虽然不在考纲里，但选择题常用来设混淆项，务必分清。

| 对比项 | 数据链路层（GBN / SR） | 传输层（TCP） |
|---|---|---|
| 窗口单位 | **帧**（或比特） | **字节**（MSS 只是讨论单位） |
| 窗口大小含义 | 最多连续发送/接收多少个**帧** | 允许发送的**字节序号区间** |
| 滑动方式 | 按帧序号滑动 | 按**字节序号**滑动 |
| 确认语义 | GBN 中 ACK $n$ = 到 $n$ 为止已收到，期望 $n+1$；SR 中逐帧确认 | ack $=N$ = 到 $N-1$ 为止已收到，期望 $N$ |
| 是否考虑字节大小 | 只关心帧数，与帧长无关 | 必须关心字节数，窗口值 $\times$ MSS 才有物理意义 |
| 是否有拥塞控制 | 无（点对点链路不存在网络范围拥塞问题） | 有（cwnd） |

:::warn 最容易踩的一条
题目里常说「窗口是 400」，一定要先看**单位**：TCP 里 400 表示 **400 字节**；若题目同时给出 MSS = 100 B，则窗口内可以装 4 个报文段；若题目说的是「窗口为 400 个报文段」，那就是 $400\times \text{MSS}$ 字节。**单位搞错，整道题全错。**
:::

##### 本章四类计算题的解题路线图

| 题型 | 识别特征 | 解题路线 |
|---|---|---|
| **序号/确认号推算** | 「第三个报文段的序号」「乙收到的确认号」 | ① 判断报文段类型（SYN / FIN / 数据）→ ② 折算成序号区间 → ③ 倒推各段起点 → ④ 确认号取「连续收到的最高序号 + 1」 |
| **窗口推算** | 「甲的发送窗口还能发送多少字节」「可连续发送的字节序号范围」 | ① 求窗口大小 $=\min(rwnd,cwnd)$ → ② 左沿 = 最新 ack → ③ 右沿 = 左沿 + 窗口大小 − 1 → ④ 还要发多少 = 右沿 − 已发送未确认的最大序号 |
| **拥塞窗口逐轮演算** | 「经过 $n$ 个 RTT 后 cwnd / 发送窗口是多少」 | ① 先处理拥塞事件：超时 → $ssthresh=cwnd/2$、$cwnd=1$；三重确认 → $ssthresh=cwnd/2$、$cwnd=ssthresh$ → ② 逐轮判断当前处于慢开始（×2）还是拥塞避免（+1）→ ③ 最后用 $\min(rwnd,cwnd)$ 求发送窗口 |
| **时间估算** | 「至少需要多长时间」「从发出 FIN 起多久关闭」 | ① 建立连接 1 RTT → ② 数据传送按 cwnd 演算出的轮次数 × RTT → ③ 释放：主动方 $1\text{RTT}+2\text{MSL}$，被动方 $1.5\text{RTT}$ → ④ 全部相加 |

:::exam 这一章在统考里的出题规律
- **选择题（每年 1~2 道）**：UDP 校验、端口号、标志位含义、序号/确认号、每次拥塞事件后的 cwnd、TIME-WAIT 与 2MSL、RTO 与 Karn 算法。
- **综合应用题（约每 2~3 年一次，9 分左右）**：把 FTP/HTTP 之类的应用层背景 + TCP 连接建立与释放的序号 + 拥塞窗口逐轮 + 发送时间估算打包在一起，有时还掺入 IP、以太网最小帧长的计算。**做这类题的关键不是记公式，而是能把序号、窗口、时间三条线分开算，各算各的再汇总。**
:::

## 本章小结表

| 考点 | 核心结论 |
|---|---|
| 传输层功能 | 进程到进程（端到端）的逻辑通信；复用（多个进程共用一个协议）与分用（按**端口**交付进程） |
| 与网络层区别 | 网络层：主机到主机，按**协议字段**分用；传输层：进程到进程，按**端口号**分用 |
| 端口号 | **16 位**，0 ~ 65535；只有**本地意义**；TCP 与 UDP 端口号相互独立 |
| 三类端口 | 熟知 **0 ~ 1023**；登记 **1024 ~ 49151**；短暂（客户端）**49152 ~ 65535** |
| 套接字 | socket = (IP 地址 : 端口号)；TCP 连接由两个套接字唯一确定 |
| 必须记住的端口 | FTP 21/20、SSH 22、Telnet 23、SMTP 25、DNS 53、DHCP 67/68、TFTP 69、HTTP 80、POP3 110、IMAP 143、HTTPS 443、SNMP 161、RIP 520 |
| UDP 特点 | 无连接、不可靠、**面向报文**、支持一对一/一对多/多对多、首部仅 **8 B**、无流量与拥塞控制 |
| UDP 首部 | 四个字段各 2 B：源端口、目的端口、**长度（首部 + 数据）**、校验和；长度最小为 8 |
| UDP 校验 | 覆盖 **12 B 伪首部 + 8 B 首部 + 数据**（不足补全 0）；**反码求和 + 回卷进位 + 取反**；全 0 表示**不校验** |
| 伪首部 | 源 IP、目的 IP、全 0、**协议号（UDP 17 / TCP 6）**、长度；**不传送、不递交**，只用于校验 |
| TCP 特点 | 面向连接、可靠、全双工、**面向字节流**、只能一对一 |
| TCP 首部 | 固定 **20 B** + 选项最多 40 B = 最长 **60 B**；数据偏移以 **4 B** 为单位，最小 5 |
| 序号含义 | 本报文段**数据第一个字节**的序号 |
| 确认号含义 | 期望收到的下一个字节序号；表示**到 ack−1 为止**的数据已正确收到 |
| 序号消耗规则 | SYN 消耗 1；FIN 消耗 1；纯 ACK 不消耗；数据段消耗字节数 |
| 六个标志位 | URG 紧急、ACK 确认、PSH 推送、RST 复位、SYN 同步、FIN 终止 |
| MSS 与 MTU | $\text{MSS} = \text{MTU} - \text{IP 首部} - \text{TCP 首部}$；MSS 只算数据载荷 |
| 三次握手 | `SYN, seq=x` → `SYN+ACK, seq=y, ack=x+1` → `ACK, seq=x+1, ack=y+1` |
| 为什么三次 | **防止已失效的连接请求报文段**到达服务器，造成服务器资源浪费 |
| 四次挥手 | `FIN, seq=u` → `ACK, ack=u+1` → `FIN+ACK, seq=w, ack=u+1` → `ACK, seq=u+1, ack=w+1` |
| 为什么四次 | TCP 是**全双工**，两个方向必须分别释放；半关闭期间 B 仍可发数据 |
| TIME-WAIT / 2MSL | ①确保最后一个 ACK 能到达 B；②使本次连接的所有报文段从网络中消失 |
| 释放最短时间 | 主动方 **1 RTT + 2MSL**；被动方 **1.5 RTT** |
| 可靠传输 | 字节编号 + 累积确认 + 超时重传 + 快速重传 + SACK |
| RTO | $RTO = RTT_S + 4\times RTT_D$；$\alpha=1/8$，$\beta=1/4$ |
| Karn 算法 | 重传的报文段**不采用其 RTT 样本**；每重传一次 **RTO 加倍** |
| 快速重传 | 收到 **3 个重复确认**立即重传，不等超时 |
| SACK | 通知已收到的**不连续字节块**，最多 4 个字节块；发送方**不一定**只重传缺失部分 |
| 流量控制 | $swnd = \min(rwnd,\ cwnd)$；接收窗口 ⊆ 接收缓存，发送窗口 ⊆ 发送缓存 |
| 零窗口 | 用**持续计时器** + **零窗口探测报文段（1 字节数据）**打破死锁 |
| 慢开始 | 每确认 1 段 +1 MSS，**每 RTT 翻倍** |
| 拥塞避免 | 每确认 1 段 +$1/cwnd$ MSS，**每 RTT +1 MSS** |
| 超时处理 | $ssthresh = cwnd/2$，$cwnd = 1$，重走慢开始 |
| 三重确认处理 | $ssthresh = cwnd/2$，$cwnd = ssthresh$，**直接进拥塞避免** |
| 拥塞 vs 流量 | 拥塞控制是**全局性**问题；流量控制是**端到端**问题 |

## 易错清单

:::warn 传输层 22 个高频陷阱
1. **「有校验和」不等于「可靠传输」**。UDP 有校验和，但校验失败只丢弃，不重传、不排序，因此是不可靠的。
2. **UDP 的复用/分用依据是目的端口号**（2018 年题 39），不是源端口号；源端口号只是让对方知道往哪儿回。
3. **网络层按协议字段分用，传输层按端口号分用**，两个层次的「复用」含义不同，不要互相套用。
4. **端口号只有本地意义**，两台主机上相同的端口号毫无关系；TCP 与 UDP 的端口号也相互独立。
5. **三类端口号分界点是 1023 和 49151**。65535 属于短暂端口号。
6. **UDP 的「长度」字段含 8 字节首部**。给长度字段求数据长度要减 8，给数据长度求字段值要加 8。
7. **伪首部不传送、不递交**，只在计算校验和时临时构造；UDP 协议号 17，TCP 协议号 6。
8. **反码求和一定要回卷进位**，最后还要**取反**；若取反结果是全 0，应写全 1。
9. **全 0 校验和表示不校验**（IPv4 的 UDP 允许），不是「校验通过」。
10. **TCP 的数据偏移以 4 字节为单位**，最小值 5（对应 20 字节固定首部），最大值 15（对应 60 字节）。别和 IP 的**片偏移（8 字节为单位）**混淆。
11. **序号是数据第一个字节的序号**；**确认号是期望收到的下一个字节的序号**。两者语义相反，写题时最容易互换。
12. **ack = N 表示到 N−1 为止的数据都已收到**，与 GBN 中「ACK n 表示到 n 为止收到」差 1。
13. **SYN 和 FIN 各消耗一个序号**，纯 ACK 不消耗。第三、四次挥手能否携带数据的规定不同：**第三次握手可以携带数据，第四次挥手不能携带数据**。
14. **第一次和第二次握手都不能携带数据**；第三次握手可以。
15. **只有主动关闭方进入 TIME-WAIT**，而且必须等 **2MSL**；被动关闭方收到最后一个 ACK 后立即 CLOSED。
16. **释放时间不是「2MSL」**：主动方是 1 RTT + 2MSL，被动方是 1.5 RTT（第 2、3 次挥手合并的最短情形）。
17. **MSL 不是 RTT**。2022 年题 39 中 MSL = 800 ms 与 RTT = 50 ms 完全无关，不要用 RTT 去算 2MSL。
18. **MSS 只包含数据载荷**，不含 TCP 首部和 IP 首部；$\text{MSS} = \text{MTU} - 20 - 20 = 1460$（以太网）。
19. **「收到 3 个重复确认」指冗余的那 3 个**，加上原来那个共 4 个对同一报文段的确认。这个 3 的计数不要数错。
20. **超时与三重确认的处理不同**：超时把 cwnd 降到 **1**；三重确认把 cwnd 降到 **新 ssthresh（原 cwnd 的一半）**，而且**直接进拥塞避免，不经过慢开始**。这是拥塞控制题的分水岭。
21. **慢开始「每 RTT 翻倍」，拥塞避免「每 RTT +1」**；不要在拥塞避免阶段也做翻倍，也不要在慢开始阶段做 +1（尽管底层实现上慢开始每个确认确实只加 1 MSS）。
22. **发送窗口是 min(rwnd, cwnd)，且已发送未确认的数据仍占用窗口**。2010 年题 39 的正确答案是 1000 B 而不是 2000 B，就是因为第 2 个 1000 B 段还没被确认。
:::
