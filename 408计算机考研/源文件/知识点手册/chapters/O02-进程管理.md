## 进程与线程

### 进程与线程的基本概念

#### 进程的定义与进程映像

程序是存放在磁盘上的静态指令和数据集合；要让程序运行，必须把它的指令和数据装入内存，并为它分配 CPU、栈等资源。**进程（Process）就是程序在一个数据集合上的一次动态执行过程，是系统进行资源分配和调度的独立单位。**

进程在某一时刻的**全部状态信息**称为**进程映像**（也称进程实体），由三部分构成：

| 组成部分 | 内容 | 特点 |
|---|---|---|
| **PCB（进程控制块）** | 进程描述信息、控制管理信息、资源清单、处理机上下文 | 常驻内存，**进程存在的唯一标志** |
| **程序段** | 二进制机器码、只读常量（字符串字面量、`const` 全局常量） | **静态、只读、可共享** |
| **数据段** | 全局/静态变量（`.data`、`.bss`）、堆（动态分配）、栈（函数调用） | **动态、可读可写、进程私有** |

数据段的细分值得记牢：`.data` 存放已初始化的全局变量和静态变量；`.bss` 存放未初始化（或初始化为 0）的全局变量和静态变量，可执行文件中只记录"需要多大空间"，装入时由操作系统清零；**堆**由程序员手动申请释放（`malloc`/`free`），从低地址向高地址增长，忘记释放即"内存泄漏"；**栈**由编译器自动管理，保存局部变量、函数参数、返回地址，从高地址向低地址增长，递归过深会栈溢出。

**进程与程序的区别：**

- 程序是静态的永久存在，进程是动态的、有生命周期的；
- 进程 = 程序 + 执行状态，即"进程是程序的一次执行"；
- 同一个程序可以对应多个进程（例如同时打开多个浏览器窗口），它们代码段相同，但数据段、堆、栈各不相同；
- 一个进程也可以执行多个程序。

:::key 创建与撤销的本质
**创建进程实质上是创建进程实体中的 PCB；撤销进程实质上是撤销进程的 PCB。**
:::

:::exam 真题考法
2023 年曾考"进程虚拟空间"、2021 年曾考"进程组织之进程控制块（PCB 内容）"。选择题常问"下列哪一项**不属于** PCB 的内容"或"进程切换时必须更新哪些寄存器"。
:::

#### 线程的基本概念

引入进程是为了让多道程序并发执行、提高资源利用率和吞吐量；但进程作为资源拥有单位，创建、撤销、切换的系统开销都很大。于是引入**线程（Thread）**——"轻量级进程"。

**线程是程序执行流的最小单位，是处理机独立调度和分派的基本单位；进程是资源分配的基本单位。**

线程自己私有的部分（即**线程上下文**）：

- 线程标识符 TID；
- 程序计数器 PC；
- 一组通用寄存器（线程现场）；
- **栈**（每个线程一个独立的栈，保存局部变量、函数调用上下文）。

同一进程内的所有线程**共享**：代码段、数据段（全局变量、静态变量）、堆、打开的文件描述符、网络套接字、信号处理程序、进程 ID 与父进程 ID、地址空间（页表）。

:::key 一句话记忆
**线程私有：TID、PC、寄存器、栈。其余全共享。**
:::

因为每个线程有自己的栈，**线程的局部变量是线程私有的**。如果需要线程间共享数据，值必须放在堆或全局可访问位置。

:::warn 易错
"同一进程的线程还可以修改别的线程栈里的数据吗？"从地址空间角度看**可以**（因为共享地址空间），但同一进程的线程属于同一用户，编程时会主动避免这种非法访问。统考按"栈是线程私有的"理解即可。
:::

#### 进程与线程的比较

| 比较项 | 进程 | 线程 |
|---|---|---|
| 定义 | **资源分配的基本单位**，程序在一个数据集上的一次动态执行 | **处理机调度的基本单位**，进程中的一个执行实体 |
| 调度 | 由操作系统调度 | 可由用户空间线程库调度，也可由操作系统调度 |
| 资源 | 拥有独立的内存空间和系统资源 | 基本不拥有资源，共享所属进程的全部资源 |
| 地址空间 | 进程间相互独立（内存保护） | 同进程内线程共享地址空间 |
| 并发性 | 进程间可并发 | 同进程内线程可并发；线程切换开销小，系统并发度更高 |
| 系统开销 | 创建、撤销、切换开销大 | 创建、撤销、切换开销小 |
| 通信 | 必须借助 IPC 机制 | 直接读写进程内共享变量即可 |
| 独立性 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| 多处理机 | 单线程进程只能在一个处理机上运行 | 多线程进程的不同线程可分配到不同处理机上并行执行 |
| 相似之处 | PCB、PID、就绪/运行/阻塞三态、父进程创建子进程、不同进程可执行同一程序 | TCB、TID、就绪/运行/阻塞三态、父线程创建子线程、不同线程可执行同一程序 |

**线程相比进程减少开销的原因（高频考点）：**

1. 线程创建比进程创建快——不必维护内存管理信息、文件管理信息，而是共享它们；
2. 线程终止比进程终止快——释放的资源少得多；
3. 同进程内线程切换比进程切换快——**它们共用同一页表，切换时不用切换页表**（页表切换在上下文切换开销中占比很大）；
4. 同进程线程间数据传递不经过内核，交互效率更高。

:::warn 易错
- 页表基址寄存器（页目录基址寄存器）在同一进程的不同线程间切换时**不需要修改**，因为共用同一个虚拟地址空间；同时原有 TLB 不会失效。切换时要更新的只有程序计数器、通用寄存器组、栈基址寄存器。
- "操作系统为每个用户级线程建立一个线程控制块"是**错误**说法（2019 年真题）。内核级线程才有内核维护的 TCB，用户级线程的 TCB 由用户态线程库维护。
:::

### 进程与线程的状态与转换

#### 三态模型与五态模型

**三种基本状态：**

| 状态 | 含义 |
|---|---|
| **运行态（Running）** | 占有 CPU 正在执行。**单处理机下任一时刻至多一个进程处于运行态，多处理机下可以有多个** |
| **就绪态（Ready）** | 已获得除处理机以外的一切所需资源，一旦得到处理机便可立即执行 |
| **阻塞态（等待态，Waiting/Blocked）** | 正在等待某资源可用（**不包括处理机**）或等待 I/O 完成，即使处理机空闲也不能运行 |

**五种状态（加上创建态、终止态）：**

| 状态 | 含义 |
|---|---|
| **创建态（New）** | 进程正在被创建，已分配 PCB，正在分配除 CPU 外的其他资源 |
| **就绪态** | 见上 |
| **运行态** | 见上 |
| **阻塞态** | 见上 |
| **终止态（Exit）** | 进程运行终止后，操作系统正在回收其占用的资源和 PCB |

#### 状态转换的合法与非法情况

合法转换只有五条：

1. **创建态 → 就绪态**：资源分配完毕，PCB 初始化完成，插入就绪队列。
2. **就绪态 → 运行态**：被调度程序选中，分配到处理机。
3. **运行态 → 就绪态**：时间片用完，或被更高优先级的进程抢占（**被动行为，由调度引起**）。
4. **运行态 → 阻塞态**：进程主动请求某种资源或等待某事件（**主动行为，通过系统调用发出**）。
5. **运行态 → 终止态**：进程正常结束或异常终止。

非法转换（必考）：

- **阻塞态 → 运行态**：不允许。阻塞的进程必须先被唤醒变为就绪态，再经调度才能运行。
- **就绪态 → 阻塞态**：不允许。进入阻塞态是进程在运行中主动发出的请求，就绪态没有 CPU，无法发出请求。
- **阻塞态 → 就绪态**是合法的，且是**被动行为**——必须由其他进程（如释放 I/O 设备的进程）调用唤醒原语完成。
- **创建态 → 运行态**不允许；创建完成后只能先进入就绪态。

:::key 判断口诀
**"运行"往下走：要么回就绪（被抢），要么去阻塞（自己等），要么结束。**
**"阻塞"只能回到就绪，"就绪"只能去运行。**
:::

#### 引起状态转换的典型事件

| 事件 | 转换 |
|---|---|
| 时间片用完 | 运行 → 就绪 |
| 被更高优先级进程抢占 | 运行 → 就绪 |
| 主动出让 CPU（`yield`） | 运行 → 就绪 |
| 请求临界资源 / 申请外设 | 运行 → 阻塞 |
| 启动 I/O 设备、读文件（等待 I/O） | 运行 → 阻塞 |
| 对值 ≤ 0 的信号量执行 P（wait）操作 | 运行 → 阻塞 |
| 对管程条件变量执行 `wait()` | 运行 → 阻塞 |
| 申请内存失败 / 创建进程资源不足 | 运行 → 阻塞 |
| I/O 完成（中断处理） | 阻塞 → 就绪 |
| 某进程退出临界区并发出唤醒 | 阻塞 → 就绪 |
| 等待的资源被释放、事件到达 | 阻塞 → 就绪 |

:::warn 三个高频陷阱
1. **"键盘输入"不是"运行→就绪"**。当前进程等待键盘输入，是从运行态转为**阻塞态**（等待 I/O 事件）。
2. **"缺页异常"不是"运行→就绪"**。缺页后进程等待页面调入，进入**阻塞态**。
3. **"执行 P(wait) 操作"是"运行→阻塞"**，只有"主动出让 CPU"才是"运行→就绪"（2023 年真题答案即为此）。
:::

:::exam 真题考法
2015-25（下列哪个事件导致执行态变就绪态）、2018-27（哪些事件导致当前进程阻塞）、2019-24（哪些事件可能唤醒进程）、2022-28（哪些操作导致执行态变阻塞态）、2023-27（哪个操作让线程从执行态变就绪态）。**几乎每年一道，属于必得分题。**
:::

#### 挂起态与七状态模型

内存空间有限，操作系统把短期内不执行的进程换出到外存，称为**挂起（Suspend）**；把更可能执行的进程从外存调回内存，称为**激活（Activate）**。加上两个挂起态就得到七状态模型：

- **就绪挂起态**：进程在外存，但只要调入内存即可立即运行；
- **阻塞挂起态**：进程在外存并且仍在等待某事件。

关键转换：

- **运行 → 就绪挂起**：程序被直接挂起；
- **阻塞 → 阻塞挂起**：内存紧张时，优先换出阻塞态进程（它占着内存却不能运行）；
- **阻塞挂起 → 就绪挂起**：所等待的事件到来（如 I/O 完成）；
- **就绪挂起 → 就绪**：内存中没有其他就绪进程，或该进程优先级高于内存中所有就绪进程；
- **就绪 → 就绪挂起**：只有在挂起阻塞态进程仍不足以释放足够内存时才这样做。

:::key
换出/换入（Swapping）由**中级调度**负责。被挂起的进程即使优先级很高也不能运行，因为它不在内存中。
:::

### 线程的实现

#### 内核支持的线程与线程库支持的用户级线程

**用户级线程（ULT，User-Level Thread）**：由用户程序自己管理和调度，创建、同步、调度全部由运行在用户空间的**线程库**（如 POSIX Pthreads、Java 线程库）完成，内核完全不知道其存在。

**内核级线程（KLT，Kernel-Level Thread）**：由操作系统内核管理和调度，内核为每个内核级线程建立 TCB，创建、同步、调度通过系统调用完成。

对比表：

| 对比项 | 用户级线程（ULT） | 内核级线程（KLT） |
|---|---|---|
| 管理者 | 用户空间的线程库，每个进程维护私有的 TCB 列表 | 操作系统内核，内核为每个线程建立 TCB |
| 内核是否感知 | **不感知**（可用于不支持线程的操作系统） | 感知并能控制 |
| 切换开销 | **小**，完全在用户空间完成，不需要陷入内核 | **大**，需要通过系统调用，存在用户态/内核态切换 |
| 阻塞影响 | **一个线程阻塞则整个进程被阻塞**（内核只看到进程） | 一个线程阻塞**不影响**同进程其他线程继续执行 |
| 并行能力 | **不能**利用多处理机，同一个进程的多个线程只能在一个 CPU 上分时复用 | **可以**分配到多个处理器上真正并行执行 |
| CPU 时间分配单位 | 以**进程**为单位分配时间片，多线程进程中的每个线程分到的时间更少 | 以**线程**为单位分配，多线程进程可获得更多 CPU 时间 |
| 调度算法 | 允许每个进程有自己的线程调度策略，程序员可自定义 | 由内核统一调度，可利用内核的优先级管理等机制 |
| 是否需系统调用 | 创建、撤销、切换都不需要 | 创建、撤销、切换都需要 |

**组合方式**：内核支持多个内核级线程的建立、调度和管理，同时允许用户程序建立、调度和管理用户级线程；若干个用户级线程通过时分多路复用地映射到若干个内核级线程上。它结合了 KLT 与 ULT 的优点：同一进程的多个线程可同时在多处理机上并行运行，且阻塞一个线程时不需要阻塞整个进程。

#### 多线程模型

| 模型 | 映射关系 | 优点 | 缺点 |
|---|---|---|---|
| **多对一** | 多个用户级线程映射到一个内核级线程 | 线程管理开销小、效率高，可在不支持线程的内核上实现 | 一个线程阻塞则整个进程阻塞；不能利用多处理机 |
| **一对一** | 每个用户级线程对应一个内核级线程 | 阻塞系统调用不影响其他线程；允许多线程在多处理机上并行 | 创建一个用户线程就要创建一个内核线程，内核线程数量受限，开销大 |
| **多对多** | n 个用户级线程映射到 m 个内核级线程（n > m） | 兼有前两者的优点，可并行又可控制开销 | 实现复杂 |

:::exam 真题考法
2012-31（进程与线程的基本叙述）、2019-23（线程的描述中错误的——答案是"操作系统为每个用户级线程建立一个线程控制块"）、2011-25（线程不能共享的是栈指针）。这类题目本质都在考"哪些共享、哪些私有"和"谁负责调度"。
:::

### 进程与线程的组织与控制

#### PCB 的作用与内容

**PCB 是进程存在的唯一标志**，进程创建后该结构常驻内存，进程结束时删除。操作系统通过 PCB 管理和控制进程，因此**管理控制所需的一切参数一定放在 PCB 中**。

| 类别 | 具体内容 |
|---|---|
| **进程描述信息** | 进程标识符 PID（系统内唯一，PID 是操作系统分配的有限资源，即可分配的 PID 个数固定，对应系统允许同时存在的最大进程数）、用户标识符 UID |
| **进程控制和管理信息** | 进程状态、进程优先级、代码运行入口地址、程序外存地址、进入内存时间、处理机占用时间、信号量使用情况、CPU 调度信息（调度队列指针等） |
| **资源分配清单** | 内存/虚存地址、代码段指针、数据段指针、堆栈段指针、打开文件表、I/O 设备信息 |
| **处理机相关信息（处理机上下文）** | 程序计数器 PC、通用寄存器值、地址寄存器值、控制寄存器值、标志寄存器值、状态字、累加器、索引寄存器、其他条件码寄存器，以及基址/界限寄存器的值等内存管理信息 |

#### 进程控制块的组织方式

| 组织形式 | 做法 | 特点 |
|---|---|---|
| **线性表** | 所有 PCB 组织在一张线性表中，表起始地址存放在内存特定位置或专用寄存器中 | 简单，但查找慢 |
| **链接队列** | 不同状态对应不同的队列：就绪队列、各类阻塞队列 | 插入删除灵活；**就绪队列只有一个，但等待不同事件的阻塞队列有多个** |
| **索引表** | 不同状态对应不同的索引表（就绪索引表、阻塞索引表） | 查找快，需要额外索引空间 |

:::key 为什么阻塞队列有多个而就绪队列只有一个
进程处于就绪态的原因只有一个——还没分配到 CPU；而阻塞原因多种多样（等 I/O、等打印机、等信号量、等消息……），因此**每一类阻塞原因单独建立一个 PCB 等待队列**。
:::

#### 进程控制的原语操作

进程控制的主要功能是对系统中所有进程实施有效管理，包括创建新进程、撤销已有进程、实现状态切换。这些功能都由**原语**实现。**原语是不可被中断的原子操作，执行期间不允许中断，因此原语的执行过程中不能进行进程调度与切换。**

**创建原语：**

1. 为新进程分配唯一的 PID，并申请一个空白 PCB（PCB 有限，申请失败则创建失败）；
2. 为进程分配运行所需资源（内存、文件、I/O 设备、CPU 时间等），资源不足时**不是创建失败，而是停留在创建态等待**；
3. 初始化 PCB：初始化标志信息、处理机状态信息、处理机控制信息，设置优先级等；
4. 若就绪队列能接纳新进程，将新进程插入就绪队列，等待调度。

引起进程创建的事件：终端用户登录、作业调度、系统提供服务、用户程序的应用请求。

**撤销原语：**

1. 找到被撤销进程的 PCB；
2. 若进程正在运行，立即剥夺其处理机；
3. 若进程还有子进程，通常应同时撤销所有子进程（**统考按此理解**；实际 Linux 中父进程结束时子进程由 init 接管成为孤儿进程，Windows 中同一进程组会一起结束）；
4. 归还进程占用的全部资源给父进程或系统；
5. 将 PCB 从所在队列中移出。

**阻塞原语（Block）：**

1. 找到被阻塞进程的 PCB；
2. 若该进程为运行态，则保护现场（保存上下文），将其状态转为阻塞态，停止运行；
3. 把 PCB 插入相应事件的等待队列，将处理机调度给其他就绪进程。

**唤醒原语（Wakeup）：**

1. 在该事件的等待队列中找到相应进程的 PCB；
2. 将其从等待队列中移出，置其状态为就绪态；
3. 把 PCB 插入就绪队列，等待调度。

:::warn 易错
- **阻塞是进程自身的主动行为**，只有运行态的进程（占有 CPU）才可能转为阻塞态；**唤醒是被动行为**，必须由其他进程调用唤醒原语完成。
- **阻塞原语与唤醒原语必须成对使用**，否则进程将永远阻塞。
- 阻止进程调度的情况：**中断处理过程中、访问内核临界区时、禁用中断期间、原语执行过程中**。注意**用户级临界区中允许调度**：例如某进程已获得打印机（处于临界区）后主动等待 I/O，仍会阻塞自己并触发调度。
:::

:::exam 真题考法
2010、2019、2020、2021、2022、2024 年多次考查。典型问法："创建进程时必须完成的操作包括哪些""撤销进程时不一定执行的是"（2024 年答案为"终止子进程"）、"操作系统为新建进程完成的工作按顺序是"。
:::

### 进程间通信

每个进程的用户空间相互独立、不能直接互访，因此需要借助内核空间（所有进程共享同一份内核空间）来实现通信。

#### 共享内存

共享内存机制是**拿出一块物理内存，映射到多个进程各自的虚拟地址空间中**，各进程通过自己的页表把虚拟地址映射到同一物理页框。这样进程 A 写入的内容进程 B 立刻可见，不需要任何数据拷贝，是**最快的 IPC 方式**。

工作过程：

1. **创建共享内存**：`shmget`（System V）或 `shm_open`（POSIX），内核在物理内存中分配区域并指定访问权限和大小；
2. **附加到进程地址空间**：`shmat` 或 `mmap`，**内核修改该进程的页表**，把虚拟地址范围映射到共享内存的物理页框；
3. **读写共享内存**：进程像访问普通内存一样直接读写，**无需系统调用，零拷贝**；
4. **同步机制**：共享内存本身**不提供任何同步**，必须配合信号量、互斥锁等使用，否则会竞态；
5. **分离**：`shmdt` 或 `munmap`，内核移除该进程页表中的映射，但物理内存仍保留；
6. **销毁**：`shmctl` 或 `shm_unlink` 标记删除，所有附加进程都分离且无引用时内核才回收物理内存。

:::key 共享内存的三个必须记牢的结论
1. 共享内存位于进程的**用户地址空间**，不在内核空间；
2. **建立**共享内存的操作（修改页表）在**内核态**；**访问**共享数据的操作在**用户态**；
3. 共享的物理页框唯一（f1 = f2 必然相等），但各进程中的**逻辑页号可以不同**（p1 与 p2 不一定相等）。
:::

:::warn 分页与分段共享的统一原则
**物理地址唯一（必须同源），逻辑地址独立（可以不同）。** 因此 2023-30 题答案是"页号 p1、p2 不一定相等，页框号 f1、f2 一定相等"；2019-28 题中"段 S 在 P1 和 P2 中应该具有相同的段号"是错误叙述。
:::

补充：进程虚拟地址空间中的**内核空间部分映射到相同的物理内存区域**（操作系统的代码和全局数据），因此内核空间天然是共享的；但**每个进程在内核态执行时使用自己独立的内核栈**，内核栈指针保存在该进程的 PCB 中。

#### 消息传递

**直接通信**：通信进程之间直接建立链路，一条链路对应一对进程，`send(P1, message)` 发送给进程 P1，`receive(P0, message)` 接收进程 P0 发来的消息。

**间接通信**：通过操作系统维护的**消息队列**（或信箱）完成。每个消息队列有唯一标识，只有共享了相同消息队列的进程才能通信。链路属性：只有共享同一消息队列的进程才建立连接；连接可以是单向或双向；一个消息队列可以与多个进程关联；每对进程可以共享多个消息队列。

**同步方式：**

- **阻塞（同步）模式**：发送者在消息被接收者收到前阻塞；接收者在没有消息时阻塞。
- **非阻塞（异步）模式**：发送者发出消息后立即继续；接收者没有消息时也立即返回。

消息队列的缺点：不适合大数据传输（Linux 中有 `MSGMAX` 限制单条消息最大长度、`MSGMNB` 限制队列总长度）；每次读写都要经过用户态与内核态之间的数据拷贝。

#### 管道

**匿名管道**：位于**内核缓冲区**（不在用户空间，也不在磁盘上）的 IPC 机制，主要用于**具有亲缘关系的进程**（父子、兄弟）之间的**单向数据流**通信。

工作流程：

1. **创建管道**：`pipe(int pipefd[2])`，返回两个文件描述符，`pipefd[0]` 读端、`pipefd[1]` 写端；内核为每个管道分配一个**环形缓冲区（循环队列）**和两个文件描述符；
2. **进程间共享**：父进程 `pipe()` 后 `fork()`，子进程继承父进程的文件描述符表，从而共享同一管道的读写端；
3. **数据读写**：写入时数据从用户空间拷贝到内核缓冲区；读取时从内核缓冲区拷贝到用户空间；
4. **生命周期**：随进程终止而销毁；所有引用管道的文件描述符关闭后，内核回收缓冲区资源（**不会持久化到磁盘**）。

**pipe 的读写规则与阻塞条件（必背）：**

| 情形 | 行为 |
|---|---|
| 写进程写**满**的管道 | **阻塞**，直到有空间 |
| 读进程读**空**的管道 | **阻塞**，直到有数据 |
| 读进程读一个**写端全部关闭**的管道 | `read` 返回 0（EOF），不阻塞 |
| 写进程写一个**读端全部关闭**的管道 | 内核向写进程发送 `SIGPIPE` 信号（即 "Broken pipe"） |
| 单次写入不超过 `PIPE_BUF`（通常 4096 字节） | **保证原子性**，多个进程同时写时数据不会交叉混合 |
| 管道是否支持定位 | **不支持** `lseek` 之类的文件定位操作，只能队尾写入、队头读出 |

其他必须记牢的结论：

- 同一时刻，管道只允许**一个读进程**执行读操作**或一个写进程**执行写操作（读写都要互斥进行）；
- 但一个管道**允许**存在多个读进程或多个写进程（它们都有该管道的文件描述符，只是操作时要抢管道的内核互斥锁）；
- 管道自身通过**互斥锁 + 两个等待队列（`rd_wait`、`wr_wait`）+ 读写指针**实现了同步与互斥，用户不需要额外写信号量；
- 管道是**半双工**的，某一时刻只能单向传输；要实现全双工需创建两个管道；
- 匿名管道只能用于有亲缘关系的进程；**命名管道（FIFO）**存在于文件系统中，可以用于任意进程之间通信。
- 管道以**字节流**为单位（无格式、无消息边界），不是以消息为单位。

:::warn 十二个自测判断（全部为"错误"的典型说法）
1. "管道位于进程的用户空间，可直接在用户态读"——**错**，管道在内核区，读写要通过系统调用在内核态完成；
2. "管道与共享内存这两种 IPC 都自己实现了同步/互斥"——**错**，共享内存本身没有同步互斥机制；
3. "管道是存放在磁盘中的一种特殊文件"——**错**，匿名管道在内存中；
4. "管道支持定位到某个具体位置读写"——**错**，只能队尾写、队头读；
5. "所有引用管道的文件描述符都被关闭后，管道内未读完的数据会被持久化到磁盘"——**错**，内核直接回收缓冲区；
6. "管道通信是以消息为单位进行写入和读出的"——**错**，是字节流；
7. "对管道的写操作不需要互斥"——**错**，读写都需要互斥。
:::

:::exam 真题考法
2014-30 曾考管道的特性（答案选"进程对管道进行读操作和写操作都可能被阻塞"）。常考选项包括"一个管道仅支持半双工通信""管道位于内存的内核区域""一个管道在同一时刻只能有一个读或一个写进程操作"。
:::

#### 信号

**信号（Signal）** 是一种**异步的、非阻塞的**通信机制，也叫"用户态中断"或"软中断"，用于通知接收进程某个事件已经发生。每个信号有一个唯一编号和对应的处理动作。信号通常只用于**简单的事件通知**，不适合复杂的数据传输。

**信号的来源：**

- 硬件来源：硬件异常（浮点除零触发 `SIGFPE`）、内存访问越界（段错误 `SIGSEGV`）、非法指令；
- 软件来源：系统调用（`kill()`、`raise()`、`alarm()`、`setitimer()`）、用户输入（`Ctrl+C` 触发 `SIGINT`）、系统事件（子进程退出时父进程收到 `SIGCHLD`）、定时器到期（`SIGALRM`）。

**常见信号：** `SIGINT`（终端中断）、`SIGKILL`（强制终止，**不可捕获、不可忽略**）、`SIGTERM`（默认终止信号，可捕获）、`SIGCHLD`（子进程终止）、`SIGALRM`（定时器）。

**传递与响应流程：** 信号产生 → 信号传递（内核把信号递给目标进程）→ 信号处理 → 执行处理函数 → 信号返回。

进程对信号有三种响应方式：

1. **执行默认操作**：多数信号的默认行为是终止进程、生成核心转储文件或暂停进程；
2. **捕捉信号**：执行用户自定义的信号处理函数；
3. **忽略信号**：不做任何处理。但 `SIGKILL` 和 `SIGSTOP` **不能被忽略或捕捉**。

:::key
**信号传递不支持排队**：短时间内多次传递同一信号，进程只会处理一次。
:::

#### 四种 IPC 机制对比

| 特性 | 共享内存 | 消息传递（消息队列） | （匿名）管道 | 信号 |
|---|---|---|---|---|
| 数据形式 | 原始字节流，直接内存访问 | 结构化消息（带类型/优先级） | 字节流（无结构） | 简单整数信号（几乎无数据） |
| 通信方向 | 双向 | 双向 | 单向（半双工） | 单向（发送→接收） |
| 同步需求 | **需要**（信号量、互斥锁） | 部分需要（阻塞接收） | 内核自动同步 | 无（异步通知） |
| 性能 | 极高（零拷贝） | 中（数据拷贝开销） | 中（内核缓冲区拷贝） | 极高（无数据传输） |
| 复杂度 | 高 | 中 | 低 | 低 |
| 进程关系 | 任意进程 | 任意进程 | 仅亲缘进程 | 任意进程（需知道 PID） |
| 持久性 | 分离后需重新映射 | 内核维护 | 随进程终止销毁 | 瞬时触发 |
| 典型应用 | 高频数据交换（视频处理） | 微内核 | Shell 管道 | 事件通知 |

## CPU 调度与上下文切换

### 调度的基本概念

调度分为三个层次：

| 层次 | 要做什么 | 调度发生在 | 发生频率 | 对进程状态的影响 |
|---|---|---|---|---|
| **高级调度（作业调度）** | 按某种规则从**后备队列**中选择合适的作业调入内存，为其创建进程 | 外存 → 内存（面向作业） | **最低** | 无 → 创建态 → 就绪态 |
| **中级调度（内存调度）** | 按某种规则从**挂起队列**中选择合适的进程将其数据调回内存 | 外存 → 内存（面向进程） | 中等 | 挂起态 → 就绪态等 |
| **低级调度（进程调度 / CPU 调度）** | 按规则从**就绪队列**中选择一个进程为其分配处理机 | 内存 → CPU | **最高** | 就绪态 → 运行态 |

- 高级调度主要用于**多道批处理系统**；**每个作业只调入一次、调出一次**；作业调入时建立 PCB，调出时才撤销 PCB。
- 中级调度即换入/换出（Swapping），目的是提高内存利用率和系统吞吐量。
- 低级调度是最基本的调度，**所有操作系统都必须有**。

### 调度的目标

| 指标 | 定义 | 说明 |
|---|---|---|
| **CPU 利用率** | $CPU利用率=\dfrac{CPU有效工作时间}{总时间}$ | 希望 CPU 尽可能忙碌 |
| **系统吞吐量** | $系统吞吐量=\dfrac{总共完成的作业数}{总共花费时间}$ | 短作业能提升吞吐量，长作业会降低吞吐量 |
| **周转时间** | $周转时间=作业完成时间-作业提交（到达）时间$ | 用户更关心单个作业的周转时间 |
| **平均周转时间** | $平均周转时间=\dfrac{各作业周转时间之和}{作业数}$ | 操作系统更关心整体表现 |
| **带权周转时间** | $带权周转时间=\dfrac{作业周转时间}{作业实际运行时间}$ | **必然 ≥ 1**，越小越好 |
| **平均带权周转时间** | $平均带权周转时间=\dfrac{各作业带权周转时间之和}{作业数}$ | 综合指标 |
| **等待时间** | 进程处于**就绪态**的时间之和 | CPU 调度算法只影响等待时间，不影响运行时间和 I/O 时间 |
| **响应时间** | 用户提交请求到系统**第一次产生响应**的时间 | 交互式系统衡量调度算法好坏的主要标准 |

:::warn 等待时间的口径
**等待时间只统计进程在就绪队列中等待 CPU 的时间之和**，不包括在后备队列中等待进入内存的时间（那属于另一指标），也不包括进程运行和 I/O 的时间。
:::

:::key 带权周转时间为什么必然 ≥ 1
因为 $周转时间 = 等待时间 + 运行时间 \ge 运行时间$，故 $\dfrac{周转时间}{运行时间} \ge 1$。
两个作业周转时间相同时，**实际运行时间更长的那个带权周转时间更小**，用户满意度更高。
:::

### 调度的实现

#### 调度器 / 调度程序

调度程序（Scheduler）由三部分组成：

| 组成部分 | 职责 |
|---|---|
| **排队器（Queuing）** | 按进程优先级、到达时间等因素把就绪进程排序并插入相应队列 |
| **分派器（Dispatcher）** | 根据调度程序选出的进程，从就绪队列中取出，把处理机分配给它 |
| **上下文切换器（Context Switcher）** | 把当前进程的内核上下文存入其 PCB，再从新进程 PCB 取出上下文装入 CPU |

**调度是一种决策行为，切换是一种执行行为。** 两者不一定同时发生（例如选出的下一个进程仍是当前进程时就不需要切换）。

#### 调度的时机

**会引起调度的事件：**

1. 当前进程**正常结束或异常终止**（运行 → 终止）；
2. 当前进程**主动阻塞**（如发起 I/O、P 操作阻塞自己，运行 → 阻塞）；
3. 当前进程**时间片用完**（运行 → 就绪）；
4. **有更高优先级的进程进入就绪队列**（创建新进程、I/O 完成唤醒阻塞进程等），当前进程被抢占（运行 → 就绪）；
5. **中断/异常/系统调用处理结束返回用户空间时**，内核检查"需要重新调度"标志，若有效则触发调度；
6. 就绪队列为空时刚来的第一个进程直接上处理机，**这也算一次 CPU 调度**。

**不能进行调度与切换的情况（必背）：**

1. **当前进程处于中断处理过程中**——中断处理涉及核心功能和关键资源，逻辑上不属于某一进程，不应被剥夺处理机；
2. **进程正在访问操作系统内核临界区**——如调度器访问就绪队列。若此时被切换，可能导致内核数据结构不一致；
3. **禁用中断（屏蔽中断）过程中**；
4. **原语执行过程中**——加锁、解锁、中断现场保护与恢复等原子操作不可中断，连中断都要屏蔽，更不能进行调度与切换。

:::warn 内核临界区 vs 用户级临界区
**只有内核临界区**才禁止调度。用户级临界区中允许调度：例如当前进程已请求到打印机（处于临界区），但它因等待 I/O 主动阻塞，此时完全可以进行调度。2012-30 题的答案就是"在进程处于临界区时不能进行处理机调度"这一说法**错误**（缺少"内核"二字）。
:::

内核中常通过 PCB 里的一个标志位（如 Linux 的 `TIF_NEED_RESCHED`）来延迟抢占：

- **设置标志位的时机**：时间片耗尽时；有更高优先级进程进入就绪态时（如 `fork()` 出优先级更高的子进程、I/O 完成后唤醒的进程优先级更高）；
- **响应标志位的时机**：中断/异常/系统调用处理结束返回用户空间时，内核检查该标志，有效则调用调度程序。

#### 抢占式与非抢占式

| 方式 | 定义 | 调度时机 | 特点与适用场景 |
|---|---|---|---|
| **非抢占式（非剥夺）** | 进程除非运行结束或自己主动放弃 CPU，否则不会被其他进程抢占 | 进程运行结束；进程主动阻塞 | 调度不频繁，系统开销小，吞吐量较大，CPU 利用率一般更高；**实时性差，一般用于批处理系统**，不适用于分时系统和大部分实时系统 |
| **抢占式（剥夺）** | 进程在执行中可能因时间片用完或有更高优先级进程进入就绪态而被抢占 CPU | 主动放弃 CPU；时间片用完；更高优先级进程就绪 | 调度频繁，实时性强，可防止进程长期独占处理器；**等待时间和响应时间更短，适用于分时系统和实时系统** |

:::key
若**不考虑 `yield` 等主动释放处理机的系统调用**，则非抢占式调度下**只会出现"运行 → 终止"和"运行 → 阻塞"，不可能出现"运行 → 就绪"**。
:::

#### 闲逛进程

**闲逛进程（Idle Process）**，又称空闲进程或空闲任务，在没有其他进程需要运行时占据 CPU，保证 CPU 始终有任务可执行。

特点：

1. **优先级最低**，一旦有其他进程需要 CPU 就立即让出；
2. **持续运行**，多数情况下只执行一个空循环，不执行任何实际操作；
3. **只运行在内核态下**；
4. **占用资源最小**，不需要 CPU 以外的资源，也不会阻塞。

#### 内核级线程与用户级线程的调度

- **用户级线程的调度**由用户态线程库完成：线程切换不需要陷入内核，开销小；但内核以**进程**为单位分配时间片，一个线程阻塞会导致整个进程阻塞。
- **内核级线程的调度**由内核完成：线程切换需要上下文切换、修改内存映像、使高速缓存（Cache）失效，开销大；但可以真正做到多处理机并行，且一个线程阻塞不影响其他线程。
- 在采用一对一或多对多模型的系统中，**调度的实际对象是线程**，进程只提供虚拟内存、全局变量等资源。

### CPU 调度算法

本节的算例统一使用下面这组进程（到达时刻、服务时间、优先级三列，**优先级数值越大优先级越高**）：

| 进程 | 到达时间 | 服务时间 | 优先级 |
|---|---|---|---|
| P1 | 0 | 5 | 2 |
| P2 | 1 | 4 | 4 |
| P3 | 2 | 2 | 1 |

#### 先来先服务（FCFS）

**算法步骤：** 按进程到达的先后顺序依次分配 CPU，直到进程执行完毕或被阻塞（例如请求 I/O），非抢占式。既可用于作业调度，也可用于进程调度。

**算例（t=0 起开始调度）：**

执行顺序：P1(0→5) → P2(5→9) → P3(9→11)。

| 进程 | 到达 | 服务 | 开始 | 完成 | 周转时间 | 带权周转时间 |
|---|---|---|---|---|---|---|
| P1 | 0 | 5 | 0 | 5 | 5 | 1.00 |
| P2 | 1 | 4 | 5 | 9 | 8 | 2.00 |
| P3 | 2 | 2 | 9 | 11 | 9 | 4.50 |

平均周转时间 $= (5+8+9)/3 = 7.33$；平均带权周转时间 $= (1+2+4.5)/3 = 2.50$。

**优点：** 简单、公平、实现容易，不会导致饥饿，对长作业（CPU 繁忙型）有利。
**缺点：** 排在长作业后面的短作业等待时间过长，**带权周转时间很大，对短作业不利**；I/O 繁忙型进程在等待 I/O 期间不能让出 CPU（严格先来后到），使 CPU 和设备利用率都低。

#### 短作业优先（SJF）/ 短进程优先（SPF）

**算法步骤（非抢占式）：** 每次调度时，在就绪队列中选择**估计运行时间最短**的作业/进程，把处理机分配给它，直到它完成或因某事件阻塞才释放处理机。

**算例（非抢占式）：**

t=0 只有 P1 到达，先运行 P1；P1 在 t=5 结束后，P2、P3 均已到达，选服务时间短的 P3(2) → P2(4)。

执行顺序：P1(0→5) → P3(5→7) → P2(7→11)。

| 进程 | 到达 | 服务 | 开始 | 完成 | 周转时间 | 带权周转时间 |
|---|---|---|---|---|---|---|
| P1 | 0 | 5 | 0 | 5 | 5 | 1.00 |
| P3 | 2 | 2 | 5 | 7 | 5 | 2.50 |
| P2 | 1 | 4 | 7 | 11 | 10 | 2.50 |

平均周转时间 $= (5+5+10)/3 = 6.67$；平均带权周转时间 $= (1+2.5+2.5)/3 = 2.00$。

**抢占式版本：最短剩余时间优先（SRTN）**

**算法步骤：** 每当有新进程进入就绪队列（或发生其他改变就绪队列的事件）就检查一次；比较新进程的**剩余执行时间**与当前运行进程的**剩余执行时间**，若新进程更短则立即抢占；若相等则按 FCFS 决定。

**算例（抢占式 SRTN）：**

t=0：只有 P1，P1 运行，剩余 5。
t=1：P2 到达（剩余 4）。P1 剩余 4，与 P2 剩余 4 相等，**不抢占**（按规定相等时按 FCFS，保持 P1）。
t=2：P3 到达（剩余 2）。P1 剩余 3 > 2，**P3 抢占**。
t=4：P3 完成。就绪队列中 P1 剩余 3、P2 剩余 4，选 P1。
t=7：P1 完成。运行 P2（剩余 4），到 t=11 完成。

执行顺序：P1(0→1) → P1(1→2) → P3(2→4) → P1(4→7) → P2(7→11)。

| 进程 | 到达 | 服务 | 完成 | 周转时间 | 带权周转时间 |
|---|---|---|---|---|---|
| P1 | 0 | 5 | 7 | 7 | 1.40 |
| P2 | 1 | 4 | 11 | 10 | 2.50 |
| P3 | 2 | 2 | 4 | 2 | 1.00 |

平均周转时间 $= (7+10+2)/3 = 6.33$；平均带权周转时间 $= (1.4+2.5+1.0)/3 = 1.63$。**SRTN 的平均等待时间和平均周转时间优于非抢占式 SJF。**

:::key 408 考试必须记住的细节
1. 题目未特殊说明时，"短作业/进程优先"**默认是非抢占式的**；
2. 在有前提条件"所有进程可同时运行"或"所有进程几乎同时到达"时，才能说 SJF 的平均等待时间、平均周转时间**最少**；若无此前提，应说**抢占式的 SRTN 平均等待时间、平均周转时间最少**；
3. 严格来说，该算法应叫"**最短下次 CPU 执行（shortest-next-CPU-burst）**"，因为调度取决于进程**下一次** CPU 执行的长度，而不是其总长度。
:::

**优点：** 平均等待时间、平均周转时间最短，可提高系统吞吐量。
**缺点：** 需要预先知道运行时间（实际不可靠，由用户提供）；对长作业不利，**可能造成长作业饥饿**；完全不考虑作业的紧迫程度。

#### 高响应比优先（HRRN）

**响应比：**

$$响应比=\frac{等待时间+要求服务时间}{要求服务时间}$$

**算法步骤：** 非抢占式。每次都只在当前运行的进程主动放弃处理机（正常/异常完成或主动阻塞）时才需要调度，此时计算就绪队列中所有进程的响应比，选择响应比最高者。

**算例：**

t=0：只有 P1，直接运行 P1 到 t=5。
t=5：就绪队列中有 P2（等待 4，服务 4）与 P3（等待 3，服务 2）。
$P2 响应比 = \dfrac{4+4}{4} = 2.00$；$P3 响应比 = \dfrac{3+2}{2} = 2.50$。选 P3。
t=7：P3 完成。P2 等待 6，$响应比 = \dfrac{6+4}{4} = 2.50$，运行 P2 到 t=11。

执行顺序：P1(0→5) → P3(5→7) → P2(7→11)。平均周转时间 $= (5+5+10)/3 = 6.67$，与本题的非抢占式 SJF 结果相同（巧合，因为 t=5 时 P3 响应比也最高）。

**优点：** 兼顾等待时间与服务时间——等待时间相同时服务时间短的优先（SJF 的优点）；服务时间相同时等待时间长的优先（FCFS 的优点）；长作业随着等待时间增加响应比不断提高，**不会饥饿**。
**缺点：** 需要知道服务时间；每次调度都要计算响应比，有一定开销。现实中不可实现，属于"理想型"算法。

#### 时间片轮转（RR，Round-Robin）

**算法步骤：** 就绪进程按 FCFS 排队；每次把 CPU 分配给队首进程，让它执行一个**时间片**（典型 20 ms ~ 50 ms）；时间片用完时由**时钟中断**通知 CPU，把该进程放到就绪队列**队尾**，再取队首进程执行；若进程在时间片内完成则直接撤离，并立即调度。

时间片轮转是**绝对抢占式**算法，进程未在时间片内运行完就会被强行剥夺处理机。计时依靠**时钟中断**：例如设时间片 10 ms、时钟中断周期 5 ms，则每次中断把该进程的剩余时间减 5 ms，减到 0 时内核就知道时间片用完、需要切换进程。**时间片越短，进程切换次数越多，系统开销越大**，真正用于运行用户进程的时间越少；影响时间片大小的主要因素是**系统响应时间、就绪队列中的进程数目、系统的处理能力**。做题时若要精确到"发生了几次调度"，还要把**被抢占进程放回队尾**这一动作单独计入。

**算例（时间片 = 2 ms）：**

| 时间区间 | 运行进程 | 说明 |
|---|---|---|
| 0–2 | P1 | t=1 P2 到达入队尾；t=2 P3 到达入队尾；P1 剩余 3，入队尾 |
| 2–4 | P2 | P2 剩余 2，入队尾 |
| 4–6 | P3 | P3 剩余 0，**完成，完成时间 6** |
| 6–8 | P1 | P1 剩余 1，入队尾 |
| 8–10 | P2 | P2 剩余 0，**完成，完成时间 10** |
| 10–11 | P1 | P1 **完成，完成时间 11** |

| 进程 | 到达 | 服务 | 完成 | 周转时间 | 带权周转时间 |
|---|---|---|---|---|---|
| P1 | 0 | 5 | 11 | 11 | 2.20 |
| P2 | 1 | 4 | 10 | 9 | 2.25 |
| P3 | 2 | 2 | 6 | 4 | 2.00 |

平均周转时间 $= (11+9+4)/3 = 8.00$；平均带权周转时间 $= (2.2+2.25+2.0)/3 = 2.15$。

:::warn RR 的两个做题要点
1. **若某一时刻进程 Pi 下处理机，同一时刻进程 Pj 到达，默认新到达的进程 Pj 先进入就绪队列**（即排在被剥夺的 Pi 之前）；
2. 时间片大小的影响：时间片**足够大**（所有进程都能在一个时间片内完成）时，RR **退化为 FCFS**；时间片**太小**会导致进程切换过于频繁，CPU 开销增大，真正用于用户进程的时间减少。时间片长短通常由**系统响应时间、就绪队列中的进程数目、系统的处理能力**决定。
:::

**优点：** 公平，响应快，**不会导致饥饿**，适用于分时操作系统，可实现人机交互。
**缺点：** 频繁的进程切换带来不小开销；不区分任务的紧急程度。

:::exam 真题考法
2024-30：10 个进程同时就绪，时间片 5 ms，队尾进程 P 只需 25 ms，求 P 的周转时间。P 需要 5 个时间片，每轮 10×5=50 ms，P 在队尾故每轮最后一个执行，共 5 轮，周转时间 = 5×50 = 250 ms（选 C）。
:::

#### 优先级调度

**算法步骤：** 每个进程/作业都有优先级，调度时选择优先级最高的进程。可用于作业调度、进程调度、I/O 调度。

- **非抢占式优先级调度**：只在进程主动释放处理机时调度；执行过程中若有更高优先级进程到来，只需将其插入就绪队列队头即可。
- **抢占式优先级调度**：就绪队列发生变化时就检查是否发起抢占，若有更高优先级进程进入则立即暂停当前进程，把处理机分配给它。
- **静态优先级**：创建进程时确定，之后一直不变（依据进程类型、资源要求、用户要求）。
- **动态优先级**：创建时给定初值，之后动态调整（依据占用 CPU 与就绪等待时间长短）。

**算例（非抢占式，数值越大优先级越高）：**

t=0：只有 P1，运行 P1。
t=5：P1 结束，P2（优先级 4）、P3（优先级 1）就绪，选 P2。
t=9：P2 结束，运行 P3 到 t=11。

| 进程 | 到达 | 服务 | 优先级 | 完成 | 周转时间 | 带权周转时间 |
|---|---|---|---|---|---|---|
| P1 | 0 | 5 | 2 | 5 | 5 | 1.00 |
| P2 | 1 | 4 | 4 | 9 | 8 | 2.00 |
| P3 | 2 | 2 | 1 | 11 | 9 | 4.50 |

**优先级设置原则（必背）：**

- **系统进程 > 用户进程**；
- **交互型（前台）进程 > 非交互型（后台）进程**；
- **I/O 繁忙型进程 > CPU 繁忙型（计算型）进程**——I/O 设备与 CPU 可并行工作，且 I/O 设备速度远比 CPU 慢，让 I/O 繁忙型进程优先可让设备尽早投入工作，提升资源利用率和吞吐量。

**动态优先级的调整时机：** 某进程在就绪队列中等待时间过长 → 提高其优先级；某进程占用处理机运行时间过长 → 降低其优先级；某进程频繁进行 I/O → 提高其优先级。

:::warn 降低优先级的合理时机
**只有在进程时间片用完时才适合降低其优先级**（2010 年真题答案）。刚完成 I/O 进入就绪队列时不应降低（它此前并未占用处理机）；长期处于就绪队列的进程应**提高**优先级以免饥饿；从就绪态转为运行态时不应降低。
:::

**优点：** 能区分紧急程度、重要程度，适用于实时操作系统，可灵活调整偏好。
**缺点：** 若源源不断有高优先级进程到来，**可能导致饥饿**。

#### 多级队列调度

把就绪队列按进程类型分成多个队列（例如前台/交互进程队列与后台/批处理进程队列），**每个队列内部可以使用不同的调度算法**，队列之间可以有固定的优先级（如只有高优先级队列为空时才调度低优先级队列），也可以按时间比例分配 CPU。

缺点：**进程一旦进入某个队列就不能在队列间移动**，若队列间采用固定优先级，低优先级队列中的进程仍可能饥饿。多处理机中这种单一调度策略的缺点更突出。

#### 多级反馈队列（MLFQ）

**算法步骤：**

1. 设置多个就绪队列，**优先级从高到低**（队列 1 最高）；各队列的**时间片从小到大**（例如队列 1 时间片 8 ms，队列 2 时间片 16 ms，队列 3 按 FCFS）；
2. 新进程一律进入**队列 1 队尾**，按 FCFS 等待调度；
3. 队列 1 中的进程若在一个时间片内完成则撤离；**若未完成则转入队列 2 队尾**；
4. 仅当第 1 级队列为空时才调度第 2 级队列；仅当第 1、2 级都为空时才调度第 3 级；
5. **若正在执行第 k 级队列的进程时，有更高优先级队列（1～k-1 级）的新进程到达，则被抢占，原进程放回第 k 级队列队尾**；
6. 处于最低优先级队列的进程按时间片轮转（或 FCFS）反复执行，不再降级；通过在低优先级队列中等待过久的进程提升到高优先级队列（"老化"）来防止饥饿。

**算例（2019-27 原型）：** 二级反馈队列，Q1 时间片 10 ms 用 RR，Q2 用短进程优先；Q1 优先，新进程先进 Q1，Q1 中执行完一个时间片未结束则转入 Q2。当前 Q1、Q2 为空，依次创建 P1（需 30 ms）、P2（需 20 ms）后立即开始调度。

- 0–10：P1 在 Q1 运行 10 ms，剩余 20 ms，转入 Q2 队尾；
- 10–20：P2 在 Q1 运行 10 ms，剩余 10 ms，转入 Q2 队尾；
- 此时 Q1 为空，调度 Q2（短进程优先）：P2 剩余 10 ms 先执行（20–30），再执行 P1 剩余 20 ms（30–50）。

P1 在 0–10 运行、10–30 就绪等待（20 ms）、30–50 运行，故 P1 等待时间为 20 ms；P2 在 0–10 就绪等待（10 ms）、10–20 运行，故 P2 等待时间为 10 ms。**平均等待时间 = (20+10)/2 = 15 ms。**

:::warn 2019 年这道题的踩坑点
算 P1 的等待时间时**极易漏掉"P2 在 Q1 执行的 10 ms 期间 P1 在等待"这一段**。必须把每个时刻谁在运行、谁在就绪逐段列出，再累加就绪时间。
:::

**优点：** 可动态调整进程优先级和时间片大小，兼顾多方面系统目标；能区分对待 CPU 密集型和 I/O 密集型进程（I/O 阻塞后回到原队列可保持较高优先级）；短作业周转时间短，一定程度上避免饥饿。
**缺点：** 算法设计复杂，极端情况下仍可能饥饿。

设计 MLFQ 需要考虑的因素（2020 年真题答案选"全部四项"）：**就绪队列的数量、就绪队列的优先级、各就绪队列的调度算法、进程在就绪队列间的迁移条件**。

#### 同一组进程用不同算法的完整对照表

仍用上面那组进程（P1：到达 0、服务 5；P2：到达 1、服务 4；P3：到达 2、服务 2），非抢占式算法中优先级的数值越大优先级越高：

| 算法 | 执行顺序 | P1 周转 | P2 周转 | P3 周转 | 平均周转 | 平均带权周转 | 是否可能饥饿 |
|---|---|---|---|---|---|---|---|
| FCFS | P1 → P2 → P3 | 5 | 8 | 9 | 7.33 | 2.50 | 否 |
| SJF（非抢占） | P1 → P3 → P2 | 5 | 10 | 5 | 6.67 | 2.00 | **是** |
| SRTN（抢占） | P1 → P3 → P1 → P2 | 7 | 10 | 2 | **6.33** | **1.63** | **是** |
| HRRN（非抢占） | P1 → P3 → P2 | 5 | 10 | 5 | 6.67 | 2.00 | 否 |
| RR（时间片 2） | P1 → P2 → P3 → P1 → P2 → P1 | 11 | 9 | 4 | 8.00 | 2.15 | 否 |
| 优先级（非抢占） | P1 → P2 → P3 | 5 | 8 | 9 | 7.33 | 2.50 | **是** |

:::key 从对照表能读出的三条规律
1. **平均周转时间最短的是抢占式 SRTN，其次是非抢占式 SJF/HRRN**——只要题目问"平均等待时间/平均周转时间最少"，先考虑 SRTN（有"同时到达"前提时可答 SJF）；
2. **RR 的平均周转时间通常较大**，但它的优势在于**响应时间短、公平、不饥饿**；
3. **FCFS 与优先级调度的本算例结果相同**只是巧合（恰好优先级顺序与到达顺序一致），不要据此认为两者等价。
:::

### 多处理机调度

#### 与单处理机调度的区别

多处理机调度要额外解决两个问题：**亲和性**与**负载均衡**。

1. **亲和性（Affinity）**：让一个进程尽量总在同一个 CPU 上运行，以保持 Cache 命中率，避免频繁到内存取数据。**软亲和**指尽量让进程在同一 CPU 上运行但不强制；**硬亲和**可写入 PCB，表示该进程只能由某一个 CPU 运行。
2. **负载均衡**：各 CPU 的繁忙程度应大致相等，不能一个 CPU 长期空闲而另一个长期繁忙。

#### 两种就绪队列组织方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **公共就绪队列** | 所有进程共享一个就绪队列 | 队列需要上锁互斥（防止多个 CPU 同时抢同一个进程），**天然实现负载均衡** | **亲和性差**（进程可能被不同 CPU 调度） |
| **私有就绪队列** | 每个 CPU 拥有自己的就绪队列 | **天然解决亲和性问题** | 需要额外的迁移机制实现负载均衡 |

负载均衡通过**迁移**实现：**推迁移（push migration）** 是系统程序把负载高的 CPU 上的进程推到负载低的 CPU 上；**拉迁移（pull migration）** 是空闲 CPU 从超载 CPU 的就绪队列中"拉"一些进程过来运行。推迁移和拉迁移可以并行执行。

### 上下文及其切换机制

#### 上下文的组成

**上下文（Context）** 是进程/线程在某一时刻的处理器状态，主要包含：

- 程序计数器 PC（下一条要执行的指令地址）；
- 通用寄存器组的值；
- 栈指针 SP、栈基址寄存器的值；
- 程序状态字 PSW、标志寄存器；
- 地址空间相关寄存器（页基址寄存器 / 页目录基址寄存器 PDBR）；
- 其他控制寄存器、条件码寄存器。

**上下文的保存位置是 PCB，不是栈。**（进程的内核栈只保存函数调用信息与中断现场；PCB 中保存的才是切换时恢复的上下文。）

#### 进程切换的完整过程

1. 挂起当前进程，把它的处理机上下文保存到它的 PCB 中；
2. 把该 PCB 移入相应队列（就绪队列或阻塞队列）；
3. 由调度程序选择另一个进程，**更新它的 PCB**：把状态从就绪改为运行，记录本次开始运行的时间（用于统计 CPU 占用率、响应时间），重置或更新与调度策略相关的字段（如把时间片重置为系统规定的初始值）；
4. 从新进程的 PCB 中取出上下文并装入 CPU 各寄存器；
5. 跳转到新进程的程序计数器所指向的位置继续执行。

Linux 的实现顺序正是如此：`__schedule()` 先 `pick_next_task()` 选出下一个进程，若 `prev != next` 则调用 `context_switch()`：先 `switch_mm_irqs_off()` **切换地址空间（页表）**，再 `switch_to()` **切换寄存器上下文**。

:::key 为什么"进程切换"必须切换地址空间，而"中断处理"不用
中断处理前后仍是同一个进程、同一个地址空间，只是从用户态陷入内核态（用户栈切到内核栈），**不涉及地址空间切换**，因此中断处理程序的执行**不算进程切换**。进程切换必须切换页表，所以涉及地址空间切换。
:::

#### 切换的开销

- 上下文切换是**纯开销**，切换期间 CPU 不做任何有用工作；
- 页表切换（地址空间切换）在开销中占比很大，还要加上 TLB/Cache 失效的代价；
- 保存和恢复寄存器需要执行多条 `load`/`store` 指令，比较耗时；
- **优化手段**：设置两组寄存器组（一组供内核、一组供用户），切换时只需改指针，无须搬移寄存器内容。

#### 中断响应、模式切换与进程切换的区别

| 对比项 | 中断响应 | 进程切换 |
|---|---|---|
| 上下文保存/恢复的时机 | **分开进行**，分别位于中断响应和中断返回中 | **连续进行**（两个不同进程之间） |
| 保存的上下文 | 中断前进程执行的上下文（可能是用户上下文） | 一定是**内核态**下的上下文 |
| 是否切换地址空间 | **不涉及** | **涉及**（切换页表） |
| 特权级 | 可能发生特权级切换 | 全程在内核态下进行 |

**模式切换 vs 进程切换：**

- **模式切换**发生在用户态响应中断/异常（用户态 → 核心态）和处理完中断异常后返回用户态（核心态 → 用户态）两种情况；它是**同一进程**在自身用户态和内核态之间的切换，二者**共用地址空间**，涉及特权级切换与用户栈/内核栈切换，只需保存和恢复**用户态上下文**（通用寄存器、PC、PSW、SP 等断点和现场信息）；
- **进程切换**发生在内核态，是从一个进程的内核态切换到另一个进程的内核态。PCB 中保存的是进程在**内核态**被切换时的完整状态；用户态的恢复依赖**中断返回机制**，不是进程切换的直接结果；
- 因此：**任何进程的切换都依靠内核完成；进程的调度和切换均发生在内核态下**（注意：用户级线程之间的切换可以由线程库在用户态完成，这是特例）。

:::warn 典型错误认知
错误："进程切换是直接在用户态之间切换，PCB 中保存的是用户态上下文。"
正确：
1. 切换永远发生在两个进程的**内核态**之间；
2. PCB 保存的是进程在内核态被切换时的完整状态；
3. 用户态恢复依赖中断返回机制，不是进程切换的直接结果。
:::

:::exam 真题考法
2024-25：支持页式存储管理的系统中，进程切换时要执行的操作包括"更新程序计数器的值""更新栈基址寄存器的值""更新页基地址寄存器的值"——三项都要做。2018 年曾考"同一进程不同线程切换时页基址寄存器是否需要改动"（不需要，因为共用同一虚拟地址空间，原有 TLB 不会失效）。
:::

## 同步与互斥

### 同步与互斥的基本概念

#### 临界资源与临界区

**临界资源（Critical Resource）**：一个时间段内只允许一个进程使用的资源。物理设备（摄像头、打印机）是临界资源；共享变量、数据、内存缓冲区同样是临界资源。

**临界区（Critical Section）**：**进程中访问临界资源的那段代码**。注意一个临界资源的相关临界区是由**不同进程各自的临界区**共同构成的——各进程对同一临界资源的操作不同，代码段自然也不同。

对临界资源的互斥访问在逻辑上分为四个部分：

| 部分 | 作用 |
|---|---|
| **进入区** | 检查能否进入临界区，并设置正在访问临界区的标志 |
| **临界区** | 访问临界资源的代码 |
| **退出区** | 将正在访问临界区的标志清除 |
| **剩余区** | 代码的其余部分 |

:::key 可重入代码
**可重入代码**是可以被重复调用执行、中断后重新执行也不会出错的代码，可同时被多个进程调用，**不属于临界资源**；可重入代码不允许被任何进程修改。进程映像中的**程序段若被共享，必须是可重入代码**。
:::

#### 同步与互斥

| 概念 | 核心思想 | 定义 | 等待原因 |
|---|---|---|---|
| **互斥（Mutual Exclusion）** | **竞争** | 多个进程因争夺**同一个**、**临时的**、**不可共享的**资源而产生的制约关系（间接制约） | **资源正忙** |
| **同步（Synchronization）** | **协作** | 多个进程为共同完成任务，在执行**次序**上需要遵循某种先后顺序而产生的制约关系（直接制约） | **前驱任务未完成，条件不满足** |

#### 四条原则

| 原则 | 含义 |
|---|---|
| **空闲让进** | 临界区空闲时，应允许一个请求进入临界区的进程立即进入 |
| **忙则等待** | 已有进程进入临界区时，其他试图进入的进程必须等待（即互斥） |
| **有限等待** | 对请求访问的进程，应保证它能在有限时间内进入临界区（不会饥饿） |
| **让权等待** | 进程不能进入临界区时，应立即释放处理机（主动阻塞），防止忙等 |

:::key
**前三条是必须实现的；"让权等待"是可选原则**——Peterson 算法、TSL/Swap 指令、自旋锁都不满足让权等待，但它们实现互斥是正确的。2020-32 题的答案就是"仅 Ⅰ、Ⅱ、Ⅲ"。
:::

:::exam 真题考法
2020-32 直接考四条原则；2018-32 考"下列同步机制中可以实现让权等待的是"（答案：信号量方法）；2016-27 考 TSL 实现互斥的性质（答案：等待进入临界区的进程不会主动放弃 CPU）。
:::

### 基本的实现方法

#### 软件方法

**判断某一软件方法是否满足四条原则的统一方法：**

- 判断**空闲让进**：观察是否存在"表达式 1 与表达式 2 同时成立"的可能；再看没有对方进程时，本进程能否通过循环进入临界区；
- 判断**忙则等待**：看本进程通过了 while 循环但还没进入临界区时切换到对方，对方能否也通过 while 循环；
- 判断**有限等待**：本进程卡在进入区时，新来的同类进程能否不断抢先进入；
- **所有软件方法都不满足让权等待**：进入区的 `while(表达式);` 循环体为空语句，一直空转，这就是**忙等**。

**（1）单标志法**

```c
// 共享整型变量
int turn = 0;   // turn = i 表示允许进程 Pi 进入临界区

/* 进程 P0 */
while (TRUE) {
    while (turn != 0);   // 若 turn 不等于本进程编号，则循环等待
    临界区;
    turn = 1;            // 访问完毕，把权限让给对方
    剩余区;
}
```

```c
/* 进程 P1 */
while (TRUE) {
    while (turn != 1);
    临界区;
    turn = 0;
    剩余区;
}
```

- 满足**忙则等待**；
- 两个进程必须**交替**进入临界区。若其中一个进程不再进入临界区，另一个进程因得不到授权也永远进不去，**违背"空闲让进"**；
- 使用 `while` 判断作为进入区，**违背"让权等待"**。

**（2）双标志先检查**

```c
bool flag[2];           // flag[i] = TRUE 表示进程 Pi 想进入临界区
flag[0] = flag[1] = FALSE;

/* 进程 P0 */
while (TRUE) {
    while (flag[1] == TRUE);   // 先检查对方是否想进
    flag[0] = TRUE;            // 对方不想进，自己上锁
    临界区;
    flag[0] = FALSE;
    剩余区;
}
```

- 解决了单标志法"必须交替进入"的缺点，可以连续使用；
- **缺点**：若 P0 通过了 while 检查但尚未执行 `flag[0] = TRUE` 时发生进程切换，P1 也能通过检查并上锁，两个进程**可能同时进入临界区**，**违背"忙则等待"**。根源在于"检查"与"上锁"不是一气呵成的，**并发程序不能保证 load 和 store 的原子性**。

**（3）双标志后检查**

```c
/* 进程 P0 */
while (TRUE) {
    flag[0] = TRUE;            // 先上锁
    while (flag[1] == TRUE);   // 再检查对方
    临界区;
    flag[0] = FALSE;
    剩余区;
}
```

- 解决了先检查法可能同时进入的问题；
- **缺点**：若 P0 置 `flag[0] = TRUE` 后发生切换，P1 也置 `flag[1] = TRUE`，则双方都在 while 中无限轮询，谁也进不去，**违背"空闲让进"和"有限等待"**。

**（4）Peterson 算法（正确的软件方案）**

```c
int turn;            // 表示该让谁进入临界区
bool flag[2];        // 表示进程是否希望进入临界区
flag[0] = flag[1] = FALSE;

/* 进程 P0 */
while (TRUE) {
    flag[0] = TRUE;                      // 1. 表示本进程希望进入
    turn = 1;                            // 2. 礼让 P1
    while (flag[1] == TRUE && turn == 1); // P1 想进且轮到 P1，则等待
    临界区;
    flag[0] = FALSE;                     // 3. 退出临界区
    剩余区;
}
```

```c
/* 进程 P1 */
while (TRUE) {
    flag[1] = TRUE;
    turn = 0;
    while (flag[0] == TRUE && turn == 0);
    临界区;
    flag[1] = FALSE;
    剩余区;
}
```

逐条验证四条原则：

- **空闲让进**：若 P1 不打算进入临界区，则 `flag[1] = FALSE`，P0 的 while 条件为假，可以立即进入，不会像单标志法那样"临界区空闲却进不去"；
- **忙则等待**：双方都希望进入时由 `turn` 决定，双方互相礼让，后礼让的一方等待，保证同一时刻只有一个进程在临界区；
- **有限等待**：P0 进入临界区后，P1 等待；P0 出来时会置 `flag[0] = FALSE`，P1 随即可以进入，不会饥饿；
- **不满足让权等待**：进不去时一直执行 while 空循环，直到时间片用完。

**软件方法小结：**

| 方法 | 思想 | 违背的原则 |
|---|---|---|
| 单标志法 | 引入共享变量 `turn`，循环检查 `turn` 是否为本进程编号 | **空闲让进**（和让权等待） |
| 双标志先检查 | 引入 `flag` 数组，**先检查**对方再上锁 | **忙则等待** |
| 双标志后检查 | 先设置自身 `flag`，**再检查**对方 | **空闲让进、有限等待** |
| Peterson 算法 | 引入 `turn` 与 `flag`，检查两个条件 | **让权等待**（且只适用于两个进程） |

#### 硬件方法

**（1）中断屏蔽方法**

```c
...
关中断;
临界区;
开中断;
...
```

思想：利用"开/关中断指令"实现，与**原语**的实现思想相同——某进程开始访问临界区到结束访问为止都不允许被中断，也就不可能发生进程切换，因此不可能出现两个进程同时访问临界区。由于进程切换通常由中断或系统调用触发，对于**单处理机**环境，只需在进入临界区时禁止中断，就能保证当前指令流有序执行、不被抢占。非抢占式内核常采用此方法。

**优点：** 简单、高效。
**缺点：**

- 要求所有调用线程都能执行特权操作，因此**只适用于操作系统内核进程，不适用于用户进程**（开/关中断是特权指令，2021 年真题考点）；
- **只能用于单处理机环境**。多处理机下，即使关闭本 CPU 的中断，其他 CPU 上的线程依然可以进入临界区；
- 频繁关中断会影响系统时钟的更新与时间片计时，因此只能在**很短的时间**内禁用中断。

**（2）TestAndSet 指令（TS，也称 TSL）**

TSL 指令由硬件实现，执行是**原子**的、不可被中断，即使两条 TSL 指令在不同 CPU 上同时执行，也会按任意次序顺序执行。功能是"测试并设置"：

```c
// 硬件原子指令（伪代码）：返回 lock 的旧值，同时把 lock 置为 TRUE
bool TestAndSet(bool *lock) {
    bool old = *lock;
    *lock = TRUE;
    return old;
}
```

1. 从内存单元读取值；
2. 测试该值是否为 TRUE，返回真或假；
3. 把内存单元的值设置为 TRUE。

```c
do {
    ...
    while (TSL(&lock));   // 上锁失败则一直轮询
    critical section;      // 临界区
    lock = FALSE;          // 退出区解锁
    ...
} while (TRUE);
```

分析：若开始时 `lock` 为 FALSE，TSL 返回 FALSE 并把 `lock` 置为 TRUE，while 条件不满足，进程进入临界区；若开始时 `lock` 为 TRUE，TSL 返回 TRUE，while 条件满足，一直轮询，直到临界区中的进程在退出区解锁或自己时间片耗尽下处理机。

相比软件方法，TSL 把**"上锁"和"检查"用硬件变成了一气呵成的原子操作**，避免了双标志先检查法的错误。

**（3）Swap 指令（EXchange / XCHG）**

```c
bool key = TRUE;
do {
    key = TRUE;
    do {
        Swap(&key, &lock);   // 原子地交换 key 与 lock
    } while (key == TRUE);
    critical section;
    lock = FALSE;
    ...
} while (TRUE);
```

思想：先用 `key` 记录之前是否被上锁，然后自己主动上锁（`lock = TRUE`），再检查 `key` 是否是 TRUE；若 `key` 为 FALSE，说明自己是第一个上锁的，可以进入临界区。

逻辑上 Swap 与 TSL 并无太大区别。

**两种硬件指令的优缺点：**

- **优点**：实现简单，容易验证正确性；适用于任意数目的进程，**单处理机和多处理机都适用**；支持系统中有多个临界区，只需为每个临界区设立一个布尔型变量；
- **缺点**：**不满足"让权等待"**，无法进入临界区的进程会占用 CPU 循环执行 TSL/Swap，导致忙等；从等待进程中随机选择进入临界区，有的进程可能一直选不上，**导致饥饿**。

:::warn TSL 的三个关键结论（2016 年真题）
1. 等待进入临界区的进程**不会主动放弃 CPU**（所以它处于就绪态/运行态，不是阻塞态）；
2. TSL 机制下**不存在阻塞态的进程**，会一直轮询；
3. `while (TSL(&lock))` 应在**开中断**状态下执行——TSL 本身是一条原子指令，不需要关中断；若整段程序都关中断，则可能很久都不响应中断。
:::

### 锁

#### 互斥锁

用互斥锁保护临界区：进程在进入临界区时 `acquire()` 获取锁，退出时 `release()` 释放锁。每个锁有一个 `locked` 变量表示锁是否可用。

**互斥锁必须用硬件机制实现**，因为 `acquire()` 中"检查锁是否可用"和"上锁"之间若发生进程切换，可能违背忙则等待，让多个进程进入临界区。实现方式有两种：获取锁之前关中断（只对单处理机有效）；或者采用**原子操作指令**（TSL / Swap）。

#### 自旋锁与忙等待

**自旋锁**：申请锁失败后一直循环申请，直到成功。

```c
// 使用 TSL 指令实现自旋锁
struct Lock { int locked; };   // 0 表示未被占用，1 表示被占用

acquire(Lock *lock) {
    while (TestAndSet(&lock->locked)) {
        // CPU 在此"忙等待"或"自旋"
    }
}

release(Lock *lock) {
    lock->locked = 0;
}
```

:::key 自旋锁申请失败时进程处于什么状态
**就绪态或运行态**。若时间片没用完，则处于运行态一直尝试获取锁；若时间片用完被剥夺处理机，则处于就绪态。**注意：单处理器上自旋锁需要抢占式调度器才能使用**，否则自旋的线程永远不会放弃处理机。
:::

**自旋锁特性总结：**

- 具有随机性，不能保证按先来后到顺序使用 CPU 资源；
- 需要忙等，时间片用完才下处理机，**违反"让权等待"**；
- 等待锁时**没有上下文切换**（上下文切换开销很大），因此在多处理器系统中若上锁时间很短，等待代价很低；
- **常用于多处理机系统**，一个核忙等，其他核照常工作并能快速释放临界区；
- **不适用于单处理机系统**（忙等过程中不可能解锁），即使有抢占式调度器性能开销也很大；
- **不提供任何公平性保证**，自旋的线程在竞争条件下可能永远自旋，**可能导致饿死**。

**无忙等待锁**：申请锁失败后主动阻塞自己，加入该锁的等待队列并让出处理机；其他进程释放锁后从等待队列中唤醒一个进程加入就绪队列。

```c
struct Lock {
    int locked;
    waitqueue q;         // 该锁对应的等待队列
};

acquire(Lock *lock) {
    while (TestAndSet(&lock->locked)) {
        block the process into q;   // 主动阻塞
        schedule();                 // 发起调度
    }
}

release(Lock *lock) {
    lock->locked = 0;
    wake a process from q;          // 从等待队列唤醒一个阻塞进程
}
```

无忙等待锁特性：由于有等待队列，可以实现申请锁进程的**先来后到，较为公平**；未申请到锁时不需要忙等，但要阻塞自己并切换其他进程，**存在上下文切换的代价**。

:::warn 忙等待的代价
忙等的本质是"用 CPU 时间换取不发生上下文切换"。因此：
- **临界区很短、多处理器**→ 自旋锁划算；
- **临界区很长、单处理器**→ 自旋锁极其浪费，应使用阻塞式锁。
:::

### 信号量

#### 整型信号量

用**一个整数型变量**作为信号量，表示系统中某种资源的数量。与普通整型变量的区别是：对信号量的操作只有三种——**初始化、P 操作、V 操作**，不能进行值判断。

```c
int S = 1;   // 整型信号量，初值表示资源数量

void wait(int S) {          // P 操作，相当于进入区
    while (S <= 0);         // 资源不够就一直轮询（忙等）
    S = S - 1;              // 申请到一个资源
}

void signal(int S) {        // V 操作，相当于退出区
    S = S + 1;              // 释放一个资源
}
```

缺点：`wait` 中用 `while (S <= 0)` 检测资源是否可用，若资源不够则一直轮询，**违反"让权等待"**。

#### 记录型信号量

用一个记录型数据结构表示信号量，**不存在忙等现象，遵循让权等待**。

```c
typedef struct {
    int value;          // 剩余资源数
    struct PCB *L;      // 等待队列（PCB 链表，通常用 FIFO）
} semaphore;

void wait(semaphore S) {          // P 操作
    S.value--;                    // 先减 1
    if (S.value < 0) {            // 资源已不够分配
        block(S.L);               // 自我阻塞，由运行态 -> 阻塞态
    }                             // 并插入该信号量的等待队列
}

void signal(semaphore S) {        // V 操作
    S.value++;                    // 先加 1
    if (S.value <= 0) {           // 仍有进程在等待该资源
        wakeup(S.L);              // 唤醒等待队列中的第一个进程
    }                             // 被唤醒进程由阻塞态 -> 就绪态
}
```

**物理意义（必背）：**

- `S.value > 0`：表示**当前还可用的资源数量**；
- `S.value = 0`：表示资源刚好用完，**没有进程在等待**（注意：不是"没有资源"）；
- `S.value < 0`：表示**资源已分配完，且有 |S.value| 个进程正在等待该资源**。

出现负值的原因是 `wait()` 中**先递减再判断**，互换了递减和测试的顺序；而在整型信号量中信号量的值不能为负。

**举例说明 `signal()` 中 `S.value <= 0` 的含义：**

设 `sem = 1`：
1. 第一个线程 P 操作后，`sem = 0`（刚好拿走最后一个资源）；
2. 第二个线程 P 操作后，`sem = -1`（资源不够，该线程阻塞在等待队列，等待队列长度 1）；
3. 第三个线程 P 操作后，`sem = -2`（第三个线程也阻塞，等待队列长度 2）；
4. 第一个线程执行 V 操作后，`sem = -1`，因为 `sem <= 0`，说明**仍有进程在等待**，于是唤醒第二个线程；第二个线程执行完后释放，`sem = 0`，此时仍有第三个线程在等待，再唤醒它；最后第三个线程释放后 `sem = 1`，回到初始状态。

:::key 三个必须记住的结论
1. **P(S)、V(S) 都是原语，执行必须一气呵成、不可被打断**。对信号量的访问必须是互斥的，因为信号量 S 是多个进程共享的变量，多个进程都可对它读写——这本身就是一个临界区问题。单处理机上可通过关中断实现；多处理机上需要用自旋锁或 `compare_and_swap` 保证原子性。
2. **考试中出现 P(S)、V(S) 操作，除非特殊说明，否则默认 S 为记录型信号量。**
3. **信号量是结构体，只能进行 P/V 操作，不能进行值判断。** 写 `if (bowl >= 1)` 是极其错误的。
:::

#### 用信号量实现互斥

**步骤：**

1. 分析并发进程的关键活动，划定临界区；
2. 设置**互斥信号量 `mutex`，初值为 1**；
3. 在进入区 `P(mutex)`——申请资源；
4. 在退出区 `V(mutex)`——释放资源。

```c
semaphore mutex = 1;   // 互斥信号量

P1() {
    ...
    P(mutex);          // 进入区：申请锁
    临界区;
    V(mutex);          // 退出区：释放锁
    ...
}
```

**注意：** 对不同的临界资源要设置不同的互斥信号量；**P、V 操作必须成对出现**——缺少 `P(mutex)` 不能保证互斥，缺少 `V(mutex)` 会导致资源永不释放、等待进程永不被唤醒；P、V 必须**夹紧**使用互斥资源的行为，中间不能有其他冗余代码。

#### 用信号量实现同步

**步骤：**

1. 分析什么地方需要实现同步关系，即必须保证"一前一后"执行的两个操作；
2. 设置**同步信号量 S，初值为 0**；
3. 在**"前操作"之后执行 V(S)**；
4. 在**"后操作"之前执行 P(S)**。

```c
semaphore S = 0;   // 同步信号量

P1() {
    ...
    语句 x;         // 前操作
    V(S);
    ...
}

P2() {
    ...
    P(S);
    语句 y;         // 后操作，要使用 x 的运行结果
    ...
}
```

同步信号量的初值不一定是 0，也可以是正整数，取决于"所期待的条件是否已经发生"。例如初值为 2 时，前驱进程释放两次后资源数达到 2，后进程才能继续。

#### 用信号量实现前驱关系

每一对前驱关系就是一个同步问题，因此：

1. **为每一对前驱关系各设置一个同步信号量，初值均为 0**；
2. 在"前操作"之后对相应的同步信号量执行 **V** 操作；
3. 在"后操作"之前对相应的同步信号量执行 **P** 操作。

例如前驱图 $S_1 \to S_2$、$S_1 \to S_3$、$S_2 \to S_4$、$S_3 \to S_4$，则需 4 个信号量 $a, b, c, d$（初值全 0），$S_1$ 末尾写 `V(a); V(b);`，$S_2$ 开头写 `P(a);`、末尾写 `V(c);`，$S_3$ 开头写 `P(b);`、末尾写 `V(d);`，$S_4$ 开头写 `P(c); P(d);`。

:::key 三句话总结 P/V 模板
**互斥**：`P(mutex)` … 临界区 … `V(mutex)`，`mutex` 初值 1，夹紧临界区。
**同步**：前操作之后 `V(S)`，后操作之前 `P(S)`，`S` 初值 0。
**前驱**：每对前驱关系一个信号量，初值 0，前驱末尾 V，后继开头 P。
:::

### 条件变量

#### 为什么要引入条件变量

用信号量解决同步问题虽然强大，但**同步问题越复杂、条件越多，需要的信号量就越多**，必须非常谨慎地处理信号量之间的顺序，否则很容易造成死锁。为此产生了**管程（Monitor）**：管程把共享数据结构和对它的操作封装起来，并**保证每次只有一个进程使用管程，天然实现互斥**，程序员无需自己实现互斥；管程还提供**条件变量**，让程序员灵活实现同步。

管程的组成：管程名称、局部于管程的共享数据结构说明、对该数据结构进行操作的一组过程（函数）、对局部于管程的共享数据设置初始值的语句。

管程的特性：

- 把操作函数封装在管程内（类似 Java 的类），外部进程只能通过调用操作函数来获取和释放资源；
- **每次只允许一个进程使用管程，天然实现互斥**；
- 管程内的数据只能被管程内的操作函数修改；
- 管程是被进程调用的，进程通过调用管程中定义的操作来访问共享资源；
- 管程是**语法范围**（语言级别的抽象），由编程语言的语法定义；
- **无法创建和撤销**，生命周期与程序一致。

#### 条件变量的用法

条件变量的本质是"进程进入管程后因某原因被阻塞，把该原因定义为一个条件变量"。不同进程被阻塞的原因可能不同，所以可以有多个条件变量；每个条件变量保存一个等待队列。

```c
// 在管程内部
condition x;                  // 声明一个条件变量

// 资源不够时（注意：先判断资源是否够，再决定是否 wait）
while (资源不够) {
    x.wait();                 // 当前进程阻塞在该条件变量上，并释放管程
}
// 资源可用时
x.signal();                   // 唤醒等待在该条件变量上的一个进程
```

对条件变量使用 `while` 循环而不是 `if`，可以解决**假唤醒（spurious wakeup）**问题。

#### 条件变量与信号量的区别

| 对比项 | 信号量 | 条件变量 |
|---|---|---|
| 是否有值 | **有值**，代表资源数量 | **没有值**，只实现排队等待和唤醒功能（资源数由管程内的共享数据结构记录） |
| 操作 | `wait(S)` / `signal(S)`（P/V） | `x.wait()` / `x.signal()` |
| 释放操作的影响 | **V 操作一定会改变信号量的值** | **`signal` 操作可能不产生任何影响**（当没有进程因该条件变量阻塞时） |
| 是否需要额外互斥 | 需要自己保证 P/V 原子性 | 管程天然实现互斥，程序员无需自己处理 |

:::key
管程中的 `signal` 操作和信号量的 `V` 操作只是**类似**，而不是**相同**——这是高频易错点。
:::

### 经典同步问题

#### 生产者-消费者问题

**问题描述：** 一组生产者进程和一组消费者进程共享一个**初始为空、大小为 n 的缓冲区**。生产者每次生产一个产品放入缓冲区，消费者每次从缓冲区取出一个产品。

三条约束：

1. 只有**缓冲区没满**时，生产者才能放入产品，否则必须等待（**同步关系**）；
2. 只有**缓冲区不空**时，消费者才能取出产品，否则必须等待（**同步关系**）；
3. 缓冲区是**临界资源**，各进程必须**互斥访问**（**互斥关系**）。

**信号量设置：**

```c
semaphore mutex = 1;    // 互斥访问缓冲区
semaphore empty = n;    // 空闲缓冲区的数量（同步）
semaphore full  = 0;    // 已有产品的数量（同步）
```

**完整伪代码：**

```c
semaphore mutex = 1;
semaphore empty = n;
semaphore full  = 0;

producer() {
    while (1) {
        生产一个产品;
        P(empty);            // 1. 申请一个空闲缓冲区（同步 P）
        P(mutex);            // 2. 申请缓冲区互斥锁（互斥 P）
        把产品放入缓冲区;
        V(mutex);            // 3. 释放缓冲区互斥锁
        V(full);             // 4. 产品数加 1，唤醒可能的消费者
    }
}

consumer() {
    while (1) {
        P(full);             // 1. 申请一个产品（同步 P）
        P(mutex);            // 2. 申请缓冲区互斥锁
        从缓冲区取出一个产品;
        V(mutex);            // 3. 释放缓冲区互斥锁
        V(empty);            // 4. 空闲缓冲区加 1，唤醒可能的生产者
        消费产品;
    }
}
```

**为什么这样设计（关键分析）：**

1. **必须先对同步信号量 P，再对互斥信号量 P**（即 `P(empty)` 在 `P(mutex)` 之前）。若颠倒顺序：假设缓冲区已满，生产者先 `P(mutex)` 拿到锁，再 `P(empty)` 时发现 `empty = 0` 而被阻塞；此时消费者想进入临界区消费，却因为 `mutex = 0` 而被阻塞。双方互相等待对方唤醒自己 → **死锁**。
2. **V 操作的顺序可以交换**，因为 V 操作不会引起阻塞（`V(mutex)` 与 `V(full)` 谁先谁后都不影响正确性）。
3. **"生产一个产品"和"消费产品"这两个动作最好放在临界区之外**。虽然从逻辑上也可以放进临界区，但那样会**延长临界区的长度**，降低并发度、降低系统效率。
4. 注意唤醒关系：消费者可以唤醒生产者（缓冲区空时），**生产者也可以唤醒生产者**（缓冲区满时第二个生产者阻塞，第一个生产者完成后将它唤醒）。

**单缓冲与多缓冲的区别：** 当 n = 1（单缓冲区）时，`empty` 与 `full` 的取值只能是 0 或 1，此时 `empty` 或 `full` 这两个一般信号量**已经天然充当了互斥信号量**，可以省去 `mutex`。但当缓冲区数量 ≥ 2 时，**必须用 `mutex` 实现互斥访问**。

:::warn 生产者-消费者问题的四个易错点
1. **顺序不能颠倒**：同步 P 必须在互斥 P 之前；
2. **P、V 必须成对**：漏掉 `V(mutex)` 会让缓冲区永不释放；
3. **单缓冲区可省 mutex，多缓冲区不可省**；
4. 题目中的"产品"/"数据"就是普通资源，不要与后面的信号混淆。
:::

**多生产者多消费者（放水果问题）：**

爸爸专放苹果，妈妈专放橘子，儿子专吃橘子，女儿专吃苹果，盘子只能放一个水果。

```c
semaphore plate  = 1;    // 盘子空位只有 1 个，可充当互斥信号量
semaphore apple  = 0;
semaphore orange = 0;

爸爸() { while (1) { P(plate); 往盘子里放苹果;   V(apple);  } }
妈妈() { while (1) { P(plate); 往盘子里放橘子;   V(orange); } }
儿子() { while (1) { P(orange); 从盘子取出橘子; V(plate); 吃橘子; } }
女儿() { while (1) { P(apple);  从盘子取出苹果; V(plate); 吃苹果; } }
```

:::key 为什么不设 `mutex` 也能互斥
因为盘子空位只有 1，且 `apple`、`orange`、`plate` 在任何时刻**最多只有一个为 1**，四个进程执行 P 操作时最多只有一个人不会被阻塞，因此天然实现了互斥。**缓冲区数量为 1 时可能天然互斥，但缓冲区数量为 2 时必须用 `mutex`。**
:::

**共享缓冲区导致的隐含死锁（必考难点）：**

两个生产者 A、B 共用一个大小为 N 的缓冲区，消费者需要"一个 A 和一个 B"才能消费。若 A 推进过快把缓冲区全部占满 A，消费者已持有 A 却还需要 B 而 B 放不进去（缓冲区满）→ **死锁**。

解决思路：把问题转化为双缓冲区问题，构造两个虚拟缓冲区，各留出配额：

```c
semaphore empty    = N;      // 箱子内空位数量
semaphore frame    = 0;      // 箱子内车架数量
semaphore wheel    = 0;      // 箱子内车轮数量
semaphore mutex    = 1;      // 互斥访问箱子
semaphore frameMax = N - 2;  // 最多还能放几个车架（保证至少给车轮留 2 个空位）
semaphore wheelMax = N - 1;  // 最多还能放几个车轮（保证至少给车架留 1 个空位）

工人1() {   // 生产车架
    while (1) {
        加工一个车架;
        P(frameMax);
        P(empty);
        P(mutex);
        车架放入箱中;
        V(mutex);
        V(frame);
    }
}

工人2() {   // 生产车轮
    while (1) {
        加工一个车轮;
        P(wheelMax);
        P(empty);
        P(mutex);
        车轮放入箱中;
        V(mutex);
        V(wheel);
    }
}

工人3() {   // 组装
    while (1) {
        P(frame); P(mutex); 箱中取出一个车架; V(mutex); V(empty); V(frameMax);
        P(wheel); P(wheel); P(mutex); 箱中取出二个车轮; V(mutex);
        V(empty); V(empty); V(wheelMax); V(wheelMax);
        组装为一台车;
    }
}
```

#### 读者-写者问题

**问题描述：** 有读者和写者两组并发进程共享一个文件。要求：

- 允许多个读进程**同时**对文件执行读操作（读者读数据后**不改变数据**，与消费者不同）；
- 同一时刻只允许一个写者写；
- 任一写者在完成写操作之前不允许其他任何进程工作；
- 写者执行写操作之前，应让已有的读者、写者全部退出。

这是典型的**分类互斥（categorical mutual exclusion）**：同类进程不互斥，异类进程互斥。

**通用解题模板（"三段式"）：** 本质是"连续多个同类进程访问同一个临界资源"——**第一个进程开始访问前对资源加互斥锁，后续同类进程不再加锁；最后一个进程访问完后解锁**。就像第一个人进房间时开门，后面的人不用开门，最后一个人离开时关门。

**（1）读者优先**

```c
semaphore rw    = 1;    // 用于读者与写者、写者与写者之间的互斥
semaphore mutex = 1;    // 用于对 count 变量的互斥访问
int count = 0;          // 正在读的读者数量

writer() {
    while (1) {
        P(rw);              // 写之前加锁
        写文件;
        V(rw);              // 写完之后解锁
    }
}

reader() {
    while (1) {
        P(mutex);           // 各读者互斥地访问 count
        if (count == 0)     // 我是第一个读者
            P(rw);          // 由我负责对文件加锁
        count++;            // 读者数加 1
        V(mutex);
        读文件;
        P(mutex);
        count--;            // 读者数减 1
        if (count == 0)     // 我是最后一个读者
            V(rw);          // 由我负责对文件解锁
        V(mutex);
    }
}
```

**为什么必须给 `count` 再设一个 `mutex`？**

假设没有 `mutex`：进程 1 判断 `count == 0` 成立（认为自己是第一个读者），此时发生进程切换；进程 2 也判断 `count == 0` 成立（也认为自己是第一个读者），也去 `P(rw)` 加锁；结果第一个读者加锁成功、第二个读者加锁失败被永久阻塞。根源在于**"判断 count"和"加锁"无法一气呵成**。

**缺点：** 只要有一个读者处于活动状态，后来的读者都会被接纳。若读者源源不断到达，写者将始终阻塞，可能**饿死**。

**（2）写者优先**

```c
semaphore rw    = 1;    // 读者与写者、写者与写者互斥
semaphore mutex = 1;    // 互斥访问 rcount
semaphore read  = 1;    // 用来禁止所有读进程（写者到来后封锁后续读者）
semaphore wmutex= 1;    // 互斥访问 wcount
int rcount = 0;         // 读者数量
int wcount = 0;         // 写者数量

reader() {
    while (1) {
        P(read);            // 若有写者在排队/执行，后来的读者阻塞在这里
        P(mutex);
        if (rcount == 0) P(rw);
        rcount++;
        V(mutex);
        V(read);
        读文件;
        P(mutex);
        rcount--;
        if (rcount == 0) V(rw);
        V(mutex);
    }
}

writer() {
    while (1) {
        P(wmutex);
        if (wcount == 0) P(read);   // 第一个写者封锁后续读者
        wcount++;
        V(wmutex);
        P(rw);                       // 等现有读者全部退出
        写文件;
        V(rw);
        P(wmutex);
        wcount--;
        if (wcount == 0) V(read);    // 最后一个写者解除对读者的封锁
        V(wmutex);
    }
}
```

**`read` 的作用分析：** 开始有若干读者在读，此时来了一个写者，执行 `P(read)` 之后，**后续的读者由于阻塞在 `read` 上都不能再进入读者队列**，而写者可以进入写者队列，因此保证了写者优先。同时，第一个写者执行了 `P(read)` 之后**也不能马上开始写**，必须等到所有已在读者队列中的读者都读完、最后一个读者通过 `V(rw)` 唤醒写者。

**（3）读写公平法**

```c
semaphore rw    = 1;    // 读者与写者、写者与写者互斥
semaphore mutex = 1;    // 互斥访问 count
semaphore queue = 1;    // 让读者和写者排队，实现读写公平
int count = 0;

writer() {
    while (1) {
        P(queue);           // 先排队
        P(rw);
        写文件;
        V(rw);
        V(queue);
    }
}

reader() {
    while (1) {
        P(queue);           // 先排队
        P(mutex);
        if (count == 0) P(rw);
        count++;
        V(mutex);
        V(queue);           // 排队结束，允许下一个进程排队
        读文件;
        P(mutex);
        count--;
        if (count == 0) V(rw);
        V(mutex);
    }
}
```

**为什么加一个 `queue` 就实现了公平？** 对比读者优先方案，读者优先中只要有读者到达就能进入读者队列；而 `queue` 阻止了读者的这种"特殊权限"——当写者执行了 `P(queue)` 后，后续到达的读者都阻塞在 `queue` 上，读者队列逐渐为空（count 减为 0），写者最终能拿到 `rw` 进入临界区。因此 `queue` 实现了读写进程**优先级平等**。

**把三种方案放在一起比较：**

| 方案 | 核心机制 | 结果 |
|---|---|---|
| 读者优先 | 第一个读者加 `rw` 锁，最后一个读者解锁 | 写者可能饿死 |
| 写者优先 | 第一个写者执行 `P(read)` 封锁后续读者 | 读者可能饿死 |
| 读写公平 | 加 `queue` 信号量让读写统一排队 | 按到达顺序访问，都不饿死 |

**读者-写者类问题的识别与迁移：** 该类问题的特点是**分类互斥**——同类进程不互斥、异类进程互斥。凡是"同一类可以多人同时进行、不同类必须独占"的场景，都可套用此模板，关键点是**设置一个计数器，第一个同类进程负责上锁，最后一个负责解锁**。

#### 哲学家进餐问题

**问题描述：** 一张圆桌上坐着 5 名哲学家，每两名哲学家之间放一根筷子（共 5 根）。哲学家只做两件事：思考和进餐。饥饿时必须**同时拿起左右两根筷子**才能进餐，进餐完放下筷子继续思考。

**该类题目的特点：只有一类进程，但要占用多种资源才能运行。**

**最初的错误解法：**

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};

philosopher(int i) {
    while (1) {
        P(chopstick[i]);              // 拿左筷子
        P(chopstick[(i+1) % 5]);      // 拿右筷子
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
        思考;
    }
}
```

**死锁原因：** 若 5 名哲学家同时拿起各自的左筷子，则所有筷子的信号量都为 0，谁也无法拿起右筷子，5 个进程全部阻塞，形成循环等待 → **死锁**。

**三种正确解法：**

**解法一：限制并发进程数（最多允许 4 人同时拿筷子）**

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore limit = 4;      // 最多允许 4 名哲学家同时尝试拿筷子

philosopher(int i) {
    while (1) {
        P(limit);
        P(chopstick[i]);
        P(chopstick[(i+1) % 5]);
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
        V(limit);
        思考;
    }
}
```

原理：至少有一名哲学家能同时拿到两根筷子，打破循环等待。**破坏了"循环等待"条件**。缺点：并发度不高。

**解法二：限制申请资源的顺序（奇数号先拿左、偶数号先拿右）**

```c
philosopher(int i) {
    while (1) {
        if (i % 2 == 1) {                    // 奇数号：先左后右
            P(chopstick[i]);
            P(chopstick[(i+1) % 5]);
        } else {                             // 偶数号：先右后左
            P(chopstick[(i+1) % 5]);
            P(chopstick[i]);
        }
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
        思考;
    }
}
```

原理：相邻两名哲学家拿筷子的顺序相反，不可能形成"每人持有一根、都在等下一根"的环。**破坏了"循环等待"条件**。缺点是**不通用**，只适用于本题这种对称结构。

**解法三：拿筷子前先检测，且拿筷子动作互斥（AND 型信号量思想）**

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};
semaphore mutex = 1;      // 保证"拿起两根筷子"是一个原子操作

philosopher(int i) {
    while (1) {
        P(mutex);                         // 先申请拿筷子的权利
        P(chopstick[i]);                  // 拿左筷子
        P(chopstick[(i+1) % 5]);          // 拿右筷子
        V(mutex);                         // 两根都拿到后才释放权利
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1) % 5]);
        思考;
    }
}
```

原理：一名哲学家在"拿两根筷子"的整个过程中持有 `mutex`，其他哲学家无法同时尝试拿筷子。因此不存在"每人拿一根、都在等第二根"的局面，**破坏了"请求并保持"条件**（要么一次拿到两根，要么一根都不拿）。

**关键辨析：** 这种方案**不会导致饥饿**——因为用完餐的哲学家总会放下两根筷子并且不再拿起，所以处于等待中的哲学家一定会等到"两根筷子都空闲"的时刻。有人误以为"旁边的筷子可能被多次拿起"，这是错的，因为 `mutex` 保证了拿筷子的动作是串行的、完整的。

**三种解法小结：**

| 解法 | 原理 | 破坏的条件 | 通用性 |
|---|---|---|---|
| 限制并发数（n-1 人尝试） | 至少一人能拿到两根筷子 | 循环等待 | 通用 |
| 奇偶不同顺序拿筷子 | 相邻哲学家拿筷顺序相反，无法成环 | 循环等待 | 不通用（对称结构可用） |
| 拿筷子动作整体互斥 | 要么一次拿到两根，要么一根不拿 | 请求并保持 | 通用（推荐） |

:::exam 真题考法
2019 年曾考"哲学家进餐问题"的 PV 操作大题，要求写出完整的过程并说明信号量的含义及初值。答题时**必须写出信号量定义与初值**，并用 P、V 操作（或 `wait()`、`signal()`）完整描述每个进程。
:::

#### 理发师问题

**核心思路转换：** 理发师问题与生产者-消费者问题的思路是一样的——顾客可以视为"生产者"（生产顾客资源），服务人员可以视为"消费者"（消费顾客资源）；反过来服务人员叫号也可视为生产了一个"服务人员资源"。取号和叫号类似于往缓冲区放东西，需要一个互斥锁。

**万能模板 1（无等待上限，服务人员可休息）**

```c
int waiting = 0;              // 正在等待的顾客数
semaphore customers = 0;      // 等待服务的顾客数
semaphore barbers   = 0;      // 空闲的服务人员数
semaphore mutex     = 1;      // 对 waiting 的互斥访问

barber() {                    // 服务人员进程（有 N 个）
    while (1) {
        P(customers);         // 有顾客才工作，否则阻塞休息
        P(mutex);
        waiting--;            // 少一名等待的顾客
        V(mutex);
        V(barbers);           // 叫号：生产一个"空闲服务人员"
        为顾客服务;
    }
}

customer() {                  // 顾客进程
    P(mutex);                 // 取号（互斥）
    if (waiting < N) {
        waiting++;
        V(mutex);
        V(customers);         // 叫醒一名休息的服务人员
        P(barbers);           // 等待被叫号
        接受服务;
    } else {
        V(mutex);             // 没位置了，离店
    }
}
```

**万能模板 2（有等待上限，服务人员可休息）**：在上面的基础上把 `waiting` 作为判断条件，顾客到店时若 `waiting` 已达上限则直接离店（模板 1 中就是这种写法）。

**万能模板 3（有等待上限，服务人员忙等）**：服务人员在没有顾客时也**不可以休息**，必须不断询问有没有顾客。因此在服务人员进程中加入判断顾客数量的语句——**对顾客资源的 P 操作就不需要了**，因为 P 操作会引发阻塞或休息。

**万能模板 4（座位已满后顾客仍继续等待，服务人员可休息）**：把 `waiting` 变量变为**信号量 `empty`**（表示店里空位数），顾客先 `P(empty)` 阻塞等待空位，再取号等待叫号。

:::key 理发师问题的做题关键
1. 只需把**模板 1** 的思路记下来，其余都是从它延伸来的。做题时先默写模板 1，再按题意修补；
2. **服务人员的数量在模板中通常是冗余条件**（N 个服务人员对应 N 个进程，或用一个信号量记录空闲服务人员数）；
3. 上述模板都**没有满足先来先服务**（因为 `V(server)` 后任意一个顾客进程都可能继续执行）。统考一般不要求先来先服务。
:::

#### 吸烟者问题

供应者每次把两种材料放在桌上，拥有第三种材料的吸烟者才能卷烟抽。设三种材料对应三个信号量 `offer1`、`offer2`、`offer3`，再加一个 `finish` 信号量让供应者知道上一轮已被取走。

```c
semaphore offer1 = 0, offer2 = 0, offer3 = 0;
semaphore finish = 0;
int i = 0;                       // 供应者轮流提供的组合

provider() {
    while (1) {
        if (i == 0)      { 将烟草和纸放到桌上; V(offer1); }
        else if (i == 1) { 将烟草和胶水放到桌上; V(offer2); }
        else             { 将纸和胶水放到桌上; V(offer3); }
        i = (i + 1) % 3;
        P(finish);                // 等吸烟者抽完再放下一组
    }
}

smoker1() {   // 有胶水的人
    while (1) { P(offer1); 卷烟抽; V(finish); }
}

smoker2() {   // 有纸的人
    while (1) { P(offer2); 卷烟抽; V(finish); }
}

smoker3() {   // 有烟草的人
    while (1) { P(offer3); 卷烟抽; V(finish); }
}
```

:::warn 易错
吸烟者问题也是"单缓冲区"结构（桌上同时只有一组材料），但由于供应者每次只放一组、且吸烟者抽完后才放下一组，**不需要额外的 `mutex`**。判断是否需要 `mutex` 的方法是：看是否存在"多个进程可能同时进入缓冲区"的风险。
:::

#### 独木桥问题

**问题描述：** 桥不允许两车交汇，但允许同方向多辆车依次通过（桥上可以有多个同方向的车）。用 P、V 操作实现交通管理防止堵塞。

**识别：** 这是**同类不互斥、异类互斥**的分类互斥问题，与读者-写者问题同构（同方向的车相当于"读者"，对向的车相当于"写者"）。

```c
semaphore mutex = 1;      // 对两个计数器的互斥访问
semaphore bridge = 1;     // 桥的互斥访问（相当于读者-写者中的 rw）
int countA = 0;           // A 方向在桥上的车数
int countB = 0;           // B 方向在桥上的车数

carA() {
    while (1) {
        P(mutex);
        if (countA == 0) P(bridge);   // 第一辆 A 方向的车负责上锁
        countA++;
        V(mutex);
        过桥;
        P(mutex);
        countA--;
        if (countA == 0) V(bridge);   // 最后一辆 A 方向的车负责解锁
        V(mutex);
    }
}
```

`carB()` 完全对称。

:::key 判断"是否类似读者-写者"的方法
**同类进程之间不互斥、异类进程之间互斥 ⇒ 套读者-写者模板。** 关键是设一个计数器记录同类进程数量，**第一个进程上锁、最后一个进程解锁**。独木桥、更衣室、录像厅、寿司店等题目都是这个套路。
:::

#### 流水线与前驱关系问题

**问题描述：** 一条流水线上有多个工序，后一工序必须等前一工序完成后才能开始；相邻工序之间有一个容量为 1 的缓冲区。

**识别：** 这是**前驱关系 + 单缓冲区**问题，每个工序既是前一工序的消费者，又是后一工序的生产者。

```c
semaphore empty1 = 1, empty2 = 1;   // 各缓冲区空位
semaphore full1  = 0, full2  = 0;   // 各缓冲区产品

工序1() {
    while (1) {
        加工零件;
        P(empty1);
        把零件放到缓冲区1;
        V(full1);
    }
}

工序2() {
    while (1) {
        P(full1);
        从缓冲区1取出零件;
        V(empty1);
        加工零件;
        P(empty2);
        把零件放到缓冲区2;
        V(full2);
    }
}

工序3() {
    while (1) {
        P(full2);
        从缓冲区2取出零件;
        V(empty2);
        加工零件;
    }
}
```

:::key 流水线问题的通用套路
对每一段缓冲区设一对信号量：`empty_i`（初值 = 缓冲区容量，容量为 1 时初值 1）和 `full_i`（初值 0）。前一工序放入产品时"先 `P(empty_i)` 再 `V(full_i)`"，后一工序取出产品时"先 `P(full_i)` 再 `V(empty_i)`"。这实际上就是把每个工序都当作一个小型的生产者-消费者。
:::

:::exam PV 操作大题的答题规范
1. **必须写出信号量定义并赋初值**，并说明每个信号量的含义；
2. **必须写出每个进程的完整循环体**，用 `P`/`V`（或 `wait`/`signal`）操作描述；
3. 用中文描述动作（如"把产品放入缓冲区"），不要遗漏；
4. **检查是否存在死锁**：连续的 P 操作是否可能造成循环等待；多个进程共享同一缓冲区时是否存在某一方把缓冲区占满的隐患；如果有，加入 `mutex` 让连续 P 操作一气呵成，或转化为双缓冲区。
:::

## 死锁

### 死锁的基本概念

#### 定义

**死锁（Deadlock）**：在并发环境下，各进程互相等待对方手里的资源，导致各进程都阻塞、无法向前推进的现象。死锁的定义包含两点：**互相循环等待** + **各个进程都被阻塞**。

#### 死锁、饥饿、死循环的区别

| 对比项 | 死锁 | 饥饿 | 死循环 |
|---|---|---|---|
| 定义 | 各进程互相等待对方手里的资源，都阻塞无法推进 | 由于长期得不到想要的资源，某进程无法向前推进 | 进程在不满足终止条件时无限循环 |
| 原因 | 循环等待对方手里的资源 | 优先级倒置、资源分配不公平或错误 | 编程错误、逻辑错误 |
| 例子 | 银行家算法问题中的死锁状态 | 低优先级进程长期得不到 CPU | 空循环、忘记更新循环条件 |
| 进程状态 | **阻塞态** | **阻塞态**（得不到 I/O 设备）或**就绪态**（上不了处理机） | **运行态** |
| 涉及进程数 | **两个或两个以上** | 可能只有一个，也可能多于一个 | 大于等于一个 |
| 性质 | **操作系统（管理者）的问题** | **操作系统（管理者）的问题** | **被管理者（程序员）的问题** |

#### 产生死锁的原因

1. **对系统资源的竞争**：各进程竞争**不可剥夺资源**，若资源数目满足不了多个进程的需要，就会因争夺资源陷入僵局。可剥夺资源（CPU、主存）不会引发死锁。
2. **进程推进顺序不当**：P1 占有 R1 又申请 R2，P2 占有 R2 又申请 R1，互相等待。
3. **信号量使用不当**：例如生产者-消费者问题中把实现互斥的 P 操作放在实现同步的 P 操作之前。
4. **由可消耗性资源引起**：多个进程通信时 `send`/`receive` 顺序处理不当，都在等一条永远不会发出的消息。

#### 四个必要条件

| 条件 | 含义 |
|---|---|
| **互斥条件** | 任何时刻只能有一个进程使用一个资源实例。只有对必须互斥使用的资源（临界资源、锁）的争夺才会导致死锁；内存、CPU、扬声器这类可同时共享的资源不会导致死锁 |
| **不可剥夺（不可抢占）条件** | 进程所获得的资源在未使用完之前不能被其他进程强行夺走，只能主动释放 |
| **请求并保持（请求与保持）条件** | 进程已经保持了至少一个资源，但又提出新的资源请求，而该资源被其他进程占有，此时请求进程被阻塞，但对自己已有的资源保持不放 |
| **循环等待条件** | 存在一种进程-资源的**循环等待链**，链中每一个进程已获得的资源同时被链中下一个进程所请求 |

:::key 四个条件必须"同时满足"才可能死锁，只要破坏其中一个，死锁就不会发生。
:::

:::warn 循环等待 ≠ 死锁
**发生死锁时一定有循环等待，但发生循环等待时未必死锁。**
若同类资源数大于 1，即使存在循环等待，等待链中的某个进程仍可能从**链外**的进程那里获得资源，从而打破循环。只有当系统中每类资源都只有一个时，循环等待才是死锁的充要条件。
:::

#### 两个常用结论

设系统有 $n$ 个进程，每个进程最多需要 $y$ 个同类资源：

- 系统**必然不会发生死锁的最少资源数**为 $n \times (y-1) + 1$；
- 反之，若系统有 $x$ 个资源、每个进程最多需要 $y$ 个资源，则**可能发生死锁的最小进程数**为 $\left\lceil \dfrac{x}{y-1} \right\rceil$。

**推导思路：** 最坏情况是每个进程都只拥有 $y-1$ 个资源并都在申请第 $y$ 个。若资源总数恰好为 $n(y-1)$，资源已用完，必然死锁；再多加一个资源，令其中一个进程获得所需的最大资源，死锁即被解除。

**用例题验证：**

- 系统有 8 台打印机，K 个进程竞争，每个进程最多需要 3 台。要保证不死锁需 $8 \ge K(3-1)+1 = 2K+1$，即 $K \le 3.5$，故 $K = 4$ 时**可能**发生死锁，答案是 4。
- 三个进程分别需要 3、4、5 台设备：最坏情况各拿到 2、3、4 台，共 9 台，只要再能额外提供 1 台就能让某个进程完成，故确保不发生死锁的最小设备数 $n = 9 + 1 = 10$。
- $n$ 个进程每个需要 2 个临界资源：最坏情况各拿到 1 个，共 $n$ 个，再加 1 个即可打破僵局，故至少需要 $n+1$ 个资源。

#### 死锁处理策略

| 策略 | 思想 | 优缺点 |
|---|---|---|
| **死锁预防（Prevention）** | 设计系统时破坏四个必要条件之一，从根本上排除死锁可能 | 一定能保证不死锁，但资源利用率低、并发度差 |
| **死锁避免（Avoidance）** | 不破坏必要条件，在资源动态分配中防止系统进入不安全状态（银行家算法） | 需要预先知道进程运行所需的资源总量，并发性次于检测法 |
| **死锁检测与解除（Detection & Recovery）** | 允许死锁发生，定期检测并在发现后解除 | **并发性最大**，但检测有开销，解除可能造成工作损失 |

按**并发性从大到小**排序：**检测死锁 > 银行家算法 > 资源预分配**。

### 死锁预防

#### 破坏互斥条件

把互斥资源改造成共享资源。例如用 **SPOOLing 技术**把打印机这种独占设备在逻辑上改造成共享设备；再如通过强大的硬件指令把需要互斥访问的代码构造成不需要锁的数据结构。

**缺点：** 有的资源本身就是非共享的（一个互斥锁不能同时被多个进程共享），有些地方还必须保护这种互斥性。因此**这种方法通常不太可行**。

#### 破坏不可剥夺条件

- 方案一：当进程请求新资源得不到满足时，**立即释放它保持的所有资源**；
- 方案二：当进程需要的资源被其他进程占有时，**由操作系统协助强行剥夺**。

**缺点：** 实现复杂、代价大；释放已获得的资源可能造成前一阶段工作失效，使进程前后两次运行的信息不连续；反复申请和释放资源会增加系统开销、降低吞吐量；可能导致进程饥饿。因此**只适用于状态容易保存和恢复的资源**（如 CPU 寄存器、内存），一般不适用于互斥锁、信号量、打印机、CD 刻录机。

#### 破坏请求并保持条件

要求"进程在请求资源时不能持有不可剥夺资源"，有两种协议：

- **协议一（静态分配）**：进程在运行前**一次申请完它所需要的全部资源**，资源未满足就不让它投入运行；
- **协议二（改进版）**：允许进程只获得**运行初期所需的资源**便开始运行，运行过程中**逐步释放**已用完的资源，然后再请求新的资源。

**缺点：** 需要准确预知需要哪些资源并提前获得；有些资源只在运行初期或快结束时短暂使用，若整个运行期一直保持就会严重降低并发和资源利用率；协议一实现简单但资源浪费严重，且可能导致饥饿；协议二改进了协议一的缺点，能更快完成任务、提高设备利用率、减少饥饿概率。

#### 破坏循环等待条件

**最实用、最经常采用的预防技术**：采用**顺序资源分配法**（资源有序分配算法）。给系统中所有资源编号，规定**每个进程必须按编号递增的顺序请求资源**，同类资源一次申请完。也就是说，进程一旦申请了资源 $R_i$，以后的申请就只能申请编号大于 $R_i$ 的资源。

**优点：** 从机制上杜绝了循环等待链。

**缺点：**

- 不方便增加新设备，可能需要重新分配所有编号；
- 进程实际使用资源的顺序可能与编号递增顺序不一致，导致资源浪费（例如 1 号资源是最后需要的，却被最先持有，使其他只需 1 号资源的进程被长时间阻塞）；
- 必须按规定次序申请资源，**用户编程麻烦**。

:::exam 常考对比
**死锁预防**靠破坏四个必要条件；**死锁避免**靠银行家算法保证系统始终处于安全状态。二者常被放在一起考（如 2015-26、2019-30、2013-32）。
另外，限制用户申请资源的顺序属于**死锁预防**（破坏循环等待），**不属于死锁避免**。
:::

### 死锁避免

#### 安全状态与安全序列

- **安全序列**：指如果系统按这种序列为进程分配资源，则每个进程都能顺利完成。只要**能找出一个安全序列**，系统就处于**安全状态**。**安全序列可能有多个。**
- **不安全状态**：如果分配资源后系统中**找不出任何一个安全序列**，则系统进入不安全状态。
- 关键结论：
  1. 处于**安全状态**，**一定不会**发生死锁；
  2. 处于**不安全状态**，**可能**发生死锁，但不一定（例如进程提前终止释放了资源，或实际所需资源小于声明的最大需求）；
  3. 发生死锁，**一定**处于不安全状态；
  4. 若进程提前归还部分资源，系统也有可能从**不安全状态重新回到安全状态**，但在分配资源以前总要考虑最坏情况；
  5. **单个进程阻塞不是死锁**，必须形成阻塞环才是死锁。

死锁避免与死锁检测的区别：

| 对比项 | 死锁避免 | 死锁检测 |
|---|---|---|
| 需要的资源信息 | 需要进程**整个生命周期**所需的资源总量（最大需求） | 只需要**当前时刻**的资源请求与分配信息 |
| 是否限制资源申请顺序 | **不会**（限制顺序属于死锁预防） | 不会 |
| 是否会给可能导致死锁的进程分配资源 | **不会** | **会**（允许死锁发生，之后再解除） |
| 典型算法 | 银行家算法 | 资源分配图化简法（死锁定理） |

#### 银行家算法的数据结构

设有 $n$ 个进程、$m$ 类资源：

| 数据结构 | 类型 | 含义 |
|---|---|---|
| **Available** | 长度为 $m$ 的向量 | `Available[j]` 表示第 $j$ 类资源的当前可用数量 |
| **Max** | $n \times m$ 矩阵 | `Max[i][j]` 表示进程 $P_i$ 对第 $j$ 类资源的最大需求 |
| **Allocation** | $n \times m$ 矩阵 | `Allocation[i][j]` 表示已分配给 $P_i$ 的第 $j$ 类资源数量 |
| **Need** | $n \times m$ 矩阵 | `Need[i][j]` 表示 $P_i$ 还需要第 $j$ 类资源的数量 |

三者关系（**必须自洽**）：

$$Need[i][j] = Max[i][j] - Allocation[i][j]$$

且满足 $\sum_i Allocation[i][j] + Available[j] = 系统中第 j 类资源总数$。

#### 安全性算法（完整步骤）

1. 令 **Work = Available**，**Finish[i] = FALSE**（$i = 0, 1, \dots, n-1$）；
2. 寻找满足下列两个条件的进程 $P_i$：
   - `Finish[i] == FALSE`；
   - `Need[i][j] ≤ Work[j]`（对所有 $j$ 成立）；
   
   若找到，转步骤 3；若找不到，转步骤 4；
3. 该进程可以顺利执行完毕并释放它的全部资源：
   
   $$Work[j] = Work[j] + Allocation[i][j] \quad (\text{对所有 } j)$$
   
   `Finish[i] = TRUE`，把 $P_i$ 加入安全序列，**返回步骤 2**；
4. 若所有 `Finish[i] == TRUE`，则系统处于**安全状态**（步骤 3 中得到的进程顺序就是一个安全序列）；否则系统处于**不安全状态**。

一句话概括：**检查当前剩余可用资源能否满足某个进程的最大需求，可以就把它加入安全序列并回收它持有的全部资源，不断重复，看最终能否让所有进程都加入安全序列。**

#### 资源请求算法

当进程 $P_i$ 发出资源请求向量 $Request_i$ 时：

1. **检查是否超过声明的最大需求**：若 `Request_i[j] > Need[i][j]`，说明请求量超过它事先声明的最大需求，**报错**；
2. **检查系统是否有足够资源**：若 `Request_i[j] > Available[j]`，说明资源暂时不够，**$P_i$ 必须等待**；
3. **试探性分配**（修改数据结构）：
   
   $$Available[j] = Available[j] - Request_i[j]$$
   $$Allocation[i][j] = Allocation[i][j] + Request_i[j]$$
   $$Need[i][j] = Need[i][j] - Request_i[j]$$
   
4. **执行安全性算法**检查此次分配后系统是否安全：
   - 若安全，则**正式分配**；
   - 若不安全，则**撤销本次试探性分配**（恢复原先的 Available、Allocation、Need），让 $P_i$ 等待。

#### 完整算例一：T0 时刻的安全性检测

设系统有 5 个进程 P0～P4、3 类资源 A、B、C，各类资源总数分别为 **A = 10、B = 5、C = 7**。T0 时刻状态如下：

| 进程 | Allocation (A,B,C) | Max (A,B,C) | Need (A,B,C) |
|---|---|---|---|
| P0 | 0, 1, 0 | 7, 5, 3 | 7, 4, 3 |
| P1 | 2, 0, 0 | 3, 2, 2 | 1, 2, 2 |
| P2 | 3, 0, 2 | 9, 0, 2 | 6, 0, 0 |
| P3 | 2, 1, 1 | 2, 2, 2 | 0, 1, 1 |
| P4 | 0, 0, 2 | 4, 3, 3 | 4, 3, 1 |

**第一步：求 Available**

已分配总量：A $= 0+2+3+2+0 = 7$；B $= 1+0+0+1+0 = 2$；C $= 0+0+2+1+2 = 5$。

$$Available = (10-7,\ 5-2,\ 7-5) = (3,\ 3,\ 2)$$

**第二步：逐个查找满足 $Need \le Work$ 的进程**

第 1 轮，Work = (3, 3, 2)：

| 进程 | Need | 是否 ≤ Work | 判定 |
|---|---|---|---|
| P0 | (7,4,3) | 7 > 3 | 否 |
| P1 | (1,2,2) | 全部满足 | **是** |
| P2 | (6,0,0) | 6 > 3 | 否 |
| P3 | (0,1,1) | 全部满足 | 是（但按编号先取 P1） |
| P4 | (4,3,1) | 4 > 3 | 否 |

选 **P1**。P1 执行完毕，释放 Allocation(P1) = (2,0,0)：

$$Work = (3,3,2) + (2,0,0) = (5,\ 3,\ 2)$$

安全序列当前为：**P1**

第 2 轮，Work = (5, 3, 2)：

| 进程 | Need | 是否 ≤ Work |
|---|---|---|
| P0 | (7,4,3) | 7 > 5，否 |
| P2 | (6,0,0) | 6 > 5，否 |
| P3 | (0,1,1) | 是 |
| P4 | (4,3,1) | 是（按编号先取 P3） |

选 **P3**。释放 Allocation(P3) = (2,1,1)：

$$Work = (5,3,2) + (2,1,1) = (7,\ 4,\ 3)$$

安全序列：P1 → **P3**

第 3 轮，Work = (7, 4, 3)：

| 进程 | Need | 是否 ≤ Work |
|---|---|---|
| P0 | (7,4,3) | 是（按编号先取 P0） |
| P2 | (6,0,0) | 是 |
| P4 | (4,3,1) | 是 |

选 **P0**（按编号顺序）。释放 Allocation(P0) = (0,1,0)：

$$Work = (7,4,3) + (0,1,0) = (7,\ 5,\ 3)$$

安全序列：P1 → P3 → **P0**

第 4 轮，Work = (7, 5, 3)：

| 进程 | Need | 是否 ≤ Work |
|---|---|---|
| P2 | (6,0,0) | 是 |
| P4 | (4,3,1) | 是 |

选 **P2**。释放 Allocation(P2) = (3,0,2)：

$$Work = (7,5,3) + (3,0,2) = (10,\ 5,\ 5)$$

安全序列：P1 → P3 → P0 → **P2**

第 5 轮，Work = (10, 5, 5)：P4 的 Need = (4,3,1) 满足，选 **P4**。

$$Work = (10,5,5) + (0,0,2) = (10,\ 5,\ 7)$$

**安全序列：P1 → P3 → P0 → P2 → P4**，所有进程 Finish 均为 TRUE，**系统处于安全状态**。

:::key 结果校验
安全序列执行完毕后，Work = (10, 5, 7)，恰好等于系统资源总数 (A=10, B=5, C=7)。**这是检查算例是否算错的快捷方法：安全序列跑完后的 Work 必须等于资源总数。**
:::

:::warn 安全序列的唯一性
本题中**第一步只有 P1 能执行**（P0、P2、P4 的 Need 都超过 Available），因此**所有安全序列都必须以 P1 开头**。之后有多个分支，因此安全序列不唯一（例如 P1 → P3 → P4 → P2 → P0 也是安全序列）。做选择题时要逐个验证选项中的序列是否真的每一步都可行。
:::

#### 完整算例二：资源请求的处理

仍用上面的系统，当前 $Available = (3, 3, 2)$。

**情形 1：P0 请求 Request = (2, 1, 0)**

1. 检查最大需求：`Request(2,1,0) ≤ Need(P0)=(7,4,3)`，通过；
2. 检查可用资源：`Request(2,1,0) ≤ Available(3,3,2)`，通过；
3. 试探性分配：

| 进程 | Allocation | Need | Available |
|---|---|---|---|
| P0 | (2, 2, 0) | (5, 3, 3) | (1, 2, 2) |
| P1 | (2, 0, 0) | (1, 2, 2) | |
| P2 | (3, 0, 2) | (6, 0, 0) | |
| P3 | (2, 1, 1) | (0, 1, 1) | |
| P4 | (0, 0, 2) | (4, 3, 1) | |

4. 安全性检查，Work = (1, 2, 2)：
   - P1 的 Need = (1,2,2) ≤ (1,2,2)，选 P1；Work = (1,2,2)+(2,0,0) = **(3, 2, 2)**；
   - P3 的 Need = (0,1,1) ≤ (3,2,2)，选 P3；Work = (3,2,2)+(2,1,1) = **(5, 3, 3)**；
   - P4 的 Need = (4,3,1) ≤ (5,3,3)，选 P4；Work = (5,3,3)+(0,0,2) = **(5, 3, 5)**；
   - P0 的 Need = (5,3,3) ≤ (5,3,5)，选 P0；Work = (5,3,5)+(2,2,0) = **(7, 5, 5)**；
   - P2 的 Need = (6,0,0) ≤ (7,5,5)，选 P2；Work = (7,5,5)+(3,0,2) = **(10, 5, 7)**。

   得到安全序列 **P1 → P3 → P4 → P0 → P2**，系统安全。**因此可以正式把资源分配给 P0。**

**情形 2：P4 请求 Request = (3, 3, 0)** —— **拒绝**

1. `Request(3,3,0) ≤ Need(P4) = (4,3,1)`（3 ≤ 4 且 3 ≤ 3），通过；
2. `Request(3,3,0) ≤ Available = (3,3,2)`，通过；
3. 试探性分配：`Allocation(P4) = (3, 3, 2)`，`Need(P4) = (1, 0, 1)`，`Available = (0, 0, 2)`；
4. 安全性检查，Work = (0, 0, 2)：逐个检查所有进程的 Need，**没有一个能被满足**：
   - P0 需 (7,4,3)：A 不足；
   - P1 需 (1,2,2)：A 不足（需 1，只有 0）；
   - P2 需 (6,0,0)：A 不足；
   - P3 需 (0,1,1)：B 不足（需 1，只有 0）；
   - P4 需 (1,0,1)：A 不足。

   一步都推不动，**系统进入不安全状态**，因此**必须拒绝该请求**。

**情形 3：P1 请求 Request = (0, 2, 0)** —— **拒绝**（这是最典型的"看似可行实则不安全"的例子）

1. `Request(0,2,0) ≤ Need(P1)=(1,2,2)`，通过；
2. `Request(0,2,0) ≤ Available(3,3,2)`，通过；
3. 试探性分配：

| 进程 | Allocation | Need | Available |
|---|---|---|---|
| P0 | (0, 1, 0) | (7, 4, 3) | **(1, 1, 2)** |
| P1 | (2, 2, 0) | **(1, 0, 2)** | |
| P2 | (3, 0, 2) | (6, 0, 0) | |
| P3 | (2, 1, 1) | (0, 1, 1) | |
| P4 | (0, 0, 2) | (4, 3, 1) | |

4. 安全性检查，Work = (1, 1, 2)：逐个检查
   - P0 需 (7,4,3)：A 分量 7 > 1，不满足；
   - P1 需 (1,0,2)：(1,0,2) ≤ (1,1,2)，**满足**。选 P1！Work = (1,1,2) + (2,2,0) = **(3, 3, 2)**；
   - P3 需 (0,1,1) ≤ (3,3,2)，选 P3；Work = (3,3,2)+(2,1,1) = **(5, 4, 3)**；
   - P4 需 (4,3,1) ≤ (5,4,3)，选 P4；Work = (5,4,3)+(0,0,2) = **(5, 4, 5)**；
   - P0 需 (7,4,3)：A 分量 7 > 5，**不满足**；
   - P2 需 (6,0,0)：A 分量 6 > 5，**不满足**。

   死循环，找不到更多可执行进程，**系统进入不安全状态**。

**结论：该请求必须被拒绝**，让 P1 等待。这个算例是最经典的考点——**请求量本身没有超过 Need 也没有超过 Available，但分配后系统不安全，所以仍要拒绝**。

#### 经典真题算例

**（1）2011-27（答案：D，不存在安全序列）**

| 进程 | 已分配 R1 R2 R3 | 尚需 R1 R2 R3 |
|---|---|---|
| P1 | 2 0 0 | 0 0 1 |
| P2 | 1 2 0 | 1 3 2 |
| P3 | 0 1 1 | 1 3 1 |
| P4 | 0 0 1 | 2 0 0 |

可用资源 = (0, 2, 1)。P1 的 Need (0,0,1) ≤ (0,2,1)，可执行；释放后 Work = (2, 2, 1)。此后 P2 需 (1,3,2) 的 R2 分量 3 > 2，P3 需 (1,3,1) 的 R2 分量 3 > 2，P4 需 (2,0,0) 可满足但执行后 Work = (2,2,2)，R2 仍只有 2，P2、P3 依然无法执行。**最终无法让所有进程加入安全序列，故不存在安全序列。**

**（2）2018-26（答案：A，系统处于不安全状态）**

系统有 4 个同类资源，P1、P2、P3 分别需要 4、3、1 个，已申请到 2、1、0 个。

- 可用资源 = 4 − (2+1+0) = **1**；
- Need：P1 = 4−2 = 2，P2 = 3−1 = 2，P3 = 1−0 = **1**；
- 只有 P3 能满足，P3 执行完毕释放 0 个资源，Work 仍为 **1**；
- 此时 P1、P2 都需 2 个而只有 1 个，谁也无法执行。

**结论：不存在安全序列，系统处于不安全状态。**

**（3）2022-26（答案：B，安全序列个数为 2）**

| 进程 | 已分配 A B C | 尚需 A B C |
|---|---|---|
| P0 | 2 0 1 | 0 2 1 |
| P1 | 0 2 0 | 1 2 3 |
| P2 | 1 0 1 | 0 1 3 |

可用资源 = (1, 3, 2)。P0 的 Need (0,2,1) ≤ (1,3,2) 满足；P1 的 Need 需要 C 资源 3 > 2，不满足；P2 的 Need 需要 C 资源 3 > 2，不满足。**第一步只能运行 P0。**

P0 执行完毕释放 (2,0,1)，Work = (1,3,2) + (2,0,1) = **(3, 3, 3)**。此时 P1 需 (1,2,3) ≤ (3,3,3) 满足，P2 需 (0,1,3) ≤ (3,3,3) 也满足。

- 序列 P0 → P1 → P2；
- 序列 P0 → P2 → P1。

**共 2 个安全序列。**

:::key 银行家算法速算技巧
1. **先把 Available 算对**：Available = 资源总数 − 各进程已分配之和。题目不给总数时，往往给出"可用资源"行，直接抄；
2. **Need = Max − Allocation**，逐个算，不要漏；
3. **每选出一个进程就立刻更新 Work 并重新从第一个进程开始扫描**（题目若规定了扫描顺序，就按规定的顺序取）；
4. **用"Work 最终是否等于资源总数"校验**；
5. 资源请求题按"三步检查 + 试探分配 + 安全性算法"作答，写清"拒绝"或"可以分配"并给出理由。
:::

### 死锁检测和解除

#### 死锁检测的时机

死锁检测算法会按系统真实情况设置合适的**时间间隔**，每隔一段时间执行一次来检测系统是否存在死锁。若检测过于频繁会浪费系统资源；若间隔太长又没有意义。

检测的触发时机：**每隔一段时间，或当 CPU 利用率显著降低时**。（不能以"死锁发生时"为触发点——只有运行了检测算法之后系统才知道是否死锁；也不能在每次进程申请资源时都检测，开销过大。）

若系统既不采取预防措施也不采取避免措施，就必须提供两个算法：**死锁检测算法**（确定系统是否已发生死锁）和**死锁解除算法**（从死锁状态恢复）。

#### 资源分配图

需要的两种信息：用某种数据结构保存资源的请求和分配信息；提供一种算法利用这些信息检测是否进入死锁状态。

**资源分配图的构成：**

| 元素 | 含义 |
|---|---|
| 进程结点（圆圈） | 对应一个进程 |
| 资源结点（方框） | 对应一类资源，方框中的小圆圈表示该类资源有几个实例 |
| 请求边（进程结点 → 资源结点） | 表示进程想申请几个资源，**每条边代表一个** |
| 分配边（资源结点 → 进程结点） | 表示已经为进程分配了几个资源，**每条边代表一个** |

**简化资源分配图的步骤：**

1. 在图中找出**既不阻塞又不是孤点的进程** $P_i$——即存在一条与它相连的有向边，且该边对应的资源申请数量**小于等于系统中已有的空闲资源数量**。若所有连接该进程的边都满足条件，则该进程能继续运行直至完成；
2. **消去它所有的请求边和分配边**，使之成为孤立的结点（相当于该进程释放了所占有的全部资源）；
3. 它释放的资源可以唤醒某些因等待这些资源而阻塞的进程，使原来的阻塞进程变为非阻塞进程，于是对这些新解放的进程重复上述操作。

**死锁定理：如果某时刻系统的资源分配图是**不可完全简化**的，那么此时系统发生死锁。**

- 若能消去图中所有的边，则称该图是**可完全简化**的，此时**一定没有发生死锁**（相当于能找到一个安全序列）；
- 若最终不能消除所有边，则**发生了死锁**；
- **注意：并不是系统中所有进程都是死锁状态。用死锁检测算法化简资源分配图后，还连着边的那些进程才是死锁进程。**

:::warn 死锁检测不关心"资源总量"
死锁检测只检测系统中是否发生死锁（是否存在循环等待的环路），一旦发现就要采取解除措施，因此**不需要知道各进程运行所需的资源总量信息**，只需要知道当前时刻的资源请求与分配情况。这正是 2015-26 题中"Ⅱ：S1 需要进程运行所需资源总量信息，而 S2 不需要"正确的理由。
:::

:::exam 真题考法
2015-26（死锁避免与死锁检测的对比）、2016-25（4 个进程共享 3 个临界资源，问死锁时处于死锁状态的进程数至少是几个——答案 3，因为 p4 只需 R2，无法单独成环，至少需要 p1、p2、p3 三个进程构成环）。
:::

#### 死锁的解除

| 方法 | 做法 | 特点 |
|---|---|---|
| **资源剥夺法** | 挂起（暂时放到外存）某些死锁进程，抢占它的资源并分配给其他死锁进程 | 应防止被挂起的进程长时间得不到资源而饥饿 |
| **撤销进程法（终止进程法）** | 强制撤销部分甚至全部死锁进程，剥夺它们的资源 | 实现简单，但代价可能很大（有些进程已运行很久、接近结束，被终止则功亏一篑） |
| **进程回退法** | 让一个或多个死锁进程回退到足以避免死锁的地步 | 要求系统记录进程的历史信息、**设置还原点**；过程中进程**主动释放**资源而非被剥夺 |

**选择"牺牲者"（撤销哪个进程、剥夺谁的资源）时可以考虑的因素：**

- 进程的**优先级**；
- 进程**已执行了多长时间**；
- 进程**还要多久才能完成**；
- 进程**已经使用了多少资源**；
- 进程是**交互式还是批处理式**。

**如何避免解除死锁时造成饥饿？** 如果一个系统基于"代价"来选择牺牲进程，那么同一进程可能总是被选为牺牲者，结果永远不能完成指定任务而饿死。因此可以在代价的考虑因素中加入**回滚次数**。

:::key 死锁与本节的整体脉络
**死锁预防**：破坏四个必要条件之一（互斥、不可剥夺、请求并保持、循环等待）。
**死锁避免**：银行家算法，保证系统不进入不安全状态。
**死锁检测**：资源分配图化简，看是否可完全简化（死锁定理）。
**死锁解除**：资源剥夺、撤销进程、进程回退。
:::

| 单标志法 | 违背空闲让进（和让权等待） |
| 双标志先检查 | 违背忙则等待 |
| 双标志后检查 | 违背空闲让进和有限等待 |
| Peterson | 满足空闲让进、忙则等待、有限等待；**不满足让权等待**；只适用于两个进程 |
| 中断屏蔽 | 只适用于内核进程、只适用于单处理机 |
| TSL / Swap | 原子操作、适用多处理机；**不满足让权等待**，可能饥饿 |
| 自旋锁 | 忙等、无上下文切换开销、多处理机短临界区适用、**单处理机需抢占式调度器** |
| 整型信号量 | `while (S <= 0);` ——违反让权等待 |
| 记录型信号量 | `S.value--` 后判断 `< 0` 则阻塞；`S.value++` 后判断 `<= 0` 则唤醒；**遵循让权等待** |
| S.value 含义 | `>0` 表示可用资源数；`=0` 表示资源刚好用完且无等待者；`<0` 时其绝对值等于正在等待的进程数 |
| 互斥模板 | `P(mutex)` … 临界区 … `V(mutex)`，`mutex = 1` |
| 同步模板 | 前操作后 `V(S)`、后操作前 `P(S)`，`S = 0` |
| 前驱模板 | 每对前驱一个信号量（初值 0），前驱末尾 V、后继开头 P |
| 条件变量 vs 信号量 | 条件变量**没有值**；`signal` 可能不产生任何影响，`V` 一定会改变信号量 |
| 生产者-消费者 | `P(empty)` 必须在 `P(mutex)` 之前，否则死锁；V 操作顺序可交换 |
| 读者-写者 | 分类互斥；第一个读者上锁、最后一个读者解锁；`count` 需要 `mutex` 保护 |
| 哲学家进餐 | 三种解法：限并发数、奇偶不同顺序、拿筷整体互斥 |
| 死锁四条件 | 互斥、不可剥夺、请求并保持、循环等待（**必须同时满足**） |
| 循环等待 vs 死锁 | 死锁一定有循环等待；循环等待不一定死锁（同类资源 > 1 时可被链外资源打破） |
| 不死锁最少资源数 | $x \times (y-1) + 1$（x 个进程、每个最多需 y 个同类资源） |
| 可能死锁最小进程数 | $\left\lceil x / (y-1) \right\rceil$ |
| 预防方法 | 破坏互斥（SPOOLing）、破坏不可剥夺（释放/剥夺）、破坏请求并保持（静态分配）、破坏循环等待（顺序资源分配） |
| 安全状态性质 | 安全 → 一定不死锁；不安全 → 可能死锁；死锁 → 一定不安全 |
| 银行家算法 | Need = Max − Allocation；安全性算法反复找 `Need ≤ Work` 的进程并回收资源 |
| 资源请求处理 | 检查 ≤ Need → 检查 ≤ Available → 试探分配 → 安全性算法 → 安全则分配，否则撤销并等待 |
| 死锁检测 | 资源分配图；**死锁定理：图不可完全简化则死锁**；还连着边的进程才是死锁进程 |
| 死锁解除 | 资源剥夺、撤销进程、进程回退 |
| 并发性排序 | 检测死锁 > 银行家算法 > 资源预分配 |

## 易错清单

1. **进程状态转换的死记法**：阻塞态不能直接到运行态，就绪态不能直接到阻塞态。**只有运行中的进程才能主动请求阻塞。**
2. **"键盘输入""缺页异常"导致的是"运行 → 阻塞"，不是"运行 → 就绪"**；只有"时间片用完""被抢占""主动 yield"才是"运行 → 就绪"。
3. **PCB 是进程存在的唯一标志**，进程切换保存的上下文放在 **PCB 中而不是栈中**；每个进程有独立的内核栈。
4. **同一进程的线程切换不需要修改页基址寄存器、不需要切换页表**，原有 TLB 不失效；需要更新的是 PC、通用寄存器、栈基址寄存器。
5. **"操作系统为每个用户级线程建立一个线程控制块"是错误的**——用户级线程的 TCB 由用户态线程库维护。
6. **用户级线程的一个线程阻塞会导致整个进程阻塞**；内核级线程不会。用户级线程**无法利用多处理机并行**。
7. **管道位于内核缓冲区**，不在用户空间也不在磁盘上；**读写都需要互斥**；**不支持 lseek 定位**；是**字节流**而不是消息；所有文件描述符关闭后缓冲区被回收而**不持久化**。
8. **共享内存本身没有任何同步机制**，必须配合信号量；共享物理页框一定相同，但各进程中的逻辑页号可以不同。
9. **等待时间只统计进程处于就绪态的时间**，不要把后备队列等待时间和 I/O 时间算进去。
10. **带权周转时间必然 ≥ 1**；周转时间相同时，运行时间长的进程带权周转时间更小。
11. **题目未说明时，"短作业优先"默认为非抢占式**；只有带"所有进程同时到达"前提时才说 SJF 平均周转时间最少，否则应说 SRTN 最少。
12. **RR 中同一时刻进程下处理机、另一进程到达时，新到达的进程先进入就绪队列**。
13. **时间片过大 RR 退化为 FCFS**；时间片过小则切换开销剧增。
14. **2019-27 多级反馈队列题的坑**：算 P1 等待时间时极易漏掉"P2 在 Q1 执行的那 10 ms 期间 P1 在就绪队列等待"这一段。
15. **2010 年考过"降低优先级的合理时机"是"进程时间片用完"**，不是"完成 I/O 进入就绪队列"或"从就绪态转为运行态"。
16. **"进程处于临界区时不能进行调度"是错的**——只有处于**内核临界区**时才不能调度，用户级临界区中可以调度。
17. **中断处理过程中、内核临界区中、禁用中断期间、原语执行期间不能进行进程调度与切换。**
18. **模式切换不一定是进程切换**：中断处理完成返回用户态时，前后可能是同一个进程。**进程切换一定发生在内核态、前后一定是不同进程。**
19. **四条原则中只有前三条必须实现**，让权等待是可选的（Peterson、TSL、Swap、自旋锁都不满足）。
20. **所有软件互斥方法都不满足让权等待**，因为进入区是空循环忙等。
21. **TSL/Swap 机制下不存在阻塞态的进程**，等待者一直是就绪态或运行态；`while (TSL(&lock))` 应在**开中断**状态下执行。
22. **关中断是特权指令**，用户进程不能使用；中断屏蔽只能用于单处理机。
23. **自旋锁在单处理机上必须配合抢占式调度器**，否则永远自旋无法解锁。
24. **记录型信号量中 `S.value = 0` 表示资源刚好用完、无进程等待**，而不是"没有资源"；`S.value < 0` 时其**绝对值**是等待进程数。
25. **信号量只能进行 P/V 操作，不能做值判断**。`if (bowl >= 1)` 是错误写法。
26. **信号量的 P(S)、V(S) 本身必须原子执行**，因为 S 是共享变量；单处理机可关中断，多处理机需要自旋锁或 CAS。
27. **生产者-消费者中 `P(empty)` 必须在 `P(mutex)` 之前**，颠倒就会死锁；**V 操作顺序可以交换**。
28. **缓冲区数量为 1 时可以省去 `mutex`**（一般信号量天然互斥），但数量 ≥ 2 时必须用 `mutex`。
29. **读-写问题中 `count` 必须用 `mutex` 保护**，否则多个读者可能都认为自己是第一个读者，造成第二个读者永久阻塞。
30. **读者优先会让写者饿死，写者优先会让读者饿死**，加入 `queue` 信号量才是读写公平。
31. **哲学家进餐的死锁根源是循环等待**，三种解法分别破坏"循环等待"（限并发数、奇偶顺序）和"请求并保持"（拿筷整体互斥）。
32. **循环等待不是死锁的充分条件**——同类资源数大于 1 时，等待链外的资源可以打破环。
33. **死锁进程至少 2 个**；**单个进程阻塞不是死锁**；发生死锁时一定有循环等待。
34. **死锁和饥饿是操作系统的问题，死循环是程序员的问题**；死锁进程处于阻塞态，饥饿进程可能处于就绪态或阻塞态。
35. **"银行家算法可以预防死锁"是错的**（它属于死锁避免，没有破坏任何必要条件）；**"银行家算法可以判断系统是否处于死锁状态"也是错的**（判断死锁要用死锁检测）。
36. **不安全状态不一定发生死锁**；但发生死锁时一定处于不安全状态。
37. **银行家算法的请求检查有三步**：不超过 Need、不超过 Available、试探分配后系统仍安全；**三者缺一不可**，任何一步失败都必须拒绝或让进程等待。
38. **死锁检测不需要进程的资源总量信息**，只需要当前时刻的请求与分配情况；而死锁避免需要整个生命周期的最大需求。
39. **化简资源分配图后，还连着边的进程才是死锁进程**，并不是系统中所有进程都死锁。
40. **死锁检测的合理触发时机是"每隔一段时间或 CPU 利用率显著降低时"**，不是"死锁发生时"（逻辑悖论）也不是"每次申请资源时"（开销过大）。
