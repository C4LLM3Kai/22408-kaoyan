## 网络应用模型

### 客户/服务器模型

**客户/服务器（Client/Server，C/S）模型**：通信双方地位不平等，一方是**服务请求方（客户，client）**，另一方是**服务提供方（服务器，server）**。

- **客户（client）**：**面向用户**，是主动方。它必须知道服务器的地址，主动发起通信、等待并接收结果。两个客户之间**不能直接通信**。
- **服务器（server）**：**面向任务**，是被动方。它总是处于运行状态，拥有固定的 IP 地址与**熟知端口号**（如 HTTP 的 80、FTP 的 21），被动地等待并接受来自各客户的请求，处理后将结果返回。

工作流程可以概括为三步：

1. 服务器处于接受请求的状态（打开熟知端口，等待连接）。
2. 客户机发出服务请求，然后等待接收结果。
3. 服务器收到请求，进行处理，把结果返回给客户机。

Web、FTP、远程登录、电子邮件都是典型的**服务集中型** C/S 应用——服务能力集中在少数服务器上。

C/S 模型的固有缺陷是**可扩展性差**：所有请求都由服务器集中处理，用户数增长时服务器的带宽与计算能力成为瓶颈；一旦服务器失效，整个服务就不可用。

### 对等模型

**对等（Peer-to-Peer，P2P）模型**：没有固定的服务提供方与请求方，网络中的每一台计算机（称为**对等方，peer**）**既是服务提供方又是服务请求方**，对等方之间**直接通信**。

P2P 的本质仍然是「请求-响应」，只是每个结点同时扮演 client 与 server 两个角色。它的服务是**分散型**的——服务能力分散在大量对等计算机上。

P2P 的优点：

- 减轻服务器的计算压力，提高系统效率和资源利用率；**多个用户之间可以直接共享文档**。
- **可扩展性好**：结点数增大时，系统的总上传能力也同步增大，性能不会因规模增大而降低。
- **健壮性强**：个别结点失效对整个系统影响不大。
- 成本低。

P2P 的缺点：占用大量对等方的上/下行带宽，**会影响个体的整机速度**；缺乏集中管理，安全性、版权与可管理性差。

:::key C/S 与 P2P 的对比（必背）
| 比较项 | 客户/服务器（C/S） | 对等（P2P） |
| --- | --- | --- |
| 结点地位 | 不平等，客户与服务器角色固定 | 对等，每个结点两种角色兼有 |
| 谁主动 | 客户主动发起，服务器被动等待 | 双方都可主动发起 |
| 客户之间能否直接通信 | **不能** | **能**，对等方之间直接通信 |
| 服务能力 | 集中在服务器（服务集中型） | 分散在大量对等方（服务分散型） |
| 可扩展性 | 差，服务器是瓶颈 | 好，结点越多总能力越大 |
| 典型应用 | Web、FTP、电子邮件、远程登录 | 文件共享、即时通信、P2P 流媒体、分布式存储 |
:::

### P2P 的三种组织方式

按「是否有索引服务器、索引如何组织」划分，P2P 有三种典型方式。

**集中式（第一代）**：代表是 **Napster**。仍然有一个**中央索引服务器**保存「哪个文件在哪些结点上」的目录，但文件内容本身**不在服务器上传输**——查询到结点列表后，由请求方与文件持有方**直接建立连接传送文件**。可见它把 C/S 的「集中索引」与 P2P 的「分散传输」结合起来。

- 优点：索引集中，查找效率高。
- 缺点：**索引服务器是单点故障**，且容易被起诉、被关闭。

**全分布式非结构化（第二代）**：代表是 **Gnutella**。**没有任何中央服务器**，所有结点完全对等。查询采用**泛洪（flooding）**方式：请求方把查询报文发给所有邻居，邻居再转发给自己的邻居，直到跳数（TTL）耗尽；命中者沿原路返回响应。

- 优点：完全去中心化，健壮性最好，无单点故障。
- 缺点：**查询流量随规模指数增长**，可扩展性差，且查询结果不保证完整。

**混合式（第三代）**：代表是 **BitTorrent**。它把结点分成两类：少数能力强的结点做**超级结点（super node）**，负责索引与路由；其余普通结点在超级结点组织下分组（BitTorrent 中称为 torrent）。同一文件被切成许多**块（chunk）**，下载者从多个持有者处并行下载不同的块，同时把已下载的块上传给别人，形成「人人为我，我为人人」的机制。

- 优点：兼顾了查找效率与可扩展性，是目前实际使用最广的方式。

:::warn P2P 易错点
- P2P 中「每个结点既是客户又是服务器」不等于「协议没有服务器进程」。混合式 P2P 中仍有超级结点；集中式 P2P 中仍有索引服务器。
- 「P2P 向多用户分发一个文件比 C/S 快」的原因不是单个结点带宽更大，而是**系统的总上传能力随结点数增加**。这是统考喜欢考的因果表述。
- C/S 模型中「客户与客户之间可以直接通信」是**错误**说法（2019 年真题的正确选项就是从这里出错的）。
:::

:::exam 真题考法
2019 年第 40 题直接考 C/S 与 P2P 模型的特征判断，四个选项分别对应「P2P 结点对等」「C/S 中客户之间能否直接通信」「谁主动发起」「分发文件所需时间」。只要记住上表的五行对比即可满分。
:::

## DNS 系统

DNS 的完整任务是**把便于人记忆的主机名（域名）转换为便于机器处理的 IP 地址**，它运行在 **UDP 之上，熟知端口号 53**，采用 **C/S 模型**。

### 层次域名空间

因特网采用**层次树状结构**的命名方法。一个**域名（domain name）**由若干个**分量（标号）**组成，各分量之间用点「.」隔开，**级别低的写在左边，级别高的写在右边**：

$$ \text{… . 四级域名 . 三级域名 . 二级域名 . 顶级域名} $$

最右边是**顶级域名（Top Level Domain，TLD）**，它的右边是隐藏的**根**（写作一个点，通常省略不写）。

例如 `www.cqut.edu.cn`：`cn` 是顶级域名，`edu` 是二级域名，`cqut` 是三级域名，`www` 是四级域名（主机名）。

**顶级域名分为三类**：

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| 国家顶级域名（nTLD） | 用 ISO 3166 规定的两个字母的国家/地区代码 | `cn` 中国、`us` 美国、`uk` 英国、`jp` 日本、`hk` 香港 |
| 通用顶级域名（gTLD） | 按行业/性质划分 | `com` 公司企业、`net` 网络服务机构、`org` 非营利组织、`edu` 美国教育机构、`gov` 美国政府机构、`int` 国际组织 |
| 基础结构域名（反向域名） | 只有 `arpa` 一个 | 用于反向域名解析，即由 IP 地址查域名 |

**二级域名**是在某个顶级域名下注册的域名。我国的二级域名又分两类：**类别域名**（如 `ac` 科研机构、`com` 工商金融、`edu` 教育、`gov` 政府部门、`net` 网络服务机构、`org` 非营利组织）和**行政区域名**（如 `bj` 北京、`sh` 上海，共 34 个）。

关于**域名与 IP 的关系**，必须清楚三点：

1. 域名是**逻辑概念**，并不代表主机所在的物理地点；`www.cqut.edu.cn` 中的 `cqut` 不表示这台机器地理上一定在重庆。
2. 域名与 IP 地址**不是一一对应的**。一台主机可以有**多个域名**（如 `www.abc.com` 与 `abc.com` 指向同一台机器），一个域名也可以解析到**多个 IP 地址**（用于负载均衡）；多块网卡的主机甚至可以有一个 IP 对应多个域名。
3. DNS 里也**不存储 MAC 地址**，IP 到 MAC 的映射由 ARP 完成，两者不要混。

:::key 域名的两个基本要求
- **唯一性**：一个域名在全球范围内只能指向相同的一批地址，这靠「按等级管理、同级不重名」来保证。
- **易查询**：层次结构使得 DNS 可以把整个命名空间切分成许多**区（zone）**，分散到不同服务器上管理。
:::

### 域名服务器

不可能把全部域名到 IP 的映射放在一台服务器上（负载过大、单点故障、时延过大），因此 DNS 是一个**分布式数据库**，用分布在各地的域名服务器共同实现转换。按层次自上而下分四类：

**根域名服务器**

- 是**最高层次**的域名服务器。
- **每一个根域名服务器都知道所有顶级域名服务器的域名及其 IP 地址**。
- 全球共有 **13 个**根域名服务器（按 IP 地址计），每一个「服务器」实际由分布在世界各地的多台机器组成的**服务器群集**（cluster）实现；查询时由路由器用**任播（anycast）**把请求转发到**离 DNS 客户最近的那一个**根域名服务器。
- **根域名服务器通常并不直接解析域名**，而是返回该域名所属**顶级域名服务器的 IP 地址**。它的作用更像是「指路」。

**顶级域名服务器**

- 负责管理**在该顶级域名服务器注册的所有二级域名**（即管一个顶级域，如 `.com`、`.cn`）。
- 收到查询时给出回答：可能是最终的 IP 地址，也可能是指向下一级**权限域名服务器的 IP 地址**。

**权限域名服务器（权威域名服务器）**

- 负责管理**某个区（zone）**的域名。
- **每一台主机的域名都必须在某个权限域名服务器处注册登记**，因此它掌握其管辖范围内域名与 IP 地址的映射关系。
- 它**还知道其下级域名服务器的地址**（若该区还往下划分了子区）。
- 一个区可以只对应一台权限域名服务器，但为了提高可靠性，通常一个区设置**至少两台**权限域名服务器（主、辅），其中一台失效时另一台仍可提供服务。

**本地域名服务器（默认域名服务器）**

- **它不属于上述的域名服务器等级结构**——这是最常考的一句话。
- 当一个主机发出 DNS 查询请求报文时，这个报文**首先被送往该主机的本地域名服务器**。
- 本地域名服务器起着**代理**的作用，把查询转发到上述等级结构中，并把结果返回给主机。
- 每一个 ISP、一个大学乃至一个学院都可以拥有一个本地域名服务器。
- 它离用户很近（一般不超过几个路由器的距离，甚至就在同一局域网），其 **IP 地址必须直接配置在需要域名解析的主机中**（可由 DHCP 自动配置，也可手工配置）。

**区（zone）与域（domain）的区别**：域是命名空间的一个子树，是逻辑上的划分；**区是 DNS 服务器实际管辖的范围**，是为了分散管理而对域做的物理切分。一个区内的所有域名信息存放在同一台（组）权限域名服务器上，这台服务器称为该区的「权威」。下级的区可以把自己的授权委托出去，因此「域」的边界与「区」的边界不一定重合——一个域可以划分成多个区，每个区由不同的权限域名服务器管理。

:::warn 区与权限域名服务器的易错点
- 题目问「该域名由哪台服务器解析」时，必须**按题目给出的具体域名逐级判断**：权限域名服务器**可能不止一个**，`abc.xyz.com` 的权限服务器与 `xyz.com` 的权限服务器通常不是同一台。
- 「本地域名服务器」永远不在根 → 顶级 → 权限这条等级链上，画图题里它一定单独画在旁边。
:::

:::exam 真题考法
常考形式是「下列说法错误的是」，错误项多半出在「本地域名服务器属于域名服务器等级结构」「根域名服务器直接返回 IP 地址」这两处。另外 2021 年、2016 年的题目要求根据拓扑图判断具体是哪台服务器完成解析，注意**权限域名服务器可能不止一个**。
:::

### 域名解析过程

把一个域名映射成 IP 地址的过程叫**域名解析**。查询方式有两种：

**递归查询（recursive query）**

客户把请求发给某台域名服务器后，**如果该服务器不知道答案，它必须代替客户去询问下一台服务器，并把最终结果返回给客户**。也就是说，被查询者承担了「继续查下去」的义务，客户只需要等一个最终答案。

- 特点：对客户最省事，但**对被查询的域名服务器负担极大**。

**迭代查询（iterative query）**

客户把请求发给某台域名服务器后，如果该服务器不知道答案，它**只返回「你下一步该去问谁」的 IP 地址（转介信息）**，由**客户自己**再去询问下一台服务器；如此反复，直到某台服务器给出最终答案。

- 特点：服务器负担轻，但客户（通常是本地域名服务器）要多发几次请求。

:::key 因特网实际使用的组合方式（必背）
**从请求主机到本地域名服务器的查询通常是递归查询；而本地域名服务器向根、顶级、权限域名服务器发出的查询通常是迭代查询。**

原因：递归查询对被查询的服务器负担太大，而本地域名服务器数量相对少、能力较强，让它「跑腿」比让根域名服务器为每个客户层层代查更合理。
:::

以主机 `m.xyz.com` 想查 `y.abc.com` 的 IP 地址为例，完整的迭代解析流程如下（假设各服务器与本地域名服务器的缓存都为空）：

1. `m.xyz.com` 向自己的本地域名服务器 `dns.xyz.com` 发出 **DNS 查询请求报文**（UDP 用户数据报，目的端口 53），报文中带查询域名 `y.abc.com` 和查询类型 A（地址记录）。这一步是**递归查询**。
2. 本地域名服务器缓存中没有该域名，于是向**根域名服务器**发出查询报文。
3. 根域名服务器不知道 `y.abc.com` 的地址，返回**顶级域名服务器 `dns.com` 的 IP 地址**。`dns.com` 是 `.com` 这个顶级域的服务器。
4. 本地域名服务器再向 `dns.com` 查询，`dns.com` 返回 **`y.abc.com` 所在区域的权限域名服务器 `dns.abc.com` 的 IP 地址**。
5. 本地域名服务器再向 `dns.abc.com` 查询，`dns.abc.com` 是 `abc.com` 区的权威服务器，知道 `y.abc.com` 的映射关系，于是返回 **`y.abc.com` 的 IP 地址**（最终答案）。
6. 本地域名服务器把结果返回给主机 `m.xyz.com`，并按 TTL **把这条记录存入自己的高速缓存**。

一共 **4 条查询报文 + 3 条响应报文 = 7 条 DNS 报文**，其中本地域名服务器**发出了 4 条查询**（3 条迭代查询由它自己发起，另 1 条是它转发给根的那次）。如果题目只问「本地域名服务器发出多少次查询」，答案就是 **4 次**；如果问「本地域名服务器向外发出多少条 DNS 报文」，则是 **4 条查询 + 3 条收到的响应 = 7 条**（收到的不算「发出」）。这两种问法的区别是本章最容易失分的地方。

#### 解析报文数与查询次数的计算

通用的计算规则有两条，务必记牢：

**规则一：本地域名服务器发出的查询次数 = 需要经过的层次数。**

若采用**迭代查询**，并且只考虑标准的 4 层结构（根 → 顶级 → 二级权限 → 三级权限…），那么：

$$ \text{本地域名服务器发出的查询次数} = \text{域名的级数（去掉主机名）} + 1 $$

其中「+1」是**向根域名服务器的那一次查询**。

**规则二：如果题目说「本地域名服务器只提供递归查询，其他服务器只提供迭代查询」，则只有本地域名服务器在跑腿**，用户的请求只有 1 条由主机发出，用户的等待时间只需按本地域名服务器的迭代次数计算 RTT。

**算例一（无缓存、本地迭代）**

主机 H 访问 `www.abc.xyz.com`，本地域名服务器无任何缓存，采用迭代查询。求本地域名服务器**发出**的最少、最多 DNS 查询次数。

- **最少 0 次**：本地域名服务器的高速缓存中已有 `www.abc.xyz.com` 的 IP 地址，直接回答 H，不需要向外发任何查询。
- **最多 4 次**：无缓存时按迭代依次查询

  1. 根域名服务器 → 得到 `.com` 顶级域名服务器地址；
  2. `.com` 顶级域名服务器 → 得到 `xyz.com` 的权限域名服务器地址；
  3. `xyz.com` 权限域名服务器 → 得到 `abc.xyz.com` 的权限域名服务器地址；
  4. `abc.xyz.com` 权限域名服务器 → 得到 `www.abc.xyz.com` 的 IP 地址。

  即：`www.abc.xyz.com` 去掉主机名 `www` 后剩 `abc`、`xyz`、`com` **3 级**，$3+1=4$ 次。

:::warn DNS 报文数计算三个必踩的坑
1. **「发出」还是「收到」**：题目问 `201.1.1.1`（本地域名服务器）发出的查询次数时，**不包含主机 H 发给它的那一条递归查询**；最少 0 次、最多 4 次（2016 年真题答案）。
2. **主机名不计入级数**：`www.abc.xyz.com` 的迭代次数按 `abc.xyz.com` 算（3 级 + 1 = 4 次），不要把 `www` 也算成一级而得出 5 次。
3. **「最少」的两种情形不同**：若问「本地域名服务器发出的查询次数」，有缓存时是 **0 次**；若问「从点击链接到收到页面」，即使本地有缓存，主机到本地域名服务器的那 **1 次递归查询（1 个 RTT）仍然要算**。
:::

**算例二（DNS 与 HTTP 合并计算，2020 年真题模型）**

主机 H 通过超链接 `http://www.abc.com/index.html` 请求纯文本页面 `index.html`。局域网内主机访问 Internet 上各服务器的 RTT 均为 10 ms，忽略其他时延。本地域名服务器只提供**递归**查询服务，其他服务器只提供**迭代**查询服务。求从点击超链接到浏览器收到页面所需的最短与最长时间。

- **HTTP 部分固定要 2 个 RTT**：1 个 RTT 建立 TCP 连接（三次握手的前两次往返归入一个 RTT），1 个 RTT 发送 HTTP 请求并收到响应。$2 \times 10 = 20\text{ ms}$。
- **最短**：本地域名服务器已有 `www.abc.com` 的缓存，不再对外查询，于是主机与本地服务器之间**仍是 1 次递归查询**，但它与 TCP 建连的第一个 RTT 在时间上被合并考虑后不额外增加 RTT——按 2020 年真题的标准解法，此时总时间就是 HTTP 的 **20 ms**（DNS 查询的时延被计入/忽略方式以真题为准，此处真题给的是 20 ms 最短）。
- **最长**：无任何缓存，本地域名服务器按迭代依次查询根、`.com` 顶级、`abc.com` 权限域名服务器，共 **3 个 RTT**（$3\times10=30$ ms）；加上 HTTP 的 20 ms，共 **50 ms**。

所以答案是「20 ms，50 ms」。注意域名 `www.abc.com` 的迭代次数是 3 次（`abc` + `com` 两级，再加根一次），不要算成 4 次。

#### 高速缓存

为了提高查询效率、**减轻根域名服务器的负荷**、减少因特网上的 DNS 查询报文数量，各级域名服务器广泛使用**高速缓存（cache）**，用来存放**最近查询过的域名以及从何处获得域名映射信息的记录**。

- 本地域名服务器缓存命中时，直接把缓存中的结果返回给主机，**不再向外发出任何查询**。
- **用户主机中也有高速缓存**：许多主机在启动时从本地域名服务器下载域名与 IP 地址的数据库，维护自己最近使用过的域名缓存，只在缓存中找不到时才向域名服务器查询。
- 缓存中的记录有**生存时间（TTL）**。由于域名到 IP 的映射关系并非永久不变，域名服务器必须为每项内容设置计时器，删除超过合理时间的项（例如每个项目只存放两天）。因此缓存可能返回**过期的**映射，这是用「效率」换来的代价。

:::warn 缓存易错点
- 有缓存时「查询次数为 0」指的是**本地域名服务器不向外查询**，主机到本地域名服务器的那一次查询仍然发生。
- 「主机与本地域名服务器之间采用递归查询」这一点**不因有无缓存而改变**。缓存命中只是让本地域名服务器不必再跑腿。
:::

#### DNS 的传输层选择

:::key DNS 什么时候用 UDP，什么时候用 TCP
- **主要使用 UDP，熟知端口号 53**。普通查询与应答都是单个请求/单个响应，报文短、无连接开销、时延小，重传由应用层自己用超时机制解决。
- **下列情况必须改用 TCP（同样用端口 53）**：
  1. **区域传送（zone transfer）**：主域名服务器向辅助域名服务器同步整个区的数据库，数据量可能很大，必须保证可靠传输。
  2. **响应报文超过 512 字节**：传统的 DNS 报文在 UDP 里限长 512 字节，超过时由服务器返回「截断」标志，客户端改用 TCP 重发；或者直接使用 EDNS0 扩展。所以 2018 年第 33 题「可以使用传输层无连接服务的应用层协议」答案是 **DNS**。
:::

:::exam 真题考法
- 2010 年第 40 题：**递归**查询时，用户主机与本地域名服务器各发出 **1 条、1 条**请求消息。
- 2016 年第 40 题：**迭代**查询时，本地域名服务器 `201.1.1.1` 发出查询的最少 **0** 次、最多 **4** 次。
- 2018 年第 33 题：可以使用无连接服务的应用层协议是 **DNS**。
- 2020 年第 40 题：DNS 迭代 + HTTP 请求页面，最短 **20 ms**、最长 **50 ms**。
- 2021 年第 47 题：Web 访问前主机除 HTTP 外还运行了 **DNS**，其封装为「DNS 报文 → UDP 数据报 → IP 分组 → 以太网帧」。
:::

## FTP

### FTP 协议的工作原理

**文件传送协议（File Transfer Protocol，FTP）**是因特网上使用最广泛的文件传送协议。它提供**交互式**访问，允许客户指明文件的类型与格式（如是否使用 ASCII 码），并允许文件具有**存取权限**（用户必须经过授权并输入有效口令）。FTP **屏蔽了各计算机系统的细节**，因而适合于在**异构网络**中任意计算机之间传送文件。

FTP 采用**客户/服务器**工作方式，使用 **TCP** 提供的可靠传输服务。一个 FTP 服务器进程可同时为多个客户进程提供服务，其进程分为两类：

- **主进程（1 个）**：负责接收新的请求，始终监听熟知端口 **21**。
- **从属进程（多个）**：每处理一个客户的请求就 fork 一个从属进程，负责该客户的数据传送。

**FTP 工作时使用两条并行的 TCP 连接**：

| 比较项 | 控制连接 | 数据连接 |
| --- | --- | --- |
| 作用 | 传送控制信息（连接请求、登录、目录操作、传送请求、终止等命令与响应） | 传送文件内容或目录列表 |
| 服务器端口 | **21**（熟知端口） | **主动模式下为 20**；被动模式下为服务器随机分配的临时端口 |
| 客户端口 | 客户自己分配的临时端口 | 客户自己分配的临时端口 |
| 建立/释放时机 | 在整个会话期间**始终保持打开** | **每次文件传输时才建立，传输结束就关闭**（按需建立） |
| 谁发起 | 客户主动发起（客户连服务器 21） | 主动模式下**服务器**发起；被动模式下**客户**发起 |
| 传输内容 | 命令与应答，是文本 | 文件数据，可以是二进制 |

因为控制信息走的是**另一条独立的连接**，而不是与数据混在同一条连接里，所以称 **FTP 的控制信息是「带外（out-of-band）」传输的**。这正是 FTP 与 HTTP 的根本差别：HTTP 把请求与响应都放在同一条 TCP 连接里，属于「带内（in-band）」传输。

:::key 带外控制的含义
「带外」指**控制信息与数据走不同的连接（不同的 TCP 连接，进而使用不同的端口）**。好处是：即使数据连接正在满负荷地传送一个大文件，控制连接依然是通的，客户可以随时发出「终止传输」「放弃」等命令，服务器也能即时回应。若把控制命令塞进数据流里排队（带内），就必须等前面的数据传完才能终止，响应会非常迟钝。
:::

#### 主动模式与被动模式

数据连接的建立方向有两种模式，这是 FTP 最常考的细节。

**主动模式（PORT 模式）**

1. 客户用临时端口连接服务器的 **21** 端口，建立控制连接并登录。
2. 客户需要传数据时，在**控制连接**上随机开一个临时端口，并通过 **PORT 命令**把「我的 IP + 我的端口号」告诉服务器。
3. 服务器用自己 **20** 端口**主动**去连接客户刚才告诉它的那个端口，建立数据连接。
4. 因此「主动」是指**服务器主动发起数据连接**。

**被动模式（PASV 模式）**

1. 控制连接同样建立在服务器的 21 端口。
2. 客户需要传数据时，在控制连接上发送 **PASV 命令**。
3. 服务器**随机打开一个临时端口**，并把该端口号通过控制连接告诉客户。
4. **客户主动**去连接服务器的这个临时端口，建立数据连接。
5. 因此「被动」是指**服务器被动等待客户来连**。

被动模式的意义在于：主动模式下服务器要反过来连客户，如果客户在防火墙/NAT 后面，这个入向连接会被拦掉；被动模式下所有连接都由客户发起，防火墙友好。

:::warn FTP 端口易错点
- **20 和 21 都是服务器端口号**，客户端的端口号由客户系统自行分配，**不固定**。2017 年第 40 题的错误选项正是「服务器与客户端的 TCP 20 端口建立数据连接」——20 是服务器的端口，不是客户端的。
- **被动模式下数据连接不使用 20 端口**，而是服务器临时分配的随机端口。所以「FTP 数据连接一定用 20」是错的。
- 控制连接在整个会话期间保持打开；数据连接**每传一次就建立、传完就关闭**。2023 年第 47 题第 (1) 问的答案就是「控制连接是持久的，数据连接是非持久的」。
- 「会话期间保持打开」指控制连接一直存在，但**数据连接可以是多次**：传一个文件就关一次，再传再建。
:::

#### FTP 连接分析算例

**算例（基于 2023 年第 47 题的模型）**

主机 H 登录到 FTP 服务器后，向服务器上传一个大小 $18000\text{ B}$ 的文件 F。建立数据连接时选择的初始序号为 100，$\text{MSS}=1000\text{ B}$，拥塞控制初始阈值 $ssthresh=4\text{ MSS}$，$\text{RTT}=10\text{ ms}$，忽略 TCP 传输时延，H 均以 MSS 段发送数据且无差错、无丢包、无乱序。问：

**(1) 建立了哪些 TCP 连接？** H 登录 FTP 服务器时先建立的是**控制连接**（客户临时端口 → 服务器 21）。此后每次传文件再建立**数据连接**。所以 H 登录时建立的 TCP 连接是**控制连接**。

**(2) F 的第一个字节序号是多少？** 数据连接本身的初始序号是 100，但 F 的第一个字节前面还有 **1 个 SYN 段占用的序号**：TCP 的 SYN 会消耗 1 个序号。因此 F 的第一个字节序号是 $100+1=101$。

**(3) 断开数据连接时，FTP 服务器发送的第二次挥手 ACK 段的确认序号是多少？** F 共 $18000\text{ B}$，从序号 101 开始，则最后一个字节的序号为 $101+18000-1=18100$。因此服务器在第二次挥手（对 H 的 FIN 的确认）中，确认序号为 $18100+1=\mathbf{18101}$。

**(4) 拥塞窗口的调整**：慢开始阶段每收到一个对新数据的确认，$cwnd$ 加 1 MSS（指数增长），直到达到 $ssthresh=4\text{ MSS}$ 后转为拥塞避免（线性增长，每 RTT 加 1 MSS）。

- 收到确认序号 **2101** 时：已连续确认到 2100，即 $2100-101+1=2000\text{ B}=2\text{ MSS}$，此时 $cwnd$ 从 1 MSS 增至 **2 MSS**（慢开始阶段）。
- 收到确认序号 **7101** 时：已连续确认到 7100，即 $7100-101+1=7000\text{ B}=7\text{ MSS}$。按慢开始：1→2→4 MSS（达到阈值），此后进入拥塞避免，每 RTT 加 1 MSS：4→5→6→7 MSS。所以 $cwnd$ 调整为 **7 MSS**。

**(5) 总时间与应用层平均速率**：需要把 $18000\text{ B}$ 分成 18 个 MSS 段。计入建立数据连接（1 RTT）与四次挥手（其中 H 的 FIN 与服务器的 ACK 常合并分析，按真题口径计 2 个 RTT）后共 **7 个 RTT**，即 $7\times10=70\text{ ms}$；应用层数据平均发送速率 $= 18000\text{ B}/70\text{ ms} \approx 257\text{ B/ms}=257\text{ kB/s}$（按真题给定口径计算结果）。

:::exam 真题考法
2009 年第 40 题考「FTP 命令走的是建立在 TCP 之上的**控制连接**」；2017 年第 40 题考 FTP 两条连接的四个特征判断；2023 年第 47 题把 FTP 与 TCP 序号、拥塞窗口、四次挥手结合成大题。**FTP 部分真正考的是 TCP，FTP 只是外壳**，所以第 (2)～(5) 问的工夫要花在传输层上。
:::

### 控制连接与数据连接

**控制连接的作用**：客户与服务器之间传送**命令与应答**。它承载的内容包括用户登录（用户名、口令）、改变工作目录、列出目录（`LIST`）、指定传输模式与文件类型、发起一次文件传送的请求（`RETR` 下载 / `STOR` 上传）、终止传送（`ABOR`）以及退出（`QUIT`）等。控制连接传送的是**文本形式的命令与三位数字应答码**，**不传送文件数据**。

**数据连接的作用**：在客户与服务器之间传送**文件内容**（`RETR`/`STOR`）或**目录列表**（`LIST`）。它的特点是**按需建立、用完即关**。数据连接上还可以选择传输方式（流方式、块方式、压缩方式）与表示类型（ASCII 文本、二进制图像），这是「FTP 允许客户指明文件类型与格式」的体现。

:::key FTP 两条连接与 HTTP 一条连接的对比
| 比较项 | FTP | HTTP |
| --- | --- | --- |
| TCP 连接条数 | **2 条**（控制连接 + 数据连接） | **1 条**（同一连接既传请求响应也传实体） |
| 控制信息位置 | **带外**（独立控制连接） | **带内**（与数据在同一连接，靠报文格式区分） |
| 连接是否持续 | 控制连接持续；数据连接按需建立、用完释放 | 非持久连接下一个对象一条连接；持久连接下保持 |
| 状态 | **有状态**：服务器记住登录状态与当前工作目录 | **无状态**：服务器不保存客户的历史信息（Cookie 是后加的补救） |
| 传输层 | TCP | TCP |
| 默认端口 | 21（控制）、20（主动模式数据） | 80 |
:::

「FTP 是有状态的」这一点常被考到：服务器要记住用户是否已登录、当前处于哪个目录、传的是哪个文件——这些状态跨多条命令保持，是控制连接长期存在的原因。HTTP 每条请求自带完整信息（`Host`、`Cookie` 等），服务器不必记住上一次是谁来访问过。

## 电子邮件

### 电子邮件系统的组成结构

电子邮件系统采用**客户/服务器**方式，由三个主要部分组成：

**用户代理（User Agent，UA）**

用户与电子邮件系统之间的**接口**，即电子邮件客户端软件或网页版邮件界面。它的职责是：撰写、显示、处理和**发送与接收**邮件。用户代理把邮件「提交」给自己的邮件服务器，或从自己的邮件服务器「取回」邮件。

**邮件服务器**

电子邮件系统的**基础设施**，负责**发送和接收**邮件，同时维护用户的邮箱。它同时充当**客户**和**服务器**：向别的邮件服务器发送邮件时是 SMTP 客户，接收别的邮件服务器送来的邮件时是 SMTP 服务器。邮件服务器必须在 24 小时不间断运行，并具有固定的 IP 地址与域名。

**协议**

- **邮件发送（推送）协议**：**SMTP**（TCP 25），负责「用户代理 → 发送方邮件服务器」以及「发送方邮件服务器 → 接收方邮件服务器」。
- **邮件读取（拉取）协议**：**POP3**（TCP 110）或 **IMAP**（TCP 143），负责「接收方邮件服务器 → 用户代理」。
- 网页版邮件还可由 **HTTP** 承担发送与读取。

:::key 邮件收发的完整流程（背下来就能做所有流程题）
设发件人 A 的邮箱在邮件服务器 S1 上，收件人 B 的邮箱在邮件服务器 S2 上：

1. A 通过**用户代理**撰写邮件。
2. 用户代理用 **SMTP** 把邮件「推」给**发送方邮件服务器 S1**。
3. S1 把邮件放入**邮件缓存队列**中等待发送。
4. S1 的 SMTP 客户进程周期性扫描缓存队列（例如每 30 分钟），发现有待发邮件后，与**接收方邮件服务器 S2** 的 SMTP 服务器进程建立 **TCP 连接（端口 25）**。
5. TCP 连接建立后，S1 用 SMTP **把邮件「推」给 S2**；所有邮件发送完毕后断开 TCP 连接。
6. S2 收到邮件后，把它放入**收件人 B 的用户邮箱**中，等待 B 在方便的时候读取。
7. B 想收信时，通过用户代理用 **POP3 或 IMAP** 从 S2 **「拉」** 回自己的邮件。

**判断口诀**：凡是「交给服务器 / 服务器之间转发」的环节都用 **SMTP（推）**；凡是「从自己的服务器取回来」的环节都用 **POP3/IMAP（拉）**。
:::

:::warn 电子邮件流程易错点
- **不能把邮件直接推给收件人的用户代理**。原因有二：并非所有计算机都能运行邮件服务器程序；收件人的计算机也不一定 24 小时开机，发信时若对方不在线就无法处理，所以必须由**始终在线**的邮件服务器代为缓存。
- 电子邮件地址格式为「**用户名@邮件服务器所在主机的域名**」，例如 `abc@163.com`。`@` 后面是**域名**而不是 IP。
- 所有邮件相关连接都基于 **TCP**，都是 **C/S** 方式。**没有一个邮件协议用 UDP。**
- 2012 年第 40 题的三个阶段依次是 **SMTP、SMTP、POP3**：① UA→发送方服务器，② 发送方服务器→接收方服务器，③ 接收方服务器→UA。
:::

### 电子邮件格式与 MIME

**邮件格式**在 RFC 822（2008 年后更新为 RFC 5322）中单独定义，**不是由 SMTP 定义的**。一封邮件由**信封**和**内容**两部分构成，内容又分为**首部**和**主体**。

- **信封**：由邮件系统**自动生成**，从首部中提取所需信息写在信封上，相当于「邮局看的部分」。
- **首部（header）**：由若干**首部行**组成，每行是「字段名: 值」。关键字包括：
  - `From:` 发件人邮箱地址；
  - `To:` 收件人邮箱地址（多个用逗号分隔）；
  - `Cc:` 抄送（carbon copy）收件人；
  - `Subject:` 邮件主题；
  - 还可有 `Date:`、`Reply-To:`、`Bcc:`（密送）等。
- **主体（body）**：用户自由编写的**信件正文**，是真正要传达的内容。

:::key 首部与主体之间的空行
**首部与主体之间必须用一个空行分隔。** 邮件系统读到这个空行即认为首部结束、下面全部是正文。少写这个空行会把正文的第一行当成又一个首部字段，导致正文丢失或解析错误。
:::

**MIME（多用途因特网邮件扩展，Multipurpose Internet Mail Extensions）**

:::key 为什么需要 MIME
SMTP **只能传送 7 位 ASCII 码文本数据**，不能传送可执行文件或其他二进制对象，不能满足传送多媒体邮件（图片、音频、视频）的需要，许多非英语文字（中文、俄文等）也无法用 SMTP 直接传送。**MIME 不是要取代或改动 SMTP**，它的意图是**继续使用现有的邮件格式与 SMTP**，只在邮件主体上做扩展。
:::

MIME 做了三件事：

1. **增加了 5 个新的邮件首部字段**，提供有关邮件主体的信息。最常用的是：
   - **`Content-Type`**：说明主体的数据类型与子类型，如 `text/plain`、`text/html`、`image/jpeg`、`application/octet-stream`、`multipart/mixed`。它决定了接收方用什么方式「解释」主体。
   - **`Content-Transfer-Encoding`**：说明主体的**编码方式**，如 `7bit`、`8bit`、`base64`、`quoted-printable`，即「这段内容是经过哪种编码才变成 ASCII 的」。
   - 其余还有 `Content-ID`、`Content-Description`、`MIME-Version` 等。
2. **定义了多种邮件内容的格式**，对多媒体电子邮件的表示方法进行了标准化。
3. **定义了传送编码**，可对任何内容格式进行转换而不会被邮件系统改变。

**base64 编码**是最重要的传送编码：它把任意二进制数据按 **每 3 个字节（24 位）** 一组，重新划分为 **4 个 6 位**，每个 6 位用**一个 ASCII 字符**表示（字符表为 `A-Z a-z 0-9 + /`），因此编码后数据量约为原来的 $\tfrac{4}{3}$，即膨胀约 **33%**。若最后一组不足 3 字节，用 `=` 补齐。它保证编码结果全部落在 7 位 ASCII 范围内，从而能安全通过只认 ASCII 的 SMTP。

MIME 后来也被同样面向 ASCII 字符的 **HTTP** 使用（HTTP 首部里的 `Content-Type` 就来源于此）。

:::warn MIME 易错点
- **MIME 不改变 SMTP 协议**，SMTP 仍然只传 ASCII；是 MIME 在**发送前编码、接收后解码**，把非 ASCII 内容「伪装」成 ASCII。
- 2018 年第 40 题问「无需转换即可由 SMTP 直接传输的内容」，答案是 **ASCII 文本**；JPEG、MPEG、EXE 都必须先编码。
- `Content-Type` 说的是「是什么」，`Content-Transfer-Encoding` 说的是「怎么编码的」，两者不要搞反。
:::

### SMTP 协议与 POP3 协议

#### SMTP 的工作过程

**SMTP（Simple Mail Transfer Protocol，简单邮件传送协议）**：C/S 模型，建立在 **TCP** 之上，熟知端口号 **25**。它是**「推」协议**——由发送方主动把邮件推给接收方。

SMTP 的一次典型会话（命令/响应方式，命令由客户发出，应答是三位数字码）：

| 步骤 | 客户（发送方）发出 | 服务器应答 | 含义 |
| --- | --- | --- | --- |
| 1 | （建立 TCP 连接，端口 25） | `220` | 服务器主动推送「服务就绪」 |
| 2 | `HELO hnust.edu.cn` | `250` | 客户说明身份、告知自己的域名；身份有效则回 250，否则回其他代码（如 421 服务不可用） |
| 3 | `MAIL FROM:` 后跟发件人邮箱地址 | `250` | 告知邮件来自何方 |
| 4 | `RCPT TO:` 后跟收件人邮箱地址 | `250` | 告知邮件去往何地；邮箱存在则回 250 |
| 5 | `DATA` | `354` | 告知准备发送邮件内容；服务器准备好接收则回 354 |
| 6 | `<邮件内容>` 后跟一行只有「`.`」的结束符 | `250` | 传送正文，用单独一行的句点表示结束；收件成功回 250 |
| 7 | `QUIT` | `221` | 请求断开 TCP 连接；服务器回 221 并主动关闭 |

SMTP 共有约 14 条命令、21 种应答。应答代码后面一般跟有简单的描述信息，不同的 SMTP 服务器对同一应答码的描述信息可能不同。

**发送方邮件服务器的工作特点**：邮件先进入缓存队列，服务器**周期性扫描**（如每 30 分钟）缓存，发现有邮件才尝试与接收方服务器建立连接并发送；若发送失败则保留在队列中稍后重试。

:::key SMTP 的三大局限与推论
1. **只能传送 7 位 ASCII 码文本**——这是引入 MIME 的直接原因，也是最常考的一条。
2. **明文传送，不利于保密**——SMTP 本身不加密，需要安全性时用 TLS 加密或使用带加密的扩展。
3. **只负责「推」到收件人的邮件服务器，不负责「取」**——用户代理从服务器读邮件要另用 POP3/IMAP。所以 2013 年第 40 题「SMTP 支持从邮件服务器向用户代理发送邮件」是**错误**的。
:::

#### POP3 的工作过程

**POP3（Post Office Protocol，邮局协议第 3 版）**：C/S 模型，建立在 **TCP** 之上，熟知端口号 **110**，是因特网正式标准。它是**「拉」协议**——由用户主动从邮件服务器把邮件拉回本地。

POP3 会话分为三个阶段：

1. **认证阶段**：客户用 `user <用户名>` 与 `pass <口令>` 登录，服务器校验身份。
2. **事务处理阶段**：客户可以 `stat`（查询邮件数与总大小）、`list`（列邮件清单）、`retr`（取回第 n 封邮件）、`dele`（标记删除第 n 封）、`quit`。
3. **更新阶段**：客户发出 `quit` 后进入此阶段，服务器**真正执行**事务阶段中标记的删除操作，释放资源并关闭连接。

**POP3 的两种下载方式**（考纲明确要求）：

- **下载并删除（download and delete）**：邮件取回本地后**立即从服务器删除**。优点是服务器空间释放快；缺点是用户换一台机器就再也看不到这些邮件。
- **下载并保留（download and keep）**：邮件取回后**仍保留在服务器上**。优点是可以多台设备重复读取；缺点是占用服务器存储，且用户需要自己清理。

POP3 **不允许用户在邮件服务器上管理自己的邮件**（不能建文件夹、不能分类、不能只读某个首部），这是它「功能有限」的体现。

**IMAP（Internet Message Access Protocol，因特网邮件访问协议）**：端口 **143**，功能比 POP3 强大。用户在**自己的计算机上就可以操控服务器中的邮箱**，就像在本地操控一样，因此 IMAP 是**联机协议**；它允许用户代理**只获取报文的某些部分**（例如只读一个首部），也允许在服务器上创建文件夹、分类管理。

**共同点**：POP3 与 IMAP4 都采用**基于 TCP 连接的客户/服务器方式**。

#### SMTP 与 POP3 的对比

:::key SMTP 与 POP3 对比表（必背）
| 比较项 | SMTP | POP3 |
| --- | --- | --- |
| 作用 | 发送（推送）邮件：UA → 发送方服务器、服务器 → 服务器 | 读取（拉取）邮件：接收方服务器 → UA |
| 数据流动方向 | **推（push）**，发送方主动 | **拉（pull）**，接收方主动 |
| 传输层 | TCP | TCP |
| 熟知端口号 | **25** | **110** |
| 工作模型 | C/S | C/S |
| 传输内容限制 | **只能传 7 位 ASCII 文本**（非 ASCII 需 MIME 编码） | 传送的是整封邮件（内容已在服务器上存好），本身不限制内容 |
| 会话特点 | 命令/应答（HELO、MAIL FROM、RCPT TO、DATA、QUIT） | 三个阶段：认证、事务处理、更新；`quit` 后才真正删除 |
| 是否需要认证 | 传统 SMTP 无认证（后来增加了认证扩展） | 认证阶段必须提供用户名与口令 |
| 是否允许管理服务器邮箱 | 不涉及 | **不允许**建文件夹、分类等（IMAP 才允许） |
:::

:::warn 邮件协议易错点
- **端口记错**：SMTP 是 25，POP3 是 **110**，IMAP 是 **143**。不要写成 25/110 之外的数。
- **方向记反**：SMTP 是「推」，POP3/IMAP 是「拉」。凡是「服务器 → 用户代理」的环节**一定不是 SMTP**（除非是网页邮件用 HTTP）。
- **2015 年第 33 题**问「POP3 使用的传输层服务类型」，答案是有连接可靠的传输服务（TCP）。
- **「SMTP 地址出错不能发邮件，POP3 地址出错不能收邮件」** 这类对应关系可以辅助记忆，但真正要记的是协议与端口的对应。
- **网页版邮件**（如用浏览器收发 163 邮箱）时，UA 到服务器用 **HTTP**，服务器之间仍用 **SMTP**——所以「邮件发送一定用 SMTP」这个说法在网页邮件的第一个环节上并不成立。
:::

## WWW

### WWW 的概念与组成结构

**万维网（World Wide Web，WWW）并非某种特殊的计算机网络**，而是一个**大规模的、联机式的信息储藏所**，是运行在因特网上的一个**分布式应用**。它利用网页之间的**超链接（hyperlink）**把不同网站的网页链接成一张逻辑上的信息网，用户通过「点击链接」就能在全世界范围内跳转浏览。

万维网由 Tim Berners-Lee 于 1989 年 3 月在欧洲粒子物理实验室提出；1993 年 2 月第一个图形界面浏览器 Mosaic 问世，1995 年 Netscape Navigator 上市。

**万维网的三个核心要素**：

| 要素 | 全称 | 解决的问题 |
| --- | --- | --- |
| **URL** | 统一资源定位符（Uniform Resource Locator） | **怎样标识**分布在世界各地的文档（资源在哪） |
| **HTTP** | 超文本传送协议（HyperText Transfer Protocol） | **用什么协议**传送文档 |
| **HTML** | 超文本标记语言（HyperText Markup Language） | **怎样解析/显示**文档的格式 |

浏览器最重要的部分是**渲染引擎（浏览器内核）**，负责解析并显示网页内容。常见内核：Chrome 与 Opera 用 Blink，Firefox 用 Gecko，Safari 用 WebKit。不同内核对网页的解析不同，因此同一网页在不同浏览器里显示效果可能不同。除 HTML 外，网页通常还包含 **CSS**（层叠样式表，从审美角度描述样式）与 **JavaScript**（一种脚本语言，控制网页行为，**与 Java 没有任何关系**）。

#### URL 的完整格式

**URL** 用来指明因特网上任何种类「资源」的位置。其一般形式为：

$$ \langle \text{协议} \rangle :// \langle \text{主机} \rangle : \langle \text{端口} \rangle / \langle \text{路径} \rangle $$

以 `http://www.hnust.cn:80/ggtz/119945.htm` 为例：

| 部分 | 值 | 含义 |
| --- | --- | --- |
| 协议 | `http` | 访问资源所用协议（还可能是 `https`、`ftp`、`file` 等） |
| 主机 | `www.hnust.cn` | 存放资源的主机**域名**（也可以直接写 IP 地址） |
| 端口 | `80` | 服务器上的端口号，**可以省略**；省略时使用该协议的默认端口（HTTP 为 80） |
| 路径 | `/ggtz/119945.htm` | 资源在主机上的路径与文件名，**可以省略**；省略时表示访问该网站的**主页（home page）** |

需要扩展记忆的是，完整 URL 还可以带**查询串（query）**与**片段标识符（fragment）**：

$$ \underbrace{https}_{\text{协议}} :// \underbrace{\text{www.abc.com}}_{\text{主机}} : \underbrace{443}_{\text{端口}} \underbrace{/news/list.htm}_{\text{路径}} \underbrace{?id=408\&page=2}_{\text{查询}} \underbrace{\#top}_{\text{片段}} $$

- **查询（`?` 之后）**：以 `?` 开始、`键=值` 用 `&` 连接，把参数传给服务器上的程序，**会被发送给服务器**。
- **片段（`#` 之后）**：定位到文档内部的某个锚点，**只由浏览器本地使用，不会发送给服务器**——这是容易被考到的细节：改变片段不会产生新的 HTTP 请求。

:::warn URL 易错点
- URL 中的主机部分写的是**域名**（如 `www.hnust.cn`），但真正建 TCP 连接前必须先用 **DNS 把它解析成 IP**。
- 「端口可省略」的前提是使用**默认端口**：HTTP 是 80，HTTPS 是 443，FTP 是 21。
- 片段标识符不参与网络请求；查询串参与。
:::

### HTTP 协议

**HTTP（超文本传送协议）** 定义了浏览器（万维网客户进程）怎样向万维网服务器请求万维网文档，以及服务器怎样把文档传送给浏览器。它建立在 **TCP** 之上，熟知端口号 **80**。

HTTP 有三个重要性质：

- **HTTP 是面向事务（transaction-oriented）的**：一次「请求-响应」就是一个不可分割的事务，**一个请求只请求一个资源**，不存在一次请求 5 个文档的说法。
- **HTTP 是无连接的**：通信双方在交换 HTTP 报文之前**不需要先建立 HTTP 连接**——但 HTTP 基于 TCP，**必须先用 TCP 三次握手建立连接**。
- **HTTP 是无状态的**：同一个客户第二次访问同一文档时，服务器的响应与第一次相同，服务器不保存客户的历史信息。这样做简化了服务器设计，但无法识别用户，因此后来引入了 Cookie。

#### HTTP 报文格式

HTTP 是**面向文本**的，报文中的每个字段都是 **ASCII 码串**，且各字段长度不确定。

**请求报文**的结构：

$$ \text{请求行} \;|\; \text{首部行} \;|\; \text{空行} \;|\; \text{实体主体} $$

- **请求行**：`方法` `空格` `URL` `空格` `版本` `CRLF`，例如 `GET /index.htm HTTP/1.1`。
- **首部行**：每行是 `首部字段名: 值` `CRLF`，可有多行。
- **空行**：一个只有 `CRLF` 的行，**标志首部结束**（必需）。
- **实体主体**：通常**不用**（`GET` 不用；`POST` 才用）。

一个典型的请求报文：

```http
GET /index.htm HTTP/1.1
Host: www.hnust.cn
Connection: close
User-Agent: Mozilla/5.0
Accept-Language: cn
```

各行含义：`GET` 指明方法，`/index.htm` 是请求的 URL，`HTTP/1.1` 是版本；`Host` 指明服务器域名（HTTP/1.1 必需）；`Connection: close` 告诉服务器发完文档后**释放连接**（即不使用持续连接）；`User-Agent` 告知浏览器类型与版本；`Accept-Language: cn` 表示希望优先得到中文版本文档。

**响应报文**的结构：

$$ \text{状态行} \;|\; \text{首部行} \;|\; \text{空行} \;|\; \text{实体主体} $$

- **状态行**：`版本` `空格` `状态码` `空格` `短语` `CRLF`，例如 `HTTP/1.1 404 Not Found`。
- **首部行**、**空行** 与请求报文同理。
- **实体主体**：服务器返回的文档内容（有些响应报文不用，如 `304`）。

常见响应状态行示例：`HTTP/1.1 202 Accepted`（接受请求）、`HTTP/1.1 400 Bad Request`（错误的请求）、`HTTP/1.1 404 Not Found`（找不到页面）。

#### 常见方法与状态码

**HTTP 方法**（请求行中的第一个字段）：

| 方法 | 含义 |
| --- | --- |
| `GET` | 请求读取由 URL 标识的信息（最常用），参数附在 URL 后面 |
| `POST` | 向服务器提交数据（如表单内容），参数放在**实体主体**中，不出现在 URL 里 |
| `HEAD` | 请求读取由 URL 标识的信息的**首部**，而**不返回实体主体**，常用于检查资源是否存在/是否被修改 |
| `PUT` | 向服务器**上传/存放**一个文档（写操作） |
| `DELETE` | 删除服务器上由 URL 标识的资源 |

**状态码**是**三位数字**，第一位表示响应类别：

| 类别 | 含义 | 常见码 |
| --- | --- | --- |
| `1xx` | 通知信息，表示已收到请求，正在继续处理 | `100 Continue` |
| `2xx` | **成功**，操作被成功接收并处理 | `200 OK`（请求成功，实体在响应中）、`202 Accepted` |
| `3xx` | **重定向**，需要进一步的动作才能完成请求 | `301 Moved Permanently`（永久移动）、`302 Found`（临时移动）、`304 Not Modified`（资源未修改，可用缓存） |
| `4xx` | **客户出错**，请求有语法错误或无法实现 | `400 Bad Request`、`403 Forbidden`（服务器拒绝）、`404 Not Found` |
| `5xx` | **服务器出错**，服务器本身发生错误 | `500 Internal Server Error` |

:::key 必须记住的状态码
- **200**：请求成功。
- **301 / 302**：永久 / 临时重定向。
- **304 Not Modified**：资源未修改。服务器用它对 `If-Modified-Since` 或 `If-None-Match` 的**条件请求**作答，**响应中不携带实体主体**，客户直接使用本地缓存——这是「Web 缓存」节省带宽的核心机制。
- **400**：请求报文有语法错误。
- **403**：服务器理解请求但拒绝执行（无权限）。
- **404**：请求的资源不存在。
- **500**：服务器内部错误。
- 记忆技巧：**2 成功、3 重定向、4 客户错、5 服务器错**。
:::

#### 非持久连接与持久连接

**非持久连接（non-persistent connection）**

**HTTP/1.0 采用非持久连接**：每次浏览器要请求一个文件，都要与服务器**建立一次 TCP 连接**，收到响应后就**立即关闭连接**。因此每请求一个文档都要有 **两倍的 RTT 开销**：

$$ T_{\text{一个对象}} = 2\,\text{RTT} + T_{\text{文档传输时延}} $$

第一个 RTT 用于 TCP 三次握手（前两次握手占用一个 RTT），第二个 RTT 用于发送 HTTP 请求并收到响应。

缺点：一个网页上往往有很多引用对象（图片、CSS、JS），请求每一个对象都要花 2 RTT；而且**每个 TCP 连接刚建立时拥塞窗口很小**，无法充分利用带宽。为减小时延，浏览器通常会建立**多个并行的 TCP 连接**同时请求多个对象（如 Chrome 对同一域名可并行 6～10 条），但这会大量占用服务器资源。这就是**非持久连接分为串行 TCP 与并行 TCP** 的由来。

**持久连接（persistent connection）**

**HTTP/1.1 默认采用持久连接**：服务器在发送响应后**仍然保持这条 TCP 连接**，使同一个客户和该服务器可以继续在这条连接上传送后续的 HTTP 请求报文与响应报文。它**不局限于同一个页面上的对象**，只要这些文档在同一台服务器上就行。

持久连接又分两种工作方式：

- **非流水线（non-pipelined）**：客户在收到上一个响应之后才能发出下一个请求。因此每个对象仍需 **1 个 RTT**，但**省掉了每个对象建 TCP 连接的 1 个 RTT**。
- **流水线（pipelined）**：客户在收到 HTTP 响应报文之前就能**连续发送多个请求报文**，这些请求一个接一个到达服务器后，服务器再一个接一个地发回响应。这样能把同一窗口内能容纳的请求「打包」发送，**省掉多个 RTT**，使 TCP 连接中的空闲时间减少。

:::key 四种连接方式的关系（务必分清）
- 按「一条 TCP 连接能传几个对象」分：**非持久**（1 个） vs **持久**（多个）。
- 非持久再按「多个连接是否同时开」分：**串行 TCP** vs **并行 TCP**（并行是「多条连接之间」的关系）。
- 持久再按「请求能否连续发」分：**非流水线** vs **流水线**（流水线是「同一条连接上请求之间」的关系）。
:::

**HTTP/1.1 与 HTTP/2 的主要差别**

| 比较项 | HTTP/1.1 | HTTP/2 |
| --- | --- | --- |
| 连接复用 | 持久连接，但同一连接上的请求**按顺序**处理（流水线的响应也须按序返回），存在**队头阻塞** | **多路复用**：同一 TCP 连接上可并行交错传输多个请求/响应，不再互相阻塞 |
| 报文格式 | **文本**（ASCII） | **二进制分帧**，把报文切成带类型的帧 |
| 首部开销 | 每个请求都重复发送完整首部行，冗余大 | **首部压缩（HPACK）**，并维护首部表，重复首部只发索引 |
| 服务器推送 | 不支持 | 支持**服务器推送（server push）**，可主动把客户即将需要的资源推过去 |
| 传输层 | TCP | 仍基于 TCP（HTTP/3 才改用基于 UDP 的 QUIC） |

一句话概括：HTTP/2 在**不改变 HTTP 语义（方法、状态码不变）**的前提下，通过**多路复用、二进制分帧、首部压缩、服务器推送**提升传输效率。

#### Cookie 与 Web 缓存（代理服务器）

**Cookie**

早期的万维网只用于查看静态文档，所以 HTTP 被设计成**无状态**协议以简化服务器设计。但现在网上购物、电子商务等应用需要服务器**识别用户**，于是引入了 **Cookie**：**Cookie 是一种对无状态的 HTTP 进行状态化的技术。**

工作过程：

1. 用户首次访问某网站时，服务器的响应报文中带一行 `Set-Cookie: 12345678`（一个由服务器生成的识别码）。
2. 浏览器把该 Cookie 存入本地 Cookie 文件，记录「哪个服务器 → 哪个识别码」。
3. 此后浏览器**每次**访问该服务器，都在请求报文中加一行 `Cookie: 12345678`。
4. 服务器根据这个识别码在自己的数据库中查到这个用户，从而「记住」用户，在服务器端维护该用户的状态（购物车、登录态等）。

因此 2015 年第 40 题中，请求报文里出现 `Cookie: 123456` 说明**浏览器此前访问过该站点**；而 `Connection: close` 表示**不使用持久连接**。

**Web 缓存与代理服务器**

**万维网缓存（Web Cache，又称 Web 缓存）** 可位于**客户机**上，也可位于**中间系统**上。位于中间系统上的 Web 缓存称为**代理服务器（Proxy Server）**。

Web 缓存把最近的一些请求和响应**暂存在本地磁盘**中。当新请求到达时，若发现这个请求与暂存的请求相同，就**直接返回暂存的响应**，而不需要按 URL 的地址再次去因特网访问该资源。

代理服务器对请求的两种处理路径：

- **缓存命中（hit）**：代理服务器本地已有该对象且未过期，**直接返回给客户**，不访问源服务器。
- **缓存未命中（miss）**：代理服务器以**客户身份**向源服务器发出 HTTP 请求，取回对象后**既转发给客户，也在本地保存一份**，供后续请求复用。

有效性检查：代理服务器用**条件请求**（`If-Modified-Since` 或 `If-None-Match`）询问源服务器「我这份还是最新的吗」。若源服务器回答 **`304 Not Modified`**（无实体主体），说明缓存仍然有效，直接使用本地副本。

:::key 代理服务器带来的好处
1. **大幅缩短响应时间**：命中时本地返回，时延远小于跨广域网访问源服务器。
2. **减少出口链路的通信量**：多个用户共享一份副本，尤其对热门资源效果显著。
3. **减轻源服务器负担**：未命中时由代理「代表」客户访问，命中时源服务器完全不参与。
:::

#### 计算一：非持久连接与持久连接所需的 RTT 数与总时间

**通用公式**

设一个页面含有 $1$ 个基础 HTML 文件（记作「基本页面」）和 $N$ 个引用对象，每个对象的传输时间为 $t_i$，往返时间为 RTT。

1. **非持久连接（串行，HTTP/1.0）**：每个对象都要新建 TCP 连接，各占 $2\text{ RTT}$：

   $$ \text{总 RTT 数} = 2 \times (N+1), \qquad T = 2(N+1)\,\text{RTT} + \sum_{i=0}^{N} t_i $$

2. **非持久连接（并行 k 条 TCP 连接）**：把 $N+1$ 个对象分成 $k$ 路并行：

   $$ T \approx 2\left\lceil \frac{N+1}{k} \right\rceil \text{RTT} + \text{（各路传输时延）} $$

3. **持久连接 + 非流水线（HTTP/1.1 默认）**：**第一个对象付 1 个 RTT 建 TCP 连接**，此后每个对象只花 1 个 RTT：

   $$ \text{总 RTT 数} = 1 + (N+1) = N+2 $$

   （第一个 RTT 里既建连接又发出第一个请求；严格地说是「1 RTT 建连 + (N+1) 个请求-响应各 1 RTT」，多数教材与真题把它合并写作 $N+2$。）

4. **持久连接 + 流水线**：建连 1 RTT + 全部 $N+1$ 个请求连续发出后各占 1 RTT：

   $$ \text{总 RTT 数} = 1 + (N+1) = N+2 \quad\text{（若所有对象能在同一批发送完）} $$

   若受 TCP 发送窗口限制需要分多批（例如窗口只能容纳 $W$ 个对象），则批数为 $\lceil (N+1)/W \rceil$，总 RTT 数为 $1 + \lceil (N+1)/W \rceil$。

   **流水线与非流水线的关键差别**：非流水线时，每个对象的「请求-响应」必须串行排队，$N+1$ 个对象要花 $N+1$ 个 RTT；流水线时，若窗口足够大，**多个请求可以并发在途**，实际所需 RTT 数可能明显少于 $N+1$。

**算例一（2024 年真题模型，非持久串行）**

浏览器**不支持并行 TCP 连接**，使用非持久 HTTP/1.0 请求 1 个 Web 页，该页引用同一网站上的 **7 个小图像文件**。求从建立 TCP 连接开始到接收完所有内容所需的 RTT 数。

- 对象总数 $N+1 = 1 + 7 = 8$ 个。
- 非持久 + 串行，每个对象 $2\text{ RTT}$。
- 总 RTT $= 2 \times 8 = \mathbf{16}$ 个 RTT。（选项 D）

**算例二（2011 年第 47 题第 (3) 问，持久非流水线）**

`rfc.html` 页面引用了 5 个 JPEG 小图像，HTTP/1.1 以**持续的非流水线**方式工作，一次请求-响应时间为 RTT。求从发出 `rfc.html` 的 Web 请求开始到浏览器收到全部内容为止需要多少 RTT。

- 题目已说明「从发出 **Web 请求**开始」，因此**不再计** TCP 建连的 RTT，也不再计发出该请求之前的时间。
- 基本页面 `rfc.html`：1 RTT。
- 5 个图像：非流水线必须收到上一个响应后才能发下一个请求，各 1 RTT，共 5 RTT。
- 总 RTT $= 1 + 5 = \mathbf{6}$ 个 RTT。

**算例三（带传输时延的完整时延计算）**

页面含 1 个 HTML 文件与 3 张图片，所有对象在同一台服务器上，$\text{RTT}=20\text{ ms}$，单个小对象传输时延可忽略。分别求：

- **非持久串行**：$2\times4=8\text{ RTT}=160\text{ ms}$。
- **持久非流水线**：$(1+4)=5\text{ RTT}=100\text{ ms}$。
- **持久流水线**（窗口足够大）：$1+4=5\text{ RTT}=100\text{ ms}$；若瓶颈链路带宽只能让每 RTT 传一个对象，则与持久非流水线相同。

可见**非持久改成持久，省下的是「每个对象一次建连 RTT」**，4 个对象共省 3 个 RTT。

**算例四（2022 年真题模型，HTTP/1.1 叠加 TCP 拥塞控制）**

主机 H 通过 HTTP/1.1 请求浏览服务器 S 上的 `news408.html`，该页引用同目录下 1 个图像。`news408.html` 大小为 $1\text{ MSS}$，图像大小为 $3\text{ MSS}$，$\text{RTT}=10\text{ ms}$，忽略 HTTP 响应首部开销与 TCP 段传输时延，已预先完成域名解析。求从请求建立 TCP 连接起，到收到全部内容所需的最少时间。

按 TCP 初始拥塞窗口为 $1\text{ MSS}$、慢开始计算：

1. 建立 TCP 连接：**1 RTT**。
2. H 请求 HTML，服务器发送 $1\text{ MSS}$ 页面：**1 RTT**。该段被确认后，服务器拥塞窗口增至 $2\text{ MSS}$。
3. H 解析页面后，在**同一连接**上请求图像；服务器先发 $2\text{ MSS}$：**1 RTT**。确认后窗口继续增大，足以发送剩余部分。
4. 服务器发送图像剩余的 $1\text{ MSS}$：**1 RTT**。

总计 $4\text{ RTT} = 4\times10 = \mathbf{40\text{ ms}}$。

:::warn RTT 计算五个必踩的坑
1. **「从何时开始计时」决定要不要算建连 RTT**。题干若说「从浏览器请求建立 TCP 连接开始」，要算；若说「从发出 HTTP 请求开始」（如 2011 年第 47 题第 (3) 问），则**不再算**建连 RTT，也不把自己这一次请求算进去。
2. **对象数 = 基本页面 + 引用对象数**，别漏掉 HTML 本身。7 张图是 8 个对象，不是 7 个。
3. **非持久连接是 2 RTT / 对象，持久连接是（建连 1 RTT + 1 RTT / 对象）**。「并行连接」要除以并行度并向上取整。
4. **区分「RTT 数」与「时间」**：题目问 RTT 数就只回整数；问时间还要乘 RTT，并在必要时加上传输时延（如 2022 年题要考虑 MSS 的分批）。
5. **DNS 的时间要不要加**：题干若说「已完成域名解析」就不加；若从「点击超链接」开始且给定了 DNS 相关的 RTT，则 DNS 的 RTT 必须计入（见 DNS 部分的算例二）。
:::

#### 计算二：带代理服务器缓存时的时延计算

设：

- 客户端到代理服务器的往返时间为 $RTT_{cp}$（通常很小，可能就在同一局域网）；
- 代理服务器到源服务器的往返时间为 $RTT_{po}$（通常较大，跨广域网）；
- $p$ 为**缓存命中率**（请求在代理处直接命中的比例）。

则：

$$ T_{\text{平均}} = p \cdot RTT_{cp} + (1-p)\cdot\left( RTT_{cp} + RTT_{po} \right) = RTT_{cp} + (1-p)\,RTT_{po} $$

**算例一（命中与未命中）**

某局域网通过代理服务器访问 Internet，客户到代理的 $\text{RTT}=2\text{ ms}$，代理到源服务器 $\text{RTT}=100\text{ ms}$，访问其中一个对象还需从代理到源服务器传输约 $8\text{ ms}$。

- **缓存命中**：$T = 2\text{ ms}$（只有客户到代理的一个往返）。
- **缓存未命中**：$T = 2 + 100 + 8 = 110\text{ ms}$。
- 若命中率 $p=0.4$：$T_{\text{平均}} = 0.4\times2 + 0.6\times110 = 0.8 + 66 = 66.8\text{ ms}$。

**算例二（带宽与冲突域，经典代理服务器题）**

某机构局域网内的主机通过一台代理服务器访问 Internet。局域网带宽 $10\text{ Mb/s}$，Internet 出口带宽 $1.5\text{ Mb/s}$，平均对象大小 $100\text{ kb}$，平均请求率 $15$ 次/秒，客户到代理的 $\text{RTT}=2\text{ ms}$，代理到源服务器 $\text{RTT}=100\text{ ms}$。

- **不设缓存时**：出口链路的到达速率 $\lambda = 15\times100\text{ kb} = 1500\text{ kb/s} = 1.5\text{ Mb/s}$，恰好等于出口带宽，链路利用率 $\rho = 1$，队列时延趋于无穷，实际时延极大。
- **设缓存且命中率 $p=0.4$ 时**：出口链路的到达速率降到 $(1-p)\lambda = 0.6\times1.5 = 0.9\text{ Mb/s}$，链路利用率 $\rho = 0.9/1.5 = 0.6 < 1$，链路不再拥塞。此时

  $$ T_{\text{平均}} = RTT_{cp} + (1-p)\left(RTT_{po} + \frac{L}{B_{\text{out}}}\right) = 2 + 0.6\times\left(100 + \frac{100\text{ kb}}{1.5\text{ Mb/s}}\right) $$

  其中 $\dfrac{100\text{ kb}}{1.5\text{ Mb/s}} = \dfrac{100\times10^3}{1.5\times10^6}\text{ s} \approx 66.7\text{ ms}$，故 $T_{\text{平均}} \approx 2 + 0.6\times166.7 \approx \mathbf{102\text{ ms}}$。

**算例三（缓存命中率的下限）**

在上例中，若要求平均时延不超过 $50\text{ ms}$，求所需的最低命中率 $p$。

$$ 2 + (1-p)\times166.7 \le 50 \;\Longrightarrow\; 1-p \le 0.288 \;\Longrightarrow\; p \ge 0.712 $$

即命中率至少要达到约 **71.2%**。

:::key 代理服务器计算的两个要点
1. **命中时只付客户到代理的时延；未命中时要付「客户到代理」+「代理到源服务器」两个时延。**
2. **代理服务器主要是通过降低出口链路的利用率来消除排队时延**：$\rho = \lambda(1-p)L / B_{\text{out}}$，$\rho$ 越小，排队时延越小。这正是「接入 ISP 带宽不变、只加一台代理服务器就能把响应时间从几分钟降到几十毫秒」的原因。
:::

:::exam 真题考法
- 2014 年第 40 题问「访问 Web 主页不可能使用的协议」，答案是 **SMTP**；可能用到 HTTP、UDP（DNS）、ARP、PPP。
- 2015 年第 40 题给出一段 HTTP 请求报文，判断四个说法。`Connection: close` 表示**不使用**持续连接；`Cookie` 表示曾访问过该站点。
- 2011 年第 47 题（9 分）综合考以太网帧解析 + ARP + 持久非流水线 RTT 数（6 个）+ 路由器转发时修改的 IPv4 首部字段。
- 2020 年第 40 题把 DNS 迭代查询与 HTTP 请求合并计时（20 ms / 50 ms）。
- 2022 年第 40 题把 HTTP/1.1 持续连接与 TCP 慢开始、MSS 结合（4 RTT = 40 ms）。
- 2024 年第 40 题考非持久 HTTP/1.0 串行请求 8 个对象的 RTT 数（16）。
:::

## 易错清单

:::warn 一、网络应用模型
- **C/S 模型中客户之间不能直接通信**，这是 2019 年真题的错误选项来源。
- P2P 中「每个结点既是客户又是服务器」指**角色**，不表示不存在索引服务器或超级结点。
- 不要用「P2P 单个结点带宽更大」解释 P2P 分发更快，正确原因是**总上传能力随结点数增加**。
:::

:::warn 二、DNS
- **本地域名服务器不属于域名服务器等级结构**，画图和说法题里它必须单独列出。
- **递归与迭代的判断**：主机→本地域名服务器是**递归**；本地域名服务器→根/顶级/权限是**迭代**（题目另有规定时按题目）。
- **查询次数计算**：`www.abc.xyz.com` 的迭代查询次数按 `abc.xyz.com` 算，是 $3+1=4$ 次，**不是** 5 次；有缓存时本地域名服务器向外发出 **0** 次。
- **别把主机 H 发给本地服务器的递归查询算进「本地服务器发出的次数」**（2016 年真题的得分点）。
- 缓存命中时，主机到本地服务器的那一次查询**仍然发生**，只是本地服务器不再跑腿。
- **DNS 主用 UDP 53**；**区域传送**和**响应超过 512 字节**时改用 **TCP 53**（2018 年第 33 题答案就是 DNS）。
- 域名与 IP **不是一一对应**，兼容多域名、多 IP、负载均衡；DNS 不存 MAC 地址。
- 权限域名服务器**可能不止一个**，具体由题目给出的域名逐级判断。
:::

:::warn 三、FTP
- **20 和 21 都是服务器端口**；客户端端口由系统随机分配，不可能是 20（2017 年第 40 题的错误项）。
- **主动模式**：服务器用 **20** 端口主动连客户；**被动模式**：服务器随机开端口并告知客户，由**客户**发起连接。所以「FTP 数据连接一定用 20」错。
- **控制连接在整个会话期间保持；数据连接每次传送按需建立、传完即关**（2023 年第 47 题第 (1) 问）。
- 「控制连接用 TCP、数据连接用 UDP」是**错的**——**两条连接都建立在 TCP 之上**（2009 年第 40 题考的就是这个）。
- **带外控制**指控制信息走独立连接，因此数据传送期间仍能发控制命令。
- FTP **有状态**（记住登录状态与工作目录），HTTP **无状态**。
:::

:::warn 四、电子邮件
- **发送用 SMTP（25），读取用 POP3（110）/ IMAP（143）**；「服务器→用户代理」绝不使用 SMTP。
- 2012 年第 40 题的三个阶段是 **SMTP、SMTP、POP3**，顺序不要颠倒。
- **SMTP 只能传 7 位 ASCII**；JPEG、MPEG、EXE 必须先经 **MIME** 编码（2018 年第 40 题答案是「ASCII 文本」）。
- **MIME 不修改 SMTP**，只是在发送前编码、接收后解码；`Content-Type` 说类型，`Content-Transfer-Encoding` 说编码方式。
- 邮件格式由 **RFC 822/5322** 定义，**不是 SMTP 定义的**；首部与主体之间**必须有空行**。
- POP3 的两种方式是**下载并删除**与**下载并保留**；POP3 **不允许**在服务器上管理邮件（建文件夹、分类），IMAP 才允许。
- **不能把邮件直接推给收件人的 UA**：对方主机不一定开机、也不一定跑邮件服务器程序。
- 网页邮件（浏览器收发）时，UA 与服务器之间用 **HTTP**，服务器之间仍用 **SMTP**。
- 邮件相关协议**全部基于 TCP**，没有一个用 UDP。
:::

:::warn 五、WWW 与 HTTP
- **HTTP 无连接**指不先建 HTTP 连接，但仍需 **TCP 三次握手**，别混淆。
- **HTTP 无状态**指服务器不记历史；Cookie 是对它做状态化的技术。
- 请求报文与响应报文都**必须以空行结束首部**；请求报文有实体主体时（`POST`）才带内容。
- **200/301/302/304/400/403/404/500** 的语义要背熟；`304` **不带实体主体**。
- **`Connection: close` 表示非持久连接**；出现它就说明不使用持续连接（2015 年第 40 题 C 选项）。
- **非持久 = 每对象 2 RTT；持久非流水线 = 建连 1 RTT + 每对象 1 RTT**。对象数要算上 HTML 本身。
- 注意题干计时起点：从「建立 TCP 连接」开始要算建连 RTT，从「发出 HTTP 请求」开始则不算（2011 年第 47 题第 (3) 问 = 6 RTT）。
- **流水线**是「同一条连接上连续发多个请求」；**并行 TCP** 是「开多条连接」。两者不是一回事。
- **URL 的片段（`#` 之后）不发送给服务器**；查询串（`?` 之后）会发送。
- 代理服务器**命中时只付客户到代理的时延**，未命中才付到源服务器的时延；它通过降低出口链路利用率消除排队时延。
:::
