##### 闲逛进程
**闲逛进程(**![](https://gw.alipayobjects.com/os/lib/twemoji/11.2.0/2/svg/2b50.svg)**)**：（Idle Process），又称为空闲进程或空闲任务，是操作系统中一种特殊的进程，用于在系统中没有其他进程需要运行时占据CPU资源。闲逛进程的主要目的是确保CPU始终有任务可执行，从而避免CPU处于空闲状态。

闲逛进程的特点如下：

1.  **优先级最低**：闲逛进程的优先级通常设置为最低，这意味着只有在没有其他进程需要运行时，闲逛进程才会被调度执行。一旦有其他进程需要CPU资源，闲逛进程会立即让出CPU，让其他进程执行。 
2.  **持续运行**：闲逛进程通常会持续运行，直到有其他进程需要CPU资源。在某些操作系统中，闲逛进程可能会执行一些简单的任务，如清理内存或执行系统维护操作。但在大多数情况下，闲逛进程仅执行一个空循环，不执行任何实际操作。
3. **只运行在内核态下； **
4.  **资源占用最小**：不需要CPU以外的资源，不会阻塞；

##### 调度的时机与调度方式（抢占式/非抢占式）（12 21 年）
1. **非抢占式调度**
+ 定义：一个进程除非运行结束或者自己主动放弃CPU，否则不会被其它进程抢占CPU。
+ 调度时机：进程运行结束；进程由于发起I/O等主动阻塞，主动放弃处理机使用权；

> 若不考虑进程执行`yield`系统调用主动释放处理机资源，那么非抢占式调度只会出现运行态到退出态或阻塞态的转变，不可能会发生运行态到就绪态的转变；
>

+ 特点：
    - 调度不太频繁，CPU利用率一般更高；（没有运行态与就绪态的切换开销）
    - 实时性比较差，**一般用于批处理操作系统**，**不能用于大部分实时操作系统和分时操作系统**。
    - 系统开销小，整体吞吐量更大；
2. **抢占式调度**
+ 定义：进程在执行过程中，可能**因为时间片用完或者有更高优先级进程进入就绪态而被抢占CPU。**
+ 调度时机：
    - 当前进程主动放弃CPU（运行结束或者进入阻塞态）
    - 当前进程时间片用完或有更高优先级的进程进入就绪态。
+ 特点：
    - 频繁调度，实时性强；
    - 可以防止一个进程长时间独占处理器的恶意行为
    - 可以优先处理更紧急的进程，也可实现让各进程按时间片轮流执行的功能(通过时钟中断)。
    - **等待时间和响应时间更短，用户体验好，适用于分时操作系统，实时操作系统。**



**<font style="color:#DF2A3F;">抢占式调度的具体实现方式（介绍了调度的时机）</font>**

在进程的PCB中，为进程设置一个**<font style="color:#DF2A3F;">标志位</font>**，例如linux中PCB里的**<font style="color:#DF2A3F;background-color:rgb(236, 236, 236);">TIF_NEED_RESCHED（记作NEED_RESCHED）</font>**标志位，其含义为“**需要重新调度**”，当某个进程的 `TIF_NEED_RESCHED` 标志被设置时，表示内核需要尽快触发调度器scheduler，重新选择下一个要运行的任务。

1. **什么时候设置这个标志位？**
+ **时间片耗尽**：当前任务的时间片用完时，内核会设置 `**<font style="color:rgb(64, 64, 64);background-color:rgb(236, 236, 236);">NEED_RESCHED</font>**`，以便让其他任务运行。
+ 当**有更高优先级的进程进入就绪态**，会设置 `**<font style="color:rgb(64, 64, 64);background-color:rgb(236, 236, 236);">NEED_RESCHED</font>**`
    - 例如**当前进程**`**fork()**`**一个优先级更高的子进程**
    - **处理I/O后唤醒阻塞进程，发现其优先级比当前运行进程优先级更高，设置 **`**<font style="color:rgb(64, 64, 64);background-color:rgb(236, 236, 236);">NEED_RESCHED</font>**`
2. **内核什么时候响应该标志（抢占点的触****发时机）？**

<font style="color:rgb(64, 64, 64);">在</font>**<font style="color:rgb(64, 64, 64);">中断/异常/系统调用处理结束返回用户空间</font>**<font style="color:rgb(64, 64, 64);">时，内核会检查当前进程的 </font>`**<font style="color:rgb(64, 64, 64);background-color:rgb(236, 236, 236);">NEED_RESCHED</font>**`<font style="color:rgb(64, 64, 64);"> 标志，若有效则触发调度；</font>

3. **什么时间点不能进行调度？**
    - **当前进程处于****<font style="color:#DF2A3F;">中断处理过程中</font>**；（中断处理通常涉及到操作系统的核心功能和关键资源，是系统工作的一部分，逻辑上不属于某一进程，不应被剥夺处理机资源。）
    - 进程**在访问操作系统内核临界区中；**(注意在用户级别的临界区中可以进行进程调度)
    - 禁用中断（屏蔽中断过程中）
    - 原语执行过程中；（如加锁、解锁、中断现场保护、恢复等原子操作。原子操作不可中断一气呵成，连中断都要屏蔽，更不应该进行进程调度与切换。）

##### 调度算法的评价指标：带权周转时间  平均带权周转时间


+ **<font style="color:#DF2A3F;">带权周转时间 </font>****=  **$ \frac{作业周转时间}{作业实际运行的时间} $(必然大于等于1，也是越小越好，对于实际运行时间相同的两个作业周转时间短的带权周转时间更短，用户满意度越高；周转时间相同的作业实际运行时间更长的，用户越满意)



+ <font style="color:#DF2A3F;"> </font>**<font style="color:#DF2A3F;">平均带权周转时间 </font>****= **$ \frac{各作业带权周转时间之和}{作业数} $

##### CPU 调度算法：最短剩余时间优先（SRTN）即抢占式短作业优先（14 年）  高响应比优先（09 年）
###### <font style="color:#DF2A3F;">短作业优先(SJF)调度算法</font>
**<font style="color:#DF2A3F;">短作业优先</font>****（**`**SJF，Shortest Job First**`**）调度算法**是一种基于作业执行时间的**<font style="color:#DF2A3F;">非抢占式调度算法</font>**。它的基本思想是**优先调度执行时间最短的作业，以最小化平均等待时间和平均周转时间。**

该调度算法也有**抢占式的版**本，即**<font style="color:#DF2A3F;">最短剩余时间优先</font>****（**`**SRTN，Shortest Remaining Time Next**`**）算法**，这是一种**基于作业剩余执行时间的抢占式调度算法**。在SRTN算法中，**当一个新的作业到达系统时（即每当有进程加入 就绪队列改变时就需要调度），**操作系统会比较该作业的剩余执行时间和当前正在执行的作业的剩余执行时间。如果该作业的剩余执行时间比当前作业的剩余执行时间更短，那么操作系统会暂停当前作业，将CPU分配给新到达的作业。如果两个作业的剩余执行时间相同，那么可以使用先来先服务（FCFS）调度算法来决定哪个作业先执行。

`SRTN`算法的优点在于它可以最小化平均等待时间和平均周转时间，因为它优先调度剩余执行时间最短的作业。这可以减少作业的等待时间和完成时间，提高系统的响应速度和吞吐量。

**<font style="color:#DF2A3F;">408考试注意的细节：</font>**

+ 若题目未特殊说明，所提到的“短作业/进程优先算法” **默认是非抢占式的**
+ 在有前提条件“所有进程可同时运行”或“所有进程几乎同时到达”的情况下，我们可以说采用SJF的调度算法的平均等待时间、平均周转时间最少，若未加该前提条件，则应该说“**抢占式的短作业/进程调度算法(SRTN)的平均等待时间、平均周转时间最少。**
+ 如果选择题中遇到”SJF的平均等待时间、平均周转时间最少“的选项，最好先判断别的选项是否有明显错误，若无更合适选项，那也应该选择该选项。



###### <font style="color:#DF2A3F;">高响应比优先(HRRN）调度算法</font>
由于`FCFS`算法是在每次调度的时候选择一个等待时间最长的作业/进程为其服务，但是没有考虑到作业的运行时间，因此导致了对短作业不友好的问题；

`SJF`算法只考虑执行时间完全不考虑各个作业的等待时间，因此导致了对长作业不友好的问题，甚至还会出现饥饿现象。

**高响应比优先调度算法（Highest Response Ratio Next，HRRN）**是一种基于响应比的非抢占式调度算法,是对这两种调度算法的平衡，**同时考虑了每个作业的等待时间和估计的运行时间**。

该算法用于作业/进程调度，在每次调度时先计算各个作业/进程的响应比，选择响应比最高的作业/进程为其服务；



                                                                              **响应比 = **$ \frac{等待时间+计算时间}{计算时间} $



该算法是**<font style="color:#DF2A3F;">非抢占式</font>**的算法，因此**只有当前运行的作业/进程主动放弃处理机（正常/异常完成，或主动阻塞）时，才需要调度，才需要计算响应比；**

优缺点：

+ 该算法综合考虑了等待时间和运行时间(要求服务时间)。 等待时间相同时，要求服务时间短的优先(SJF的优点)；要求服务时间相同时，等待时间长的优先(FCFS的优点)；
+ 对于长作业来说，随着等待时间越来越长，其响应比越来越大，从而**避免了长作业饥饿的问题**；
+ 然而，HRRN算法也存在一些问题。首先，它需要知道每个作业的执行时间，但在实际情况下，作业的执行时间通常是未知的。

###### 基于公平原则的调度算法
> 之前介绍的几种典型调度算法所保证的只是满足要求的进程优先运行，如优先级调度算法可以保证优先级最高的进程优先运行，但并不保证进程占用了多少处理机时间;另外也未考虑调度的公平性。本小节将介绍两种相对公平的调度算法。
>

**保证调度算法**

1. **算法定义**：保证调度向用户所做的并不是优先运行保证，而是明确的**性能保证**，该算法**可以做到调度的公平性**。 该调度算法会根据每个进程自创建以来实际获得的 CPU 时间来决定谁应该优先获得处理机。目标是**<font style="color:#DF2A3F;">保证每个进程在长期运行中都能获得相同的处理机资源（在多进程情况下，每个进程应获得</font>**$ \frac{1}{n} $**<font style="color:#DF2A3F;">  的处理机时间）</font>**。  
2. **具体实现原理：**
+ **追踪**每个进程自创建以来的 CPU 使用时间。
+ **计算**进程应获得的 CPU 时间（例如，系统有 5 个进程，理论上每个进程应该获得 20% 的 CPU 时间）。
+ **比较**进程的实际获得时间和应获得时间的比率。比如：
    - 进程 A 的比率是 0.5（表示它获得的 CPU 时间低于预期）。
    - 进程 B 的比率是 0.8。
    - 进程 C 的比率是 1.2（表示它已经获得的 CPU 时间超出预期）。
+ **选择**比率最低的进程，并将 CPU 资源分配给它，直到它的比率超过下一个进程为止。
3. **它与RR算法的区别**

| 调度算法 | 时间片轮转算法  | 保证调度算法 |
| :---: | --- | --- |
| **调度依据** | 时间片轮转算法是基于“时间片”的轮转，不考虑进程的历史 CPU 使用情况。 | 公平调度算法则考虑进程的历史 CPU 使用情况，优先将资源分配给那些实际获得资源较少的进程。 |
| **处理公平性的方式** | 在**短期**内是公平的，但无法确保在长期内每个进程都获得相等的处理机资源。 | **长期**公平的，保证所有进程在一个较长的周期内平均分配到相同的 CPU 时间。 |
| **性能** | 对于短任务（如交互式任务）可能更有利，因为每个进程都会快速轮流获得 CPU | 根据历史资源分配情况调整，有时会导致某些进程不得不等待较长时间。 |


**公平分享调度算法**

公平分享调度算法（Fair-Share Scheduling Algorithm）的目标是**为每个****<font style="color:#DF2A3F;">用户</font>****而不是进程提供公平的处理机时间分配**。为了实现这一点，调度算法需要考虑每个用户的进程数量，并在分配处理机时间时确保不同用户间的公平性。

1. 问题背景 : 在经典的时间片轮转算法（Round-Robin，RR）中，每个进程都能获得相等的时间片。如果用户 1 启动了 4 个进程，而用户 2 只启动了 1 个进程，则时间片的分配会造成用户 1 获得更多的处理机时间。即：
    - 用户 1 的 4 个进程每个都轮到一个时间片，因此用户 1 占用系统总 CPU 时间的 80%。
    - 用户 2 只有 1 个进程，因此它只占用 20% 的 CPU 时间。

尽管在这种情况下**对进程是公平的，但对用户是不公平的，**因为用户 2 的 CPU 资源远少于用户 1。

2. **公平分享调度算法的目标**：公平分享调度算法关注用户之间的公平性，而不是单独的进程。它会根据用户的进程数量进行调整，以**确保每个用户的进程总体上分配到的处理机时间是公平的**。例如，两个用户中的每个用户都应该获得相同的处理机时间（如果没有其他要求）。
3. **示例解释**
+ 情况 1：**用户之间平分 CPU 资源**
    - 系统中有两个用户：用户 1 有 4 个进程（A、B、C、D），用户 2 有 1 个进程（E）。
    - 公平分享调度算法的目标是确保两个用户各自获得 50% 的处理机时间。
    - 因为用户 1 有 4 个进程，而用户 2 只有 1 个进程，直接使用 RR 算法会导致不公平。因此，必须采用强制调度序列来保证公平性。

强制调度序列的逻辑如下：

    - 让用户 1 的进程 A 先运行一次，然后用户 2 的进程 E 运行一次。
    - 之后再让用户 1 的进程 B 运行，接着是用户 2 的进程 E。
    - 依次让用户 1 的其他进程 C、D 运行，每次都让用户 2 的进程 E 夹在其中。

具体的调度序列就是：

```plain
A E B E C E D E A E B E C E D E……
```

在这种情况下，尽管用户 1 有 4 个进程，用户 2 只有 1 个进程，但在每轮调度中，两个用户的总 CPU 时间是相等的（每个用户都获得 50% 的处理机时间）。

+ 情况 2：**若需要用户 1 获得 2 倍于用户 2 的 CPU 资源**
    - 现在假设用户 1 应该获得 2 倍于用户 2 的处理机时间。
    - 由于用户 1 有 4 个进程，用户 2 有 1 个进程，强制调度的目标是使用户 1 获得 2 倍于用户 2 的 CPU 资源。

强制调度序列的逻辑如下：

    - 用户 1 的进程 A 和 B 先分别运行一次，接着用户 2 的进程 E 运行一次。
    - 然后用户 1 的进程 C 和 D 分别运行，再次轮到用户 2 的进程 E。
    - 这个循环持续进行，每次用户 1 都有两个进程运行，之后才轮到用户 2 的进程运行一次。

具体的调度序列为：

```plain
A B E C D E A B E C D E A B E C D E……
```

在这种情况下，用户 1 的进程总共占用 2/3 的处理机时间，而用户 2 的进程 E 占用 1/3 的处理机时间，从而满足用户 1 获得 2 倍 CPU 资源的要求。



###### 实时调度算法
      在实时系统中，任务通常被分为两类：**硬实时任务（HRT, Hard Real-Time tasks）和软实时任务（SRT, Soft Real-Time tasks）**。每种任务都有其特定的**截止时间（Deadline）**，即任务必须在某个时间点之前完成。  

> + **硬实时任务（HRT）**:
>     - **定义**: 硬实时任务的截止时间是**绝对必须满足的**。如果硬实时任务没有在规定的截止时间前完成，系统的功能可能会出现严重问题，甚至导致灾难性后果。
>     - **例子**: 比如控制医疗设备、航空控制系统或自动驾驶汽车中的关键部件。这些任务若没有及时完成，可能会导致安全问题或系统失败。
> + **软实时任务（SRT）**:
>     - **定义**: 软实时任务的截止时间相对灵活。如果软实时任务未能在截止时间前完成，尽管可能会引起一些性能上的降低或用户体验的影响，但不会导致系统的崩溃或严重后果。
>     - **例子**: 视频流媒体的播放、音频处理等，延迟可能会导致用户体验的下降，但不会引起系统崩溃。
>

###### 实现实时调度的基本条件
1. **提供必要的信息**

为了实现实时调度，系统应向调度程序提供与任务相关的信息，包括:

    - ①**就绪时间**，指某任务的状态转换为就绪状态的起始时间，在周期任务的情况下，它是事先预知的一串时间序列;
    - ②**开始截止时间和完成截止时间**，对于典型的实时应用，只须知道开始截止时间或者完成截止时间;
    - ③**处理时间**，一个任务从开始执行直至完成所需的时间;
    - ④**资源要求**，任务执行时所需的一组资源;
    - ⑤**优先级**，如果某任务的开始截止时间被错过了(势必引起故障)，则应赋予该任务“**绝对”优先级**;如果其开始截止时间的错过对任务的继续执行无重大影响，则可赋予其“**相对”优先级**以供调度程序参考。
2. **系统处理能力强**

在实时系统中，若处理机的处理能力不够强，则有可能因处理机忙不过来而致使某些实时任务不能得到及时处理，从而导致发生难以预料的后果。假定系统中有m个周期性的HRT任务，它们的处理时间表示为C，周期时间表示为P，则在单处理机情况下，必须满足下式所示的限制条件，系统才可调度。顺便说明一下，该限制条件并未考虑任务切换所花费的时间，因此，当利用该限制条件时，还应适当地留有余地。

$ \sum_{i=1}^{m} \frac{C_i}{P_i} \le 1 $

提高系统处理能力的途径有二:

+ ①采用**单处理机**系统，但须增强其处理能力，以显著减少对每个任务的处理时间;
+ ②采用**多处理机**系统，假定系统中的处理机个数为N，则应将上式所示的限制条件改为:$ \sum_{i=1}^{m} \frac{C_i}{P_i} \le N $
3. **采用抢占式调度机制**

在含有HRT任务的实时系统中，广泛采用抢占式调度机制，这样便可满足HRT任务对截止时间的要求。但这种调度机制比较复杂。对于一些小的实时系统，如果能预知任务的开始截止时间，则对实时任务的调度可采用非抢占式调度机制，以简化调度程序和任务调度时所花费的系统开销。但在设计这种调度机制时，应使所有的实时任务都比较小，并在执行完关键性程序和临界区代码后能及时地将自己阻塞起来，以便释放处理机并供调度程序去调度开始截止时间即将到达的任务。

4. **采用快速切换机制**

为保证HRT任务能及时运行，在系统中还应采用快速切换机制，使之能进行任务的快速切换。该机制应具有如下两方面的能力。

+ ①**对中断的快速响应能力**。对紧迫的外部事件请求中断能及时响应，要求系统具有快速硬件中断机构，此外，还应使禁止中断的时间间隔尽量短，以免耽误时机(影响其他紧迫任务的执行)。
+ ②**快速的任务分派能力**。为了提高分派程序的任务切换速度，应使系统中的每个运行功能单位适当地小，以减少任务切换的时间开销。

###### 实时调度算法分类
1. **非抢占式调度算法**
+ **非抢占式轮转调度算法**。由一台计算机控制若干个相同的(或类似的)对象，为每个被控对象建立一个实时任务，并将它们排成一个轮转队列。调度程序每次选择队列中的第一个任务投入运行。当该任务完成后，便把它挂在轮转队列的末尾进行等待，调度程序再选择下一个队首任务运行。这种调度算法可获得数秒至数十秒的响应时间，可用于要求不太严格的实时控制系统。
+ **非抢占式优先级调度算法**。如果在系统中还含有少数具有一定要求的实时任务，则可采用非抢占式优先级调度算法，系统会为这些任务赋予较高的优先级。当这些实时任务到达时，系统会把它们安排在就绪队列的队首，等待当前任务自我终止或运行完成后，再通过调度执行队首的高优先级进程。这种调度算法在做了精心的处理后，有可能使进程的响应时间减少到数百毫秒至数秒，因而可用于有一定要求的实时控制系统。

![](https://cdn.nlark.com/yuque/0/2024/png/42876865/1726939148509-c32baa7e-1d18-4486-be77-011bed611957.png)

2. **抢占式调度算法**

可根据抢占发生时间的不同，将抢占式调度算法进一步分成以下两种算法。

+ **基于时钟中断的抢占式优先级调度算法**。在某实时任务到达后，如果它的优先级高于当前任务的优先级，则此时并不立即抢占当前任务的处理机，而是等到时钟中断发生后，调度程序才会剥夺当前任务的执行，将处理机分配给新到的高优先级任务。该算法能获得较好的响应效果，其调度时延可降低到几毫秒至几十毫秒，可用于大多数的实时系统。
+ **立即抢占的优先级调度算法**。在这种调度算法中，要求OS具有快速响应外部中断事件的能力。一旦出现外部中断，只要当前任务未处于临界区，便能立即剥夺当前任务的执行，把处理机分配给请求中断的紧迫任务。该算法能获得非常快的响应，其调度时延可降低到几百微秒至几毫秒。图3-6所示为4种实时调度算法所对应的调度时间情况。

###### 最早截止时间优先算法
最早截止时间优先(earliest deadline first，EDF)算法根据任务的截止时间确定任务的优先级，任务的截止时间越早，其优先级越高，具有最早截止时间的任务排在队列的前面。调度程序在选择任务时，总是选择就绪队列中的第一个任务，并为之分配处机。EDF算法既可用于抢占式调度方式中，也可用于非抢占式调度方式中。

**多处理器调度的方法**

1. **非对称多处理**：让一个**主处理器**负责所有调度决定、IO处理以及其他系统活动，其他的处理器只负责执行用户代码。

> 优点：因为只有一个处理器访问系统数据结构（访问内存、I/O等资源），减少了数据共享的需要（减少冲突）。	
>
> 缺点：主处理器故障会导致整个系统崩溃；主处理器会成为性能瓶颈；
>

2. **<font style="color:#DF2A3F;">对称多处理</font>**(**<font style="color:#DF2A3F;">S</font>**ymmetric **<font style="color:#DF2A3F;">M</font>**ulti**<font style="color:#DF2A3F;">P</font>**rocessing，**<font style="color:#DF2A3F;">SMP</font>**)
    - 即每个处理器运行自己的调度程序
    - 所有进程可能处于**一个共同的就绪队列**中，或每个处理器都有它**自己的私有就绪进程队列**。不管如何，调度这样进行:每个处理器的调度程序都检查共同就绪队列，以便选择执行一个进程。
    - 如果多个处理器试图访问和更新一个共同的数据结构，那么每个处理器必须仔细编程。必须确保两个处理器不会选择同一进程，而且进程不会从队列中丢失。（以及调度程序对共享资源的访问需要进行同步）

> 几乎所有现代操作系统，包括Windows、Linux 和MacOS，都支持SMP，本节余下部分讨论有关SMP系统的多个问题。
>

**处理器亲和性**

考虑一下，当一个进程运行在一个特定处理器上时缓存会发生些什么，由于进程最近访问的数据更新了处理器的缓存，因此，进程的后续内存访问通常通过缓存来满足。现在考虑一下，如果进程移到其他处理器上则会发生什么。

    1. 原来运行的处理器缓存的内容应设为无效
    2. 迁移到的处理器缓存需要重新填充

由于缓存的无效或重新填充的代价高，大多数SMP系统试图**避免将进程从一个处理器移到另一个处理器，而是试图让一个进程运行在同一个处理器上**。这称为**处理器亲和性**，即**一个进程对它运行的处理器具有亲和性**。

处理器的亲和性具有多种形式：

    1. 当一个操作系统**试图保持进程运行在同一处理器**上时(但不保证它会这么做，这个进程也可迁移到其他处理器)，这种情况称为**软亲和性**(soft affinity)。
    2. 相反，有的系统提供系统调用以便支持**硬亲和性**，从而允许某个进程运行在某个处理器子集上。
    3. 许多系统提供软的和硬的亲和性。例如，Linux实现软亲和性，但是它也提供系统调用 schedsetaffinity()以支持硬亲和性。

系统的内存架构可以影响处理器的亲和性，下图为采用**非统一内存访问**(NonUniform Memory Access，NUMA)的一种架构，其中一个 CPU 访问内存的某些部分会比其他部分更快。通常情况下，这类系统包括组合CPU和内存的板卡。每个板的CPU 访问本板内存快于访问其他板的内存。如果操作系统的CPU 调度和内存分配算法一起工作，那么当一个进程分配到一个特定的亲和处理器时，它应分配到同板上的内存。这个例子还说明操作系统通常不按教科书描述的那样清楚地定义与实现。

![](https://cdn.nlark.com/yuque/0/2024/png/42876865/1726211664461-e6c3e39d-fd6f-4f98-82dc-4d76a0fadf51.png)

**对称多处理器SMP的进程分配**

| **<font style="color:#DF2A3F;">静态进程分配</font>** | **<font style="color:#DF2A3F;">动态进程分配</font>** |
| :---: | :---: |
| 进程从开始到结束都被分配到一个固定的处理机上运行 | 进程在执行中可分配到任意空闲处理及执行 |

| 调度开销小 | 调度开销大 |
| 各处理机可能忙闲不均（有的空闲有的忙） | 各处理机的负载是均衡的 |
| 处理器亲和性好 | 处理器亲和性差 |

**对称多处理器SMP的负载均衡**

对于 SMP系统，重要的是**保持所有处理器的负载平衡，以便充分利用多处理器的优点**。否则，一个或多个处理器会空闲，而其他处理器会处于高负载状态，且有一系列进程处于等待状态。负载平衡(load balance)设法将负载平均分配到 SMP系统的所有处理器。

其实SMP的动态进程分配不止上面那种，也分为两种情况：

+ 对于有些系统(它们的处理器具有私有的可执行进程的队列)，负载平衡是必需的；
+ 而对于具有公共队列的系统，负载平衡通常没有必要，因为一旦处理器空闲，它立刻从公共队列中取走一个可执行进程。

> 同样重要的是，要注意对于大多数支持SMP的现代操作系统，每个处理器都有一个可执行进程的私有队列。
>

负载平衡通常有两种方法:

1. **推迁移**：一个特定的任务周期性地检查每个处理器的负载，如果发现不平衡，那么通过将进程从超载处理器推到(push)空闲或不太忙的处理器，从而平均分配负载。
2. **拉迁移**：当空闲处理器从一个忙的处理器上拉(pull)一个等待任务时，发生拉迁移。

> 推迁移和拉迁移不必相互排斥，事实上，在负载平衡系统中它们常被并行实现。例如，Linux 调度程序实现了这两种技术。
>

有趣的是，负载平衡往往会抵消处理器亲和性的好处。也就是说，保持一个进程运行在同一处理器上的好处是进程可以利用它在该处理器缓存内的数据。无论是从一个处理器向另一处理器推或拉进程，都会失去这个好处。与通常的系统工程情况一样，关于何种方式是最好的，没有绝对规则。因此，在某些系统中，空闲的处理器总是会从非空闲的处理器中拉进程;而在其他系统中，只有当不平衡达到一定程度后才会移动进程。



**多核处理器**

传统上，SMP系统具有多个物理处理器，以便允许多个线程并行运行。然而，计算机硬件的最近做法是，将多个处理器放置在同一个物理芯片上，从而产生多核处理器(multicore processor)。每个核都保持架构的状态，因此对操作系统而言它似乎是一个单独的物理处理器。**采用多核处理器的 SMP系统与采用单核处理器的 SMP系统相比，速度更快，功耗更低。**	

多核处理器的调度问题可能更为复杂。下面我们来分析一下原因。研究人员发现，当一个处理器访问内存时，它花费大量时间等待所需数据。这种情况称为内存停顿(memory stall)，它的发生原因多种多样，如高速缓存未命中(访问数据不在高速缓冲里)。下图显示了内存停顿，在这种情况下，处理器可能花费高达50%的时间等待内存数据变得可用。为了弥补这种情况，许多最近的硬件设计都采用了多线程的处理器核，即每个核会分配到两个(或多个)硬件线程。这样，如果一个线程停顿而等待内存，该核可以切换到另一个线程。下图显示了一个双线程的处理器核，这里线程0和线程1的执行是交错的。从操作系统的角度来看，每一个硬件线程似乎作为一个逻辑处理器，以便运行软件线程。因此，在双线程双核系统中，操作系统会有4个逻辑处理器。UItraSPARCT3CPU具有16个处理器核，而每个核有8个硬件线程。从操作系统的角度，就有128个逻辑处理器。

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1765273518870-34f285e4-293b-4e1b-a54a-1c5ca68fee2b.png)

一般来说，处理器核的多线程有两种方法:**粗粒度(coarse-grained)和细粒度(fine- grainded)的多线程**。

+ 对于粗粒度的多线程，线程一直在处理器上执行，直到一个长延迟事件(如内存停顿)发生。由于长延迟事件造成的延迟，处理器应切换到另一个线程来开始执行。然而，线程之间的切换成本是高的，因为在另一个线程可以在处理器核上开始执行之前，应刷新指令流水线。一旦这个新的线程开始执行，它会开始用指令来填充流水线。
+ 细粒度(或交错)的多线程在更细的粒度级别上(通常在指令周期的边界上)切换线程。而且，细粒度系统的架构设计有线程切换的逻辑。因此，线程之间的切换成本很小。	

注意，一个多线程多核处理器实际需要两个不同级别的调度。

+ 一个级别的调度决策由操作系统做出，用于选择哪个软件线程运行在哪个硬件线程(逻辑处理器)。对于这个级别的调度，操作系统可以选择任何调度算法，如之前提过的FCFS,多级反馈队列等调度算法。
+ 另一个级别的调度指定每个核如何决定运行哪个硬件线程。在这种情况下，有多种策略可以采用。例如采用一个简单的轮转算法，安排8个硬件线程到每个核。另一个例子是，Intel Itanium 为双核处理器，而且每个核有两个硬件线程。每个硬件线程有一个动态的紧迫值，它的取值范围为0~7，用0表示最低的紧迫性，而7表示最高的。Itanium 有5个不同的事件，用于触发线程切换。当这些事件发生时，线程切换逻辑会比较两个线程的紧迫性，并选择紧迫性较高的线程在处理器核上执行。

:::color2
**如何判断软件实现方法是否遵循上面那四个原则？**

+ 判断是否遵循**<font style="color:#DF2A3F;">空闲让进</font>**
    1. 观察是否有可能让表达式1与表达式2同时成立；
    2. 观察没有p1的话，P0能否通过循环进入临界区，没有p0的话，P1能否通过循环进入临界区.
+ 判断是否遵循**<font style="color:#DF2A3F;">忙则等待</font>**
    - 当p0通过while循环，但是没有进入临界区，此时切换P1，看P1能否也通过while循环，若可以，则不符合忙则等待；完了再反向检查一下；
+ 判断是否遵循**<font style="color:#DF2A3F;">有限等待</font>**
    - 当p1处于临界区，p0卡在进入区一直通过不了while循环，此时新来了一个p1进程后，仍然可以比p0先进入临界区，那么p0则不满足有限等待，有可能会饥饿；
+ 所有的软件实现方法**<font style="color:#DF2A3F;">都不遵循让权等待</font>**：上图进入区的`**<font style="color:#DF2A3F;">while(表达式)；</font>**`含义为如果表达式为真，则会一直执行这个循环，直到因为时间片到期被剥夺处理机或者因为表达式为假，方可跳出循环；该循环的循环体为空语句，这就是所谓的忙等。

:::

1. **<font style="color:#DF2A3F;">单标志法</font>**： 有两个进程，其中一个进程在访问完临界区后会把使用临界区的权限交给另一个进程，也就是说每个进程使用临界区的权限只能被另一个进程赋予

```c
//共享整形变量标志
int turn = 0;
turn = 1; //表示允许进入临界区的是进程P1
```

```c
/*进程P0*/
while(TRUE){
    //若turn等于本进程编号，准入临界区
    while(turn != 0);
    临界区；
    turn = 1;//允许对方进入临界区
    剩余区；
}
```

```c
/*进程P1*/
while(TRUE){
    //若turn等于本进程编号，准入临界区
    while(turn != 1);
    临界区；
    turn = 0;//允许对方进入临界区
    剩余区；
}
```

+ 满足**忙则等待**
+ 两个进程必须交替进入临界区，如果其中一个进程不再进入临界区，那么另一个进程由于未得到它的授权也永远进不去，这**<font style="color:#DF2A3F;">违背了“空闲让进</font>**<font style="color:#DF2A3F;">”</font>的原则
+ 另外由于使用while判断语句作为进入去，**违背了“让权等待”。**



2. **<font style="color:#DF2A3F;">双标志法先检查</font>**：设置一个布尔型数组flag[ ],数组中各个元素用来标记各进程想进入临界区的意愿，比如“flag[0] = true”意味着0号进程P<sub>0</sub>现在想要进入临界区。每个进程在进入临界区之前先检查当前有没有别的进程想进入临界区，如果没有，则把自身对应的标志flag[i]设为true，之后访问临界区。

```c
//共享数组,表示两进程是否在临界区；
bool flag[2]; 
flag[0] = flag[1] = FALSE; 
```

```c
/*进程P0*/
while(TRUE){
    while(flag[1] = TRUE); //检查对方是否在临界区；
    //通过循环说明对方不在临界区，那么P0先设置标志再进入临界区；
    flag[0] = TRUE; 
    临界区；
    flag[0] = FALSE; //表示本进程已退出临界区；
    剩余区；
}
```

```c
/*进程P1*/
while(TRUE){
    while(flag[0] = TRUE); //检查对方是否在临界区；
    //通过循环说明对方不在临界区，那么P0先设置标志再进入临界区；
    flag[1] = TRUE; 
    临界区；
    flag[1] = FALSE; //表示本进程已退出临界区；
    剩余区；
}
```

:::color1
解决了单标志法需要循环进入的缺点，可以连续使用了，但是由于进程的异步性又产生了新的问题。如果P0进程通过了while循环，但是还没有进入临界区，就发生进程切换（例如时间片到期），让P1执行，P1也能通过while循环进入临界区，这样一来这两个进程可以同时进入临界区，<font style="color:#DF2A3F;">违背了“</font>**<font style="color:#DF2A3F;">忙则等待</font>**<font style="color:#DF2A3F;">”的原则</font>，原因在于进入区的“检查”和“上锁 ”不是一气呵成的，这两个过程之间很可能会发生进程切换。即**并发程序不能保证load和store的原子性**。

:::



3. **<font style="color:#DF2A3F;">双标志法后检查</font>**：双标志先检查法的改版。前者由于无法一气呵成完成先“检查”后“上锁”的操作，因此导致了两个进程同时进入临界区的问题，为此人们想到了先“上锁”后“检查”的方法来避免该问题。

```c
//共享数组,表示两进程想进入临界区；
bool flag[2]; 
flag[0] = flag[1] = FALSE; 
```

```c
/*进程P0*/
while(TRUE){
    flag[0] = TRUE;
    while(flag[1] = TRUE); //检查对方是否在临界区；
    临界区；
    flag[0] = FALSE; //表示本进程已退出临界区；
    剩余区；
}
```

```c
/*进程P1*/
while(TRUE){
    flag[1] = TRUE; 
    while(flag[0] = TRUE); //检查对方是否在临界区；
    临界区；
    flag[1] = FALSE; //表示本进程已退出临界区；
    剩余区；
}
```

:::danger
观察两个while循环中的表达式能否同时成立，考虑到进程P0在置flag[0] = TRUE后发生进程切换，进程P1在置flag[1] = TRUE后无法进入临界区，即使再调度到进程P0，P0也无法进入临界区，这下**违背了“空闲让进”和“有限等待”**，两个进程都想进又都不谦让，就干脆都别进了。

:::

| 方法 | 思想 | 缺点 |
| :---: | :---: | :---: |
| 单标志法 | 引入共享变量turn，循环检查直到turn = 本进程编号 | 违背空闲让进和让权等待，只能两个进程交替使用 |
| 双标志先检查 | 引入flag共享数组，先检查对方是否进入临界区 | 有可能会同时进入临界区，从而违背忙则等待 |
| 双标志后检查 | 引入flag共享数组，先设置自身flag，再检查对方 | 当两进程都想进入临界区，有可能都进不去，违背有限等待 |
| `**<font style="color:#DF2A3F;">peterson</font>**`**<font style="color:#DF2A3F;"> 算法</font>** | 引入turn和flag数组，进入临界区时检查两个条件 | 违背让权等待，且只适用于两个进程之间互斥进入临界区 |

##### 经典同步问题：读者写者问题
> **问题描述**：有读者和写者两组并发进程，共享一个文件，当两个或两个以上的读进程同时访问共享数据时不会产生副作用，但若某个写进程和其他进程(读进程或写进程)同时访问共享数据时则可能导致数据不一致的错误。因此要求：
>
> + 允许多个读进程可以同时对文件执行读操作；(注意这里的读者进程与消费者进程不同，读者进程在读数据后并不会改变数据，而消费者则会将当前数据清除)
> + 同一时刻只允许一个写者往文件中写信息；(两个及以上写进程同时共享数据可能会导致数据错误覆盖的问题)
> + 任一写者在完成写操作之前不允许其他任何进程工作；
> + 写者执行写操作之前，应让已有的读者写者全部退出； (读进程与写进程同时共享数据，可能导致读出的数据不一致的问题)
>

+  应用场景：适用于并发线程读取和修改数据结构、数据库或文件系统的任何情况。 在写入或修改数据结构时，通常需要禁止其他线程读取，以防止读者线程中断正在进行的修改并读取不一致或无效的数据。与生产者 - 消费者问题一样，解决方案是不对称的。 读者和写者在进入关键部分之前执行不同的代码。 同步约束是： 
    1.  任何数量的读者可以同时进入关键部分。 
    2.  写者必须拥有对关键部分的独占访问权。 



换句话说，当任何其他线程（读者或者写者）在那里时，写者不能进入临界区；而当写者在那里时，其他线程都不可以进入。

这里的排除模式可以被称为**分类互斥（categorical mutual exclusion）**。 临界区中的线程不一定排除其他线程，但是在临界区中存在一个类别会排除其他类别。



> **通用解题模板**：读者写者问题，其**本质就是连续多个同类进程访问同一个临界资源的问题**。
>
> 第一个进程开始访问临界资源前，需要对资源加上互斥锁，后面的进程再访问时就不用再对资源加互斥锁了，直到最后一个进程访问完后，发现自己是最后一个进程，就解锁互斥锁。这就像一种情况：第一个人进房间时必须顺手开门，后面进来的人和离开的人就不用开门，直到最后一个人离开房间时才需要顺手关门。
>

1. 实现方法一：读者优先

> 基于读者优先策略的方法，只要有一个读者处于活动状态，后来的读者都会被接纳。如果读者源源不断地出现地话，那么写者就始终处于阻塞状态，可能会“饿死”。
>



![](https://cdn.nlark.com/yuque/0/2024/png/42876865/1718418460824-5ea5da7e-40b8-4cd4-8fe3-0a073dcf52a3.png)

假设每个读者的读操作都耗时较长，读者写者到达的顺序是：`读者1---读者2---读者3---写者A---读者 4---写者 B---读者 5`，则：

+ 读者 1、读者 2、读者 3 到达，rw加锁，开始读；
+ 写者 A 到达，但是读者还在读，未释放 rw 锁，因此不能写；
+ 读者 4 到达，可以开始读；
+ 写者 B 到达，但是读者还在读，未释放 rw 锁，因此不能写；
+ 读者 5 到达，可以开始读；  
等到读者们都读完，释放 rw 锁，写者才可以开始写。

2. 实现方法二：写者优先

> 所谓写者优先，即：当有读者进程正在执行，写者进程发出申请，这时应该拒绝其他读者进程的请求，等待当前读者进程结束后立即执行写者进程，只有在无写者进程执行的情况下才能够允许读者进程再次执行。
>
> 为此在读者进程的基础上，增加信号量read值为1，用来禁止所有的读进程；增加一个写者进程的计数器，初值为0，用于实现写优先；另外自然也要为写者进程的计数器设置一个互斥信号量用来互斥访问；因此，伪代码如下：
>

![](https://cdn.nlark.com/yuque/0/2024/png/42876865/1718418460836-b18d6728-c8c4-43f0-bae6-92fde7569358.png)

> 注意，这里 `read` 的作用，开始有多个读者读数据，它们全部进入读者队列，此时来了一个写者，执行了 `P(read)` 之后，后续的读者由于阻塞在 `read` 上，都不能再进入读者队列，而写者到来，则可以全部进入写者队列，因此保证了写者优先。
>
> 同时，第一个写者执行了 `P(read)` 之后，也不能马上开始写，必须等到所有进入读者队列的读者都执行完读操作，通过 `V(write)` 唤醒写者的写操作。
>

假设每个读者的读操作都耗时较长，读者写者到达的顺序是：`读者1---读者2---读者3---写者A---读者 4---写者 B---读者 5`，则：

+ 读者 1、读者 2、读者 3 到达，Write 加锁，开始读；
+ 写者 A 到达，Read 加锁，但是读者还在读，Write 锁仍未释放，因此不能写；
+ 读者 4 到达，Read 锁仍未释放，不能开始读；
+ 写者 B 到达，Write 锁仍未释放，因此不能写；
+ 读者 5 到达，Read 锁仍未释放，不能开始读；
+ 等到读者 1 到 3 都读完，释放 Write 锁，写者 A 才可以开始写，写完后 Write 解锁。由于写者 A 不是最后一个写进程，因此 Read 不解锁；
+ 写者 B 进行写操作，写完后 Write 解锁，由于写者 B 是最后一个写进程，因此 Read 解锁；
+ 读者 4、读者 5 依次进行读操作。

3. 实现方法三：读写公平法

公平策略：

+ 优先级相同；
+ 写者、读者互斥访问；
+ 只能一个写者访问临界区；
+ 可以有多个读者同时访问临界资源；

> 为实现读写公平，我们设置一个互斥信号量queue,其作用是让读者和写者进行排队，当有reader进程执行时，queue = 0 ,因此writer进程会进入等待，直到queue变为1；当writer进程执行时同理；因此，我们借助queue实现了读写进程的优先级平等。
>

![](https://cdn.nlark.com/yuque/0/2024/png/42876865/1718418461128-4cdf42df-d915-44f4-92c9-1518855acf49.png)

> 看完代码不知你是否有这样的疑问，为什么加了一个信号量 `queue`，就实现了公平竞争？
>
> 对比方案一的读者优先策略，可以发现，读者优先中只要后续有读者到达，读者就可以进入读者队列， 而写者必须等待，直到没有读者到达。
>
> 没有读者到达会导致读者队列为空，即 `rcount=0`，此时写者才可以进入临界区执行写操作。
>
> 而这里 `queue` 的作用就是阻止读者的这种特殊权限（特殊权限是只要读者到达，就可以进入读者队列）。
>
> 比如：开始来了一些读者读数据，它们全部进入读者队列，此时来了一个写者，执行 `P(queue)` 操作，使得后续到来的读者都阻塞在 `queue` 上，不能进入读者队列，这会使得读者队列逐渐为空，即 `rcount` 减为 0。
>
> 这个写者也不能立马开始写（因为此时读者队列不为空），会阻塞在信号量 `rw` 上，读者队列中的读者全部读取结束后，最后一个读者进程执行 `V(rw)`，唤醒刚才的写者，写者则继续开始进行写操作。
>

假设每个读者的读操作都耗时较长，读者写者到达的顺序是：`读者1---读者2---读者3---写者A---读者 4---写者 B---读者 5`，则：

+ 读者 1、读者 2、读者 3 到达，rw 加锁，开始读；
+ 写者 A 到达，queue 加锁，但是读者还在读，rw 锁仍未释放，因此不能写；
+ 读者 4 到达，但是读者还在读，queue 和 rw 锁仍未释放，不能开始读；
+ 写者 B 到达，queue 锁和 rw 锁仍未释放，因此不能写；
+ 读者 5 到达，但是读者还在读，queue 和 rw锁仍未释放，不能开始读；
+ 等到读者 1 到 3 都读完，释放 rw 锁，写者 A 才可以开始写；
+ 接下来就是按读者 4、写者 B、读者 5 的顺序依次访问文件。

##### 程序的链接与装入（11 年）
创建进程首先要将程序和数据装入内存，一般需要以下几个步骤

+ **编译**：由**编译程序**将用户源代码编译成为若干**目标模块**（就是把高级语言**翻译成机器语言**）
+ **链接**：由**链接程序**将编译后形成的一组目标模块及所需的**库函数**链接在一起，形成一个完整的装入模块（即可执行文件）
+ **装入**：由**装入程序**将装入模块**装入内存**运行

> 【注】：
>
> + **编译后**，每个目标模块都从0号单元开始编址，但是这**仅仅是相对于该模块的逻辑地址**；
> + 当**链接程序**将各个模块链接成一个完整的可执行目标程序时，将顺序依次按各个模块的相对地址构成统一的从0号单元开始编址的逻辑地址空间(即虚拟地址空间)。（即**链接后形成整个程序的完整逻辑地址空间**）
> + 操作系统通过内存管理部件**MMU**将进程使用的逻辑地址转换为物理地址。
>

###### 程序的链接
其中**程序的链接**有如下三种方式（**该阶段****<font style="color:#DF2A3F;">生成完整的逻辑地址</font>**）

1. **静态链接**：在程序运行开始之前，先将各目标模块及他们所需要的库函数链接成一个完整的装入模块，以后不再拆开 。
2. **装入时动态链接**：将用户源程序编译后所得到的一组目标模块，在装入内存时，采用**边装入边链接**的方式。其**优点是便于修改和更新，便于实现对目标模块的共享**（将一个目标模块链接到几个应用模块上）。 

> 例如在装入一个目标模块时，若发生一个外部模块调用事件，将引起装入程序去找出相应的外部目标模块，并将它装入内存，还要修改目标模块中的相对地址。
>

3. **运行时动态链接**：在程序执行中需要某目标模块时，才对它进行链接。凡在程序执行中未用到的目标模块，都不会被调入内存和链接到装入模块上。其优点是能加快程序的装入过程，还可节省内存空间。

> 链接指的是把标准库连入程序的虚拟地址空间，静态链接在磁盘中就完成这一步，而动态链接在OS修改页表的一瞬间才链入主程序的虚拟地址空间；
>
> 装入时动态链接在装入模块的时候修改页表，具体来说，是主程序装入内存的时候看需要哪个动态库，就一起装入内存并修改页表；而运行时动态链接是主程序在执行的时候，运行到了某个函数发现是某个动态库里面的，就去把这个动态库调入内存并且修改页表。
>

##### 内存保护（09）
为避免主存中多道程序相互干扰,防止某程序出错而破坏其他程序的正确性,或某程序不合法地访问其他程序或数据区,应该对每个程序进行存储保护,包括操作系统程序和用户程序。为了对操作系统存储保护提供支持,**硬件必须具有以下3种基本功能**。

1. 支持至少两种特权模式：即内核态和用户态 
2. 使部分CPU状态只能由操作系统内核程序进行读写而用户进程不能读写； 

> 特权模式位、页表首地址、TLB内容等都只能由操作系统内核程序通过特殊的指令(一般称为**管态指令**或特权指令)进行访问。常用的管态指令(特权指令)包括刷新cache、刷新TLB、改变特权模式、输入/输出、停止处理器执行等。
>

3. 提供让CPU在管理模式和用户模式之间相互转换的机制。 

> 执行系统调用指令、响应异常和中断、异常和中断处理后的“返回”指令   
硬件通过提供相应的专用寄存器、专门的指令、专门的状态/控制位等,和操作系统一起实现上述3个功能。通过这些功能,并把页表保存在操作系统的地址空间,操作系统就可更新页表,并防止用户进程改变页表,以确保用户进程只能访问由操作系统分配给的存储空间。 
>

**所谓内存保护，就是保证各个进程在各自的存储空间内运行，互不干扰**

1. **<font style="color:#DF2A3F;">存储区域保护</font>**
+ **方法一：在CPU中设置一对**`**上、下限寄存器**`**，存放进程的上、下限地址。进程的指令在访问地址时，CPU进行越界检查**



![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1747310179014-e5e5b7ab-9060-4ca4-b79d-9047c56fd2f0.png)

+ **方法二：采用重定位寄存器（基址寄存器）和界地址寄存器（限长寄存器）进行越界检查。**重定位寄存器中存放的是进程的`起始物理地址`；界地址寄存器存放的是进程的`最大逻辑地址`

> 一般来说**重定位寄存器整个系统就一个，因为CPU同一时刻只执行一条指令或访问数据。**而且寄存器成本高，设置多了也不现实。
>



![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1747310532371-feb6ff03-e821-4bfa-af21-c879a429648d.png)



> 注意两个寄存器的区别，一个用来“比”，一个用来“加”；**加载这两个寄存器时必须使用特权指令**，只有操作系统内核才可以加载这两个存储器，因此允许OS内核对其修改，而不允许用户程序修改。
>

以上提到的内存保护属于**存储区域保护**，就是看是否发生了“**地址越界**”，即是否访问了不该访问的区域。

+ 对共享区或已获授权的其他用户信息可读不可写;

##### 页面调入策略（什么时候调入页面 从哪里调入页面）
为了让进程能够正常运行，必须事先将要执行的那部分程序和数据所在的页面调入内存。

###### 什么时候调入页面
主要有以下两种调页策略，实际场景中，两种策略会结合使用

1. **预调页策略**： 根据**局部性原理**，一次调入若干相邻的页面可能要比一次只调入一个页面更加高效，但如果调入的一批页面中大多数都没有被访问，效率就会很低。**因此，需要采用以预测为基础的预调页策略，将预计在不久之后便会被访问的页面预先调入内存**，但目前预测成功率平均不超过50%

应用场景：

    - 在第一次将进程调入内存时，此时可将程序员指出的那些页先调入内存。
    - 在采用工作集的系统中，每个进程都具有一张表，表中记录有运行时的工作集，每当程序被调度运行时，就将工作集中的所有页调入内存。
2. **请求调页策略**： 进程**在运行期间**发现缺页时才将所缺页面调入内存。该策略下，调入的页面一定会被访问到，但是**由于一次只能调入一页，所以****<font style="color:#DF2A3F;">I/O开销较大</font>**



###### 从哪里调入页面
具有对换功能的操作系统中，通常会把**磁盘空间**划分为**文件区和对换区**两部分：其中**文件区主要用于存放文件，追求存储空间利用率,采用****<font style="color:#DF2A3F;">离散分配方式</font>**；对换区空间仅占一小部分。**被换出的进程数据就存放在对换区**。由于对换的速度直接影响系统的整体速度，因此对换区空间的管理主要追求换入换出速度，所以**<font style="color:#DF2A3F;">对换区采用连续分配方式</font>**。总之，**<font style="color:#DF2A3F;">对换区的I/O速度要远快于文件区</font>**

由于对换区磁盘I/O速度要快于文件区，因此就有如下三种情况

+ **若系统拥有足够的对换区空间：** 页面的调入、调出都是在**内存与对换区**之间进行，这样可以保证**页面的调入、调出速度很快**。在进程运行前，将**相关数据从文件区复制到对换区，之后把需要的页面从对换区调入内存；**
+ **若系统缺少足够的对换区空间：** 凡是**不会被修改的数据都直接从文件区调入**，由于这些页面不会被修改，因此**换出时不必写回磁盘**，下一次需要时再从文件区调入即可。**对于可能被修改的部分，换出时需要写回对换区，下次需要时再从对换区调入；**
+ **UNIX方式：** 运行之前进程有关的数据**全部放在文件区**，所以**未使用过的页面，都可以从文件区调入**；**被使用过页面的换出时，则写回对换区，下次需要直接从对换区调入**

##### 页框回收
前面我们学习了页框分配，也就是给进程分配物理页框，我们当时学习了固定分配以及可变分配，所谓的可变分配就是先为每个进程分配一定数目的页框，在进程运行期间，可以根据情况做适当的增加或者减少，这里的减少就是**<font style="color:#DF2A3F;">页框回收</font>**。但是这个页面如果在调入内存后内容发生更改了，那就得写回磁盘，不能直接清空当成空页框。一般来说，这种被系统回收的页框，会被放入空闲页框链尾，里面的内容在下一次分配之前不会被清空。这也是12年真题的说法。下面将介绍与之相关的内容，选自汤小丹mooc版操作系统p186《页面缓冲算法》。

###### 影响页面换入换出的影响因素
:::color2
这部分也可以归入**虚拟存储器的性能影响因素**

:::

1. **页面置换算法**：这是最重要的影响因素，因为一个好的页面置换算法，可以使得进程在运行过程中具有较低的缺页率，从而减少页面换入换出的次数。
2. **将已修改页面写回磁盘的频率**：对于已经被修改过的页面，在将其换出时，应当写回磁盘。如果采取每当有一个页面要被换出时，就将它写回磁盘的策略，则意味着每换出一个页面就需要启动一次磁盘。但如果在系统中已建立了一个**<font style="color:#DF2A3F;">已修改换出页面链表</font>**，则针对每个要被换出的页面（已修改），系统可暂不把它们写回磁盘，而是将它们挂在已修改换出页面链表上，仅**当被换出页面数目达到一定值（如64）时，再将它们一起写回到磁盘上**，这样就显著地减少了磁盘I/O的操作次数，或者说，减少了已修改页面换出的开销。
3. **将磁盘内容读入内存的频率**：在设置了已修改换出页面链表后，在该链表上就暂时有了一批装有数据的页面，**如果有进程在这批数据还未写回磁盘时需要再次访问这些页面，则无须从磁盘上调入**，而可直接从已修改换出页面链表中获取，这样不仅可以降低将页面从磁盘读入内存的频率，而且可以减少页面换入的开销。或者说，只须花费很小的开销，便可使这些页面又回到该进程的驻留集中。



###### 页面缓冲算法
页面缓冲算法就是采用上述思想，在原页面置换算法的基础上增设已修改页面链表，保存已修改且需要被换出的页面，等被换出的页面数目达到一定值时，再一起换出至磁盘，以达到减少页面换出开销的目的。页面缓冲算法的主要特点是：

+ 显著地降低了页面换入/换出的频率，使磁盘I/O的操作次数大为减少，因而减小了页面换入/换出的开销；
+ 正是由于换入/换出的开销大幅度减小，其采用一种较简单的置换策略（如FIFO页面置换算法）时不需要特殊硬件的支持，实现起来非常简单。



页面缓冲算法已在不少系统中被采用，下面介绍VAX/VMS系统中所使用的页面缓冲算法。在该系统的内存分配策略中**采用了可变分配局部置换方式，系统为每个进程分配一定数目的物理页框，系统自己保留一部分空闲物理页框。**为了能显著地降低页面换入/换出的频率，**在内存中设置了以下两个链表。**

1. **<font style="color:#DF2A3F;">空闲页面链表</font>**。实际上空闲页面链表是一个空闲物理页框链表，这些系统掌握的空闲物理页框用于分配给频繁发生缺页的进程，以降低这些进程的缺页率。当这些进程需要读入一个页面时，它们便可利用空闲物理页框链表中的第一个物理页框来装入该页。当有一个未被修改的页面要换出时，实际上并不将它换出到磁盘，而是将它所在的物理页框挂在空闲链表的末尾。应当注意，**这些挂在空闲链表中的、未被修改的页面中是有数据的，如果以后某进程需要这些页面中的数据，则可从空闲链表上将它们取下，这免除了从磁盘读入数据的操作，减少了页面换入的开销。**
2. **<font style="color:#DF2A3F;">修改页面链表</font>**。修改页面链表是由已修改的页面所形成的链表。设置该链表的目的是减少已修改页面换出的次数。当进程需要将一个已修改的页面换出时，系统并不会立即把它换出到磁盘上，而是会将它所在的物理页框挂在修改页面链表的末尾。这样做的目的是降低将已修改页面写回磁盘的频率，进而降低将磁盘内容读入内存的频率。



###### 哪些页框可以被回收
> 页框回收算法按照页框所含内容的不同，将页框区分为以下几种类型，并以不同的方式处理：
>
> + 不可回收页：包括空闲页、内核空间使用的页、临时锁定的页等。
> + 可交换页：用户态进程的匿名页或与其他进程共享的页，这些页在硬盘上没有对应的区域，需要写入交换区（swap区）
> + 可同步页：如文件映射到内存的页(例如程序的代码段、数据段等)，这些页在硬盘中有备份，系统只需检查页是否被修改过，如果被修改过则写回硬盘
>

系统内存紧张的时候，就会进行回收内存（页框）的工作，主要有两类内存可以被回收，而且它们的回收方式也不同。

+ **<font style="color:#DF2A3F;">文件页(File-backed Page)</font>**：内核缓存的**磁盘数据(**Buffer)和内核缓存的**文件数据(**Cache)都叫作文件页。大部分文件页，都可以直接释放内存，以后有需要时，再从磁盘重新读取就可以了。而那些被应用程序修改过，并且暂时还没写入磁盘的数据(也就是**脏页**)，就得先写入磁盘，然后才能进行内存释放。所以，**回收干净页的方式是直接释放内存，回收脏页的方式是先写回磁盘后再释放内存（如上，可能先挂到修改页面链表，暂时不写入磁盘）。**
+ **<font style="color:#DF2A3F;">匿名页(Anonymous Page)</font>**：这部分内存没有实际载体,不像文件缓存有硬盘文件这样一个载体，**比如堆、栈数据等**。这部分内存很可能还要再次被访问，所以**不能直接释放内存**，它们回收的方式是通过Linux 的 Swap 机制，Swap 会把不常访问的内存先写到磁盘中,然后释放这些内存，给其他更需要的进程使用。再次访问这些内存时，重新从磁盘读入内存就可以了。

> 文件页和匿名页的回收都是基于 **LRU 算法**，也就是优先回收不常访问的内存。
>



###### 连续页框分配算法--伙伴算法的页框回收
Linux系统采用“伙伴算法”对内存中具有不同长度的连续空闲页框进行统计和记录。将内存中连续的空闲页框视为空闲页框块，并根据它们的大小（连续页框的数量）分组。分配页框是一个化整为零的过程，会产生很多碎片，而系统也必须有把零碎的页框合并成大的连续页框块的机制，Linux使用伙伴算法的逆操作进行页框的回收。回收页框时，算法先检查是否有大小相等的伙伴页框块存在，若有，则将它们合并成一个大小为原来两倍的新空闲页框块，每次合并完后，还要检查是否可以继续合并成更大的页框块。

<font style="color:rgb(0, 0, 0);">1. 整个结构体变量的对齐方式与其中对齐方式最严格的成员相同。  
</font><font style="color:rgb(0, 0, 0);">2. 结构体成员在满足其对齐方式的条件下，取最小可用位置作为成员在结构体中的偏移量。  
</font><font style="color:rgb(0, 0, 0);">3. 结构体大小应当为对齐边界长度的整数倍(结构体的大小必须是其最大成员大小的倍数，以保证结构体在数组中也是对齐排放。)  
</font><font style="color:rgb(0, 0, 0);">4. 如果嵌套了结构体，嵌套的结构体对齐到自己的最大对齐数的整数倍处，结构体的整体大小就是所有最大对齐数(含嵌套结构体的对齐数)的整数倍</font>
