# 2.4 死锁

#### 2.4.1 资源分类


1. **可重用资源和可消耗性资源**

| 比较项 | 可重用资源 | 消耗型资源 |
| :---: | --- | --- |
| 定义 | **使用后可以重复利用的资源**，对该类资源的请求和释放通常是利用**系统调用**来实现的 | **一次性使用后就不可重复使用的资源**，是在进程运行期间，由进程动态地创建和消耗的，通常是由生产者进程创建，由消费者进程消耗 |
| 典型例子 | + **硬件**：处理器、I / O通道、主和副存储器、设备等<br/>+ **软件**：文件、数据库和信号量等数据结构 | 在I/O缓冲区的中断、信号、消息等 |
| 分配与释放模式 | 在使用完成后会释放，供其他进程继续使用 | 使用后不再存在，需要重新生成或获取 |
| 其他性质 | 1. **资源不能被删除且在任何时刻只能有一个进程使用；**<br/>2. 这些资源在被释放后可再次使用。通常需要进行**互斥或同步机制**来防止资源竞争。 | 1. 每一类可消耗资源的**单元数目在进程运行期间是可以不断变化**的，可以是0或者很多；<br/>2. 进程在**运行过程中可以不断地创造可消耗性资源**，并将其放入该类资源的缓冲区，以增加其数目；也可以请求若干个该类资源用于消耗并不再返回； |
| 死锁可能性 | 存在被多个进程同时请求而导致死锁的可能，eg：**每个进程占用一部分资源并请求其它资源** | 不容易导致死锁，但是仍有可能，例如进程间相互等待接收对方的消息 |
| 管理方式 | 采用资源分配表、互斥锁等方法管理 | 需要有生产者-消费者机制或信号机制 |
| 使用场景 | 多用户系统、共享系统资源 | 网络通信、作业处理等 |




2. **可抢占性资源和不可抢占性资源**

| 比较项 | 可抢占资源 | 不可抢占资源 |
| :---: | --- | --- |
| 定义 | **可以在被分配后中断并分配给其他进程,** 例如优先级调度中的抢占处理机、在内存紧张时将一个进程从内存调到外存上抢占其内存空间 | **一旦分配后不可中断，只能由持有进程释放** |
| 典型例子 | CPU、内存、网络带宽 | 打印机、文件、锁、数据库事务等临界资源 |
| 分配方式 | 可以中断当前持有者并重新分配 | 一旦分配，需等待当前持有者主动释放 |
| 死锁可能性 | 由于可以中断,一般来说不会死锁 | 资源不能被中断，容易导致死锁 |
| 管理方式 | 需要某种调度策略（如抢占式调度） | 需要资源等待和释放策略 |
| 使用场景 | 多任务调度、动态资源分配 | 事务处理、设备使用、批量作业 |

#### 2.4.2 常见并发缺陷(了解即可)
1. 非死锁缺陷：
+ **违反原子性缺陷**：违反了多次内存访问中预期的可串行性(即代码段本意是原子的，但是在执行过程中并没有强制实现原子性)。例如在多线程中两个线程对同一个变量检查并修改，但是运行过程中由于线程切换发生类似引用空指针的错误导致程序崩溃。解决方案：给共享资源的访问加锁；
+ **违反顺序缺陷**：两个进程内存访问的预期顺序被打破了(即A应该在B之前执行，然而实际运行并不是这个顺序)；修复方案：通过条件变量或者信号量加入同步。



2. **死锁(deadlock)缺陷**

---

#### 2.4.3 死锁的概念
1. **死锁、饥饿、死循环的区别**

|  | 死锁 | 饥饿 | 死循环 |
| --- | --- | --- | --- |
| 定义 | 在并发环境下，各进程互相等待对方手里的资源，导致各进程都阻塞，无法向前推进的现象。 | 由于长期得不到想要的资源，某进程无法向前推进的现象；比如短进程优先算法中如果有源源不断的短进程到来，那么长进程就会一直得不到处理机； | 进程在没有满足终止条件时会无限循环 |
| 发生原因 | 循环等待对方手里的资源 | 优先级倒置、资源分配不公平或错误 | 编程错误、逻辑错误或资源竞争 |
| 例子 | 死锁状态下的银行家算法问题 | 低优先级进程无法获得CPU时间片、内存等 | 空循环、忘记更新循环条件等 |
| 进程状态 | **阻塞态** | **阻塞态**(得不到I/O设备)或**就绪态(**上不了处理机) | **运行态** |
| 解决方法 | 预防、检测和解决死锁 | 资源分配公平、优先级正确、控制资源使用 | 修改程序逻辑、添加终止条件或优化算法 |
| 处于该种状态的进程数量 | 两个或两个以上 | 可能只有一个，也可能大于1个 | 大于等于1个 |


> **三者都是进程无法顺利向前推进的现象(故意设计的死循环除外)，死锁和饥饿是管理者(OS)的问题，死循环是被管理者的问题。**
>



2. **死锁产生的原因**
    1.  **对系统资源的竞争**：当各进程竞争不可抢占性资源时，若该类资源数目满足不了多个进程的需要，使得进程在运行过程中因争夺资源而陷入僵局，从而导致死锁。 
    2.  **进程推进顺序不当**：进程运行过程中，请求和释放资源的顺序不当同样会导致死锁。例如并发执行的进程P1、P2分别申请并占有了资源R1、R2，之后进程P1又紧接着申请资源R2，而进程P2又在申请资源R1，二者会因为申请的资源被对方占有而阻塞，从而发生死锁。 
    3.  **信号量的使用不当**：如生产者消费者问题中，如果实现互斥的P操作在实现同步的P操作之前就有可能导致死锁； 
    4.  **由可消耗性资源引起的死锁**：如果多个进程之间通信时，对消息的receive和send操作的顺序没有处理好，都在先等待receive消息再send消息，导致这几个进程永远阻塞在receive操作上，因为在等待一条永远不会发出的消息，于是产生死锁。 

**总之对不可剥夺资源的不合理分配，可能导致死锁。**



3. **<font style="color:#DF2A3F;">死锁产生的必要条件</font>**：产生死锁必须同时满足以下四个条件，**只要任意一个条件不满足，死锁就不会发生**。
+  **互斥条件**：**<font style="color:rgb(48,62,79);">任何时刻只能有一个进程使用一个资源实例</font>**

> 只有对必须互斥使用的资源的争夺才会导致死锁，如临界资源、锁等。像内存、CPU、扬声器这种可以同时让多个进程使用的资源是不会导致死锁的，因为进程不用阻塞等待这种资源。 
>

![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165605428-596274d5-1979-47c3-ace3-4312352e98e9.png) 

+ **不可剥夺(抢占)条件**：进程所获得的资源在未使用完成之前，不能由其他进程强行夺走，只能主动释放。 

![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165605402-96c07acc-5d8c-4e19-991a-28822a9ec099.png) 

+  **请求并保持条件**：进程已经保持了至少一个资源，但又提出了新的资源请求，而该资源又被其他进程占有，此时请求进程被阻塞，但又对自己已有的资源保持不放。

 ![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165605388-f9f05cb2-bc73-4f80-a3a6-e9bfd96de6f3.png) 

+  **循环并等待条件**:存在一种进程资源的**循环等待链**，链中的每一个进程已获得的资源同时被下一个进程所请求。 



![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165605412-2d629828-7719-4188-8d27-6f39ca3719e8.png)



> 注意：**<font style="color:#DF2A3F;">发生死锁时一定有循环等待，但是发生循环等待时未必死锁</font>**。如果同类资源数大于1，即使有循环等待，等待链中的一个进程可能从等待链以外的进程那里获得自己的资源，从而打破死锁。但是如果系统中每类资源都只有一个，那么循环等待就是死锁的充要条件了。
>



由以上四个必要条件，可得以下常用结论：

+  若系统有 x 个进程，每个进程需要 y 个资源，则该系统必然不会发生死锁的最少资源是 $ x*(y-1) + 1 $个。
+  若系统有 x 个资源，每个进程需要 y 个资源，则该系统可能发生死锁的最小进程数为 $ \left\lceil \dfrac{x}{y-1} \right\rceil $。 

> 【推导思路】系统有 x 个进程，每个进程已拥有 y-1 个资源，此时如果资源总数刚好为 x*(y-1) 个，意味着资源已用完，则一定发生死锁，此时再多加一个资源，令其中一个进程获得所需的最大资源，则死锁解除。即使每个进程所需资源数各不相同，一样可以按此思路分析。
>

#### 2.4.4 死锁预防
1.  **破坏互斥条件**：若允许系统资源都能共享使用，则系统不会进入死锁状态。 
    - 比如：SPOOLing技术，操作系统可以采用SPOOLing技术把独占设备在逻辑上改造成共享设备，比如用该技术把打印机改造为共享设备…
    - Herlihy提出了设计各种无等待(wait-free)数据结构的思想，即**通过强大的硬件指令，可以将需要互斥访问某种资源的那段代码构造成不需要锁的数据结构，**这样便破坏了互斥条件(详情见OSTEP 第32章)

缺点：有的资源本身就是非共享的，例如一个互斥锁不能同时被多个进程所共享，这种资源不可以被改造成可共享资源。并且有些地方还得保护这种互斥性，因此**这种方法通常不太可行。**

2.  **破坏不剥夺条件**：方案一：当请求新的资源得不到满足时，立即释放保持的所有资源；方案二：当某个进程需要的资源被其他进程所占有时，可以由OS协助将想要的资源强行剥夺。  
缺点： 
+ 实现起来很复杂，且需付出很大代价；
+ 释放已获得的资源可能造成进程前一阶段工作的失效，即便采取了某些防范措施，也还会使进程前后两次运行的信息不连续。因此这种方法通常适用于状态容易保存和恢复的资源，如CPU寄存器和内存。一般不适用于其他资源，如互斥锁、信号量、打印机、CD刻录机这一类资源。
+ 反复地申请和释放资源会大大增加系统开销，降低系统吞吐量。
+ 可能会导致进程饥饿。



3. **破坏请求并保持条件**：为了能破坏“请求并保持条件”，系统必须做到：当一个进程在请求资源时，它不能持有不可抢占资源。可通过以下两个不同的协议实现：
+ 协议1：采用静态分配方法，即**进程在运行前一次申请完它所需要的全部资源**，在它的资源未满足以前，不让它投入运行。可通过”要求进程申请资源的系统调用在所有其他系统调用之前进行“
+ 协议2：是对协议1的改进，它允许一个进程只获得运行初期所需的资源后，便开始运行。进程运行过程中再逐步释放已分配给自己的的、且已用完的全部资源，然后再请求新的所需资源。第二种协议不但能使进程更快地完成任务，提高设备的利用率，还可以减少进程发生饥饿的机率。



缺点：这个方案需要我们准确地知道需要哪些资源，并且提前抢到这些资源。有些资源可能仅在运行初期或运行快结束时才使用很短的时间，因此如果进程的整个运行期间都一直保持着所有资源，就会降低并发，造成严重的资源浪费，资源利用率极低；另外，该策略也有可能导致某些进程饥饿。



4. **破坏循环等待条件**：最实用也是最经常采用的预防技术。可以**采用顺序资源分配法**，首先给系统中的资源编号，**规定每个进程必须按编号递增的顺序请求资源**，同类资源一次申请完。也就是说，只要进程提出申请分配资源R<sub>i</sub>，则该进程在以后的资源申请中就只能申请编号大于R<sub>i</sub>的资源。

缺点：

+ 不方便增加新的设备，可能需要重新分配所有的编号；
+ 进程实际使用资源的顺序可能和编号递增顺序不一致，会导致资源浪费；
+ 必须按规定次序申请资源，用户编程麻烦。



> 聪明的程序员根据锁的地址做为获取锁的顺序，按照地址从高到低，或者从低到高的顺序加锁，`do_something()`函数就可以保证不论传入参数是什么顺序，函数都会用固定的顺序加锁。因此在获取多个锁时，通过简单的技巧，就可以确保简单有效的无死锁实现。——OSTEP

#### 2.4.5 死锁避免


预防与检测解除方案的折中：不事先破坏死锁必要条件，而是在资源动态分配中防止系统进入不安全状态；

+  **安全序列**：指如果系统按照这种序列分配资源，则每个进程都能顺利完成。只要能找出一个安全序列，系统就是**安全状态**。当然，**安全序列可能有多个**。 
+  如果分配了资源以后，系统中找不出任何一个安全序列，系统就进入了**不安全状态**。这就意味着之后可能所有进程都无法顺利地执行下去。当然如果有进程提前归还了部分资源，那**系统也有可能重新回到安全状态**，不过在分配资源以前总是要考虑最坏的情况。 
+  如果系统处于**安全状态**，就**一定不会**发生死锁。如果系统进入不安全状态，就**可能**发生**死锁**。(处于不安全状态不一定发生死锁，但发生死锁时一定是在不安全状态)，一定要形成了阻塞环才是死锁，单个进程阻塞不是死锁。 
+  因此可以在资源分配以前预先判断这次分配是否会导致系统进入不安全状态，以此决定是否答应资源分配请求。这也是”银行家算法“的核心思想。 



银行家算法：



![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165605351-9bb9627d-c2d1-4cf9-8c4f-7cd94119c320.png)



**银行家算法步骤：**

+ 检查此次申请是否超过了之前声明的最大需求数；
+ 检查此时系统剩余的可用资源是否还能满足这次请求；
+ 试探着分配，更改各数据结构；
+ 用安全性算法检查此次分配是否会导致系统进入不安全状态



**安全性算法步骤**：检查当前的剩余可用资源是否能满足某个进程的最大需求，如果可以，就把该进程加入安全序列，并把该进程持有的资源全部回收。不断重复上述过程，看最终是否能让所有进程都加入安全序列。

#### 2.4.6 死锁检测和解除
死锁检测算法会根据系统真实情况设置合适的时间间隔，每隔一段时间执行来检测系统是否存在死锁，否则可能会浪费系统资源而没有有效进程的推进。

若系统既不采取预防死锁的措施，也不采取避免死锁的措施，系统就很可能发生死锁，在这种情况下，系统应该提供两个算法：

+ 死锁检测算法：用于检测系统状态，以确定系统中是否已经发生了死锁；
+ 死锁解除算法：从死锁状态中恢复的算法；

##### 2.4.6.1**死锁的检测**
为了能对系统是否已发生了死锁进行检测，必须：

+ 用**某种数据结构**来保存资源的请求和分配信息；
+ 提供**一种算法**，利用上述信息来检测系统是否已进入死锁状态；



1. 该数据结构就是**资源分配图**，其构成有：

| 名称 | 解释 |
| :---: | :---: |
| 进程结点 | 对应一个进程 |
| 资源结点 | 对应一类资源，一些资源可能有多个 |
| 进程结点→资源节点的边 | 表示进程想申请几个资源(每条边代表一个) |
| 资源结点→进程节点 | 表示已经为进程分配了几个资源(每条边代表一个) |


![](https://cdn.nlark.com/yuque/0/2024/png/27371136/1715165606024-cf79ae5b-b272-4a65-ad28-db9a31a9be17.png)



> 如果系统中剩余的可用资源数足够满足进程的需求，那么这个进程暂时是不会阻塞的，可以顺利地执行下去。如果这个进程执行结束了把资源归还系统，就可能使某些正在等待资源的进程被激活，并顺利地执行下去。相应的，这些被激活的进程执行完了之后又会归还一些资源，这样可能又会激活另外一些阻塞的进程...
>
> 如果按上述过程分析，最终能消除所有边，就称这个图是**可完全简化**的。此时**一定没有发生死锁**（相当于能找到一个安全序列）。
>
> 如果最终**不能消除所有边**，那么此时就是**发生了死锁**。**最终还连着边的那些进程就是处于死锁状态的进程**。
>



2. **使用死锁检测算法简化资源分配图**：

##### 2.4.6.2**死锁的解除**
一旦检测出死锁的发生，就应该立即解除死锁。

解除死锁的主要方法有：

1.  **资源剥夺法**: 挂起（暂时放到外存上）某些死锁进程，并抢占它的资源，将这些资源分配给其他的死锁进程。但是应防止被挂起的进程长时间得不到资源而饥饿. 
2.  **撤销进程法**（或称**终止进程法**）：强制撤销部分、甚至全部死锁进程，并剥夺这些进程的资源。这种方式的优点是实现简单，但所付出的代价可能会很大。因为有些进程可能已经运行了很长时间，已经接近结束了，一旦被终止可谓功亏一篑，以后还得从头再来。 
3.  **进程回退法**：让一个或多个死锁进程回退到足以避免死锁的地步。这就要求系统要记录进程的历史信息，设置还原点。 

> 如果采用了撤销部分进程或资源剥夺法的方法，可以根据  
**进程优先级、已执行多长时间、还要多久能完成、进程已经使用了多少资源、进程是交互式的还是批处理式等**来决定确定哪个(或哪些）死锁进程应该终止或被剥夺资源。
>

> 在解除死锁的过程中如何确保不会发生饥饿？即如何保证资源不会总是从同一个进程中被抢占。
>
> 如果一个系统是基于代价来选择牺牲进程，那么同一进程可能总是被选为牺牲的。结果这个进程永远不会完成指定任务，从而饿死。因此我们可以在代价的考虑因素中加上回滚次数。
>
