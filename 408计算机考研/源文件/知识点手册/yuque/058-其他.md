### 磁盘的inode区介绍
:::info
**inode区介绍**：inode就是索引结点，在unix文件系统中，所有的磁盘索引结点集中连续存放，如图所示。每个inode结点大小相同，因此索引结点编号是隐含的，不会显式存放在inode结点里面，此外，用于表示“文件物理结构”的“混合索引表”被包含在inode结点中，通过混合索引表可以找到一个文件中每个块存储的物理位置。

+ 在Unix文件系统中，每个文件必须对应一个inode结点，而inode结点的总数量是有上限的。如：该示意图中，仅用两个磁盘块，即8KB作为inode区，假设每个inode大小为64B，则该文件系统最多只能存储8KB/64B=128个inode结点，相应地，该系统最多只能支持128个文件。
+ 当一个进程通过open系统调用打开某个文件时，操作系统需要将该文件对应的inode结点读入主存。

:::

### 磁盘中的根目录介绍
![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748195768236-611aab03-2a15-42ad-a349-2f06dbf648f1.png)

1. 根目录的信息存储在磁盘的固定位置，这样可以保证开机时，能够找到根目录，再从根目录出发找到其他信息
2. 开机时，根目录的内容通常会被加载到内存，并一直常驻内存
3. 由于Unix文件系统采用了“索引节点”，因此每个目录项只需包含“文件名、inode号”，文件的具体属性包含在inode中
4. 每个目录文件中默认包含两个目录项，分别是“.”和“..”，“.”表示当前目录，“..”表示上一级目录。根目录比较特殊，没有所谓的“上一级目录”，因此它的目录项“..”指向自身

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748229721446-e8ecbf6a-b354-4bf7-b48c-9bcbac9fcd75.png)

假设在UNIX文件系统下有一进程利用open系统调用打开路径为/dir1/14.md的文件（从根目录开始查找）

1. 通过开机常驻内存的根目录找到目录项dir1，根据目录项dir1可知目录文件dir1对应的inode号为1
2. 从磁盘的inode区将该inode结点读入内存，通过1号inode结点可以得到目录文件dir1的索引信息，也就知道了目录文件dir1的每一块存储在什么位置，接下来，先读入目录文件dir1的第一块（7号磁盘块），尝试查找目录项14.md，如果没找到，再读入目录文件dir1的第二块（8号磁盘块），找到目录项14.md
3. 当找到文件14.md的目录项后，根据目录项记录的7号inode结点，将该inode结点加载进内存专用缓冲区，并且在系统打开文件表中登记表项，指针域记录该inode结点在内存中的物理位置，同时登记其他信息，设置文件打开计数（访问计数）为1，表示当前有一个进程正在使用14.md文件。
4. 发起open调用的进程会有进程打开文件表，需要在进程打开文件表中新建一个条目，记录其打开方式以及系统打开文件表索引，最后返回该条目对应的fd。在进程打开文件表中不会记录文件的inode结点，而是用系统打开文件表的索引找到系统打开文件表中对应文件的inode结点。
5. 根据open调用返回的fd，即可对该文件进行操作。



### 硬链接与软链接
+ **硬链接**：基于索引节点的共享方式，在这种共享方式中，文件目录项由文件名和索引节点号构成，需要共享文件时，将用户目录项中的索引节点号保持相同即可（指向同一个索引节点），并且将该索引节点的链接计数+1；
+ **软连接**：又叫符号链接，共享文件时，目录项指着一个新的索引结点，其索引节点对应的文件类型为软链接文件，里面有一条以绝对路径或相对路径的形式指向其他文件或者目录的引用。

### open系统调用
#### 磁盘索引结点与内存索引结点![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748235580377-9a8dacc2-9ea9-4b3b-b170-be0973c45604.png)
:::color2
+ 磁盘索引结点存放在磁盘的inode区中，进程通过检索目录获取文件名对应的目录项，并根据里面的inode号将对应的索引结点载入内存，索引节点里面存放着文件的元数据，里面有着文件类型、存取权限、创建时间、物理地址（直接索引、间接索引）、链接计数/文件大小（总块数）等信息；
    - 文件类型：标识该文件是目录/普通文件/软链接等
    - 存取权限：控制文件的访问权限
    - 物理地址（直接索引、间接索引等）：实现逻辑地址到磁盘物理地址的映射
    - 链接计数：记录文件被硬链接的次数
    - 其他信息：如文件大小、创建时间等辅助信息
+ 当磁盘索引结点调入内存（内核专用缓冲区）以后，可以供多个进程共享使用，因此需要增加一些内存属性以便操作系统使用，如
    - inode编号：标识对应外存inode的编号
    - 状态位：包含修改位(决定是否需要写回外存)
    - 互斥锁：保证多进程共享访问时的互斥
    - 访问计数：记录文件被打开的次数
    - device号：标识inode所在的逻辑设备号

:::

在某些系统的设计中，为了不在内存inode中加入太多信息使其冗余，便建立一张**<font style="color:#DF2A3F;">系统级打开文件表</font>**，每个表项对应一个已经打开的文件（即inode已经载入内存），表项中保存了inode在内存中的位置信息以及其他附属信息。

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748237253026-02aaceb2-d64e-4f7c-a881-0b91257ae031.png)

各进程虽然可以共享已经装入内存的inode（系统级打开文件表中的表项），但是每个进程对于文件的访问可能有模式/访问速度等各方面的差异，为了记录不同进程对于文件的不同访问情况，操作系统为每个进程创建了一张进程级打开文件表（或文件描述符表/用户级打开文件表），该表的物理地址被记录在进程PCB中，这个表也是在内存中的内核区域（不能在用户态下访问）

**假设进程P1首次打开使用**`**fd = open("root/dir1/c.mp4",r)**`，并且该文件之前从未有人打开过，下面便是这个打开文件背后所做的事

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748243631945-5a0ebdb5-5076-40b5-82bf-838f1f5605ea.png)

:::success
open系统调用必要参数：文件路径，访问权限（如只读、读&写）。打开文件后，文件的读写和关闭都不再以文件路径为参数，而是以打开文件返回的文件标识符fd为参数，即必须打开文件后，才可以进行文件读写和关闭操作。

因此，我们可以总结一下**open系统调用的处理过程**

1. 根据路径查找各级目录，如果在目录缓存中没有命中，就去磁盘中将目录文件读入内存，逐层检索直到找到目标文件的目录项
2. 根据目录项，得到inode编号，然后根据该编号，去系统打开文件表中检索
    1. 如果未命中，需要从磁盘中将该inode结点载入内核专用缓冲区，检查是否逾越访问权限，如果没有，在系统级打开文件表中新增一个表项，访问计数记为1，并将inode在内存中的位置信息记录在inode指针里；如果访问非法，则此次打开失败；
    2. 如果命中，且没有访问越权，则将访问计数值+1；
3. 在进程打开文件表中，新建一个表项，并记录其对应的系统打开文件表索引；
4. 将该表项的索引值作为fd返回给用户进程

:::

#### 多个进程打开同一个文件
![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748361018340-713badcf-c6be-4480-a803-9c36e3a12cff.png)

多个进程同时打开同一个文件的情况：假设现在有另外一个进程P2，同样的想要打开文件c.mp4。

由于进程P1之前已经打开了文件c.mp4，同时文件c.mp4的inode已经被加载到内存当中，且在系统打开文件表中注册了表项，所以当进程P2打开文件c.mp4的时候，操作系统做的事情就是在进程P2的进程打开文件表当中，新建一个表项。在这个表项当中，会用一个指针指向系统打开文件表。同时，系统打开文件表当中这个文件的访问计数+1。现在c.mp4的访问计数为2，表示此时有两个进程打开了文件入。

值得注意的是，不同的进程在打开文件的时候，它的打开方式可以各不相同。比如在这个例子当中，进程P1是以只读的方式打开文件c.mp4的。而进程P2是以读和写的方式打开这个文件的。打开文件的方式不同，那么接下来这两个进程可以对文件进行的操作就不同。对于进程P1来说，接下来只能去读这个文件。而对于进程Q来说，可以读也可以写这个文件。

总之，在系统打开文件表当中，一个文件只会对应一个表项。如果这个文件被多个进程同时打开，那么会让这些进程的打开文件表去指向系统打开文件表相应的位置。

:::success

### create系统调用
目的：在指定路径path下创建一个空文件，可以指定该文件的类型和访问权限等；

### 进程打开文件表（文件描述符表）的共享与继承
在进程那一章节的学习我们说，打开文件作为进程的一种资源，那学习了文件操作之后我们知道这是因为进程拥有进程级打开文件表(文件描述符表)，拥有对文件的操作能力；

同一个进程的不同线程共享进程打开文件表，因此每一个线程都可以用相同的文件描述符fd访问相同的文件。

父进程通过fork()系统调用创建子进程时，子进程会继承（复制）父进程的文件描述符表，这意味着子进程也可以访问父进程可以访问的文件，这也是管道通信的基础，父进程通过pipe()系统调用创建管道文件，然后fork()创建子进程，子进程继承该文件描述符，至此，父子进程都可以访问到这个管道文件，借助该管道文件实现进程间通信。

### lseek系统调用
`lseek()` 是 Linux/Unix 系统中用于**调整文件读写指针**（文件偏移量）的系统调用，允许对文件进行**随机访问**。

```c
off_t lseek(int fd, off_t offset, int whence);
```

+ **参数说明**：
    - `fd`：文件描述符（通过 `open()` 或 `creat()` 获得）。
    - `offset`：偏移量（字节数），其意义由 `whence` 决定。
    - `whence`：基准位置，可选值如下：
        * `SEEK_SET`：文件开头（偏移量直接指定位置）。
        * `SEEK_CUR`：当前读写位置（偏移量为相对值）。
        * `SEEK_END`：文件末尾（偏移量为相对末尾的偏移）。
+ **返回值**：
    - 成功时返回新的文件读写指针（文件偏移量（以字节为单位））。
    - 失败时返回 `-1`

**使用示例**

1. 移动文件指针到文件开头

```c
lseek(fd, 0, SEEK_SET); // 文件偏移量置为 0
```

2. 移动文件指针到文件末尾

```c
lseek(fd, 0, SEEK_END); // 常用于获取文件大小或追加数据
```

3. 相对当前位置移动

```c
lseek(fd, 100, SEEK_CUR); // 向后移动 100 字节
lseek(fd, -50, SEEK_CUR); // 向前移动 50 字节
```

4. 获取文件大小

```c
off_t file_size = lseek(fd, 0, SEEK_END);
// 注意：仅适用于普通文件，设备文件或管道可能返回错误
```

5. 在文件中间插入数据

```c
// 将文件指针移动到第 100 字节处
lseek(fd, 100, SEEK_SET);
// 写入数据会覆盖原有内容
write(fd, buffer, len);
```

### read系统调用
`<font style="color:rgba(0, 0, 0, 0.85);">read</font>`<font style="color:rgba(0, 0, 0, 0.85);"> 系统调用用于从指定的文件描述符所对应的文件读取数据到用户空间缓冲区。文件描述符可以指向普通文件、设备文件、管道、套接字等支持读取操作的对象。</font>

```c
read(int fd, void *buf, size_t count);
```

+ `**<font style="color:rgb(0, 0, 0);">fd</font>**`<font style="color:rgba(0, 0, 0, 0.85);">：文件描述符，通常通过 </font>`<font style="color:rgb(0, 0, 0);">open()</font>`<font style="color:rgba(0, 0, 0, 0.85);">、</font>`<font style="color:rgb(0, 0, 0);">pipe()</font>`<font style="color:rgba(0, 0, 0, 0.85);"> 等系统调用获得</font>
+ `**<font style="color:rgb(0, 0, 0);">buf</font>**`<font style="color:rgba(0, 0, 0, 0.85) !important;">：用户空间缓冲区的指针，用于存储（读/写）读取的数据。</font>
+ `**<font style="color:rgb(0, 0, 0);">count</font>**`<font style="color:rgba(0, 0, 0, 0.85) !important;">：期望读取的最大字节数</font>
+ <font style="color:rgba(0, 0, 0, 0.85) !important;">返回值：若执行成功，返回值代表实际读取的字节数，若失败返回-1.</font>

<font style="color:rgba(0, 0, 0, 0.85) !important;">读/写文件的逻辑区域为以文件读写指针指向位置为起点，长度为count的字节流。</font>

<font style="color:rgba(0, 0, 0, 0.85) !important;">具体处理过程：</font>

1. **<font style="color:rgb(0, 0, 0) !important;">用户程序</font>**<font style="color:rgba(0, 0, 0, 0.85) !important;"> 在用户态下调用 </font>`<font style="color:rgb(0, 0, 0);">read(fd, *buf, count)</font>`<font style="color:rgb(0, 0, 0);">，陷入内核态；</font>
2. <font style="color:rgb(0, 0, 0);">根据fd找到进程打开文件表（文件描述符表）的对应表项，根据访问权限位判断是否支持读取操作；</font>
3. <font style="color:rgb(0, 0, 0);">若支持读操作，再去系统打开文件表，然后找到文件对应的inode，根据读写指针位置，再根据inode里的文件位置信息，去将读区域所在的磁盘块读入内存中的内核缓冲区；</font>
4. <font style="color:rgb(0, 0, 0);">将需要读取的数据从内核缓冲区读入用户空间的buf中；</font>
5. <font style="color:rgb(0, 0, 0);">返回实际读取的字节数。</font>

![](https://cdn.nlark.com/yuque/0/2025/png/42876865/1748364319114-e43b8a8a-70ac-427c-9971-d8337f1b7e5b.png)

:::success
读操作是从当前进程的读写指针所指明的位置开始往后偏移的，比如此时进程P1要读1024个字节。首先根据读写指针的位置和此次要读的数据量，操作系统就可以知道，这一次读的数据一定是被包舍在0号块和1号块当中，根据文件的inode就可以找到这个文件的各个块存放在磁盘的什么位置，接下来，操作系统会把这两个磁盘块都读入到内存，并且是读入到内存的内核缓冲区。然后再把0号块的末尾504字节复制到用户区，接下来再把1号块头部的520字节也复制到用户区。这样就完成了read系统调用。

:::

> 因为磁盘、硬盘、U盘等存储设备基本都是Flash块设备，因为块设备硬件本身有读写限制等特征，块设备是以一块一块为单位进行读写的（一个块包含多个扇区，而一个扇区包含多个字节）， 一个字节的改动也需要将该字节所在的block全部读取出来进行修改，修改完成之后再写入块设备中，所以导致**对块设备的读写操作非常不灵活 ；而内存可以按字节为单位来操作，而且可以随机操作任意地址数据，非常地很灵活 ，**所以对于操作系统来说，会先将磁盘中的静态文件读取到内存中进行缓存，读写操作都是针对这份动态文件，而不是直接去操作磁盘中的静态文件，不但操作不灵活，效率也会下降很多，因为内存的读写速率远比磁盘读写快得多。
