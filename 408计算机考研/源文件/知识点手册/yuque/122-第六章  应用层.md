## 6.1 网络应用模型
根据网络应用程序在各种端系统上的组织方式和它们之间的关系，分为以下两种：

|  | 客户/服务器（`Client/Server,C/S`）模型 | 对等（`Peer-to-Peer,P2P`）模型 |
| :---: | --- | --- |
| **对象** | + 客户机$ Client $：服务请求方，**面向用户**<br/>+ 服务器$ Server $：服务提供方，**面向任务**，总是处于运行状态，等待客户的服务请求。 | 对等方($ peer $)：任意一对计算机； |
| 示意图 | ![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230822231127294.png) | ![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230822231142689.png) |
| **常用应用** | $ Web $、$ FTP $、远程登录、电子邮件等**服务集中型应用**   （即应用服务集中在服务器上） | $ p2p $文件共享、快播、迅雷、即时通信、$ p2p $流媒体、分布式存储等   服务分散型应用；（服务分撒在大量对等计算机上） |
| **工作流程** | 1. 服务器处于接受请求状态<br/>2. 客户机发出服务请求，等待接收结果<br/>3. 服务器收到请求，进行处理，得到结果返回给客户机 | 本质上看来就是$ C/S $,只不过**每一台计算机（对等方）既可以是服务提供方，也可与是服务请求方。对等方相互之间直接通信** |
| **特点** | 1. $ C/S $模式中各计算机地位不等，服务器可对用户进行权限限制；<br/>2. **客户机之间不能进行通信**；<br/>3. 可扩展性不佳；<br/>4. **客户机面向用户，服务器面向任务**； | 1. 减轻了服务器的计算压力，提高了系统效率和资源利用率<br/>2. **多个用户之间可以共享文档；**<br/>3. 可扩展性好；系统性能不会因规模增大而降低；<br/>4. 网络健壮性强，个别结点失效问题不大；<br/>5. 但是会影响个体的整机速度；<br/>6. 成本低； |

## 6.2 动态主机配置协议``DHCP``
| **协议英文全称** | **网络应用模型** | **运行在** | **熟知端口号** | **常考题型** |
| :---: | :---: | :---: | --- | --- |
| $ Dynamic\ Host\  $<br/>$ Configuration\  Protocal $ | $ C/S $ | $ UDP $**之上** | **服务器端：**$ UDP\  67 $**   ****客户端：**$ UDP\ 68 $ | **综合题小问** |


### 6.2.1 `DHCP`**的作用**
常用于给主机动态地分配地分配$ IP $地址，提供了**即插即用**的联网机制，允许一台计算机加入新的网络和获取$ IP $地址而不用手工参与。

> 局域网内主机开机启动$ DHCP $，然后$ DHCP $服务器为局域网中各主机配置参数：$ IP $地址、子网掩码、默认网关的$ IP $地址、$ DNS $服务器的$ IP $地址
>

### 6.2.2 `DHCP`**的工作过程**
1. `DHCP`报文的封装应用层中的`DHCP`客户端**报文**在运输层加上$ UDP $首部（包括源端口号68和目的端口号67）被封装成 $ UDP $** 用户数据报**，然后在网际层加上$  IP $ 首部被封装成 $ IP $** 数据报**，再根据所使用的网络接口，加上**帧头**封装成相应的数据链路层的**帧**（例如以太网帧）进行发送。
2. **基本工作过程**

![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230823145610166.png)

> 1. `DHCP`发现报文的源``IP``地址为`0.0.0.0`是因为主机目前还未分配到``IP``地址,将`IP`地址设为全0，本地网络上的所有主机都可以收到该报文；目的``IP``地址为`255.255.255.255`是**因为主机并不知道网络中有哪几个**``DHCP``**服务器，也不知道它们的**`IP`**地址；**
> 2. `DHCP`报文段内封装由事务`ID`和``DHCP``客户端的`MAC`地址等信息，只有在应用层始终运行着`DHCP`服务器进程的`DHCP`服务器才会接收该报文并作出响应；其他的主机接收到就会将其丢弃；
> 3. `DHCP`服务器接收到发现报文后根据客户端的`MAC`地址查自己的数据库，若有针对它的配置信息则使用该信息配置``DHCP``提供报文，若没有则采用默认配置信息来构建提供报文；**注意，在**``DHCP``**服务器挑选待租用给主机的**`IP`**地址后时，会使用**`ARP`**来确保所选**`IP`**地址未被网络中其他主机占用。**
> 4. ``DHCP``服务器发送`DHCP OFFER`时，源`IP`地址为服务器自身``IP``地址，**目的地址仍为广播地址。因为主机目前还没有配置**``IP``**地址，为了让主机收到，只能发送广播。这样的话，网络中所有设备都会收到该**``IP``**数据报，对其层层解封后解封到**``DHCP``**提供报文，但是只有在应用层运行着**``DHCP``**客户进程的主机才会接收该报文并进行处理，再根据该报文的事务**`ID`**确定是否是自己所请求的报文，若是，则接收，否则丢弃。**
> 5. `DHCP`客户在发出`DHCP`请求后可能会收到多条`DHCP`提供报文（`OFFER`）,一般情况下会选择先接收到的那个。
> 6. `DHCP`**提供报文中一般含有以下配置信息：例如**`IP`**地址、子网掩码、地址租期、默认网关和**`DNS`**服务器的**`IP`**地址等**
> 7. `DHCP`客户收到OFFER后，向`DHCP`服务器发送`DHCP`请求报文（`REQUEST`），封装有该报文的`IP`数据报源`IP`地址还是`0.0.0.0`因为此时`DHCP`客户端刚从多个`DHCP`提供报文中选择了一个作为自己的`DHCP`服务器，此时它首先需要征得该服务器的同意，之后才能正式使用该`IP`地址。**目的**`IP`**地址仍然是广播报文，这样做的目的是不用挨个向网络中的每一个**`DHCP`**服务器告知自己是否选择了它作为自己的**`DHCP`**服务器，当各个**`DHCP`**服务器收到该报文，根据该报文里的事务ID、**`DHCP`**客户端的MAC地址、接收租约中的**`IP`**地址和提供该租约的**`DHCP`**服务器的**`IP`**地址，就知道自己是否被它选上了；**
> 8. `DHCP`服务器同意该请求，于是给`DHCP`客户发送`DHCP`确认报文（`DHCP ACK`），目的地址仍是广播地址。`DHCP`客户收到该确认报文以后便可以使用该租用`IP`地址了。**注意，在使用该**`IP`**地址之前，主机仍会使用**`ARP`**检测该主机是否已被网络中其他主机所使用。若被占用，**`DHCP`**会给**`DHCP`**服务器端发送**`DHCP`**谢绝报文来谢绝**`IP`**地址租约，并重新发送**`DHCP`**发现报文。**
> 9. 当`IP`地址的租约期过去一半的时候，`DHCP`会发送请求报文用于**续约**，当`DHCP`服务器收到该报文后，有3种可能的处理方法
>     - **同意续约请求**，发送`DHCP`确认报文，则`DHCP`客户得到了新的租约期；
>     - **不同意续约请求**，给`DHCP`客户发送`DHCP NACK`否认报文，`DHCP`收到该报文后立即停止使用该`IP`地址并立即寻找下家（真干脆），发送`DHCP`发现报文；
>     - （冷暴力）**未作出响应**，这样的话在租用期过了87.5%后，`DHCP`客户必须重新发送请求报文用于续约，然后等待`DHCP`服务器响应。如果还不做出响应（搁这PUA呢），租用期到期后，`DHCP`客户立即停止使用并寻找下家。
> 10. `DHCP`**客户可以随时提前终止租约期**，如果不想用了，直接给`DHCP`服务器发送`DHCP`释放报文（`DHCP` RELEASE）即可。封装该报文的`IP`数据报的源`IP`为`0.0.0.0`，目的`IP`地址为`255.255.255.255`
>

### 6.2.3 `DHCP`的中继代理
如下左图中由于广播报文不会被路由器转发，会被丢弃，所以不能获取配置参数。我们不愿意在每一个网络上都设置一个`DHCP`服务器，因为这样会使得`DHCP`服务器数量太多。因此现在一般是使每一个网络中至少有一个`DHCP`中继代理($ relay\ agent $),它配置了`DHCP`服务器的IP地址，当中继代理收到主机以广播形式发送的`DHCP`发现报文后，就以单播形式向`DHCP`服务器转发此报文，并等待回答。

## 6.3 域名系统（`DNS`）
| 协议英文全称 | 网络应用模型 | 运行在 | 熟知端口号 | 常考题型 |
| :---: | :---: | :---: | :---: | --- |
| $ Domain\ Name\ system $ | $ C/S $ | $ UDP $之上 | $ 53 $ | 选择 |


【作用】：将便于人们记忆的主机名转换为便于机器处理的 $ IP $ 地址

> **注意，域名**$ /IP/MAC $**与主机都不具有一一映射的关系，1台主机可能对应着多个不同的域名**$ /IP/MAC $**。**
>

【**因特网的域名结构**】：

+ 因特网采用层次树状结构的域名结构。
+ 域名的结构由若干个分量组成，各分量之间用“点”隔开，分别代表不同级别的域名。

> **… .三级域名.二级域名.顶级域名**
>
> 例如$ cqut.edu.cn $   ,$ cqu $(三级域名)， $ edu $(二级)、$ cn $ (顶级域名) 、根（隐藏）
>

![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230823162045145.png)

【**域名服务器**】：域名和`IP`地址的映射关系必须保存在域名服务器中，供所有其他应用查询。显然不能将所有信息都储存在一台域名服务器中。DNS使用**分布在各地的域名服务器**来实现域名到IP地址的转换。自上而下分别是**根域名服务器、顶级域名服务器、权限域名服务器**

**分类**：

1. **根域名服务器**
    - 根域名服务器是最高层次的域名服务器。
    - 管辖顶级域 $ cn/com/hk/uk/us/net $ 等，每个根域名服务器都知道所有的顶级域名服务器的域名及其IP地址。
    - **任何本地域名服务器对任何域名进行解析，只要自己无法解析，就请求根域名服务器**（若缓存中存有部分待解析的域名，则可以跳过根域名服务器。例如本地缓存存有$ .com $ ，在查询$ www.baidu.com $ 时可以直接请求$ .com $ 顶级域名服务器）
    - **根域名服务器通常并不直接对域名进行解析，而是返回该域名所属顶级域名的顶级域名服务器的 **$ IP $** 地址。**
2. **顶级域名服务器**：
    - 负责管理在该顶级域名服务器注册的所有二级域名
    - 当收到`DNS`查询请求时就给出相应的回答，可能是给出$ IP $地址，也可能是指出下一级权限域名服务器的$ IP $地址。
3. **权限域名服务器**：
    - 权限域名服务器负责管理某个区的域名。
    - **每一个主机的域名都必须在某个权限域名服务器处注册登记**。因此权限域名服务器知道其管辖的域名与`IP`地址的映射关系。
    - **另外，权限域名服务器还知道其下级域名服务器的地址。**
4. **本地域名服务器**
    - **本地域名服务器不属于上述的域名服务器的等级结构**
    - 当一个主机发出`DNS`请求报文时，**这个报文就首先被送往该主机的本地域名服务器。**
    - **本地域名服务器起着代理的作用，会将该报文转发到上述的域名服务器的等级结构中。**
    - 每一个因特网服务提供者ISP，一个大学，甚至一个大学里的学院，都可以拥有一个本地域名服务器，它有时也称为默认域名服务器。
    - 本地域名服务器离用户较近，一般不超过几个路由器的距离，也有可能就在同一个局域网中。**本地域名服务器的**`IP`**地址需要直接配置在需要域名解析的主机中。**

**因特网的域名解析过程**

> 1. 为了提高`DNS`的查询效率，并**减轻根域名服务器的负荷**和减少因特网上的`DNS`查询报文数量，在各级域名服务器中广泛地使用了**高速缓存**。**高速缓存用来存放最近查询过的域名以及从何处获得域名映射信息的记录**(由于域名到`IP`地址的映射关系并不是永久不变，**为保持高速缓存中的内容正确，域名服务器应为每项内容设置计时器并删除超过合理时间的项**,例如，每个项目只存放两天)

## 6.4 文件传输协议（`FTP`）
1. 文件传输协议（`File Transfer Protocol,FTP`）的**作用**：
+ 提供**交互式**的访问，允许客户指明文件的类型与格式（如指明是否使用ASCII码），并**允许文件具有存取权限**（如访问文件的用户必须经过授权，并输入有效的口令）
+ `FTP`屏蔽了各计算机系统的细节，因而适合于在异构网络中任意计算机之间传送文件。
2. FTP采用**客户/服务器**的工作方式，使用**TCP**可靠的传输服务。一个FTP服务器进程可同时为多个客户进程提供服务：
    - **主进程(单个)**：用于接收新的请求，对应着控制连接 `21port.`
    - **从属进程(多个)**：用于处理单个请求的数据连接。
3. FTP工作时使用两个并行的TCP连接

|  | 主动模式（`PORT`） | 被动模式（`PASV`） |
| :---: | :---: | :---: |
| **工作原理** | 客户端连接到**服务器的21号端口** —>登录成功准备读取数据   –>客户端随机开放端口并发送命令—>**服务器通过20号端口**与   客服端开放端口连接，发送数据 | 客户端要读取数据发送命令到服务器，**服务器随机开放端口**，并发送   端口号告知客服端，然后**客户端主动与其连接**，进行数据传输 |
| **服务器端口号** | **20** | **服务器随机开放** |
| 数据连接由谁建立 | **服务器主动连接客户**，所以叫主动模式 | **服务器被动等待客户的连接**，所以叫被动模式 |
| 示意图 | ![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230822222952136.png) | ![](https://typora-darkmoon.oss-cn-nanjing.aliyuncs.com/image-20230822223029921.png) |


> 【注】：
>
> 1. 端口号20、21都是服务器端口号，客户端的端口号由客户端系统自行分配；
> 2. 由于`FTP`使用一个分离的”控制连接“， 所以也称FTP的控制信息是带外（`out-of-band`）传输的
>

    - **控制连接**（端口号21）：用于**传输控制信息**（连接请求、传送请求等），不传输数据信息，由于在传输数据的时候也可以通过控制连接发生控制命令（例如终止传输），所以**控制连接在整个会话期间一直保持打开状态**。

## 6.5 电子邮件
### 6.5.1 电子邮件系统的组成
电子邮件系统采用**客户/服务器**方式

+ **用户代理**：用户与电子邮件系统的接口，即电子邮件客户端软件；
+ **邮件服务器**：电子邮件系统的基础设施，用于发送和接收邮件，同时还要维护用户的邮箱。（同时充当$ C $ 和$ S $）
+ **协议**：包括**邮件发送**协议（$ SMTP $、$ HTTP $）和**邮件接收(读取)协议**（$ POP3 $、$ IMAP $）等

> 注意：
>
> 1. $ SMTP $为“推”服务，即由发送方将邮件“推”给接收方；$ POP3 $为“拉”服务，即由接收方从发送方“拉”出邮件；
> 2. 以上所有连接都是基于$ TCP $，所有服务都是基于$ C/S $
> 3. $ SMTP $地址出错：不能发送邮件；  $ POP3 $地址出错：不能接收邮件；   $ https $ 地址出错，既不能发也不能收；  $ mail $地址出错，发错人或者发不出（查无此人）
>

【电子邮件的收发过程】：

1. 发信人通过**用户代理**（即写信的界面例如QQ邮箱软件）来撰写邮件；
2. 用户代理通过$ SMTP $发邮件发送给**发送方的邮件服务器**；
3. **发送方的邮件服务器**将邮件放入邮件缓存队列中等待发送；
4. **发送方的邮件服务器**发现缓存中有待发送的邮件，就向**接收方的邮件服务器**建立$ TCP $连接；
5. $ TCP $连接建立后，**发送方的邮件服务器**远程向**接收方的邮件服务器**发送邮件，当所有邮件发送完毕后断开$ TCP $连接；
6. **接收方的邮件服务器**接收到邮件后，将邮件存入**收件人的用户邮箱**中等待收信人在方便的时候读取；
7. 收信人在打算收信时，通过用户代理使用$ POP3 $或者$ IMAP $将自己的邮件从**接收方的邮件服务器**中取回。

### 6.5.3 邮件读取协议
| 邮局协议`POP3` | 因特网邮件访问协议`IMAP` |
| :---: | :---: |
| $ Post\ Office\ Protocol $ | $ Internet\ Message\ Access \ Protocol $ |
| 端口号：$ 110 $ | 端口号：$ 143  $ |
| 非常简单、功能有限的邮件读取协议 | 复杂但是功能比$ POP3 $强大的邮件读取协议 |
| 用户**只能以下载并删除**方式或**下载并保留**方式   从邮件服务器下载邮件到用户计算机上 | **用户在自己的计算机上就可以操纵邮件服务器中的邮箱**，   就像在本地操控一样，因此$ IMAP $是一个联机协议 |
| **不允许用户在邮件服务器上管理自己的邮件。**   （例如创建文件夹、对邮件进行分类管理等） | 允许用户代理只获取报文的某些部分，例如可以只读取报文的一个首部 |


**相同点：二者都采用基于**$ TCP $**连接的客户/服务器方式。**
